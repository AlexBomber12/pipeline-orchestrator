# PR-283: Per-task Retry button in Tasks queue UI for ERROR badges with retry counter cap

Branch: pr-283-per-task-retry-button
- Type: feature
- Complexity: medium
- Depends on: PR-279, PR-280
- Priority: 1
- Coder: codex

## Problem

Sprint 15b Phase 1 decision: when daemon writes status:error to a task file (via PR-279), operator triages with one of two paths:

- **Re-upload changed file** (handled in PR-284): operator edits spec content, validator detects content hash change, transitions to queued.
- **Per-task Retry button**: operator wants to re-attempt without spec changes (e.g., transient INFRA failure passed). One-click reset of frontmatter status:error → queued + clear cancellation_cause. Counter caps at N=3 to prevent infinite retry loops on inherently broken specs.

This PR ships the Retry button. PR-284 ships the re-upload changed-only enforcement (mutually exclusive triage paths).

## Scope

1. **New endpoint** POST `/repos/{name}/tasks/{pr_id}/retry` in `src/web/routes/repo_control.py` or new `tasks_control.py` module. Handler:
   - Validate repo exists, validate task file exists.
   - Read retry counter from Redis: `metrics:retry_count:{repo}:{task_id}`. Default 0.
   - If counter >= cap (`daemon.retry_button_cap`, default 3), return 409 Conflict with hint "Edit task spec or delete to proceed".
   - Else: increment counter, write back to Redis with TTL 30 days.
   - Delete cancellation cause: `redis.delete(cause_key(repo_slug, task_id))` and remove from `cancellation_index:{repo_slug}` zset.
   - Write `status: queued` to task file frontmatter via `write_frontmatter_status` (from PR-279).
   - Commit with message `"[RETRY] PR-{pr_id} cleared by operator (attempt {N}/{cap})"` plus `[skip ci]` trailer. Push to main.
   - Return 200 with HTMX swap fragment showing the task back in TODO group.

2. **UI button in Tasks queue.** `src/web/templates/components/tasks_panel.html` ERROR group section: each task gets a Retry button if `retry_count < cap`. Disabled state shows tooltip with the counter and hint when `retry_count >= cap`. Button uses HTMX `hx-post="/repos/{repo}/tasks/{pr_id}/retry"` with confirmation dialog `"Retry PR-XXX? Counter will increment to {N+1}/{cap}."`.

3. **Counter exposure.** Backend handler that builds tasks_panel context loads `metrics:retry_count:{repo}:{task_id}` for each ERROR task and exposes as `retry_count` field on the rendered task view model.

4. **Counter reset on file content change** is handled in PR-284 (re-upload changed-only). Cross-reference: when re-upload validator detects content change, it deletes the retry counter alongside other cleanup. This PR does not implement reset, only consumption.

5. **Config field** `daemon.retry_button_cap: int = Field(default=3, ge=1, le=20)` in `src/config.py`. Document in config.yml as commented-out field with default note.
