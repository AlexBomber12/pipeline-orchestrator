# PR-217: Add ConfigUpdateService for consistent config mutation

## Problem

Four web endpoints mutate config but with inconsistent side effects (per PR-211 baseline tests):

| Endpoint | Writes config | Sets dirty | Publishes wake |
|---|---|---|---|
| POST /repos/{name}/coder | yes | yes | yes |
| PUT /settings/repos | yes | no | no |
| PUT /settings/repo/{name} | yes | no | yes |
| PUT /settings/daemon | yes | no | no |

The coder endpoint is the canonical one; the other three are missing pieces. Operator changes review_timeout via Settings UI, daemon does not get a dirty signal, change propagates only via 5s config_watcher polling. The UI suggests immediate apply when the API actually relies on polling.

## Scope

Add `ConfigUpdateService` (or shared helper). Migrate all 4 endpoints to use it. Behavior bound by PR-211 baseline tests: each endpoint after migration writes config, sets dirty for affected repos, publishes wake for affected repos.

## Files to modify

`src/web/services/config_updates.py` (new file, create directory if needed):

```
"""Shared helper for web config mutations."""

from __future__ import annotations

import logging
from collections.abc import Iterable

from src import keyspace
from src.events import publish_wake

logger = logging.getLogger(__name__)


async def apply_config_mutation(
    *,
    redis_client,
    affected_repo_names: Iterable[str],
    event_type: str,
) -> None:
    """Set dirty flags and publish wake events for affected repos.

    Call this after the config.yml file has been written. The function
    performs two side effects per repo: SET control:{repo}:config_dirty
    and PUBLISH on orchestrator:wake:{repo}. Failures are logged at
    warning level and do not raise; the polling fallback in the daemon
    will pick up changes within CONFIG_WATCH_INTERVAL_SEC even if the
    Redis publish fails.
    """
    for name in affected_repo_names:
        dirty_key = keyspace.control_config_dirty(name)
        try:
            await redis_client.set(dirty_key, "1")
        except Exception:
            logger.warning(
                "Failed to set %s; daemon polling fallback will pick up "
                "config change within CONFIG_WATCH_INTERVAL_SEC",
                dirty_key,
            )
        try:
            await publish_wake(redis_client, name, event_type)
        except Exception:
            logger.warning(
                "publish_wake failed for %s; daemon will pick up %s on "
                "next polling tick",
                name,
                event_type,
            )
```

## Implementation notes

The order of operations matters: write config first, then set dirty, then publish wake. If publish fires before dirty key is set, daemon could wake and find no dirty key, then go back to sleep. Set the inbox flag first, then ring the doorbell.

The Redis client may be `None` in degraded mode. Guard with `if redis_client is not None:` before calling `apply_config_mutation`. Endpoints must still complete and return 200.

Daemon-level config write affects all active repos. Sending wake to every repo can be wasteful for clusters with 20+ repos but for now (single repo, or small fleets) the simplicity wins. Document this trade-off in the function docstring.

The `event_type` parameter is for observability only; daemon does not interpret event_type beyond "got a wake message". Pick names that match the existing convention: `coder_swap`, `settings`, `pause`, `resume`, `stop`, `upload`.

After this PR ships, all 4 config-mutating endpoints have identical side-effect behavior. Future endpoints adding config mutation must use `apply_config_mutation` (add a comment in `src/web/app.py` near the route definitions to remind reviewers).
