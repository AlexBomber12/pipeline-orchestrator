## Problem

PR-275 catches cross-repo intent in task body before dispatch. PR-276 catches Tier 1 forbidden actions in coder stdout post-execution. PR-277 catches Tier 1 violations in PR diffs post-push. All three layers detect violations but a coder reading AGENTS.md finds no explicit prohibition list — it can only infer the rules indirectly from existing sections (`work_modes`, `daemon_mode`, `auto_pr_runbook`, `review_fix_runbook`).

PR-278 adds an explicit `forbidden_actions` managed section to AGENTS.md that lists the Tier 1 prohibitions in plain language. Coders following the AGENTS.md top-to-bottom convention encounter the rule before any work mode execution. The managed section reconciliation framework (PR-192a/b/c) propagates the section to all managed repos via operator-driven `/onboarding/apply`. After PR-278 merges and operator runs apply on each managed repo, the prohibition list lives in megaraid-dashboard and sms-gateway-v2 AGENTS.md as well.

The section is **declarative documentation**, not enforcement. Enforcement is in PR-275/276/277. PR-278 closes the documentation gap so a coder asked to "do X" where X is forbidden has explicit guidance to refuse rather than relying on indirect inference from runbooks.

   Section content:

   ```
   <!-- pipeline-orchestrator: managed BEGIN forbidden_actions -->
   ## Forbidden actions
   
   The following actions are NEVER permitted under any work mode (AUTO PR, PLANNED PR, MICRO PR, FIX FEEDBACK). The pipeline-orchestrator daemon detects them at three layers (cross-repo intent in task body, coder stdout scan, PR diff scan) and ESCALATEs with `GUARDRAIL: <category>: <excerpt>` cause. If you find yourself about to take any of these actions, STOP and add an `ESCALATE: <reason>` line to your stdout instead.
   
   - **Repository creation or deletion via `gh repo create` / `gh repo delete`**: the daemon authorizes you to operate within the repository where the task lives. Creating or deleting repositories at GitHub-org level is out of scope for any task.
   - **Force-push to the protected default branch**: the protected default branch (typically `main`) holds linear, reviewed history. Rewrites destroy that history and bypass the merge contract. Use a feature branch and a PR review instead.
   - **Branch deletion of the protected default branch**: deleting the default branch destroys the trunk. The daemon does not authorize this action under any circumstances.
   - **Direct commits to the protected default branch without an intervening `gh pr create`**: every change reaching the default branch must go through a PR with a passing CI run and a non-stale Codex review thumbs up. Direct commits via admin override (when the operator's GitHub account has admin permissions) bypass the merge contract; the daemon detects and ESCALATEs.
   - **Cross-repo intent in task body**: if a task spec body references a repository name distinct from the current repository, the daemon ESCALATEs before dispatch. The operator misuploaded the task; do not attempt to operate across repositories.
   <!-- pipeline-orchestrator: managed END forbidden_actions -->
   ```

## Implementation notes

The new section content is straightforward documentation. The order in MANAGED_SECTIONS tuple matters for the reconciliation framework: it determines where the section is appended on first reconciliation against an AGENTS.md that lacks the markers. Inserting after `branch_naming` gives a logical reading order: scope and naming → forbidden actions → work mode runbooks.

The cross-reference to "the protected default branch" in the section content uses the same phrasing as PR-276/277 to maintain consistency with the regex catalogue's named target. Operators reading this section understand it applies to whatever branch their `repo_config.branch` points to (typically main, occasionally master or develop).

The section is propagated to managed repos via `/onboarding/apply`. After this PR merges, the operator runs apply on each managed repo. Managed repos' AGENTS.md will then have the new section appended (or inserted into an existing managed-section block depending on reconciliation logic). The same operator action item is documented in the Sprint 15a #7 cleanup PR (PR-274) for AGENTS.md updates landed via that PR; PR-278 piggybacks on the same operator workflow.

Estimated diff size: ~30-40 LOC across 4 files. Of that, ~16 LOC is the new AGENTS.md section, ~1 LOC is the MANAGED_SECTIONS addition, ~15-20 LOC is tests.
