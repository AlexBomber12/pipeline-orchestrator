## Problem

`self._last_push_at` is written from two different time sources:

- Writer A (`src/daemon/recovery.py:670, 676` in `_rehydrate_last_push_at`): reads `head_commit_date` via `gh_prs.get_pr_metadata` then `gh_runner._parse_iso` — **GitHub-side committer timestamp**, canonical
- Writer B (`src/daemon/handlers/fix.py:544` in `record_fix_push`): `push_time = datetime.now(timezone.utc)` — **daemon wall clock at detection moment**
- Writer C (`src/daemon/handlers/fix.py:739` in no-push branch): `self._last_push_at = datetime.now(timezone.utc)` — **daemon wall clock**

`_has_new_codex_feedback_since_last_push` (`src/daemon/handlers/watch.py:414-462`) compares `_last_push_at` against `comment.created_at` values returned by GitHub. Those are GitHub-side timestamps.

When daemon wall clock at the moment of `record_fix_push` invocation exceeds the GitHub timestamp of a still-pending Codex review on the same head, the review becomes permanently invisible to the feedback check. Daemon enters WATCH→ESCALATE→IDLE→re-pick infinite loop.

Production incident reproduction (2026-05-10, PR #407 stuck 27+ min):

- 02:32:43 UTC — git push of commit 2d34d60c10 (GitHub committer date)
- 02:35:31 UTC — Codex review submitted on 2d34d60c10 (GitHub timestamp)
- ~02:50 daemon wall clock — `record_fix_push` invoked after post-restart FIX cycle, captures `datetime.now()` ~02:50, overwrites `_last_push_at` from canonical 02:32:43 to 02:50
- Subsequent WATCH checks: `02:35:31 > 02:50` is False, feedback check returns NONE, daemon never enters FIX iteration #2

## Solution

`record_fix_push` and the no-push fallback branch both read the canonical GitHub committer date via `get_pr_metadata`, mirroring `_rehydrate_last_push_at`. Fall back to `datetime.now(timezone.utc)` only when the GitHub fetch fails, to preserve liveness of the WATCH cycle when GitHub is unreachable.

A helper `_canonical_push_timestamp(pr_number: int) -> datetime` on the runner class centralizes the read so future writers do not re-introduce the wall-clock mistake.

## Threat model

**Threat addressed**: daemon wall-clock-vs-GitHub-clock skew silently disables WATCH→FIX transition logic.

**Other layers protecting**: `_rehydrate_last_push_at` already correctly uses committer date on daemon restart; the bug surfaces only between restart and the first `record_fix_push` invocation in the new daemon session.

**Why this layer needed**: `record_fix_push` is the ONLY writer of `_last_push_at` during normal FIX cycle operation. Without this fix, every FIX iteration re-introduces the skew, eventually exceeding any Codex review submitted within seconds of the push.
