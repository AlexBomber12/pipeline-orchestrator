## Scope

The archive contains an untested reference example. Implement this inline contract against the current source; do not assume archive files are present in the checkout.

Classify using current task/PR applicability and binding equality, not task ID alone. approval_unavailable or an active row whose current binding cannot be established -> unknown, no decision controls. An active row with a current binding but no approval for that binding -> action, with the existing Approve/Reject requests. An old failed approval for a different binding is historical and must not turn the new decision into a retry of the old one. Matching pending/deferred -> applying, neutral. Matching failed -> failed, display the reason and only actions actually supported by the endpoint. Applied/inactive/superseded -> history.

Important verified endpoint behavior: _approve_guardrail_decision returns the existing acknowledgement for a previously stored binding, including failed; it does not requeue it. Therefore never display Approve again for the same failed binding. A changed HEAD/task/failure may create a genuinely new binding and gets an explicitly labelled Approve current PR action after the current context is verified. Do not change approval endpoints or manufacture a binding to enable a button.

Use the same classification for dashboard attention and the repo panel. Preserve distinct retained results by binding in the history view rather than collapsing them by task ID. Respect the existing bounded history window; do not add unbounded scans, delete records or add expiration. Each failed current decision remains visible with its recorded explanation even when reapproval is unsupported.

## Acceptance criteria

- Reuse the existing persisted decision bindings, bounded reads and backend eligibility. A failed matching acknowledgement cannot be labelled retryable. Distinct retained bindings may need grouped rows within the existing history window; show unavailable/truncated history honestly rather than promising all-time completeness.

- Case A (active, binding, no approval for it): amber panel, Approve + Reject.
- Case B (approval pending/deferred for the current binding): neutral, no Approve.
- Case C (same binding failed and active): red explanation; no ineffective Approve again. A different verified current binding is a new decision, not a retry of the failed acknowledgement.
- Case D (old applied decision while an unrelated task is CODING): no amber/red panel; one collapsed neutral history row.
- Case E (approval_unavailable): neutral, no action buttons.
- No record is deleted or hidden from history; approve/reject requests are unchanged.

- The completion-evidence fix PR-468 is merged. Runtime deployment of that fix is an operator release step before this upload group is admitted; this task does not deploy it.

- Cover same-binding failed, different-binding failed, unknown current binding and multiple retained results for one task. No offered action may acknowledge success without the documented effect.
