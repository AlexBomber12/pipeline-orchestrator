# PR-227c: Migrate kwargs/selector construction and replace web type annotation

Branch: pr-227c-kwargs-selector-plugin
- Type: refactor
- Complexity: medium
- Depends on: PR-227b
- Priority: 1
- Coder: claude

## Problem

This is part 3 of 3 in the PR-227 split. PR-227a migrated breach lifecycle. PR-227b migrated rate-limit thresholds. PR-227c finishes the abstraction by migrating the remaining hardcoded branches: kwargs construction and selector logic.

Today, every handler that calls `plugin.run_planned_pr` or `plugin.fix_review` constructs kwargs inline with claude-specific or codex-specific argument shapes. After this PR, plugins return their own kwargs via `build_run_kwargs` and handlers do not need to know the plugin-specific argument names.

Also: `web/app.py` (or post-PR-225 `web/routes/repo_control.py`) imports `ClaudePlugin | CodexPlugin` directly for type annotation. Replace with the `CoderPlugin` Protocol so adding a third coder does not require editing the web layer.

## Scope

Add `build_run_kwargs` method to `CoderPlugin` Protocol. Implement in `ClaudePlugin` and `CodexPlugin`. Replace all inline kwargs construction in handlers. Replace `ClaudePlugin | CodexPlugin` type annotation in web with `CoderPlugin`.

This is the final piece — after PR-227c, integrating a third coder requires only adding a new plugin class and registering it.

def build_run_kwargs(self, *, repo_path, task, model, breach_monitor=None):
    kwargs = {
        "repo_path": repo_path,
        "task_branch": task.branch,
        "model": model,
    }
    if breach_monitor is not None:
        kwargs["breach_monitor"] = breach_monitor
    return kwargs

## Implementation notes

This is the largest of the three sub-changes because kwargs construction touches the hot path (every CODING and FIX cycle). Pay extra care reading the existing kwargs at each callsite.

Some handlers use task-specific kwargs that vary by handler (e.g. `fix.py` may pass review-specific arguments). The `build_run_kwargs` method must accept enough parameters to cover all handlers. If a handler needs to pass extra kwargs not covered by the Protocol method signature, do one of:
- Option A: extend `build_run_kwargs` signature with optional kwargs.
- Option B: have handlers compose kwargs by calling `plugin.build_run_kwargs(...)` and adding handler-specific keys on top.

Pick B for simplicity. Plugins return the base dict; handlers add fix-specific or coding-specific keys.

After this PR, `grep -n 'coder_name == "claude"\\|coder_name == "codex"' src/daemon/handlers/` should return 0 for behavior branches. Selection-only branches (e.g. `if coder_name in registry: ...`) are fine.

The mock third coder test is the acceptance criteria. If `FakeCoderPlugin` (a hypothetical third plugin defined only in tests) can drive the daemon through CODING → WATCH → FIX → MERGE without any production code change, the abstraction is leak-free.
