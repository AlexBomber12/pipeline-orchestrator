# PR-253: OBS-BE detection wiring - CRASH/ESCALATE/TIMEOUT/INFRA categories

- Complexity: medium
- Depends on: PR-252
- Priority: 2
- Coder: claude

## Problem

OBS-BE expanded from `docs/roadmap.md`. PR-252 ships the storage substrate. This PR wires the four detection paths so each cancellation surface writes a structured cause record:

1. **CRASH** — uncaught exception or non-zero exit without ESCALATE marker. Detected in `src/daemon/handlers/error.py` and runner-level exception handlers. Payload: `exit_code`, `stderr_tail` (last 500 chars).
2. **ESCALATE** — deliberate ESCALATE marker on last non-empty stdout line of coder subprocess. Detected in `src/daemon/handlers/coding.py` exit-zero classifier. Payload: `reason_text`.
3. **TIMEOUT** — per-cycle, per-PR, per-FIX, planned-PR overall budget hit. Detected in PR-218 timeout policy code. Payload: `limit_type`, `duration_elapsed_sec`, `active_phase`.
4. **INFRA** — gh CLI / network / Redis / auth subsystem fault. Detected in `src/github/cache.py` retry-exhaustion path and `src/web/services/repo_state.py` Redis-unavailable path. Payload: `subsystem`, `retry_count`, `last_attempt_iso`.

Without these wired writes, PR-254 UI surfacing has no data to show.

## Scope

Four wiring deliverables, each ~30-50 LOC, plus tests covering each category writes the right payload shape:

1. CRASH wiring in `error.py` and exception-handler paths.
2. ESCALATE wiring in `coding.py` exit-zero classifier.
3. TIMEOUT wiring in PR-218 timeout policy.
4. INFRA wiring in `cache.py` and `repo_state.py`.

OPERATOR_RECOVERY and NO_PUSH_DEADLOCK categories are wired by PR-247 (recovery button) and PR-258 (OBS-BB) respectively — explicitly out of scope here.

## Files to modify

`src/daemon/handlers/error.py` — at the top of `_transition_to_error` (or similar entry point), capture exit info and write cause. Add a parameter or detect from existing context:

```
from src.cancellation import CancellationCause, record_cancellation_cause

# Inside _transition_to_error, after determining error_message and
# before clearing current_task:
if self.state.current_task is not None:
    cause = CancellationCause(
        category="CRASH",
        payload={
            "exit_code": self._last_subprocess_exit_code or -1,
            "stderr_tail": (self._last_subprocess_stderr or "")[-500:],
            "error_message": error_message,
        },
    )
    try:
        await record_cancellation_cause(
            self.redis_client,
            self.repo_slug,
            self.state.current_task.task_id,
            cause,
        )
    except Exception as exc:
        self.log_event(
            f"[ERROR] Failed to record cancellation cause: {exc} - "
            f"continuing without storage."
        )
```

Wrap in try/except and swallow Redis failures — cause storage is best-effort, not blocking.

`src/daemon/handlers/coding.py` — locate the ESCALATE marker detection (probably in `_diagnose_exit_zero_no_pr` or near subprocess exit handling). When ESCALATE detected:

`src/github/cache.py` — at retry-exhaustion in `retry_transient`:

```
# When all retries exhausted and operation re-raises:
if task_id_in_context:  # threading task context through cache.py
    cause = CancellationCause(
        category="INFRA",
        payload={
            "subsystem": "gh_api",
            "retry_count": max_retries,
            "last_attempt_iso": datetime.now(timezone.utc).isoformat(),
            "error_class": type(last_exception).__name__,
        },
    )
    # ... record ...
```

NOTE: `cache.py` does not have task context in scope; threading it through is invasive. Alternative: emit a cause from the CALLER (handler that catches the RuntimeError) rather than from cache.py itself. Prefer this approach — pass cause-writing responsibility to the handler that catches the exception, where task context is in scope. Apply same pattern in `repo_state.py`: when Redis unavailable, the caller knows the task and writes INFRA cause.

`src/cancellation/storage.py` (extend from PR-252) — no changes needed; PR-252 helpers cover all categories.

## Implementation notes

Each detection point wraps the cause write in try/except. Cause storage is best-effort; if Redis is the failing subsystem, recursive failure is possible. Always log the failure but never let storage error block the cancellation transition.

The wiring order across categories matters for dual-attribution corner cases (e.g., subprocess crash AND timeout fire same task). Convention: write whichever category fires FIRST. The dashboard surfaces the first cause; subsequent context appears in event log.

After this PR ships, every CANCELED task in dashboard has a cause record. PR-254 surfaces them. Production verification: trigger a manual ESCALATE in a coder subprocess, confirm cause appears in Redis at `cancellation:{repo}:{task_id}` with category="ESCALATE".
