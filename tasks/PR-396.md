# PR-396: Enforce complete current-HEAD evidence at the merge boundary

Branch: pr-396-merge-expected-head
- Type: bugfix
- Complexity: high
- Depends on: PR-395
- Priority: 1
- Coder: any

Audit references: A09, A10, A11.

## Problem and intended result

WATCH decides from CI/review snapshots, while MERGE can synchronize the base and push a different commit before gh pr merge. src/github/prs.py:merge_pr does not pass an expected HEAD. A change between observation and merge can therefore escape the checks that allowed it.

Complete the evidence chain introduced by the preceding tasks. The merge operation must accept only the exact current SHA for which required CI and trusted review are satisfied, with guardrails and other existing inhibitors still enforced.

## Read before editing

- src/daemon/handlers/watch.py and src/daemon/handlers/merge.py, including pre-merge sync and conflict resolution.
- src/github/prs.py:merge_pr, checks/reviews evidence interfaces and GitHub cache invalidation.
- src/inhibitor.py, quarantine/suppression checks and current PR state hooks.
- tests/github/test_prs.py, tests/test_github_client.py and the existing MERGE/WATCH coverage modules in tests/runner/.

## Required behavior

1. Construct one merge decision for repo/PR/base/head SHA using complete required CI evidence from PR-393 and review provenance from PR-395. With the production policy, any absent, stale or inconsistent component blocks merge. Respect explicit no-review/no-checks settings only as configured policy; they cannot turn transport failure into evidence or waive configured required checks.
2. After pre-merge sync creates or pushes a commit, clear the prior merge permission, return to WATCH and obtain CI/review for that new SHA. Reuse the exact review-trigger path rather than adding another poster. When sync creates no new commit, validate that the remote HEAD still equals the assessed SHA.
3. Change merge_pr to receive expected_head_sha and pass the installed gh CLI's expected-head guard, --match-head-commit. No production call site may merge without an expected SHA. Missing SHA blocks the operation. Keep --squash and the intended branch-deletion behavior.
4. A HEAD mismatch is a reconcile-and-wait outcome, not a successful merge or automatic task failure. An ambiguous merge response requires a direct read: mark DONE only after GitHub confirms MERGED. CLOSED without merge and UNKNOWN are distinct. Do not blindly repeat a merge on an unverified newer HEAD.
5. Preserve checks for quarantine, scope-bound guardrail decisions, cross-repository PR handling, base branch and config.auto_merge. Temporary GitHub failures must leave task/run/PR identity recoverable.
6. Update every wrapper/call site and its test. Document that server-side branch protection is an additional rollout concern: changing GitHub settings or the service status/upload push model is outside this PR.

## Acceptance criteria

- A controlled push between gate evaluation and merge produces an expected-head rejection and a return to fresh checks.
- A pre-merge sync commit cannot merge using the previous commit's CI or +1.
- Missing required integration, stale approval, mismatched evidence SHA and quarantined PR each prevent the merge call.
- A valid current-HEAD PR still merges automatically under the existing policy.
- An ambiguous successful server merge is reconciled without duplicate work and is marked DONE only from positive confirmation.
- Every merge wrapper supplies a nonempty expected SHA; no alternate code path avoids the new boundary.
