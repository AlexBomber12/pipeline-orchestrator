# PR-393: Preserve complete CI evidence and required-check policy

Branch: pr-393-ci-evidence-completeness

- Complexity: high
- Depends on: none
- Priority: 1
- Coder: any

Audit references: A10.

## Problem and intended result

src/github/checks.py currently combines check-runs and commit statuses even if only 1 request succeeded, and _map_rest_ci_status_to_enum discards fetch_ok. A partial response can therefore look successful. It also treats an observed subset as the whole check policy. A green unit job is insufficient when the integration job is absent, waiting or unavailable.

Preserve completeness and the exact commit identity from retrieval through the public CI query path. Required checks for a repository must all be present and successful on that HEAD before the result can authorize a merge.

## Required behavior

1. Introduce a small typed CI evidence value in the existing GitHub layer. Record repo/PR where relevant, full head SHA, fetch time, completeness per authoritative source, normalized contexts, required-policy result and a stable pending reason. Keep legacy enum-facing helpers as adapters where needed. Missing or inconsistent SHA and incomplete pagination cannot produce successful evidence.
2. Both check-runs and combined statuses must have a known successful retrieval before their union is complete. A successful empty response is different from a failed response. A cached entry retains its SHA, age and completeness; incomplete data must never overwrite provenance as complete. Preserve bounded caching and existing infrastructure-failure classification.
3. Add an optional per-repository required_checks list to RepoConfig, with validation and a documented exact-name policy. Populate the tracked example configuration for pipeline-orchestrator with the observed GHA job names unit and integration. Do not invent requirements for the other 2 repositories. Document that a preserved server config must explicitly adopt the intended required_checks at deployment.
4. With a nonempty required_checks policy, every named context must have terminal success on the same SHA. A missing context is pending even when every visible check is green. Collapse reruns/history by context and authoritative attempt identity so an old failure does not override a newer success and an old success does not override a newer pending run. Match check-run identity including the producing app when metadata is available; do not merge unrelated contexts merely because display names collide.
5. Without an explicit required list, preserve the compatible policy of evaluating all observed contexts, but still require complete retrieval and at least 1 real context when allow_merge_without_checks is false. Document this weaker policy clearly. An explicit allow_merge_without_checks permits a known empty set only; it never turns a transport failure into success or waives a configured required context. Preserve known failure results even when another source is unavailable.
6. Keep statusCheckRollup/REST fallback semantics aligned. An unknown CI result remains pending with a reason rather than becoming a task failure simply because GitHub could not answer. Do not change the fix/retry policy or add a new GitHub client.

## Acceptance criteria

- Failed check-runs retrieval plus 1 successful commit status cannot authorize merge; the symmetric case behaves the same.
- Complete empty responses respect the explicit no-checks policy; incomplete empty responses never pass.
- Required unit success with integration missing or pending remains pending; both current successes pass.
- Duplicate context history, reruns, pagination failure, stale cache and mismatched SHA retain correct outcomes.
- Existing infrastructure-class failure and backoff behavior remains covered.
- Parsing an old RepoConfig succeeds without mutating it; the new required_checks value survives load/save.
