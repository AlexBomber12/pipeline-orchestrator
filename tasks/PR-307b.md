## Reading order note for the implementing coder

This task is the **runner integration** of the notification webhook feature. The delivery module + config landed in PR-307a (`src/daemon/notifications.py` with `send_guardrail_notification` and `_parse_guardrail_cause_for_notification` available; 4 new `DaemonConfig` fields). This PR wires the delivery into `src/daemon/runner.py` `_transition_to_error` GUARDRAIL block with an `asyncio.wait_for` outer timeout and try/except + log_event wrapper.

If implementation exceeds 80 LoC excluding tests, escalate via stdout.

## Problem

PR-307a built the notification delivery module in isolation. The daemon needs to invoke it at the GUARDRAIL escalation point so operator gets notified. The natural callsite is `_transition_to_error` where the GUARDRAIL message already produces the cancellation cause. PR-307b adds the side-effect call.

Critical: the integration must not crash the daemon. Webhook server might be slow, unreachable, or returning errors. The runner's escalation path must complete regardless. Use `asyncio.wait_for` with a buffer above the inner httpx timeout to bound worst-case latency.

### 2. Integration in `_transition_to_error`

Find the GUARDRAIL block in `_transition_to_error`. Currently (verify exact line numbers via grep before editing) there is a side-effect block where guardrail causes update a Redis pending set. The notification call goes adjacent to that.

Locate the existing block (likely shape):

```python
if message.startswith("GUARDRAIL") and self.state.current_task is not None:
    # existing PR-305 pending-set update or similar logic
    ...
```

Append the notification call inside the same conditional, after any existing side-effects:

```python
parsed = _parse_guardrail_cause_for_notification(message)
if (
    parsed
    and self.app_config.daemon.guardrail_notification_webhook_url
    and parsed["tier"] >= self.app_config.daemon.guardrail_notification_min_tier
):
    pr_number = (
        self.state.current_pr.number
        if self.state.current_pr is not None
        else None
    )
    timeout_seconds = self.app_config.daemon.guardrail_notification_timeout_seconds
    try:
        await asyncio.wait_for(
            send_guardrail_notification(
                webhook_url=self.app_config.daemon.guardrail_notification_webhook_url,
                repo_name=self.name,
                pr_id=self.state.current_task.pr_id,
                pr_number=pr_number,
                owner_repo=self.owner_repo,
                tier=parsed["tier"],
                category=parsed["category"],
                excerpt=parsed["excerpt"],
                rule=parsed["rule"],
                timeout_seconds=timeout_seconds,
                dashboard_base_url=self.app_config.daemon.dashboard_base_url,
            ),
            timeout=timeout_seconds + 2.0,
        )
    except asyncio.TimeoutError:
        self.log_event(
            "[GUARDRAIL] notification webhook timed out"
        )
    except Exception as exc:
        self.log_event(
            f"[GUARDRAIL] notification webhook failed: {exc}"
        )
```

Rationale for the outer `wait_for` buffer (+2.0 above inner httpx timeout): a misbehaving webhook server that opens TCP but never responds would otherwise block the asyncio event loop until OS-level TCP timeout (~2 minutes), stalling daemon activity for that repo. The 7-second worst case (5s default httpx + 2s buffer) is acceptable.

The inner httpx timeout is enforced by `send_guardrail_notification` itself (PR-307a). The outer wrapper is belt-and-suspenders against pathological cases where httpx itself misbehaves (event-loop-blocking bug, mock-test scenarios).

## Risk notes (for PR description)

The `asyncio.wait_for` outer wrapper is the critical defense-in-depth against a misbehaving webhook server. Without it, a server that accepts the TCP connection but never sends an HTTP response would hold the daemon's asyncio event loop for ~2 minutes (OS-level TCP timeout), stalling all activity for that repo. With it, worst-case latency is `timeout_seconds + 2.0` (default 7 seconds).

Notification is best-effort by design. A failed notification does not retry, does not block escalation, does not change the cancellation cause record. Operator who needs guaranteed delivery should monitor the daemon log for `"[GUARDRAIL] notification webhook"` failure lines and investigate webhook health separately.

If the webhook server has a strict rate limit, two near-simultaneous Tier 2 trips could exceed it. PR-307 v1 does no rate limiting on the daemon side; rate limit is the webhook provider's responsibility. If this becomes a problem, a future PR can add per-repo notification throttling (e.g., one notification per pr_id per hour).
