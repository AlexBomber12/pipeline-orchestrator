**P0 priority — production bug observed 2026-05-01. Should run in parallel with Batch A (no dependencies).**

## Problem

On 2026-05-01 the operator observed 76 alternating events in the dashboard event log:

- `[INFRA] No tasks available.`
- `[INFRA] IDLE: merged PR check failed: gh api repos/AlexBomber12/pipeline-orchestrator/pulls?state=closed&base=main&per_page=100&page=1 --include -H If-None-Match: W/"02a8b5b4..." failed (exit 1): gh: HTTP 304; continuing with local merged-status heuristics.`

Every IDLE cycle (5 minutes) produces both events. The "HTTP 304" is **not** a failure — 304 Not Modified is the success path for ETag conditional requests. The error message wording misclassifies it as a failure.

**Root cause** in `src/github_client.py::_etag_get` (around line 175):

```python
status, headers, body = _split_include_response(raw)
if status == 304:
    if cached is None:
        return None  # <-- THIS IS THE BUG
    _etag_cache.move_to_end(path)
    return cached[1]
```

When `gh api` returns 304 but the local in-memory cache is empty (typical after daemon restart, or when cache eviction dropped this entry), `_etag_get` returns `None`. The caller `_etag_get_paginated` interprets `None` on page 1 as failure and raises `RuntimeError`. The exception bubbles up to `idle.py:443` which logs `[INFRA] IDLE: merged PR check failed`.

This is logically wrong because:
1. The server responding 304 means it received a valid `If-None-Match` from us — but if `cached` is `None` we did not send `If-None-Match`. The 304 must therefore be a normal-load 304 from a previous request whose ETag we evicted, or a defensive 304 from a load-balancer caching layer. Either way, an empty payload is not failure.
2. The dashboard already has a fallback path: `idle.py:448` sets `merged_prs = []` and continues. The error message about "merged PR check failed" makes operators think the daemon is broken.

## Scope

Two related fixes in one PR:

1. `_etag_get`: when 304 arrives without a cached entry, treat as empty 200 (return empty list/dict per endpoint convention) or retry without `If-None-Match`. Pick the simplest correct option.
2. Update the dedup logic so the alternating "no tasks" + "merged check failed" pair is treated as one repeating cycle. Or — simpler — silence the merged-check log line when the only failure is HTTP 304.

## Files to modify

`src/github_client.py`:

In `_etag_get`, replace the 304-no-cache branch:

```python
if status == 304:
    if cached is None:
        # Server returned 304 but we have no cached body.
        # This happens when our cache was evicted/cleared but the
        # GitHub edge cache still has the ETag. Retry without
        # If-None-Match to force a full 200 response.
        retry_args = ["api", path, "--include"]
        retry_raw = run_gh(retry_args)
        if not isinstance(retry_raw, str) or not retry_raw.lstrip().startswith("HTTP/"):
            return retry_raw
        retry_status, retry_headers, retry_body = _split_include_response(retry_raw)
        if retry_status is None or not (200 <= retry_status < 300):
            return None
        retry_body = retry_body.strip()
        if not retry_body:
            return None
        try:
            payload = json.loads(retry_body)
        except json.JSONDecodeError:
            return None
        etag = retry_headers.get("etag")
        if etag:
            _etag_cache_put(path, etag, payload)
        return payload
    _etag_cache.move_to_end(path)
    return cached[1]
```

## Implementation notes

The 304-no-cache scenario happens reliably after `docker compose restart daemon` because the in-memory `_etag_cache` is empty. The GitHub edge cache (or our request from the previous daemon process) populated the server's view of "this client's last seen state". Our retry without `If-None-Match` forces a fresh 200 with body and ETag, repopulating our cache.

This is one extra `gh api` call per affected endpoint per daemon restart. Negligible cost, since after the first hit the cache is warm.

Alternative considered: persist the ETag cache to Redis so it survives restarts. Rejected for this PR — that is a larger change. The retry-on-empty-cache approach is the minimal fix that closes the operator-visible bug.

The dashboard event log spam closes immediately on next deploy because `idle.py` no longer logs the "merged PR check failed" line for HTTP 304 cases.
