## Problem

PR-306 dashboard panel (future) needs to fetch guardrail-flagged PRs for a repo over HTTP. PR-305a added the storage helper that enumerates pending guardrail decisions; PR-305b exposes that helper as a JSON endpoint mounted on the existing `repo_control` router.

## Scope

### 1. New GET endpoint

Add to `src/web/routes/repo_control.py`, near other GET endpoints (insert near line 974 where `@router.get("/repos/{name}/tasks", ...)` lives, or near `@router.get("/api/repo/{name}/queue", ...)` at line 1179 — match the cleaner placement):

```python
@router.get(
    "/api/repo/{name}/guardrail/pending",
    response_class=JSONResponse,
)
async def get_repo_guardrail_pending(request: Request, name: str) -> Response:
    """List pending guardrail decisions for a repo, oldest first.

    Returns a JSON object with shape::

        {
            "pending": [
                {
                    "pr_id": "PR-296",
                    "rule": "large_diff_threshold",
                    "excerpt": "+1800 LOC across 35 files",
                    "recorded_at": 1746789012
                },
                ...
            ]
        }

    The list is sorted ascending by ``recorded_at`` so operators triage
    in arrival order. Bounded by the underlying helper's ``limit`` (100).

    Returns 404 if the repo name does not match any configured repo.
    """
```

Implementation outline:

1. Look up the repo config via existing `_find_repo_config_by_name(request, name)` helper. If not found, return `JSONResponse({"error": "repo not found"}, status_code=404)`.
2. Resolve `repo_slug` from the repo config (same pattern as other endpoints; usually `repo_config.repo_slug` or derived from `name`). Match the pattern used by adjacent endpoints in the file.
3. Get the redis client from request state (same pattern as adjacent endpoints; usually `request.app.state.redis` or via dependency).
4. Call `await list_pending_guardrail_decisions(redis_client, repo_slug)`.
5. Build the response payload:
   ```python
   payload = {
       "pending": [
           {
               "pr_id": entry.task_id,
               "rule": entry.rule,
               "excerpt": entry.excerpt,
               "recorded_at": entry.recorded_at,
           }
           for entry in pending
       ]
   }
   ```
6. Return `JSONResponse(payload)`.

### 3. Tests

Create new test file `tests/web/test_guardrail_pending_endpoint.py`. Use the existing FastAPI test-client fixture pattern from `tests/web/test_retry_endpoint.py` as reference.

- `test_guardrail_pending_returns_empty_list_when_no_pending`: setup repo with no cancellation causes, GET endpoint, assert response status=200 and JSON body `{"pending": []}`.

- `test_guardrail_pending_returns_sorted_oldest_first`: setup 3 guardrail causes with `created_at` T, T+10, T+5, GET endpoint, assert `[pr_id of T, pr_id of T+5, pr_id of T+10]` order in response.

- `test_guardrail_pending_filters_out_non_guardrail_subsources`: setup 2 guardrail causes + 1 coder-subsource cause, GET endpoint, assert response contains only the 2 guardrail entries.

- `test_guardrail_pending_extracts_rule_and_excerpt_from_payload`: setup cause with `payload={"subsource": "guardrail", "rule": "large_diff_threshold", "excerpt": "+1800 LOC"}`, GET endpoint, assert response entry has `rule="large_diff_threshold"` and `excerpt="+1800 LOC"`.

- `test_guardrail_pending_repo_isolation`: setup causes in repo_a and repo_b, GET `/api/repo/repo_a/guardrail/pending`, assert response only contains repo_a entries.

- `test_guardrail_pending_repo_not_found_returns_404`: GET `/api/repo/nonexistent/guardrail/pending`, assert status=404.

- `test_guardrail_pending_bounded_at_100`: setup 150 guardrail causes, GET endpoint, assert `len(response["pending"]) == 100`.
