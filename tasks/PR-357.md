## Problem

Operator-reject events (subsource=operator_reject, written via review rejection flow in PR-305c) live in cancellation Redis records but have no dedicated visibility. Historic queries "what did I reject last week and why" require:

1. Knowing which task IDs were rejected (no listing surface)
2. Per-task `redis-cli GET cancellation:<repo>:<task_id>` reads
3. Manual extraction of operator_reject_rule and operator_reject_excerpt from payload

Painful for retrospective review or pattern detection.

## Solution

Add page `/repo/{name}/rejects` listing all operator_reject events from cancellation_index sorted desc by timestamp. Each row: task_id, timestamp, rule that fired, excerpt of the offending content.

Reuses cancellation_index for discovery (no new index needed - existing zset has all rejected tasks).

### Endpoint

```python
@router.get("/repo/{name}/rejects", response_class=HTMLResponse)
async def operator_reject_history(
    request: Request,
    name: str,
    limit: int = Query(50, ge=1, le=500),
) -> HTMLResponse:
    redis_client = request.app.state.redis
    cfg = load_config(...)
    if not any(r.name == name for r in cfg.repos):
        raise HTTPException(404, f"Unknown repo: {name}")

    # Read ALL cancellation records for repo, filter to operator_reject
    task_ids = await redis_client.zrevrange(f"cancellation_index:{name}", 0, -1)
    rejects: list[dict] = []
    for task_id in task_ids:
        cause = await read_cancellation(redis_client, name, task_id, refresh_ttl=False)
        if cause is None:
            continue
        subsource = (cause.payload or {}).get("subsource") if isinstance(cause.payload, dict) else None
        if subsource != "operator_reject":
            continue
        rejects.append({
            "task_id": task_id,
            "canceled_at": cause.canceled_at.isoformat(),
            "rule": (cause.payload or {}).get("operator_reject_rule"),
            "excerpt": (cause.payload or {}).get("operator_reject_excerpt", "")[:200],
        })
        if len(rejects) >= limit:
            break

    return templates.TemplateResponse(request, "operator_rejects.html", {
        "repo_name": name,
        "rejects": rejects,
        "limit": limit,
    })
```

## Threat model

**Threat addressed**: forensic gap for operator decisions. Pattern detection on operator rejects requires the surface this PR provides.

**Other layers protecting**: PR-322 subsource registry includes operator_reject metadata. PR-332 diagnostic API can return single-task reject details. PR-357 is the listing surface.

**Why this layer needed**: retrospective review workflow. Operator reviewing weekly trends in approvals needs the listing, not per-task lookups.

### Caller audit

New page. Reads cancellation_index (existing zset). Walks records sequentially. Performance: each call iterates up to 500 task_ids and reads cancellation records for each. With ~50 active rejects per repo (estimated), latency ~50ms acceptable. If repo accumulates 10k rejects, pagination may be needed - out of scope here, but document the threshold.

`read_cancellation(refresh_ttl=False)` per PR-345 contract: this page renders for historical review and should NOT extend TTL on records the operator did not explicitly investigate. Verify the False flag passes.

## Out of scope

- Filtering by rule or date range - out of scope; simple time-desc list.
- Exporting to CSV - out of scope.
- Linking from operator_reject row to diagnostic_panel - minor convenience, out of scope.
- Cross-repo aggregation - out of scope.

## Success signal

`/repo/pipeline-orchestrator/rejects` shows the last 50 operator rejects with rule and excerpt. Empty state renders cleanly for repos with no rejects. Page load <500ms on production with ~100 cancellation records per repo.
