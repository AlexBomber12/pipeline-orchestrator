## Problem

`BoundedRecoveryPolicy` exists in `src/daemon/recovery_policy.py` and is used at 4 sites: dirty-tree (preflight.py:28), GitHub API budget pause and slowdown (runner.py:324, 333), FIX iteration cap and no-push deadlock (fix.py:651, 658).

It is NOT used at two structurally identical patterns in error.py:

1. `_error_skip_count` — counter increments on consecutive same-context errors, threshold 3, action "log and stay ERROR"
2. `_error_diagnose_count` — counter increments on each diagnose attempt, threshold 3, action "log and stay ERROR"

Both are open-coded. The author of error.py either did not know BoundedRecoveryPolicy existed or wrote error.py first.

This is the cheapest cleanup PR with high coherence value. After migration, all 5 threshold-based recovery policies share the same telemetry shape and guarantees.

## Scope

Convert both error.py counters to BoundedRecoveryPolicy instances. Behavior bound by PR-210 baseline tests; all 6 tests must continue to pass.

```
    """Log when error skip ceiling is reached.

    Stays in ERROR per existing policy; the runner-level reset on
    next non-ERROR cycle clears the counter via
    self._error_skip_policy.reset().

        "until operator intervention or next non-ERROR cycle"
    )

def _on_error_diagnose_threshold(self) -> None:
    """Log when diagnose attempt ceiling is reached."""
    self.log_event(
        "[ERROR] max AI diagnosis attempts (3) reached; staying ERROR"
    )
```

## Implementation notes

`BoundedRecoveryPolicy` API per `src/daemon/recovery_policy.py`:
- `attempt()` — increment counter; returns nothing
- `attempts` — read current count
- `threshold_reached` — read whether max_attempts is hit (or exceeded)
- `reset()` — zero the counter and threshold flag
- `on_threshold` — callback fires when threshold first reached

The `_error_skip_context` field stays separate because the policy is count-only; context comparison and reset on context change is the caller's responsibility. This is consistent with how the existing 4 sites use the policy (e.g. dirty-tree resets the policy on a clean cycle, not on a "different dirty pattern").

After this PR ships, all 5 threshold-based recovery sites share the same idiom: `policy.attempt(); if policy.threshold_reached: handle_threshold(); else: continue`. New code adding similar semantics should use BoundedRecoveryPolicy from day one.
