# PR-206: Settings save publishes wake events

Branch: pr-206-settings-pubsub-wake
- Type: feature
- Complexity: low
- Depends on: PR-205
- Priority: 3
- Coder: any

## Problem

Per-repo settings changes (coder swap, review_timeout_min, other per-repo flags) currently apply on the next daemon poll cycle. With base 60s poll interval the user perceives this as a 0-60s lag. With PR-184 extended IDLE polling, the lag grows to 300s. A user who swaps coder from Claude to Codex during a long IDLE period waits up to 5 minutes to see the change reflected in the next picked task.

The fix is the same pub/sub doorbell pattern as PR-205. Settings save endpoints publish a wake event on `orchestrator:wake:{repo_name}` after their existing save logic. Daemon, already subscribed via PR-183 plumbing, wakes immediately and runs its standard cycle which re-reads config.

PR-206 depends on PR-205 not for code (both could land in either order) but for narrative clarity: control commands first, settings second. The PR-205 implementation establishes the pattern which PR-206 simply applies to a different surface.

## Scope

Two per-repo settings endpoints publish wake events:

1. POST /repos/{name}/coder (per-repo coder swap, around line 1187 in `src/web/app.py`)
2. PUT /settings/repo/{name} (per-repo settings such as review_timeout_min, around line 2114)

Out of scope for this PR: daemon-level settings (PUT /settings/daemon, line 1670). These are global, not per-repo, and the wake helper takes a repo_name parameter. A broadcast variant is a separate question deferred to a future PR. Daemon-level changes still apply on next tick of every repo as today.

Out of scope for this PR: structural endpoints that add or remove repos (POST/DELETE /settings/repos around lines 1957 and 1978). These trigger daemon restart or repo discovery via existing mechanisms; pub/sub is not the right tool.

Out of scope for this PR: the bulk PUT /settings/repos endpoint (line 2044) that updates multiple repos at once. If desired in a follow-up PR, the same pattern applies but the endpoint loops over affected repos and calls `publish_wake` for each.

## Files to modify

`src/web/app.py`:

- In the per-repo coder swap endpoint, after the existing save logic completes successfully, call `publish_wake(name, "coder_swap")`.
- In the per-repo settings endpoint, after the existing save, call `publish_wake(name, "settings")`.
- Wrap each call in a try-except that swallows Redis errors at warning level, same pattern as PR-205. Settings save must remain functional even when Redis pub/sub is unavailable.

`tests/`:

- Test: coder swap endpoint publishes a wake event with event_type "coder_swap" on the correct channel.
- Test: per-repo settings endpoint publishes with event_type "settings".
- Test: Redis unavailable does not break either endpoint.
- Test: end-to-end demonstrating coder swap during long IDLE wakes daemon within 2 seconds.

## Implementation notes

`publish_wake` is already imported in `src/web/app.py` from PR-183 and reused in PR-205. Do not redefine.

Publish goes after persistence, not before. If publish fires before the new coder name is committed to Redis or config storage, daemon could wake and re-read the old value, spin back to sleep, and the setting application gets delayed back to the original polling lag.

Choice of event_type strings: "coder_swap" and "settings" are descriptive only, used for log lines and debugging. Daemon does not branch on these values. They are free strings, no enum needed in this PR.

Daemon code is not modified in this PR. The subscriber from PR-183 wakes on any published message and the existing config-read path runs on each cycle.
