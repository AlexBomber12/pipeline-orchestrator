# PR-289: Tier 2 guardrails secret-pattern scan — detect credentials in diff additions with redacted excerpts

Branch: pr-289-tier2-guardrails-secret-patterns
- Type: feature
- Complexity: medium
- Depends on: PR-288
- Priority: 1
- Coder: codex

## Problem

A coder may inadvertently commit a credential into a diff: an environment variable's literal value pasted into a config file, a test fixture containing a real API key, a `.env` file accidentally added without `.gitignore` coverage, or a generated artifact containing OAuth tokens. PR-272 pre-push hook does not inspect diff content. Tier 1 patterns target known-bad git operations, not data exfiltration. The blast radius of a leaked credential is high (GitHub-org access, AWS resources, AI provider API quota); detection needs to be fast and the response must NOT echo the credential anywhere.

Existing tools like `gitleaks` and `trufflehog` run as CI checks but operate post-merge or as separate workflows the daemon does not consume. The daemon needs in-loop detection before merge.

PR-289 extends `scan_pr_diff` with a secret-pattern catalogue. The catalogue covers high-confidence patterns from major providers plus a generic high-entropy heuristic for anonymous strings on suspicious context lines (`secret=`, `token=`, `api_key=`, `password=`).

Critical security requirement: the violation excerpt **never includes the matched secret value**. Excerpts contain only the file path, line number, and pattern category. The matched bytes stay in the GitHub commit (the daemon does not modify history) but the daemon's logs, dashboard event log, and Redis findings cache do not duplicate the leakage surface.

## Scope

Extend `src/daemon/guardrails.py` `scan_pr_diff` with secret-pattern detection.

### 1. New helper `_scan_secrets_in_additions(diff_text)`

Iterates over `+` prefixed lines (additions only — not context, not deletions) grouped by file path. For each addition, checks against the secret pattern catalogue. Returns list of `(file_path, line_in_diff, category)` tuples; values are NEVER returned, only categorical metadata.

### 2. Secret pattern catalogue

Group A: high-confidence provider tokens (regex matches imply active credentials):

```python
SECRET_PATTERNS_A = [
    ("github_pat_classic",
     re.compile(r"\bghp_[A-Za-z0-9]{36}\b")),
    ("github_pat_finegrained",
     re.compile(r"\bgithub_pat_[A-Za-z0-9_]{82}\b")),
    ("github_oauth",
     re.compile(r"\bgho_[A-Za-z0-9]{36}\b")),
    ("github_app_token",
     re.compile(r"\b(?:ghs|ghu|ghr)_[A-Za-z0-9]{36}\b")),
    ("aws_access_key",
     re.compile(r"\b(?:AKIA|ASIA|AGPA|AIDA|AROA|AIPA|ANPA|ANVA)[A-Z0-9]{16}\b")),
    ("anthropic_api_key",
     re.compile(r"\bsk-ant-[A-Za-z0-9_-]{30,}\b")),
    ("openai_api_key",
     re.compile(r"\bsk-(?:proj-)?[A-Za-z0-9]{30,}\b")),
    ("private_key_block_begin",
     re.compile(r"-----BEGIN (?:RSA |OPENSSH |DSA |EC |PGP |ENCRYPTED )?PRIVATE KEY(?: BLOCK)?-----")),
    ("slack_bot_token",
     re.compile(r"\bxox[baprs]-[A-Za-z0-9-]{10,}\b")),
    ("stripe_secret_key",
     re.compile(r"\bsk_(?:live|test)_[A-Za-z0-9]{24,}\b")),
]
```

Group C: file-path indicators (file additions that almost always contain secrets):

```python
SUSPICIOUS_FILE_PATHS = [
    re.compile(r"(?:^|/)\.env(?:\.[a-z]+)?$"),  # .env, .env.local, .env.production
    re.compile(r"(?:^|/)credentials\.json$"),
    re.compile(r"(?:^|/)service-account.*\.json$"),
    re.compile(r"\.pem$"),
    re.compile(r"\.p12$"),
    re.compile(r"\.pfx$"),
    re.compile(r"id_rsa$"),
    re.compile(r"id_ed25519$"),
]
```

A diff that adds a new file matching one of these paths emits a `suspicious_secret_file` violation regardless of line content (the file existence is the signal).

### 3. False-positive suppression

Several common patterns generate false positives:

- **Test/example placeholders**: lines containing `EXAMPLE`, `PLACEHOLDER`, `YOUR_KEY_HERE`, `xxxxxxxx`, `1234567890` should not trigger Group B even if they have key=value form.
- **Hash digests**: 40-char (SHA-1) and 64-char (SHA-256) hex strings match high-entropy heuristic but are not credentials. Suppress when value is hex-only AND length is exactly 40, 56, 64, or 96.
- **UUIDs**: standard UUID format with hyphens already excluded by `[A-Za-z0-9_+/=.-]` not allowing `-` at certain positions; verify regex does not match canonical UUIDs.
- **Base64-encoded test data**: lines with comments `# test fixture`, `// example`, `"""mock"""` nearby. This is harder; v1 ignores this case and accepts the false-positive risk for clearer detection.

Group A patterns are high-confidence and do NOT receive false-positive suppression — a real `ghp_*` token is either valid or expired but always credential-shaped, so reporting it is correct even if the operator already revoked it.

### 4. Extend `scan_pr_diff`

Append after existing Tier 1 + Tier 2 large-diff (PR-288) checks:

```python
secret_findings = _scan_secrets_in_additions(diff_text)
for file_path, line_in_diff, category in secret_findings:
    excerpt = (
        f"Secret pattern '{category}' detected in {file_path} "
        f"(line {line_in_diff} of diff). Value redacted."
    )
    violations.append(GuardrailViolation(
        tier=2,
        category="secret_in_diff",
        excerpt=excerpt[:200],
        rule=(
            "AGENTS.md prohibits committing credentials. "
            "Rotate the leaked secret immediately and remove "
            "from git history."
        ),
    ))
```

Note `category` of the GuardrailViolation is the constant string `"secret_in_diff"` for ALL secret findings. The specific pattern category (`github_pat_classic`, `aws_access_key`, etc.) appears in the excerpt for operator visibility but is NOT in the structured category field — this keeps downstream cancellation card classification simple.

## Implementation notes

The redaction requirement is the most important constraint. Common mistake: an excerpt like `f"Found {match.group()} in {file}"` echoes the secret. Defensive shape: pass only `(file, line_number, category_string)` from `_scan_secrets_in_additions` upward; never return or store the matched value.

The high-entropy heuristic is intentionally conservative. Many legitimate strings (commit SHAs, build hashes, config UUIDs, version identifiers) have moderate entropy. The Shannon-entropy threshold of 4.0 plus the placeholder-suppression logic targets the worst-case false-positive sources without filtering all real credentials. Group A high-confidence patterns provide the core security value; Group B catches what Group A misses but accepts some false-positive overhead.

The `secret_scan_enabled` config flag exists for the rare repo where false-positive noise dominates legitimate signal. Default-on because security wins outweigh occasional manual override; track repo-specific disablements and review periodically.

Estimated diff size: ~250-350 LOC. Of that, ~150-200 LOC is the catalogue + helpers, ~5 LOC is config, ~100-150 LOC is tests (each pattern needs positive + negative coverage).
