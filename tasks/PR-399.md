# PR-399: Preserve recoverable work before destructive Git transitions

Branch: pr-399-preserve-work-before-reset
- Type: bugfix
- Complexity: high
- Depends on: PR-398
- Priority: 1
- Coder: any

Audit references: A14.

## Problem and intended result

Recovery, task status writes and retry/reset operations use forced checkout, hard reset and clean. A backup branch or git bundle preserves commits but does not preserve staged, unstaged or untracked work. A recovery action can therefore remove the very work needed to understand or continue a failed attempt.

Create a shared preservation barrier for destructive Git operations. Reuse existing backup facilities and caller reservations, and keep the distinction between operational work preservation and a full disaster-recovery backup.

## Required behavior

1. Add a shared work-preservation API returning an immutable snapshot reference plus a completeness result. Capture repo/base/HEAD/branch, worktree/index status, relevant local-only commits, staged and unstaged changes including binary contents, and untracked files that the planned operation would remove. Preserve a detached HEAD too. Do not assume that a patch or bundle alone captures all of these.
2. Store recovery material outside the managed worktree under a private /data recovery area keyed by repo and operation/attempt identity. Restrict permissions, validate paths, avoid following symlinks outside the repository and never upload recovery material or credentials to GitHub. Keep indexes/manifests separate from public logs; include file hashes and enough metadata for restoration to a separate directory.
3. Classify the destructive operation's actual scope. A clean operation that would delete no unsaved work should not create a redundant large backup. If snapshots exceed a configured limit, disk space is insufficient, a file changes during capture or preservation is incomplete, stop before destructive Git and expose the reason. Do not silently omit files and claim recoverability. Do not delete existing backups to make this operation pass.
4. Route relevant destructive paths in runner status writes, recovery, repo sync/preflight, error cleanup, FIX/MERGE and web retry/reset through the barrier. Reuse their existing execution/reservation guards. Check supervisor cleanup from PR-398 before modifying a coder worktree. This task must not weaken busy guards or claim to solve cross-process ownership; that remains the next sprint.
5. Where a destructive action is provably safe because the relevant state is clean and no local-only commits would be lost, record that decision through the same API rather than adding undocumented bypasses. Inventory remaining forced checkout/reset/clean calls in the PR and explain their preservation or safety path.
6. Provide a read-only inspect and separate-directory restore helper usable on an isolated snapshot. Restoration must not overwrite the live checkout by default. Record a snapshot reference in existing diagnostic/run history so the operator can find saved work without exposing its content.

## Acceptance criteria

- Restore staged and unstaged edits, binary files, untracked files, a local-only commit and detached HEAD state into a fresh temporary directory and compare bytes/index meaning.
- Permission/read errors, changing files, full-disk/size-limit simulation and interrupted capture prevent the destructive operation.
- A symlink pointing outside the repo is preserved as a link without reading its target.
- Clean/no-loss paths avoid redundant backups, while every audited destructive call has an explicit decision.
- Snapshot metadata and private file contents are excluded from commits and public diagnostics.
- Existing completion evidence, status writes and retry reservations keep their prior meanings; tests verify preservation before mutation.
