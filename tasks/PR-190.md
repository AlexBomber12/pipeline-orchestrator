# PR-190: Asymmetric push verification in fix.py normal path

Branch: pr-190-asymmetric-push-verification
- Type: bugfix
- Complexity: low
- Depends on: none
- Priority: 3
- Coder: any

## Problem

This is Sprint F1.3 PR-159 from the original plan (now PR-190). The stop-cancel path in `fix.py` already verifies after kill that pushes since the last known SHA actually arrived on origin (`_verify_push_after_kill` or similar). The normal (non-cancel) path does not have this verification — it trusts that if the coder process did not error out, pushes succeeded.

This trust is occasionally wrong. Coder can complete without error but the push subprocess may have silently failed (network glitch, partial output, etc). Daemon then enters WATCH on a PR that has no fresh commits relative to its expected state.

The fix is to apply the same verification on the normal path: after coder process exits cleanly, verify origin has the expected commits before transitioning state.

## Scope

Add push verification in the normal-exit path of fix.py, mirroring the stop-cancel path's existing logic.

## Files to modify

`src/daemon/handlers/fix.py`:
- Identify the existing `_verify_push_after_kill` (or equivalent) method.
- Refactor or extract into a shared helper `_verify_pushes_since(last_known_sha)` callable from both paths.
- In the normal-exit path (around the place where coder exits 0 and we are about to transition to WATCH), call the verification.
- If verification fails (no new commits on remote), log event `Coder exited cleanly but no push detected` and either retry or transition to HUNG depending on existing policy.

`tests/test_fix_handler.py`:
- Test: normal exit with verified push → continues to WATCH.
- Test: normal exit without push → logged event + handled as no-push.
- Test: stop-cancel path still works (regression).

## Implementation notes

The existing kill-path verification uses `gh api repos/owner/repo/commits/<sha>` or similar to check remote. Use the same primitive.

If the verification API call itself fails (network error during verification), log warning and proceed optimistically — failing the verification check should not block the daemon on infrastructure flakiness. This is the same fail-open principle as PR-189.
