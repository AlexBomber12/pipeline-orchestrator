# PR-191a: ETag conditional requests for REST GET helpers

- Depends on: PR-180
- Priority: 1
- Coder: any

## Problem

This is OBS-AC Leverage 3, part 1 of 2. GitHub REST API supports ETag conditional requests via `If-None-Match` header. When the response has not changed since the cached ETag, the server returns HTTP 304 Not Modified with empty body, and **this 304 response does not count against the rate limit budget**.

For polling daemons that re-query the same endpoints repeatedly with low data turnover (most polling cycles return identical data), ETag conditional requests are essentially free for the common case.

This PR adds ETag support to the REST GET helper functions in `src/github_client.py` for single-resource endpoints (PR detail, commit, check-runs for a single SHA, status for a single SHA).

PR-191b (follow-up) will extend the support to list endpoints (PR list, comment list) which have additional pagination considerations.

## Scope

Add an in-memory ETag cache keyed by URL. Helper function `_etag_get(url)` checks cache, sends `If-None-Match` if cached, parses response, updates cache.

The cache is in-memory only (lost on daemon restart). Persistent cache could be a future optimization but is not needed for the primary diet effect.

## Files to modify

`src/github_client.py`:
- Add module-level dict `_etag_cache: dict[str, tuple[str, dict]]` mapping URL to (etag, last_response_payload).
- Add helper function `_etag_get(url, *args)` that:
  - Looks up URL in cache.
  - If cached, sends `gh api {url} -H "If-None-Match: {etag}"`.
  - If response is 304 (gh api may surface this as exit code or specific stderr), return cached payload.
  - Otherwise parse response, extract `ETag` header, update cache, return payload.
- Refactor existing single-resource REST GET calls (commit, check-runs, status, single PR fetch) to use `_etag_get`.
- Do NOT touch list endpoints in this PR (those are PR-191b).

`tests/test_github_client.py`:
- Test: first call populates cache.
- Test: second call uses If-None-Match.
- Test: 304 response returns cached payload.
- Test: 200 response with new ETag updates cache.
- Test: cache miss after eviction (set max size, e.g. 500 entries).

## Implementation notes

`gh api` does pass through `-H` flags. Verify by testing with a known endpoint that supports ETag.

Detecting 304 from `gh api`: if `gh api` surfaces 304 as exit non-zero with specific message, parse stderr. If it surfaces as empty stdout, check return value. Code the detection carefully — getting this wrong means cache never hits.

Cache eviction: simple LRU with max 500 entries is enough. Daemon polls a small fixed set of URLs.

Thread safety: daemon is single-process, single-threaded asyncio. No locking needed for the cache dict.
