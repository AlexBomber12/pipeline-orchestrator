## Problem

Per OBS-CY (roadmap 2026-05-10): dashboard upload route silently overwrites status:DONE frontmatter when same-named spec exists in upload zip. Realistic regression mode: LLM regenerating a task spec zip for a partial-update upload inadvertently includes already-merged spec at status:TODO. Upload accepts, daemon picker re-dispatches a coder against the already-merged branch. Risk surface: redo waste, cross-repo orphan branches.

## Solution

Modify upload route to merge frontmatter status on file collision instead of naive overwrite. Rule: if existing file's frontmatter has `status: DONE` OR `status: ERROR` (daemon-written terminal states), preserve that status in the upload result. The new file body is taken from upload but frontmatter status is preserved.

If existing file has `status: TODO` or no status, full overwrite proceeds (operator intent: replace work-in-progress spec).

### Logic sketch

```python
async def _preserve_or_replace_on_collision(
    existing_path: Path,
    upload_content: str,
) -> str:
    """Return the content to write, preserving terminal status fields."""
    if not existing_path.exists():
        return upload_content
    existing_status = _read_task_frontmatter_status(existing_path)
    if existing_status in ("DONE", "ERROR"):
        # Preserve terminal status; replace body
        upload_body = _strip_frontmatter(upload_content)
        return _attach_frontmatter(upload_body, status=existing_status)
    return upload_content
```

Wire into the upload validation/staging path before the file write to tasks/.

## Threat model

**Threat addressed**: OBS-CY silent regression of merged-spec status to TODO causing daemon re-dispatch. PR-337 closes by gating overwrite on terminal vs non-terminal current status.

**Other layers protecting**: PR-338 (MCP get_repo_task_status tool) lets LLM clients verify status before preparing zip, preventing the collision at the source. Defense in depth.

**Why this layer needed**: server-side guard. Even if LLM clients fail to use the MCP tool, the upload route refuses to regress terminal status.

### Caller audit

Upload route consumers: dashboard UI (drag-and-drop, batch zip) and any external HTTP client. Both paths go through `/repos/{name}/upload-tasks`. New collision-preserve logic is invisible to caller - same response shape, same status codes.

Edge case: operator INTENTIONALLY wants to reopen a DONE task by uploading a TODO version. Workaround per PR documentation: delete the DONE file first via redis-cli or git rm, then upload new TODO version. Or use Retry button which already handles ERROR→TODO. This PR does not block intentional reopens; just gates accidental ones.
