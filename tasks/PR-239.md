# PR-239: Fix duplicate @codex review post on PR creation (same-second timestamp race)

Branch: pr-239-codex-review-dedup-same-second
- Type: bugfix
- Complexity: low
- Depends on: none
- Priority: 1
- Coder: claude

## Problem

Verified in production 2026-05-03 on PR-237: daemon posts `@codex review` twice on PR creation despite the dedup logic in `_post_codex_review_result`. Operator screenshot showed two identical `@codex review` comments by `AlexBomber12` posted within the same minute. First is the coder's mandatory PLANNED PR runbook post (`AGENTS.md` rule); second is the daemon safety-net post that should have skipped due to dedup.

Root cause is a same-second timestamp race in `src/github/comments.py::get_recent_codex_review_request_time`:

```
if after_iso and (not created_raw or created_raw <= after_iso):
    continue
```

GitHub returns commit timestamps and comment timestamps in ISO-8601 with second granularity (e.g. `2026-05-03T03:10:42Z`). When the coder commits, pushes, and posts `@codex review` all within one wall-clock second (typical for automated subprocess flow):
- `commit.committer.date` rounds to T seconds
- `comment.created_at` rounds to T seconds (same value)
- Filter `created_raw <= after_iso` becomes `T <= T` → True → comment is SKIPPED from dedup
- Daemon sees zero matching PR-author triggers
- Daemon posts its own `@codex review` → 2x

This is the "PR-author dedup" gate from PR-196 design. The `<=` was intentionally conservative to handle FIX cycles where comments from BEFORE the new fix-push commit must be discarded as stale. Same-second equality at second granularity was not modeled, so legitimate triggers posted within the commit's UTC second are dropped.

Production cost: 3x `@codex review` per PR creation (1 coder post + 1 daemon post + the codex bot's auto-trigger reaction at PR open) means 3x Anthropic API spend per PR creation cycle plus codex-side queue noise. At Sprint 12's 36 PRs that is meaningful waste; it grows linearly with throughput.

Defense-in-depth secondary issue: when `gh api /commits/{sha}` has not yet propagated for a freshly-pushed commit (rare edge cache lag, observed sporadically), `_extract_commit_date(commit_payload)` returns empty. `_post_codex_review_result` gates the dedup on `pr_author and head_commit_date and ...`; empty `head_commit_date` falsifies the gate entirely, dedup never runs, daemon posts duplicate. This is rarer than the same-second race but contributes to the same symptom.

## Scope

Two changes:

1. **Primary fix:** change `<=` to `<` in the comment-filter inside `get_recent_codex_review_request_time`. Same-second matches now count as valid triggers. FIX-cycle correctness is preserved because real fix-push cycles always advance the commit timestamp by more than one second (push has multi-second latency).

2. **Defense-in-depth fix:** when `head_commit_date` is empty in `get_pr_metadata`, fall back to the PR's own `created_at` timestamp from the same `pr_payload` already fetched. PR creation time is a sound dedup anchor for the fresh-PR case (all valid triggers happen after PR creation by definition). For FIX cycles `head_commit_date` is reliably populated, so the fallback only kicks in for the regression case.

Add tests covering both scenarios.

```
from __future__ import annotations

from datetime import datetime, timezone
from unittest.mock import patch

from src.github import comments


def test_dedup_counts_same_second_comment(monkeypatch):

        {
            "user": {"login": "AlexBomber12"},
            "body": "@codex review",
            "created_at": "2026-05-03T03:10:42Z",

            "_DT",
            (),

            },
        ),
    )
```

```
def test_get_pr_metadata_includes_pr_created_at(monkeypatch):
    """get_pr_metadata exposes the PR's own created_at for dedup fallback."""
    from src.github import cache as gh_cache
    from src.github import prs as gh_prs

    fake_pr = {
        "user": {"login": "AlexBomber12"},
        "head": {"sha": "abc123"},
        "created_at": "2026-05-03T03:10:30Z",
    }
    fake_commit = {
        "commit": {"committer": {"date": "2026-05-03T03:10:42Z"}}
    }

    def fake_etag_get(path):
        if path.endswith("/pulls/237"):
            return fake_pr
        if path.endswith("/commits/abc123"):
            return fake_commit
        return None

    monkeypatch.setattr(gh_cache, "_etag_get", fake_etag_get)

    metadata = gh_prs.get_pr_metadata("owner/repo", 237)
    assert metadata["author"] == "AlexBomber12"
    assert metadata["head_sha"] == "abc123"
    assert metadata["head_commit_date"] == "2026-05-03T03:10:42Z"
    assert metadata["pr_created_at"] == "2026-05-03T03:10:30Z"
```

## Implementation notes

The `<=` to `<` change at the comment filter is the most surgical. It changes one character and adds a comment line. Test coverage for same-second equality is the verification that future refactors do not regress.

The `pr_created_at` fallback adds one field to `get_pr_metadata` return value and one fallback line in `_post_codex_review_result`. Pure additions, no removals; existing callers see new field as `dict.get("pr_created_at")` returning empty string when absent (no breaking change for any caller that does not consume the new field).

After this PR ships, the regression must not reproduce on the next 5-10 PR creations. If it does, root cause was different and additional diagnosis is needed (likely `head_commit_date` empty case is more common than estimated, or there is a third dedup path leak).
