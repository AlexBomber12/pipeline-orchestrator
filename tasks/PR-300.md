# PR-300: Main branch commit attestation audit — periodic scan flagging commits without verified CI history

Branch: pr-300-main-commit-bypass-audit
- Type: feature
- Complexity: medium
- Depends on: none
- Priority: 2
- Coder: codex

## Problem

OBS-BX from 2026-05-04 production session: operator git push to megaraid-dashboard origin/main returned `remote: Bypassed rule violations for refs/heads/main: Required status check "CI" is expected.` GitHub branch protection rule requires CI passing on merge but admin (account owner) can bypass via direct push. Same pattern enables Codex CLI to commit straight to main if it has admin token (already covered by PR-272 pre-push hook for daemon-dispatched coders, but unguarded for any other path the admin token reaches).

The pre-push hook is in-flight prevention — it runs before the push completes and refuses by exit code. PR-300 is post-fact detection — for every commit landed on main, the daemon verifies there was a passing CI run on that exact SHA's history. Commits without CI = audit violation, operator notified.

This is a defense-in-depth layer paired with PR-272 (pre-push) and PR-289b/277 (Tier 1 guardrails). A bypass can only happen via:
1. Admin force-push (caught by Tier 1 stdout scan if coder ran the command; caught by Tier 1 diff scan post-push).
2. Operator manual push from terminal (not caught by pre-push hook because the hook is repo-local and may not be installed on every operator clone).
3. GitHub web UI direct edit (rare; GitHub's branch protection blocks unless admin overrides).

PR-300 catches (2) and (3) via post-fact audit. Cannot prevent the bypass — by the time the daemon sees the commit, it's already on main — but surfaces the violation immediately so operator can investigate and revert.

## Scope

Three deliverables:

### 1. New module `src/daemon/main_commit_audit.py`

Pure logic, no daemon coupling. Functions:

```python
from dataclasses import dataclass
from typing import Iterable

@dataclass(frozen=True)
class MainCommitAuditFinding:
    sha: str
    short_sha: str  # first 7 chars
    message_first_line: str  # truncated to 120 chars
    parent_count: int  # 1 = direct commit, 2+ = merge commit
    pr_number: int | None  # extracted from merge commit message if present
    violation_category: str  # "direct_commit_no_pr", "merge_commit_pr_unverified", "merge_commit_pr_failed_ci"
    rule: str  # human-readable rule for operator notification

def audit_main_commits(
    owner_repo: str,
    lookback_n: int = 10,
    audited_shas: set[str] | None = None,
) -> list[MainCommitAuditFinding]:
    """Audit the most recent N commits on main for CI bypass.
    
    audited_shas: SHAs already checked in prior runs (Redis-cached);
    skipped to avoid repeat work on stable history.
    
    Returns: findings for unaudited SHAs that fail the audit.
    Empty list when all unaudited SHAs pass.
    """
```

Audit logic per SHA:
1. Fetch commit metadata via `gh api repos/{owner_repo}/commits/{sha}` to get `parents[]` and `commit.message`.
2. If `len(parents) == 1` (direct commit): violation `direct_commit_no_pr`. Operator action: revert.
3. If `len(parents) == 2` (merge commit):
   a. Extract PR number from commit message via regex `r"^Merge pull request #(\d+)"` or `r"\(#(\d+)\)$"` (handles both merge-commit and squash-merge default messages).
   b. If PR number not extractable from message: violation `merge_commit_pr_unverified` (manual merge bypassing daemon — possible legit operator action but worth flagging).
   c. If PR number extracted: query CI status via `gh api repos/{owner_repo}/commits/{parents[1].sha}/check-runs`. If no check-runs OR no SUCCESS check-run: violation `merge_commit_pr_failed_ci`.
4. If `len(parents) > 2`: octopus merge; flag as `merge_commit_pr_unverified` (uncommon, worth investigation).

The function does NOT mutate state or post comments; pure read-only audit.

### 2. Hook integration in IDLE cycle

In `src/daemon/handlers/idle.py`, add a low-frequency call to `audit_main_commits` once per N IDLE cycles (default N=20 per repo, configurable via `app_config.daemon.main_commit_audit_interval_idle_cycles`). The interval is conservative because: (a) main commit history changes slowly in normal operation, (b) the audit costs 1 REST call per unaudited commit, (c) we cache audited SHAs to avoid repeat work.

Implementation in handle_idle:

```python
self._main_commit_audit_counter = (
    getattr(self, "_main_commit_audit_counter", 0) + 1
)
audit_interval = self.app_config.daemon.main_commit_audit_interval_idle_cycles
if self._main_commit_audit_counter >= audit_interval:
    self._main_commit_audit_counter = 0
    audited_shas = await _load_audited_shas_from_redis(self.redis, self.name)
    findings = await asyncio.to_thread(
        audit_main_commits,
        self.owner_repo,
        lookback_n=10,
        audited_shas=audited_shas,
    )
    if findings:
        for finding in findings:
            self.log_event(
                f"[MAIN-COMMIT-AUDIT] VIOLATION "
                f"{finding.violation_category}: {finding.short_sha} "
                f"\"{finding.message_first_line}\""
            )
        await _record_audit_findings_in_redis(
            self.redis, self.name, findings
        )
    # Mark all just-checked SHAs as audited (success or violation)
    await _mark_shas_audited_in_redis(
        self.redis, self.name, [...newly_audited_shas...]
    )
```

Helpers `_load_audited_shas_from_redis`, `_record_audit_findings_in_redis`, `_mark_shas_audited_in_redis` go in the same `main_commit_audit.py` module (or a sibling `main_commit_audit_redis.py` if separation feels cleaner).

Redis key shape:
- `audit:main_commits:{repo}:audited` — Redis SET of audited SHAs, TTL 30 days.
- `audit:main_commits:{repo}:findings` — Redis LIST of MainCommitAuditFinding JSON entries, TTL 30 days, max length 100.

### 3. Dashboard surface

Optional minor: surface the findings in the existing dashboard event log via the `[MAIN-COMMIT-AUDIT]` event prefix. The existing event_log infrastructure already streams these to the operator via SSE without any additional code. The findings list in Redis serves as a separate "audit log" view that a future PR can build a dedicated dashboard panel for; PR-300 ships only event_log surfacing.

## Implementation notes

The audit is **best-effort** — failures of the GitHub API or Redis cache are logged but do not crash the daemon. Operator visibility depends on the dashboard event log; if the daemon crashes mid-audit, the next IDLE cycle retries from the latest unaudited SHA. The Redis cache's 30-day TTL gives enough window to retry transient failures without losing progress.

The `lookback_n=10` default means the audit covers the most recent 10 commits per scan. With 20 IDLE cycles between scans (~5-10 minutes apart depending on repo activity), the audit covers 10 commits per ~10 minutes, which exceeds typical merge throughput of ~3 PRs/hour for managed repos. Operator-set higher throughputs may need to increase `lookback_n` to avoid windowing past the audit; track in config docstring.

Squash merge limitation: GitHub squash merge produces a single commit on main with no parent on the merged branch, so the audit cannot trace back to the original PR's CI runs from the merge commit alone. The PR is still discoverable via the merge commit message tail "(#42)", but its head SHA before squash is gone from main's history. For PR-300 v1, squash-merged commits are flagged as `direct_commit_no_pr`. Operators using squash merge for managed repos should either (a) configure `repo_config` to skip the audit for squash-merge-default repos, or (b) accept the false-positive flag and track via the audit log.

Future enhancement (Sprint 15d or 16): query the closed PR via `gh api repos/{repo}/pulls/{number}` to retrieve `head.sha`, then check that head SHA's CI status. This adds 2 REST calls per squash merge but eliminates the false positive. Track as backlog item.
