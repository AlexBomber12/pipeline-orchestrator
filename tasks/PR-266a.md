# PR-266a: _parse_tasks_from_headers helper + golden recovery fixtures

Branch: pr-266a-recovery-headers-helper
- Type: refactor
- Complexity: low
- Depends on: PR-262, PR-258d
- Priority: 2

## Problem

PR-266 (the original monolithic recovery refactor) carried high invariant risk because it simultaneously added a new helper, swapped recover_state to use it, dropped the legacy QUEUE.md probe, and hydrated the new `RepoState.current_queue`. Each of those is a separate concern with its own revert profile. Splitting the work into 266a (helper + golden fixtures, behavior-neutral), 266b (audit-mode + flagged swap), and 266c (cleanup) reduces blast radius and gives an observable verification window before the legacy path retires.

This PR is part one. It adds `_parse_tasks_from_headers` as a sibling to the existing `_parse_base_queue` (no caller switches yet) and lands a battery of golden state-transition fixtures that PR-266b will use as integration anchors. With both pieces in place, PR-266b becomes a switch-and-observe rather than a switch-and-pray.

## Scope

Three deliverables:

1. New helper `_parse_tasks_from_headers(self) -> list[QueueTask] | None` in `src/daemon/recovery.py` that walks `tasks/PR-*.md`, calls `parse_task_header`, applies `_resolve_merged_state` from PR-262, and returns the same `list[QueueTask]` shape that `_parse_base_queue` returns. No production caller wired in this PR; the helper is exercised only via tests.
2. Golden recovery fixtures under `tests/fixtures/recovery/` covering eight scenarios that have historically broken or that this Sprint must keep working. Each scenario is a directory with `before.json` (input task list + open PR list + crashed/recovered task pr_id sets), and `expected.json` (post-recovery state including pipeline state, current_task pr_id, current_pr number if any, current_queue contents).
3. Helper unit tests in `tests/runner/test_parse_tasks_from_headers.py` exercising the helper in isolation against representative fixtures.

The eight golden scenarios:

- `megaraid_already_merged_via_api`: DOING task whose branch is in API merged set but git log scan misses (Conventional Commits subject). Expected post-state: ignore stale DOING -> IDLE.
- `pr_186_crash_no_pr`: DOING task with no matching open PR, not in merged set. Expected post-state: CANCELED, manual re-upload required.
- `pr_247_operator_recovered`: DOING task in `_recovered_task_pr_ids`. Expected post-state: stay IDLE pending re-upload.
- `pending_queue_sync`: open PR with `queue-done-*` branch present. Expected post-state: `pending_queue_sync_branch` populated.
- `fresh_clone_empty`: no `tasks/` directory. Expected post-state: IDLE with empty queue.
- `mid_cycle_unpushed_commits`: DOING task whose branch has unpushed commits in the working tree (crashed runner). Expected post-state: commits preserved on origin, task CANCELED.
- `legacy_unstructured_skipped`: one task file lacking the structured header. Expected post-state: file skipped, recovery completes on the rest.
- `clean_doing_with_open_pr`: DOING task with matching open PR, not yet merged. Expected post-state: WATCH on that PR.

## Behavior

`_parse_tasks_from_headers`:

1. Walk `tasks/PR-*.md` files in `self.repo_path/tasks/`. Skip files that fail `parse_task_header` only when the failure matches `_is_missing_task_header_error` or `_is_legacy_unstructured_task_error` (same filter as `_select_next_task_from_dag`).
2. Collect successfully-parsed `headers: list[TaskHeader]` plus a `task_files: dict[str, str]` mapping pr_id to repo-relative file path.
3. If `headers` is empty, return None (no snapshot can be parsed; mirrors `_parse_base_queue`'s contract).
4. Call `_resolve_merged_state(...)` from PR-262 to get the merged-API + git-log union.
5. For each header, call `derive_task_status` against the merged state plus the runner's open-PR list, current_task pr_id, current_task pr_id stop set, and recovered task pr_id set.
6. Build `list[QueueTask]` with statuses applied. Order is deterministic: sort by priority asc, then pr_id natural order (matches `get_eligible_tasks`).
7. Fold in CANCELED override for any pr_id in `self._crashed_task_pr_ids` (rehydrated by PR-247's existing `_load_recovered_task_pr_ids`). DONE rulings stand; CANCELED applies only when the derived status is TODO or CANCELED.
8. Return the list.

The helper is pure modulo the `gh` subprocess call inside `_resolve_merged_state` and the `git log` call inside `get_merged_pr_ids`. No Redis writes, no state mutation on `self`.

The golden fixtures are JSON, not Python pickles, so they remain reviewable in PR diffs and survive serialization-format changes. Each `before.json` describes the inputs to recover_state at a level abstracted from the runner's full state machine: just the task list, open PRs, merged set, and the relevant pr_id sets. The matching `expected.json` describes the recover_state result projection: pipeline state value, optional current_task pr_id, optional current_pr number, optional pending_queue_sync_branch, and the populated current_queue contents.

## Implementation notes

The helper's reliance on `_resolve_merged_state` from PR-262 means the API merge probe runs on every recovery as well as on every IDLE cycle. That is intentional: recovery is exactly the path where the daemon must reconcile post-restart with the truth on GitHub, and the API check is the strongest signal available. The 200-500ms call adds to startup time but happens once per recovery, not per cycle thereafter.

The eight goldens are deliberately not exhaustive. They probe known scenarios and historical regressions. New regressions discovered during PR-266b's audit window become new goldens added to the fixture directory; the parameterized test picks them up automatically.

The `before.json` schema does NOT include the on-disk Status field of PR-*.md files. That field exists today but is informational; the daemon's truth is `state.current_queue` post-PR-263 and the merged-state probe pre-PR-263. Fixtures that need to express "this task was DOING when daemon crashed" express it via `crashed_task_pr_ids` (PR-186 contract) or by including a matching open PR on that branch (the helper derives DOING from open-PR match). Either way, reproducible without leaning on the on-disk Status field.

The fixture directory `README.md` files are short (3-5 sentences each) but carry enough operator context that anyone reviewing a future regression sees immediately which scenario the fixture probes.

## Success criteria

1. `_parse_tasks_from_headers` returns a deterministic, sorted `list[QueueTask] | None` with statuses derived via `_resolve_merged_state`.
2. All eight golden fixtures parse correctly via the helper, producing exactly the `current_queue` projection in their `expected.json`.
3. No existing recovery test fails. No production code path switches to the new helper.
4. CI green on PR branch.
5. The fixtures directory is in-repo, reviewable JSON, and ships with `README.md` per scenario.
