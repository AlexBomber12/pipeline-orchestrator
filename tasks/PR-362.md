## Problem

Before Sprint 15b Phase 2 (PR-276/PR-277, 2026-05-08..09) removed `PipelineState.HUNG`, the `handle_hung` method polled `gh pr view --json state` every cycle and transitioned HUNG -> IDLE on MERGED or CLOSED detection. This handled the case where an operator (or another daemon) manually merged or closed the current PR externally.

PR-276/PR-277 deleted the handler without migrating this behavior. Consequence: when an operator manually closes the current PR via `gh pr close` or the GitHub UI, the daemon does not detect it. WATCH keeps polling, hits review_timeout, escalates to ERROR (now with single repost per PR-358), and the task gets parked even though the operator has already disposed of it.

Production observation 2026-05-14: operator manually closed PR #443 (during PR-305c debugging). Daemon continued WATCH cycle on the closed PR, hitting timeout -> ESCALATE -> re-pick -> WATCH again. Loop did not stop until Redis state reset.

OBS-DE B2 sub-behavior remains documented as open since 2026-05-13 MICRO-1 ship. This PR closes it.

## Solution

Add periodic poll of PR state in WATCH handler. When PR state is MERGED or CLOSED, transition runner to IDLE with `current_task=None`, clear `current_pr`, log the externally-resolved transition, and let the IDLE handler pick the next eligible task.

### Where to inject the check

Inside `handle_watch`, after `get_open_prs` returns and `found` resolution is complete (around `src/daemon/handlers/watch.py:228` where `_maybe_reclassify_stuck_pending` is called). If `found` is present, additionally check its state. If `found` is None AND the runner had a `current_pr` last cycle, the PR likely transitioned to MERGED or CLOSED (since `get_open_prs` only returns open PRs).

There are two viable paths; pick the second for clarity:

**Path A (cheaper):** if `get_open_prs` returns no PR matching the current branch, and `state.current_pr` was set last cycle, query `gh pr view {number} --json state` directly to confirm MERGED or CLOSED before transitioning. One extra API call per "disappeared" cycle.

**Path B (chosen):** every WATCH cycle, if `state.current_pr` is set, fetch state via existing `get_pr_metadata` helper. Confirms state authoritatively without depending on get_open_prs filtering.

Path B is preferred because:
- get_pr_metadata is already called in WATCH for review timing (via `_review_timeout_park_cleared`).
- A single combined call per WATCH cycle is simpler than reasoning about "PR disappeared, was it merged or closed".
- Cache layer in `gh_cache` already dedups identical reads within a poll cycle.

### Concrete change

After the existing PR-found resolution near `watch.py:228`, add:

```python
if found is not None:
    pr_state = await asyncio.to_thread(
        gh_prs.get_pr_state,
        self.owner_repo,
        found.number,
    )
    if pr_state in ("MERGED", "CLOSED"):
        await self._handle_external_pr_resolution(found, pr_state)
        return
```

The new helper `get_pr_state` lives in `src/github/prs.py`:

```python
def get_pr_state(repo: str, pr_number: int) -> str | None:
    """Return PR state string: 'OPEN', 'MERGED', 'CLOSED', or None on error.

    Uses ``gh pr view {number} --json state -q .state`` which is the
    canonical state field. State 'CLOSED' is GitHub's term for
    closed-without-merge; 'MERGED' is post-merge. Both are terminal
    states from daemon's perspective: it should release the task.
    """
    try:
        result = gh_runner.run_gh([
            "pr", "view", str(pr_number),
            "--json", "state",
            "-q", ".state",
        ], repo=repo)
        return result.strip() if isinstance(result, str) else None
    except Exception:
        return None
```

The new runner method `_handle_external_pr_resolution`:

```python
async def _handle_external_pr_resolution(
    self,
    found: "PRInfo",
    pr_state: str,
) -> None:
    """Release task when PR was merged or closed outside the daemon.

    Distinct from the daemon's own merge path which goes through
    handle_merge with the full reconcile machinery. External
    resolution means the PR is already terminal on GitHub; daemon
    just needs to release the task and resume IDLE.
    """
    self.log_event(
        f"[WATCH] PR #{found.number} externally resolved as "
        f"{pr_state}; releasing task and returning to IDLE."
    )
    if pr_state == "MERGED":
        # Mirror the post-merge cleanup that handle_merge does
        # for daemon-driven merges. Frontmatter status:done
        # write so the picker does not re-dispatch.
        current_task = self.state.current_task
        if current_task is not None:
            await self._write_frontmatter_status_done(current_task)
    # CLOSED-without-merge does NOT write status:done because
    # the task may legitimately need to re-run. Operator
    # closed it explicitly; let normal Retry/re-upload flow
    # handle the next step.
    self.state.state = PipelineState.IDLE
    self.state.current_task = None
    self.state.current_pr = None
    await self.publish_state()
```

The `_write_frontmatter_status_done` helper already exists; if naming differs, locate it via grep on `write_frontmatter_status` in src/.

### CLOSED-without-merge semantics

Decision: do NOT auto-write status:done for CLOSED state. Rationale: operator's intent on `gh pr close` is ambiguous - could be "throw this away" (next cycle should NOT re-dispatch the same task) OR "give up for now, re-pick later" (next cycle SHOULD re-attempt).

The safer default is to leave frontmatter status untouched. If operator wants the task discarded permanently, they can mark `status: done` manually or remove the task file. If they want re-attempt, they upload a fresh version (which the OBS-CY upload-preserve logic handles correctly).

For MERGED state, intent is unambiguous: PR went through, task is complete, write status:done.

## Threat model

**Threat addressed**: daemon continues WATCH loop on a PR that has been externally merged or closed, wasting cycles and eventually parking the task in ERROR with subsource=review_timeout even though the PR is already disposed.

**Other layers protecting**: none after PR-276/PR-277 removed `handle_hung`. The repost-once logic from PR-358 adds 40min total delay before terminal ERROR but does not detect external resolution.

**Why this layer needed**: closes the regression from PR-276/PR-277. Restores the B2 sub-behavior of pre-PR-277 `handle_hung` in the WATCH handler where the PR state is being polled anyway.

### Caller audit

`get_pr_state` is a new helper, called only from WATCH. No conflict with existing `get_pr_metadata` or `get_open_prs` callers.

`_handle_external_pr_resolution` is a new runner method, called only from WATCH. No callers anywhere else.

`write_frontmatter_status` (existing helper) is already called from `handle_merge`; this PR adds one more call site. The helper is idempotent (writing status:done to an already-done frontmatter is a no-op).

## Out of scope

- Detecting state transitions for PRs other than `current_pr`. The daemon manages one PR at a time per repo; other open PRs are out of scope.
- Notifying webhook subscribers on external resolution. Webhook flow is decoupled; if operator wants notification on close/merge, GitHub native notifications cover it.
- Cancellation cause recording for external resolution. External resolution is not a failure - it is an operator-driven completion. No cancellation_cause write needed.

## Success signal

On test fixture: WATCH with PR #443 active. Operator simulated `gh pr close 443`. On next WATCH poll, daemon logs "PR #443 externally resolved as CLOSED; releasing task and returning to IDLE", transitions to IDLE, current_task and current_pr both cleared. Dashboard 5s poll shows task in TODO group with no "current operation" indicator. Operator can re-pick or modify the task without daemon contention.

On production: next time operator manually merges or closes a PR managed by daemon, daemon releases within one WATCH cycle (~60s) instead of waiting for review_timeout (~40min including PR-358 repost) and then leaving an ERROR cancellation record.
