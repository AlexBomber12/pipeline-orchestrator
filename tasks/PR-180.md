## Problem

Daemon WATCH and MERGE polling cycles call `gh pr list --json statusCheckRollup,...` which uses GitHub GraphQL API. GraphQL quota is 5000/hour for personal tokens and is shared across daemon polling, Codex Connector reviewer, IDE extensions, and CI re-run triggers. During the 2026-04-28 debug session this quota exhausted twice within 2 hours of intensive work and blocked CI re-runs.

Approximate burn from `statusCheckRollup` is 100-300 GraphQL points per polling cycle depending on PR count and check rollup depth. At `poll_interval_sec: 60` with one active repo, this dominates daemon-side GraphQL consumption.

REST API has a separate 5000/hour budget which is consistently underused (4900+ remaining at the time of GraphQL exhaustion). REST endpoints `GET /repos/{owner}/{repo}/commits/{sha}/check-runs` and `GET /repos/{owner}/{repo}/commits/{sha}/status` together return equivalent information to `statusCheckRollup`.

## Scope

Replace the GraphQL `statusCheckRollup` data fetching path in `src/github_client.py` with REST `check-runs` plus `status` calls. Map the combined REST response to the same `CIStatus` value the existing `statusCheckRollup` mapping function produces.

The PR list itself (numbers, titles, branches, head SHA, etc) continues to be fetched via existing `gh pr list` paths since those fields do not require GraphQL-specific resolvers. The change is scoped strictly to the rollup status portion.

`config.yml` and `config.test.yml`:

## Implementation notes

`gh api` automatically uses REST core quota. No flags needed to force REST. The CIStatus enum (existing) has values like SUCCESS, FAILURE, PENDING, NEUTRAL — preserve exact semantic mapping.

For CI status combining check-runs + status: if any check-run is failure or status is failure → FAILURE. If any pending → PENDING. If all success → SUCCESS. If empty → NEUTRAL.

Pagination of `/check-runs` is rare in practice (most PRs have <30 check runs) but needs to be handled. Use `gh api --paginate` flag or check for `total_count` and iterate.
