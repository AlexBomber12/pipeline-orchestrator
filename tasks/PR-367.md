## Problem

The DONE task list on the dashboard renders tasks in source-iteration order (oldest-first). At 175+ DONE PRs accumulated, finding the most recently merged PR requires scrolling to the bottom. Operator's typical workflow is "what did the daemon merge most recently" which today requires manual scroll.

Source of the bug: `_views_for(TaskStatus.DONE)` at `src/web/routes/repo_control.py:676-687` returns:

```python
async def _views_for(status: TaskStatus) -> list[dict[str, object]]:
    return [
        await _task_view(task, name, redis_client)
        for task in tasks
        if task.status == status
    ]
```

The iteration order of `tasks` (the local list) reflects file discovery order, which is alphabetical by PR ID. PR-001 first, PR-359 last. Newest-merged is at the end.

## Solution

Sort the DONE list reverse-chronologically by merge timestamp. Source of truth for merge timestamp is the `merged_at` field on the task view (populated from Redis `done_index:{repo}` entry or from the git commit log).

### Implementation

In `_views_for`, special-case DONE bucket with a post-build sort:

```python
async def _views_for(status: TaskStatus) -> list[dict[str, object]]:
    views = [
        await _task_view(task, name, redis_client)
        for task in tasks
        if task.status == status
    ]
    if status == TaskStatus.DONE:
        # Newest-first: most recently merged PRs appear at the top
        # of the DONE list for fast operator scan.
        views.sort(
            key=lambda v: v.get("merged_at") or "",
            reverse=True,
        )
    return views
```

The fallback `or ""` handles tasks where merged_at is missing or null (e.g. legacy tasks committed before the timestamp field landed). Those tasks sort to the bottom alphabetically, matching pre-PR behavior - acceptable fallback.

### Why not sort all buckets

TODO and DOING buckets have meaningful order based on dependency chain and priority. Sorting them by timestamp would obscure that order. ERROR bucket is small enough that order does not matter much. Only DONE has the operator-pain pattern of "most recent at bottom".

### Optional: surface a sort toggle

Not in this PR. If operator wants oldest-first occasionally (e.g. for historical audit), a future polish PR can add a "Sort: newest/oldest" toggle. Defer until requested.

## Threat model

**Threat addressed**: operator productivity friction. Finding the most recent merged PR currently requires scrolling past 175+ entries.

**Other layers protecting**: none. Sort order is purely UI-side.

**Why this layer needed**: dashboard usability for the most-frequent operator query ("what merged most recently"). Trivial fix with high daily value.

### Caller audit

`_views_for` is called once per status bucket from the route handler. The change is internal to the helper. No callers see new behavior beyond the DONE list ordering improvement.

The sort key uses string comparison on ISO 8601 timestamps which is lexicographically correct for that format. No timezone normalization needed because all timestamps are UTC.

## Out of scope

- Sort toggle UI ("newest first / oldest first" buttons). Defer.
- Per-status custom sort orders. The choice to sort only DONE is intentional; other buckets benefit from source order.
- Server-side pagination of DONE list. Out of scope; current rendering scales adequately to ~500 entries.

## Success signal

On test fixture: DONE list returned with timestamps in descending order. On production: dashboard DONE section shows most-recently-merged PR at the top; operator scrolls only when looking for older entries.
