# PR-244: MCP server core scaffold (FastMCP HTTP service + docker compose entry)

Branch: pr-244-mcp-server-scaffold
- Type: feature
- Complexity: medium
- Depends on: none
- Priority: 2
- Coder: claude

## Problem

Per the MCP architectural decision recorded in `docs/roadmap.md` (section "MCP server as bar for agents", 2026-05-02), the orchestrator needs a Model Context Protocol server that LLM coders can pull configuration and validation from on demand instead of bundling templates into every managed repo. v1 ships with 4 tools (`validate_task_spec`, `get_task_schema`, `get_agents_md_template`, `suggest_next_pr_number`) but they require a running MCP server to be hosted on. This PR delivers the server scaffold; tools land in PR-245 (read-only) and PR-246 (functional).

The server runs as a third docker compose service alongside `daemon` and `web`, uses the same Docker image (just different command), exposes HTTP transport on `localhost:5173`, and mounts `/data/repos` read-only so future tools can scan target repo `tasks/` directories. No tools are registered in this PR; only the framework, healthcheck, and deployment plumbing.

## Scope

Three deliverables:

1. New `src/mcp/` package with `server.py` that instantiates a `FastMCP` server, registers a healthcheck endpoint, and runs HTTP transport on port 5173.
2. New service entry in `docker-compose.yml` named `mcp` reusing the existing image, mounting `/data/repos` read-only and `/app` read-only, exposing port 5173.
3. Add `mcp[cli]` to `requirements.txt`. Use Anthropic's official MCP Python SDK (which includes `FastMCP` class via `from mcp.server.fastmcp import FastMCP`).

No tool registrations beyond the healthcheck. No Redis dependency. No GitHub API access. No coder subprocess invocation. The server is intentionally minimal so PR-244 and PR-245 can land tools without coupling to scaffold concerns.

`src/mcp/server.py` (new):

```
"""MCP server entrypoint.

Run with ``python -m src.mcp.server``. HTTP transport on
``localhost:5173``. No authentication; deployment is self-hosted scope
only and the port is bound to localhost in docker compose.

Tools register here via decorators in PR-244 and PR-245. This module
handles only server instantiation, healthcheck, and run loop.
"""

from __future__ import annotations

import logging

from mcp.server.fastmcp import FastMCP

logger = logging.getLogger(__name__)

mcp = FastMCP("pipeline-orchestrator")


@mcp.tool()
def healthcheck() -> dict[str, str]:
    """Return server liveness and version info.

    LLM clients can call this to confirm the MCP server is reachable
    before invoking other tools. Operators can also verify the service
    is up via ``curl http://localhost:5173/...`` (exact endpoint
    determined by FastMCP's HTTP routing).
    """
    return {"status": "ok", "service": "pipeline-orchestrator-mcp", "version": "v1"}


def main() -> None:
    """Run the MCP server with HTTP transport on port 5173."""
    logging.basicConfig(level=logging.INFO)
    logger.info("Starting MCP server on 0.0.0.0:5173")
    mcp.run(transport="streamable-http", host="0.0.0.0", port=5173)


if __name__ == "__main__":
    main()
```

`requirements.txt` — add to the runtime deps section:

```
mcp[cli]>=1.27.0
```

The `[cli]` extra includes the FastMCP class and HTTP transport machinery. Pin minimum version 1.27.0 because that is the version available as of April 2026 with stable Streamable HTTP support. Do not pin upper bound; SDK follows semver and minor versions are compatible.

`docker-compose.yml` — add a new service after `daemon`, before `redis`:

```
  mcp:
    build: .
    command: python -m src.mcp.server
    user: "1000:1000"
    mem_limit: 1g
    ports:
      - "${MCP_PORT:-5173}:5173"
    volumes:
      - .:/app:ro
      - ./data/repos:/data/repos:ro
    environment:
      PYTHONUNBUFFERED: "1"
    restart: unless-stopped
```

No `depends_on: redis` because the MCP server does not use Redis. No `HOME`, `CLAUDE_CONFIG_DIR`, `GH_CONFIG_DIR` env vars because it does not invoke `gh` or `claude` CLI. Read-only mount of `/data/repos` matches the architectural choice in PR-243 design (Q1 resolution): MCP reads target repo task lists, never writes. If future tools (Sprint 14 `onboard_repo`) need to write, migrate to delegating writes through the daemon's HTTP API rather than flipping this mount to read-write.

The `${MCP_PORT:-5173}` env-var override matches the existing `${WEB_PORT:-8800}` pattern in `docker-compose.yml` so operators can rebind the port if 5173 conflicts with another service on the host.

## Tests

`tests/mcp/__init__.py` (new, empty).

`tests/mcp/test_server.py` (new):

```
"""Smoke tests for the MCP server scaffold.

These tests verify that the server can be instantiated and that the
healthcheck tool is registered. They do not start the HTTP transport
(that requires a running event loop and port binding); transport
correctness is covered by future integration tests in Sprint 16.
"""

from __future__ import annotations


def test_mcp_server_imports():
    """Verify the server module imports without side effects."""
    from src.mcp import server

    assert server.mcp is not None
    assert server.mcp.name == "pipeline-orchestrator"


def test_healthcheck_tool_registered():
    """Verify the healthcheck tool is discoverable via the server registry."""
    from src.mcp.server import mcp

    # FastMCP exposes registered tools via _tool_manager or similar.
    # Use the public API that returns tool names; if the SDK exposes
    # ``list_tools`` async method, run it via ``asyncio.run``.
    import asyncio

    tools = asyncio.run(mcp.list_tools())
    tool_names = [t.name for t in tools]
    assert "healthcheck" in tool_names


def test_healthcheck_returns_status_ok():
    """Verify the healthcheck function returns the expected payload."""
    from src.mcp.server import healthcheck

    result = healthcheck()
    assert result["status"] == "ok"
    assert result["service"] == "pipeline-orchestrator-mcp"
    assert "version" in result
```

The exact API for `list_tools` may differ slightly between mcp SDK versions; if `mcp.list_tools()` is not directly available, use whichever introspection method the installed `mcp` SDK exposes (e.g., `mcp._tool_manager.list_tools()` or iterate over `mcp.tool_manager._tools`). Confirm at implementation time by running `python -c "from mcp.server.fastmcp import FastMCP; print(dir(FastMCP('x')))"` inside the daemon container.

## Implementation notes

`mcp[cli]>=1.27.0` adds approximately 3 transitive deps (`pydantic` already installed, `anyio` already transitive via httpx, plus mcp's own modules). Verify after `pip install` that `requirements.txt` resolves cleanly and no version conflicts with the existing pinned versions of `pydantic==2.11.3`, `httpx==0.28.1`, etc.

The healthcheck tool returns a plain dict because that is the simplest schema FastMCP can serialize. If the MCP spec requires a specific health endpoint structure (some clients may expect a `/health` HTTP route rather than a tool call), revisit by reading FastMCP's docs at `https://gofastmcp.com` or the `mcp[cli]` SDK examples directory; for v1 the tool-call form is sufficient for any Claude Code or Claude Desktop client.

The container memory limit `mem_limit: 1g` is a starting estimate. Adjust if the SDK's HTTP server exhibits higher idle memory than expected.

Port `5173` was selected per the roadmap design decision. If 5173 conflicts on the home server, the `${MCP_PORT:-5173}` override lets operators rebind without code change.

After this PR ships, validate end-to-end:

```
curl -s http://localhost:5173/...  # exact path from FastMCP HTTP routing

```

If healthcheck reachable and logs clean, the scaffold is operational and PR-244 can land its first real tool registrations on top.
