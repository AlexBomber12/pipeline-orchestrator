## Problem

Today, "why a task is suppressed and whether it is still suppressed" is answered by reading cancellation causes plus seven other independent mechanisms (status_write_failed, diagnose_exhausted, skip_ai_error_diagnose, _crashed_task_pr_ids, quarantined_prs, stopped_task_pr_ids, the two error counters), each with its own storage and cleanup. There is no single object that answers "is task X suppressed, and why". The R1 plan collapses all of them into one model; this PR builds the interface for that model without migrating any mechanism yet.

This is R1.2. It is a pure scaffold: define a port, back it with the existing Redis cancellation storage, and prove it returns the same answers as direct reads. No mechanism moves onto it in this PR (that is R1.6). Refactor invariant 1: one owner per fact; this port becomes that owner in later PRs.

## Solution

### Define the port

Add `src/suppression/__init__.py` (new package) with a `SuppressionStore` Protocol exposing:

- `async def suppress(repo, task_id, reason: SuppressionReason, detail: dict) -> None` - record that a task is suppressed for a canonical reason, with rich forensic detail.
- `async def clear(repo, task_id) -> None` - remove the suppression (operator Retry / reupload).
- `async def is_suppressed(repo, task_id) -> SuppressionRecord | None` - return the active suppression or None.
- `async def list_suppressed(repo, *, since=None, limit=None) -> list[SuppressionRecord]` - for the dashboard.

Define a `SuppressionRecord` dataclass carrying: task_id, reason (SuppressionReason), detail (dict), created_at, and an `approved_once` bool (for the guardrail accept-once flow that R1.8 will use; default False, stored but unused until then).

### Two-layer storage stated in the interface

Document in the module docstring and enforce in the interface design that the store has two layers (refactor invariant 3):

- Coarse layer (durable): the fact "suppressed + reason" is intended to live in frontmatter (status:error + blocked_reason). The port does not write frontmatter in this PR - it only documents that R1.3/R1.4 will supply the coarse layer. For now `is_suppressed` reads the rich layer only.
- Rich layer (lost-tolerant): detail, approved_once, counters - live in Redis.

This PR implements only the rich (Redis) layer behind the port. The coarse layer is wired in R1.3/R1.4. State this boundary explicitly in the docstring so a later reader does not assume the port is already durable.

### Redis implementation wraps existing storage

Add `src/suppression/redis_store.py` implementing `SuppressionStore` by delegating to the existing `src/cancellation/storage.py` functions:

- `suppress` -> build a `CancellationCause` (category="ERROR", payload carrying subsource=reason.value plus the detail dict) and call the existing `safe_record_cancellation_cause`. Reuse the existing TTL constants and index machinery; do NOT introduce a new key family.
- `clear` -> call existing `safe_delete_cancellation_cause`.
- `is_suppressed` -> call existing `get_cancellation_cause`; if a cause exists, build a `SuppressionRecord` from its payload; map the payload subsource string back to a `SuppressionReason` via the registry; if the subsource is not a canonical reason, treat it defensively as crash and log once.
- `list_suppressed` -> call the existing `list_recent_cancellations` and map each to a `SuppressionRecord`.

Reuse, do not reimplement. The point of this PR is a clean interface over proven storage, not new storage.

### Align the index TTL while here (closes B)

The audit found the cancellation index (`index_key`, 90d) outlives the cause keys (30d) by 60 days, so the index can reference expired causes. Since this PR is the new owning layer for these reads, fix the desync: either set the index TTL to match the cause TTL, or ensure `is_suppressed`/`list_suppressed` skip index members whose cause has expired (the existing `prune_dead_index_members` does part of this - confirm it runs on the read path). Pick the approach that does not lose forensic history the operator may still want; document the choice. Add a test that an expired cause never surfaces as an active suppression via the port.

## Test acceptance criteria

In `tests/suppression/test_redis_store.py` (use a fake or in-memory Redis fixture consistent with existing cancellation tests):

- `test_suppress_then_is_suppressed`: suppress a task with reason guardrail and a detail dict; assert `is_suppressed` returns a record with reason guardrail and the detail preserved.
- `test_clear_removes_suppression`: suppress then clear; assert `is_suppressed` returns None.
- `test_is_suppressed_none_when_absent`: assert `is_suppressed` returns None for an unknown task.
- `test_store_matches_direct_cancellation_read`: suppress via the port, then read the underlying cause via the existing `get_cancellation_cause`; assert the subsource and payload match what the port wrote.
- `test_list_suppressed_returns_records`: suppress three tasks; assert `list_suppressed` returns three records mapped from causes.
- `test_unknown_subsource_defensive_crash`: write a cause with a subsource string not in the registry directly, then read via the port; assert the record reason defaults to crash and a single warning is logged.
- `test_expired_cause_not_active`: simulate an index entry whose cause key has expired; assert the port does not surface it as an active suppression (closes B).
- `test_approved_once_round_trips`: suppress with approved_once True in detail; assert `is_suppressed` returns a record with approved_once True.

## Threat model

**Threat addressed**: there is no single object that owns "is this task suppressed and why". Eight mechanisms answer pieces of it with independent lifecycles, which is the source of the drift bugs. This port is the future single owner.

**Threat introduced**: a parallel read path (the port) over the same storage could diverge from direct reads if the mapping is wrong. Mitigated by `test_store_matches_direct_cancellation_read` and by delegating to the existing storage functions rather than reimplementing them.

**Other layers protecting**: nothing depends on the port yet (no mechanism migrated), so a port bug cannot affect production behavior in this PR. The existing mechanisms continue to run unchanged.

### Caller audit

The port has no production callers in this PR - it is scaffold. The only code touched outside the new package is the optional index-TTL alignment in `cancellation/storage.py`; run `grep -rn "index_key\|READ_REFRESH_TTL"` and confirm any change there preserves the existing dashboard cancellation-history reads (they call `list_recent_cancellations`, which must keep returning the same window).

## Out of scope

- Migrating any mechanism onto the port (R1.6).
- Writing the coarse frontmatter layer (R1.3/R1.4).
- SQLite implementation - the port is designed to allow it later, but only the Redis impl ships now.
- The guardrail accept-once UI (R1.8) - approved_once is stored but not yet acted on.

## Success signal

On test fixture: the port round-trips suppress/clear/is_suppressed/list and returns records identical in reason and detail to direct cancellation reads; an expired cause never appears as active. On production: no behavior change (scaffold only); the new package imports cleanly and the existing cancellation dashboard is unaffected.
