# PR-352: Pre-merge-sync sub-state visibility with merge_phase field

Branch: pr-352-merge-phase-substate
- Type: feature
- Complexity: medium
- Depends on: none
- Priority: 3
- Coder: any

## Reading order before coding

1. Read this entire spec.
2. Read `src/daemon/handlers/merge.py` for current MERGE state handler.
3. Grep `pre_merge_sync\|merge_pr\|gh pr merge\|gh pr ready` to find current phase progression.
4. Read `src/models.py` RepoState for field-add pattern.

## Problem

MERGE state can last 5+ minutes during heavy CI/heavy review-rebase cycles. Operator sees only `state=MERGE` badge with no sub-phase visibility. Is daemon waiting for review-rebase? Waiting for `gh pr merge`? Stuck in post-merge cleanup? No surface.

## Solution

Add `merge_phase: str | None` field to RepoState, populated by merge handler at each phase transition:

- `pre_merge_sync` (rebase against base, conflict resolution attempt)
- `ready_to_merge` (PR-E: `gh pr ready` for draft PRs)
- `merging` (`gh pr merge --merge` in flight)
- `post_merge_cleanup` (delete remote branch, sync local main)

Dashboard renders the phase as subtitle under the MERGE badge.

### Model field

```python
class RepoState(BaseModel):
    ...
    merge_phase: Optional[str] = None  # set during MERGE state only; None otherwise
```

### Handler instrumentation

In `src/daemon/handlers/merge.py`:

```python
async def handle_merge(state: RepoState, ...) -> None:
    state.merge_phase = "pre_merge_sync"
    await publish_state(state)
    rebase_result = await _pre_merge_sync(...)

    state.merge_phase = "ready_to_merge"
    await publish_state(state)
    await _gh_pr_ready_if_draft(pr_number)

    state.merge_phase = "merging"
    await publish_state(state)
    await _gh_pr_merge(pr_number)

    state.merge_phase = "post_merge_cleanup"
    await publish_state(state)
    await _post_merge_cleanup(...)

    state.merge_phase = None
    state.state = PipelineState.IDLE
    await publish_state(state)
```

### Dashboard rendering

In `src/web/templates/components/repo_cards.html`, under MERGE badge:

```jinja
{% if repo.state.value == 'MERGE' and repo.merge_phase %}
<span class="text-xs text-gray-400 ml-2 italic">{{ repo.merge_phase | replace('_', ' ') }}</span>
{% endif %}
```

## Test acceptance criteria

- `test_merge_phase_pre_merge_sync_during_rebase`: capture state writes during rebase step, assert merge_phase="pre_merge_sync".
- `test_merge_phase_ready_to_merge_during_gh_ready`: assert merge_phase="ready_to_merge".
- `test_merge_phase_merging_during_gh_merge`: assert merge_phase="merging".
- `test_merge_phase_post_merge_cleanup_after_merge_success`: assert merge_phase="post_merge_cleanup".
- `test_merge_phase_cleared_on_idle_transition`: assert state.merge_phase is None after MERGE→IDLE.
- `test_merge_phase_persists_across_publish_cycles`: serialize and deserialize, assert merge_phase preserved.
- `test_dashboard_renders_phase_under_merge_badge`: render template with merge_phase=pre_merge_sync, assert text "pre merge sync" in HTML.
- `test_dashboard_omits_phase_for_non_merge_state`: state=CODING, assert no phase rendered.
- `test_merge_phase_cleared_on_error_path`: simulate exception during merging, assert merge_phase reset on error transition.

## Threat model

**Threat addressed**: MERGE state opaqueness during long cycles. Operator cannot distinguish "waiting on CI" from "stuck in post-merge cleanup".

**Other layers protecting**: log lines exist for each phase but require docker logs grep. Dashboard surface is the visibility win.

**Why this layer needed**: routine ops visibility. Pre-merge-sync hung for 10+ min should be obvious from dashboard glance.

### Caller audit

`publish_state` callers in merge.py: 4 new calls added. Each publish_state already does Redis HSET, so additional state field merge_phase is included automatically.

Schema-add to RepoState: existing serializers (Redis HSET, JSON, dashboard JSON) preserve the new field automatically (Pydantic Optional with default None). Existing tests should continue passing because field is additive.

Exception handling: if merge raises mid-phase, merge_phase stays at last value until next state transition. Test asserts ERROR transition clears it. Edge case: if daemon crashes during MERGE, merge_phase retains last value forever in Redis (which is correct - operator sees "merge_phase=merging" forensic state).

## Out of scope

- Operator-facing rebase conflict resolution UI - separate spec.
- Sub-phase timing instrumentation (per-phase duration histograms) - out of scope, can layer on later for analytics.
- Cancellation of merge mid-phase - operator can use Stop button; mid-phase abort behavior matches existing Stop semantics.

## Success signal

Trigger MERGE state on test repo. Dashboard shows "MERGE • pre merge sync" then "MERGE • ready to merge" then "MERGE • merging" then "MERGE • post merge cleanup" within visible 5-second poll intervals. After IDLE transition, sub-phase disappears.
