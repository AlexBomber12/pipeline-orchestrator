## Problem

The backend now parks operator-clearable ERRORs visibly (PR-380), but the operator has no UI to act on a guardrail park specifically, and no repo-level escape hatch when the task-level Retry is not available. Two gaps:

- Guardrail park needs an explicit operator choice: reject (leave parked, the spec must be edited before retrying, otherwise the guardrail trips again) or accept-once (clear the park one time, knowing it will trip again if the spec is unchanged).
- A repo-level "Reset to IDLE" button is needed as the manual escape independent of whether the task-level Retry button rendered, forcing a clean exit from any ERROR.

Operator decision (2026-05-22): the guardrail card shows accept/reject, and the reject path tells the operator to fix the spec before retrying.

This is R1.8.

## Solution

### Guardrail suppression card

When a task is parked with a guardrail suppression, render a card (extend or specialize `cancellation_card.html`) showing: the guardrail finding excerpt from the suppression detail, and two actions:

- Reject: leaves the suppression in place. Shows the text "Edit the spec before retrying, or the guardrail will trigger again." This is the default, safe choice. No backend state change beyond confirming the park stands.
- Accept once: sets `approved_once=True` on the suppression record (via the port) and clears the park so the task becomes eligible one time. The card warns: "This bypasses the guardrail once. If the spec is unchanged the guardrail will trigger again on the next run."

The accept-once semantic: clearing the suppression with approved_once set lets the task run once. If it trips the guardrail again, a fresh suppression is recorded (approved_once defaults False again), so accept-once does not permanently disable the guardrail.

### Repo-level Reset to IDLE button

On the repo tile (repo_cards.html) and the repo detail summary, when the repo state is ERROR, show a "Reset to IDLE" button in the controls area. It calls a new endpoint that performs the full clean exit: clear the suppression for the current task (port), delete the cancellation cause and any diagnose-exhausted detail, write the task frontmatter back to TODO (clearing blocked_reason per PR-378), force repo state to IDLE, and publish a wake. This is the manual escape hatch that does not depend on the task-level Retry button having rendered.

Reuse the retry endpoint's clearing logic where possible - the reset is retry-at-repo-level plus a forced state transition. Do not duplicate the clearing code; factor a shared helper if needed.

### Wire into the existing controls

Add the Reset button to the `_controls.html` macro gated on `repo.state.value == 'ERROR'`, styled consistently with the existing play/pause/stop buttons. It needs an `hx-confirm` ("Reset this repo to IDLE? The current task returns to TODO.") because it is a state-forcing action.

### Do not regress the task-level Retry

The task-level Retry button (now reliably present after R1.4) stays. The repo-level Reset is additive - a coarser hammer for when the operator wants to clear the whole repo state, or when a task-level button is somehow unavailable.

## Threat model

**Threat addressed**: operator cannot act on a guardrail park (no accept/reject choice) and has no repo-level escape when a task-level button is unavailable. The reject text encodes the operator's policy decision: fix the spec before retry.

**Threat introduced**: a Reset button that force-transitions to IDLE could be clicked accidentally, returning a task to TODO mid-investigation. Mitigated by the hx-confirm and by the fact that reset only clears suppression + sets TODO (the task spec on disk is untouched, so no work is lost - the operator re-runs from the same spec).

**Other layers protecting**: accept-once does not permanently disable the guardrail (a re-trip records a fresh suppression); the task-level Retry remains for the normal case.

### Caller audit

The new endpoints are operator-triggered; no daemon caller. They reuse the retry endpoint's clearing helper - confirm the helper is factored so both call one implementation. The Reset button is rendered conditionally; confirm the condition (`state == ERROR`) matches how other state-gated controls are rendered in `_controls.html`.

## Out of scope

- Auto-detecting whether the spec changed between accept-once and the next run (the operator owns that; accept-once is explicitly a one-time bypass).
- Bulk reset across multiple repos (the global pause/stop coordination is separate, already shipped).
- Changing guardrail thresholds or detection.

## Success signal

On test fixture: a guardrail park renders accept/reject with the fix-spec text; accept-once sets the flag and clears once; the repo Reset button appears only in ERROR, forces a clean IDLE exit, and reuses the retry clearing logic. On production: an operator facing a guardrail park can read the finding, choose reject (and go fix the spec) or accept-once, and can always Reset a stuck repo to IDLE without a docker restart.
