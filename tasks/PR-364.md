2. Read `src/queue_parser.py:53-60` - the current `TYPE_SYNONYMS` dict (5 entries: bug, fix, chore, feat, task) and the `_COMPLEXITY_VALUES` frozen set (3 entries: low, medium, high).

## Problem

Operator-friendly synonyms for frontmatter values are partially implemented. The current state at `src/queue_parser.py:53-60`:

```python
TYPE_SYNONYMS: dict[str, str] = {
    "bug": "bugfix",
    "fix": "bugfix",
    "chore": "refactor",
    "feat": "feature",
    "task": "feature",
}
_COMPLEXITY_VALUES = {"low", "medium", "high"}
```

Two gaps:

1. **Missing `infra` synonym** mapped to `config`. Operator regularly types `Type: infra` for infrastructure work (Docker config, CI workflow, deploy scripts). Validation rejects with "infra is not a valid type". Observed 2026-05-01.

2. **Missing COMPLEXITY_SYNONYMS dict entirely**. Operator types `Complexity: small`, `Complexity: medium`, `Complexity: large` (common English progression). Only `small` is meant to be `low`, `medium` is OK, `large` is `high`. None of these alternatives are accepted; validation rejects all but the canonical 3.

Both gaps cause partial upload rejection: well-formed file PR-001 with `Complexity: small` survives validation if it sits in a batch with other rejected files (per OBS-AV-2), but the daemon then trips on the same value at pick time. Need synonym dict to fix at parse time.

## Solution

### Extend TYPE_SYNONYMS

Add `infra` mapping to `config`:

```python
TYPE_SYNONYMS: dict[str, str] = {
    "bug": "bugfix",
    "fix": "bugfix",
    "chore": "refactor",
    "feat": "feature",
    "task": "feature",
    "infra": "config",
}
```

### Add COMPLEXITY_SYNONYMS

Following the same pattern:

```python
COMPLEXITY_SYNONYMS: dict[str, str] = {
    "small": "low",
    "large": "high",
    "s": "low",
    "m": "medium",
    "l": "high",
    "xs": "low",
    "xl": "high",
}
_COMPLEXITY_VALUES: frozenset[str] = frozenset({"low", "medium", "high"})
```

Notes on synonym choices:

- `small/medium/large` is the common English size progression.
- `s/m/l/xs/xl` is the t-shirt sizing convention familiar from agile estimation.
- Canonical values `low/medium/high` always pass without synonym lookup.

### Wire the new dict into normalization

Find the existing function that uses `TYPE_SYNONYMS` (around line 318-319 in queue_parser.py):

```python
elif task_type in TYPE_SYNONYMS:
    task_type = TYPE_SYNONYMS[task_type]
```

Add the parallel block for complexity:

```python
elif complexity in COMPLEXITY_SYNONYMS:
    complexity = COMPLEXITY_SYNONYMS[complexity]
```

Position the new block right next to the existing complexity validation (around line 329). Maintain consistent ordering: canonical-set check, then synonym-table fallback, then ValidationError.

### Case handling

Normalize input to lowercase before lookup. Currently TYPE_SYNONYMS lookup is case-sensitive; operator writing `Type: Infra` (capital I) would still fail. Add `.lower()` normalization for both type and complexity values during parsing.

## Threat model

**Threat addressed**: operator-friendly synonyms reduce upload friction. Without synonyms, operator must memorize canonical vocabulary and edit each spec by hand when their natural phrasing differs.

**Other layers protecting**: per-spec validation rejection. Without synonyms, rejection happens with a "valid values" error message which forces operator to manually fix and re-upload. Synonym table closes the loop at the parser.

**Why this layer needed**: spec authoring is currently the major operator bottleneck for the daemon pipeline. Reducing the vocabulary-canonicalization burden makes the system more usable.

### Caller audit

`TYPE_SYNONYMS` and `COMPLEXITY_SYNONYMS` are read from `_normalize_frontmatter` in queue_parser.py only. The normalized values flow into `TaskHeader` and from there to `tasks/QUEUE.md` (now eliminated, but the consumer pattern is the same): the picker, the dashboard, the metrics layer all see canonical values only. No downstream consumer sees the synonym alternatives.

MCP `validate_task_spec` calls the same parser; new synonyms automatically apply at upload-time validation too.

Test fixtures that exercise TaskHeader parsing should be unaffected because they currently use canonical values.

## Out of scope

- Atomic upload validation (per OBS-AV sub-bug 3). Covered by sibling PR-365.
- Synonym tables for other frontmatter fields (priority, branch, coder). Out of scope; these fields are not currently sources of operator friction.
- Internationalization of synonyms (Russian operator types `Тип: ошибка` etc.). Out of scope; all spec frontmatter remains English-only.
