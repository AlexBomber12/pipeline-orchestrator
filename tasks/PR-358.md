## Problem

When PR review stays PENDING for `review_timeout_min` (default 20 min) in WATCH state, daemon today transitions directly to terminal ERROR (subsource=review_timeout) and parks the task with `skip_ai_error_diagnose=True`, requiring operator Retry. There is no automatic mid-window retry of `@codex review` before declaring the PR terminally hung.

Observed production incident on 2026-05-17: PR #465 hung after 21 minutes with review=PENDING, ci=SUCCESS. Codex never posted a review. Daemon transitioned PR-330b into terminal ERROR. Manual Retry was required. Worse, the operator-visible Retry button only appeared after a docker restart due to a separate snapshot sync bug (see PR-359, sibling spec).

Historical context: before PR-276/PR-277 (Phase 2 deploy 2026), the daemon had a dedicated `PipelineState.HUNG` state with a handler that posted `@codex review` and held the PR in watch loop instead of escalating. PR-276/277 collapsed HUNG into the broader state machine but did NOT re-implement the repost-before-ERROR behavior inside WATCH. This PR closes that regression.

## Solution

When WATCH hits review_timeout for the first time on a given PR-iteration:

1. Force-post `@codex review` via `self._post_codex_review(pr_number, bypass_same_head_dedup=True, bypass_author_dedup=True)`. The existing HungMixin method already handles error logging; do not re-wrap it.
2. Set `state.review_timeout_repost_attempted = True`.
3. Reset the review_timeout window by stamping `state.current_pr.last_activity = datetime.now(timezone.utc)` so the next WATCH cycle measures elapsed from now, not from the original push.
4. Log `[WATCH] PR #N hung after Xm; posted @codex review repost (1/1), restarting review window.`
5. Stay in WATCH. Do NOT call `_commit_task_status_change` or `_transition_to_error`. Do NOT set `skip_ai_error_diagnose`.

On the SECOND hit of review_timeout (when `review_timeout_repost_attempted` is already True), execute the existing terminal-ERROR path lines 398-440 unchanged. Subsource stays `review_timeout`. The cancellation payload SHOULD include `repost_attempted: true` so dashboard forensic surfaces can confirm the daemon tried.

The `review_timeout_repost_attempted` flag MUST reset to False on PR-iteration boundaries. The natural boundaries are:

- Transition WATCH -> FIX (CHANGES_REQUESTED handled, daemon writes a fix push, new review cycle begins). Reset at the top of `handle_fix` or wherever the FIX transition is committed.
- Transition WATCH -> MERGE (review APPROVED, daemon moves to merge). Reset at the top of `handle_merge`.
- New current_pr assignment (different PR number/branch entirely). Already handled implicitly via the RepoState `__setattr__` hook proposed below.

            posted = self._post_codex_review(

                f"posted @codex review repost (1/1), restarting review window."
            )
            await self.publish_state()
            return

        # below so the operator sees the park instead of an invisible hang.

    # Second hit, OR first hit with failed repost: terminal ERROR path
    # (existing lines 398-440 logic, unchanged except payload addition).
    message = (
        f"PR #{found.number} hung after {elapsed_min:.0f}m "
        f"(review={review.value}, ci={ci.value})"
    )
    current_task = self.state.current_task
    if current_task is not None:

            status_written = await self._commit_task_status_change(

        message,
        save_run_record_as="error",
        log_prefix="[ESCALATE]",
        log_message=f"{message}.",

            category="ERROR",
            payload={
                "subsource": "review_timeout",
                "reason_text": message,
                "previous_state": PipelineState.WATCH.value,
                "elapsed_min": int(elapsed_min),

## Threat model

**Threat addressed**: review_timeout silently parks the task with no automatic recovery attempt. Codex transient unavailability (rate-limit blip, bot restart, GitHub API hiccup) costs an operator-Retry click instead of being auto-recovered.

**Other layers protecting**: `_maybe_retrigger_stale_review` (watch.py:642) covers some silent-Codex cases earlier, but it has 1-hour per-repo debounce that frequently blocks during active FIX-loops where PRs push every 2-3 minutes. The 20-minute review_timeout is the next safety net after that gate, and this PR adds a single repost shot inside it before declaring terminal ERROR.

**Why this layer needed**: closes the regression from PR-276/PR-277 (HUNG state removal) which lost the "post @codex review once before escalating" behavior. Without this, every Codex blip during PENDING review wedges the daemon until operator clicks Retry.

### Caller audit

`_post_codex_review` is already called in 5+ sites across watch.py, hung.py, coding.py. New callsite uses `bypass_same_head_dedup=True, bypass_author_dedup=True` to defeat the dedup logic that would otherwise reject the repost as duplicate of an earlier `@codex review` for the same HEAD SHA. Bypass is correct here because the dedup is anti-flood protection, and 20 minutes since the original is past any reasonable flood window.

`review_timeout_repost_attempted` field on RepoState: additive Pydantic field with default False. Old Redis payloads deserialize cleanly (Pydantic Optional default). No migration script needed.

`__setattr__` hook extension: 2 new `super().__setattr__("review_timeout_repost_attempted", False)` lines inside existing branches. Behavior preserved for all other field writes.

`handle_fix` and `handle_merge` flag resets: idempotent (setting False when already False is a no-op). Safe to put at top of handler entries even if the handler is called multiple times for the same PR (e.g. via cycle replay during recovery).

Reset on terminal ERROR path: NOT done. The flag stays True after terminal ERROR so that if operator-Retry recovers the task and re-enters WATCH on the same PR (which `_review_timeout_park_cleared` enables), the next iteration starts fresh. Actually wait - re-check: operator-Retry deletes cancellation cause -> run_cycle clears skip_ai_error_diagnose + transitions to IDLE -> next IDLE pick fires CODING on the task. CODING entry assigns a new `current_pr` -> __setattr__ resets the flag. So no explicit reset on terminal ERROR path is needed; the natural CODING transition handles it.

Exception: if operator manually marks PR as needs-review and the SAME PR re-enters WATCH without going through CODING (uncommon path), the flag may stay True. Acceptable: worst case, daemon goes straight to terminal ERROR on the next review_timeout without retrying, which is still safer than infinite retry loop. Document as known limitation.

## Out of scope

- CHANGES_REQUESTED + no-new-feedback case (watch.py:330-348). That block uses `_maybe_retrigger_stale_review` with its own gates. A future spec may apply similar 1-shot repost semantics there if operator observes it as a separate failure mode.
- EYES (Codex acknowledged but never produced verdict) case (watch.py:363-368). Currently handled by `_maybe_retrigger_on_codex_bot_error` then falling through to `_maybe_retrigger_stale_review`. Out of scope.
- Configurable repost count > 1. Operator confirmed empirically that Codex does not silently fail twice in a row, so 1 repost is sufficient. Future spec may make count configurable if 2+ silent failures become observable.
- Recovery handler changes. Recovery DOING + open PR -> WATCH is already correct; restart posture is handled by the existing resume flow.
- Snapshot sync of in-memory ERROR fallback (the "Retry button only after restart" bug). Covered by sibling PR-359.
