5. Read `src/daemon/handlers/idle.py:297-310` - `_is_legacy_unstructured_task_error` and `_is_missing_task_header_error`, which handle legacy-parse exceptions.

## Problem

After PR-386 migrates all task files to frontmatter format (verified via --verify on all three repos), the legacy header-format parse path is dead weight: it complicates `queue_parser.py` and `task_status.py`, forces every status feature to consider two formats, and is a source of subtle drift. With the corpus uniform, the legacy path can be removed.

This is R2.2. It MUST NOT ship until the operator confirms PR-386's migration + --verify passed on all three repos (pipeline-orchestrator, megaraid-dashboard, sms-gateway-v2). This is a hard precondition.

## Solution

### Remove the legacy parse branch

In `src/queue_parser.py`, delete the legacy header-format parse branch and `_LEGACY_FALLBACK_SUFFIXES`. The parser now requires frontmatter; a file without frontmatter is a parse error (the migration guarantees none exist). Keep the frontmatter parse path as the single path.

### Simplify task_status

In `src/task_status.py`, remove `_LEGACY_FALLBACK_SUFFIXES` and any legacy-format handling. The status derivation now reads frontmatter only (consistent with R1.7's Variant 2 priority).

### Simplify idle exception handling

In `src/daemon/handlers/idle.py`, `_is_legacy_unstructured_task_error` becomes unnecessary if the legacy format no longer exists. Evaluate whether `_is_missing_task_header_error` is still needed (a genuinely malformed new file could still miss a header). Keep the malformed-file handling, remove only the legacy-format-specific handling. Decide by reading what each exception path catches.

### Defensive guard for stragglers

Although the migration should leave no legacy files, add a clear error message when the parser encounters a non-frontmatter file post-removal: "Task file <path> is in legacy header format; run scripts/migrate_task_format.py --apply." This turns a would-be silent parse failure into an actionable message, in case a legacy file is uploaded after the cutover.

### Update the schema doc

Remove the legacy-token acceptance note from `docs/TASK_SCHEMA.md` (the "for one release cycle the parser accepts legacy tokens" paragraph) since that cycle is now complete.

## Threat model

**Threat addressed**: permanent dual-format code paths complicating every status feature.

**Threat introduced**: if a legacy file slips through (uploaded after migration, or a repo not migrated), the parser now rejects it. Mitigated by the hard precondition (R2.2 ships only after --verify passes on all repos), by the actionable error message naming the fix, and by the migration script remaining available.

**Other layers protecting**: upload validation runs the parser, so a legacy file uploaded post-cutover is rejected at upload with the actionable message rather than silently entering the queue.
