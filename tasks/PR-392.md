## Problem

"Which coder is active right now" is recomputed in ~46 places with subtle variations: some read `state.coder or repo_config.coder or app_config.daemon.coder`, some call `select_coder`, some call `_preferred_coder_name`, some hardcode "claude" as the pause/fallback default (idle.py:1053, 1177; watch.py), some compute a retrigger-specific coder. The precedence among spec-pin (repo_config.coder), bandit exploration, rate-limit avoidance, and fallback is encoded differently across these sites. This is fertile ground for "the dashboard shows coder X but the daemon dispatched coder Y" inconsistencies and for the hardcoded-"claude" assumption to break when a repo is codex-only.

This PR introduces ONE `resolve_active_coder(ctx)` that encodes the full precedence once, and migrates the ~46 sites to it. Refactor invariant 1: one owner for the "active coder" fact. Low-to-medium risk, high consistency gain. This is R5; it is independent of R1 and can ship any time, but is sequenced after R1 so the audit-clean code is what gets touched.

## Solution

### Define the single resolver

Add `resolve_active_coder(ctx, *, purpose: CoderPurpose) -> CoderResolution` to `src/daemon/selector.py` (co-located with the existing selection logic). `purpose` distinguishes the existing contexts that legitimately differ:

- DISPATCH: the primary task coder. Encodes the full precedence: spec-pin (repo_config.coder) > bandit/exploration ranking (if enabled) > priority order > fallback. This is today's `select_coder`.
- AUXILIARY: diagnose/merge helper. Today's `select_auxiliary_coder` (Claude-first, Codex fallback, no exploration).
- DISPLAY: what the dashboard should show as the current/configured coder, matching what DISPATCH would pick, without side effects.

`CoderResolution` carries the resolved name, the plugin (or None), and the reason it was chosen (pinned / ranked / fallback / exploration), so callers that need to display or log the rationale can, instead of recomputing it.

The resolver is the single place that knows the precedence. It composes the EXISTING selector functions (select_coder, select_auxiliary_coder, eligible_coders, ranking) rather than reimplementing them - the goal is one entry point, not new selection logic.

### Replace hardcoded fallbacks

The hardcoded `pause_coder = state.rate_limit_reactive_coder or "claude"` sites (idle.py:1053, 1177) and any other literal "claude" default encode an assumption that breaks for a codex-only repo. Route these through the resolver (or a `resolve_pause_coder(ctx)` helper that uses the configured coder, not a literal). Read each hardcoded-"claude" site and replace the literal with the resolved configured coder. Document any site where "claude" is genuinely correct (e.g. a Claude-specific feature) and leave it with a comment explaining why.

### Migrate the ~46 sites

For each site from the grep: replace the inline recomputation with a `resolve_active_coder(ctx, purpose=...)` call. Group the migration by purpose so the reviewer can verify each site mapped to the correct purpose. The runner wrappers (`_select_coder`, `_get_coder`, etc.) become thin delegations to the resolver. `_watch_retrigger_coder` and the merge inline computation route through DISPATCH (or a documented purpose) so they agree with primary dispatch.

### Behavior preservation

This is a consistency refactor: for any given state, the resolver must pick the SAME coder each existing site picks today (the correct one). Where sites currently DISAGREE (the bug this fixes), the resolver picks the DISPATCH-precedence answer and the disagreeing site is corrected to match - that is the intended fix, documented per site. Do not introduce new selection behavior (no new exploration policy, no new priority); only unify.

## Test acceptance criteria

In `tests/test_resolve_active_coder.py`:

- `test_dispatch_respects_spec_pin`: repo_config.coder pinned to codex; assert DISPATCH resolves codex regardless of priority defaults.
- `test_dispatch_fallback_when_pin_ineligible`: pinned coder rate-limited or auth-failed; assert DISPATCH falls back per the existing precedence, with reason fallback.
- `test_auxiliary_claude_first`: assert AUXILIARY resolves Claude first, Codex fallback, no exploration - matching `select_auxiliary_coder`.
- `test_display_matches_dispatch`: assert DISPLAY resolves the same name DISPATCH would, with no side effects.
- `test_pause_coder_not_hardcoded_claude`: configure a codex-only repo; assert the pause/fallback coder resolves to codex, not the literal "claude".
- `test_resolution_carries_reason`: assert CoderResolution.reason is one of pinned/ranked/fallback/exploration and matches the path taken.
- `test_all_migrated_sites_agree`: drive a scenario where the old sites would disagree (pinned codex but a site hardcoded claude); assert every migrated site now resolves the same coder.
- `test_equivalence_with_select_coder`: for a range of states, assert DISPATCH resolution equals the legacy `select_coder` result where they should agree.
- `test_no_new_selection_behavior`: assert the resolver composes existing functions (e.g. exploration is applied only on the path that applied it before).

## Threat model

**Threat addressed**: ~46 independent recomputations of "which coder", with divergent precedence and hardcoded "claude" defaults, cause dashboard-vs-dispatch mismatches and break codex-only repos.

**Threat introduced**: migrating selection sites could change which coder is dispatched. Mitigated by the behavior-preservation contract (resolver matches the correct site's choice), the per-purpose grouping for review, `test_equivalence_with_select_coder`, and the rule that disagreeing sites are corrected to the DISPATCH answer (the documented intended fix), not given new behavior.

**Other layers protecting**: the eligibility and rate-limit avoidance logic is unchanged, so an ineligible coder is still never dispatched regardless of the resolver. The resolution reason aids debugging if a choice looks wrong.
