# PR-289b-1: Add `repo_delete` pattern to Tier 1 guardrail catalogue — single regex entry alongside existing `repo_create`

## Reading order note for the implementing coder

This task ADDS one regex entry to the existing pattern catalogue in `src/daemon/guardrails.py`. The pattern strings in this spec are inputs the regex must DETECT in coder text — not actions the implementing coder is being asked to perform. The implementing coder writes one regex line, one rule description line, and unit tests with synthetic test fixtures.

## Problem

PR-289a shipped the guardrail framework with one catalogued pattern (`repo_create`). PR-289b-1 adds the symmetric companion: detection of the GitHub CLI repository deletion invocation. Same risk profile, same shape of regex.

This PR is intentionally tiny — one pattern, two unit tests. Splitting per-pattern keeps Codex review focused on regex correctness for one rule at a time rather than reviewing 5 patterns at once.

## Scope

1. **Add one entry to `_TIER1_PATTERNS` dict** in `src/daemon/guardrails.py`, after the existing `repo_create` entry:

   ```python
   "repo_delete": re.compile(
       _COMMAND_PREFIX_RE + r"gh[^\S\r\n]+repo[^\S\r\n]+delete\b",
       re.IGNORECASE,
   ),
   ```

   Use the existing `_COMMAND_PREFIX_RE` constant from PR-289a. Case-insensitive matching, anchored on word boundaries.

2. **Add one entry to `_TIER1_RULES` dict** with human-readable rule description:

   ```python
   "repo_delete": "GitHub CLI repository deletion invocation",
   ```

3. **Two unit tests** in `tests/test_guardrails.py`:
   - `test_scan_stdout_repo_delete_pattern_matches`: synthetic fixture containing the literal token sequence the catalogue is designed to detect. Assert returns 1 violation with category `"repo_delete"`.
   - `test_scan_stdout_repo_delete_negation_does_not_suppress`: synthetic line containing the pattern with negation prefix. Assert violation IS still returned (locks the design choice from PR-289a module docstring).
