# PR-205: Control commands publish wake events

Branch: pr-205-control-pubsub-wake
- Type: feature
- Complexity: low
- Depends on: PR-183
- Priority: 2
- Coder: any

## Problem

After PR-183 ships, upload feels live (1-2s wake instead of up to 60s). Control buttons (Pause, Resume, Stop) still suffer the original lag because they only write Redis keys and wait for the next polling tick to pick them up. The user observes this as "Paused, resuming soon..." persisting up to a full poll cycle, and worse on PR-184 extended IDLE polling where ticks can be 300s apart.

The fix is to reuse the same Redis pub/sub backbone introduced in PR-183. Each control endpoint publishes a wake event on the existing channel `orchestrator:wake:{repo_name}` after writing its control flag. Daemon, already subscribing to that channel for upload, wakes immediately and runs its existing poll cycle. Polling control keys remains untouched as a defense-in-depth fallback (per the doorbell-vs-inbox pattern documented in roadmap.md).

This change is intentionally minimal. The pub/sub backbone is doorbell only. Daemon does not trust message content, only the fact that it received a message. All authoritative state remains in Redis keys read by the existing polling path.

## Scope

Three control endpoints publish wake events after their existing logic completes successfully:

1. POST /repos/{name}/pause
2. POST /repos/{name}/resume
3. POST /repos/{name}/stop

Each call goes through `publish_wake(repo_name, event_type)` from `src/events/wake.py` (introduced in PR-183) with `event_type` set to "pause", "resume", or "stop" respectively.

Out of scope for this PR: any change to daemon main loop. The subscriber added in PR-183 already wakes on any message published to `orchestrator:wake:{repo_name}` regardless of event_type.

Out of scope for this PR: dirty-tree reset is daemon-internal automatic recovery (`src/daemon/preflight.py::_auto_reset_dirty_tree`), no user button exists, no publish needed.

## Files to modify

`src/web/app.py`:

- In the pause endpoint (around line 1143), after the existing code that writes the pause flag and returns the response, call `publish_wake(name, "pause")`.
- In the resume endpoint (around line 1159), after the existing resume logic, call `publish_wake(name, "resume")`.
- In the stop endpoint (around line 1173), after the existing stop signal write, call `publish_wake(name, "stop")`.
- Wrap each publish call in a try-except that swallows Redis errors and logs them at warning level. A failed publish must not break the control endpoint response. The polling fallback in daemon will still pick up the control flag within one tick.

`tests/`:

- Test: pause endpoint publishes a wake event with event_type "pause" on the correct channel.
- Test: resume endpoint publishes a wake event with event_type "resume".
- Test: stop endpoint publishes a wake event with event_type "stop".
- Test: when Redis is unavailable, control endpoints still return success and the control flag is written normally (publish failure is non-fatal).
- Test: an end-to-end test that demonstrates daemon waking on a control publish (similar in structure to the PR-183 upload wake test, but pressing Pause).

## Implementation notes

`publish_wake` already exists from PR-183. Do not redefine it. Do not change the channel naming convention.

The publish call goes after the control flag is committed to Redis, not before. If publish fires before flag is set, daemon could wake and find no flag yet, then spin back to sleep. Set flag first, then ring the doorbell.

The publish is fire-and-forget. Do not await success confirmation. The pub/sub guarantee is "at most one delivery to current subscribers". Daemon polling is the at-least-once safety net.

The polling control-key check in daemon main loop is unchanged. Do not remove it. Do not optimize it. It exists as fallback for missed messages, daemon restarts, Redis disconnects.
