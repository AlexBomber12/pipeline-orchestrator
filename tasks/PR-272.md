# PR-272: Pre-push hook branch validation defense in depth

Branch: pr-272-pre-push-hook-branch-validation
- Type: feature
- Complexity: low
- Depends on: PR-271
- Priority: 1
- Coder: claude

## Problem

PR-270 and PR-271 prevent the recurring scope-expansion failure mode at the prompt level: daemon now sends explicit `Task:` and `File:` headers plus inline task body, and AGENTS.md instructs the coder to use those values directly without consulting QUEUE.md or other PR-*.md files. This closes the most common failure path. However, the coder is an LLM and remains capable of ignoring instructions; nothing today prevents it from running `git checkout -b <other-branch-name>` mid-session and pushing to that branch.

The defense-in-depth fix is a `pre-push` git hook installed by the scaffolder (and re-installed at every IDLE cycle as a safety net) that validates the local branch name matches an expected value before allowing the push to proceed. Daemon writes the expected branch name to `.git/info/expected-branch` immediately before invoking the coder; the hook reads that file and compares to `git symbolic-ref HEAD`. If mismatch, the hook prints a structured error to stderr and exits 1, which causes `git push` to fail. Daemon detects the no-push exit (existing OBS-BB / coder exit=0 diagnostic path) and ESCALATES with a precise cause `branch_renamed_by_coder`.

This catches:
- Coder running `git checkout -b <wrong-branch>` mid-session.
- Coder running `git branch -m <new-name>` to rename a branch.
- Any third-party tooling that creates a branch with a different name.

It does NOT prevent the coder from working on the wrong scope (that is an LLM behavior problem); but it prevents wrong-scope work from reaching the remote, which is what matters for the merge-eligibility contract.

## Scope

Three deliverables:

1. New script `scripts/install-pre-push-hook.sh` that installs a `.git/hooks/pre-push` file with executable permissions. The hook reads `.git/info/expected-branch` (one line, the expected branch name) and compares to the output of `git symbolic-ref --short HEAD`. If `expected-branch` file is absent, the hook is no-op (so manual git operations from the operator are not affected). If the file is present and the branch differs, the hook prints to stderr the structured message `[pre-push-hook] BLOCKED: expected branch '<exp>' but HEAD is on '<actual>'. Aborting push.` and exits 1.

2. `src/daemon/handlers/coding.py` updated to write the expected branch to `.git/info/expected-branch` immediately before invoking `plugin.run_auto_pr`. The write is `Path(self.repo_path) / ".git" / "info" / "expected-branch"` and the content is the value of `self.state.current_task.branch`. The `info/` directory always exists in a git repo (created by `git init`) so no mkdir needed. Use `write_text(branch + "\n", encoding="utf-8")` for clean formatting.

3. `src/daemon/scaffolder.py` updated to invoke `scripts/install-pre-push-hook.sh` during the scaffolding step that already creates other repo-managed assets. The installation is idempotent (script overwrites the hook file unconditionally) so re-running it on every scaffolder pass is safe and serves as a self-healing mechanism if the hook file is deleted or corrupted by external tooling.

The hook is installed unconditionally on every managed repo. Existing managed repos (megaraid-dashboard, sms-gateway-v2, pipeline-orchestrator itself) get the hook on their next scaffolder pass automatically.

## Behavior

After this PR ships:
- Daemon writes `.git/info/expected-branch` containing the task's expected branch name (e.g., `pr-272-pre-push-hook-branch-validation`) just before invoking coder.
- Coder runs, creates branch, commits, attempts `git push`.
- Hook runs, reads expected-branch, compares to `git symbolic-ref --short HEAD`.
- Match: hook exits 0, push proceeds. Normal flow.
- Mismatch: hook exits 1, push aborts. Coder sees the structured stderr, may retry on the correct branch (rare) or exit. Either way, daemon detects no-push and ESCALATES.
- Manual operator git operations (when the file is absent or stale): hook no-ops because `expected-branch` file is gone (daemon deletes it after CODING completes — see implementation notes for the cleanup path).

## Implementation notes

The hook script template:
```bash
#!/bin/bash
# Pre-push hook installed by pipeline-orchestrator scaffolder.
# Validates branch name against .git/info/expected-branch when daemon
# writes it. Manual git operations (no expected-branch file) are no-op.
set -euo pipefail
EXPECTED_FILE=".git/info/expected-branch"
if [[ ! -f "$EXPECTED_FILE" ]]; then
    exit 0
fi
EXPECTED=$(<"$EXPECTED_FILE")
ACTUAL=$(git symbolic-ref --short HEAD 2>/dev/null || echo "<detached>")
if [[ "$EXPECTED" != "$ACTUAL" ]]; then
    echo "[pre-push-hook] BLOCKED: expected branch '$EXPECTED' but HEAD is on '$ACTUAL'. Aborting push." >&2
    exit 1
fi
exit 0
```

The install script `scripts/install-pre-push-hook.sh`:
```bash
#!/bin/bash
# Installs the pre-push hook in $1 (repo path).
# Idempotent: overwrites existing hook unconditionally.
set -euo pipefail
REPO="${1:?usage: $0 <repo_path>}"
HOOK_FILE="$REPO/.git/hooks/pre-push"
mkdir -p "$REPO/.git/hooks"
cat > "$HOOK_FILE" <<'EOF'
<hook script content from above, embedded as heredoc>
EOF
chmod +x "$HOOK_FILE"
```

Cleanup of `.git/info/expected-branch` after coder exits is important so that manual operator pushes (e.g., when the operator manually pushes to main from the same worktree) are not blocked. Add the cleanup in the `_post_coder_resolution` path of `coding.py`, in a try/except so that a missing file does not raise. The cleanup runs regardless of coder exit code.

The hook only blocks `git push`. It does NOT block `git commit`, `git checkout`, `git branch`. The coder is free to do those internally; only the push to remote is gated. This is the right gate because:
- If coder commits to wrong branch but never pushes: daemon detects no-push exit, ESCALATES, no harm done (wrong-scope work stays local).
- If coder commits to wrong branch and tries to push: hook blocks, daemon detects no-push exit, ESCALATES with the structured stderr message captured in CLI logs.
- If coder commits to right branch and pushes: hook passes, normal flow.

The script path (`scripts/install-pre-push-hook.sh`) is consistent with `scripts/ci.sh` and `scripts/make-review-artifacts.sh` already used in the repo. The scaffolder invocation already handles those scripts; add this one to the same flow.

The defense-in-depth nature of this PR means it is acceptable for the hook write to fail silently on the daemon side (with a warning log). PR-271 already changed daemon to use AUTO PR with explicit prompt headers, which closes the primary scope-expansion path. The hook is a safety net for the residual case where the coder ignores prompt instructions. A failed hook installation reduces protection but does not break anything.

The `Coder: claude` assignment is intentional — same reasoning as PR-270 and PR-271. Even though PR-271 should have shipped before this PR runs (depends_on chain), the meta-risk of scope expansion on this PR itself is reduced by Claude's lower drift tendency.
