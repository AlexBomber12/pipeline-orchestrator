# PR-391: Merge Settings into one Usage limits block

Branch: pr-391-usage-limits-ui
- Type: ux
- Complexity: medium
- Depends on: PR-390
- Priority: 2
- Coder: any

## Reading order before coding

1. Read this entire spec and PR-390 (the unified backend gate).
2. Read `src/web/templates/components/settings_daemon.html:67-104` - the "Rate Limits" section (session/weekly pause percent inputs).
3. Read `src/web/templates/components/settings_spend_ceiling.html` - the "Spending controls" section (session/weekly ceiling + warning threshold).
4. Read `src/web/routes/settings.py` - the handlers that persist these fields.

## Problem

The dashboard presents two separate Settings sections - "Rate Limits" and "Spending controls" - for what PR-390 unified into one usage gate. The operator finds the distinction unclear (audit #9). With the backend merged, the UI should present one coherent "Usage limits" block so the mental model matches the implementation.

This is R3.3, the UI half of the usage-gate unification. It is presentation-only; the backend (PR-390) already unified the logic and kept all config fields parseable.

## Solution

### One Usage limits section

Replace the two sections with a single "Usage limits" block that exposes the unified gate's controls coherently:

- Pause thresholds (session and weekly): the percent of the usage window at which the daemon pauses dispatch. This is what both the old rate-limit pause percent and the spend-ceiling percent fed into; present them as the unified pause thresholds, with a clear explanation that the daemon pauses proactively before the provider returns a limit response.
- Warning threshold: the percent at which a warning webhook fires (the old spend-ceiling warning threshold).

Group them with explanatory copy that states plainly: these thresholds pause dispatch proactively, above the reactive provider-limit detection which is always on. This addresses the operator's "I still do not understand the difference" by explaining the layering in one place.

### Map inputs to the backward-compatible fields

PR-390 kept the legacy config fields parseable. The unified UI writes to those same fields (so persistence is unchanged) but presents them under one coherent block. Decide the cleanest mapping (e.g. the pause threshold input persists to the rate-limit pause percent field, the ceiling input to the spend-ceiling field) and document it, OR if PR-390 introduced unified field names, write to those. Read PR-390's config mapping and follow it exactly so the UI and backend agree.

### Preserve all existing controls

Every control that existed (session pause, weekly pause, session ceiling, weekly ceiling, warning threshold, reset-to-defaults) must remain reachable in the unified block. Do not drop a control; reorganize them. If two old controls fed the same unified concept, present one input and document the consolidation.

### Keep the htmx persistence pattern

The existing sections use htmx `hx-post` / `hx-put` on change to persist individual fields. Preserve that pattern in the unified block so persistence behavior (immediate save on change) is unchanged.

## Threat model

**Threat addressed**: two Settings sections for one unified concept confuse the operator about how usage limiting works.

**Threat introduced**: reorganizing inputs could drop a control or mis-map a field, silently changing a threshold. Mitigated by `test_all_controls_present` (every old control reachable) and `test_persists_to_same_fields` (persistence unchanged), and by following PR-390's documented field mapping exactly.

**Other layers protecting**: PR-390 kept all config fields parseable, so even if the UI mapping needs a follow-up tweak, the underlying values persist correctly.
