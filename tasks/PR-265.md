# PR-265: Migrate cancellation services to RepoState.current_queue snapshot

Branch: pr-265-cancellation-services-snapshot
- Type: refactor
- Complexity: medium
- Depends on: PR-263
- Priority: 2
- Coder: claude

## Problem

`src/web/services/repo_state.py` exposes two functions that build the cancellation-cause graph from disk:

- `build_repo_task_nodes(repos_dir, repo_name, ...)` at line 175 reads `tasks/QUEUE.md` via `parse_queue`.
- `compute_repo_dependents_count(repos_dir, repo_name, ...)` at line 222 calls `build_repo_task_nodes`, inheriting the disk read.
- `compute_repo_blocked_set(repos_dir, repo_name, ...)` similarly.

These power the dashboard's PR-254/PR-257 cancellation surface ("why was this canceled" and "how many tasks does this canceled root block"). The disk-read makes them subject to the same QUEUE.md drift that triggered the megaraid incident: if the on-disk projection is stale or missing, the cancellation surface shows wrong counts.

PR-263 made `RepoState.current_queue` the in-memory truth. This PR migrates the three service functions to read the snapshot first, falling back to disk only when the snapshot is None (daemon hasn't reached IDLE yet for that repo).

## Scope

Three deliverables:

1. Migrate `build_repo_task_nodes` to read `RepoState.current_queue` via the `load_current_queue` helper added in PR-264. Disk fallback preserved.
2. Verify `compute_repo_dependents_count` and `compute_repo_blocked_set` inherit the migration cleanly through their `build_repo_task_nodes` dependency.
3. Update tests for the three functions to cover both snapshot and fallback paths.

## Behavior

`build_repo_task_nodes(repos_dir, repo_name, *, extra_canceled_ids=None) -> list[TaskNode]`:

1. Call `load_current_queue(repo_name)` (helper from PR-264).
2. If snapshot is non-None, build TaskNodes from the snapshot list.
3. If None, fall through to the existing `parse_queue(queue_path)` disk path.
4. Apply the `extra_canceled_ids` overlay logic unchanged in either branch.

`compute_repo_dependents_count` and `compute_repo_blocked_set` call `build_repo_task_nodes`, so they inherit the migration with zero changes.

The fallback is preserved here for the same independent-revertability reason as PR-264. PR-267 deletes the fallback after recovery (PR-266) lands.

## Implementation notes

The migration is purely substitutional: same input shape (TaskNode list), same output (dependents_count dict, blocked_set, etc), just a different data source. The risk surface is small because TaskNode construction is mechanical from QueueTask fields.

The existing `(OSError, UnicodeDecodeError)` error handling in `build_repo_task_nodes` (returns empty list to keep the dashboard 200-OK) extends to the snapshot path: if the Redis fetch fails, the helper returns None and the function falls through to disk. If both fail, the empty-list-on-failure contract stands.

The migration deliberately does not touch the `extra_canceled_ids` overlay logic. That parameter is how the dashboard injects cancellation causes recorded in Redis whose `task_id` may not yet have CANCELED status in the queue snapshot (e.g. cancellation recorded mid-cycle, not yet reflected in the next IDLE write). The overlay continues to fold those ids in regardless of source path, preserving the existing behavior under the PR-256/PR-257 design.

The Sprint 15a #6 elimination removes the disk-fallback path in PR-267. After that, this function reads only from the snapshot. The Redis-fetch error path becomes "return empty list" outright, which is acceptable because the cancellation surface degrading to empty during a Redis outage is preferable to 5xx rendering.
