# PR-194: Production config tracking via overlay file

Branch: pr-194-config-production-overlay
- Type: feature
- Complexity: low
- Depends on: none
- Priority: 2
- Coder: any

## Problem

This is the production config gap from the 2026-04-28 sigkill debug session lesson 5. Production `config.yml` had ~15 daemon overrides (review_timeout_min, planned_pr_timeout_sec, rate_limit splits, statusline_hook, etc) that existed only as a local file on the production host, never committed to the repo. When `git reset --hard` ran during deploy, config.yml reverted to upstream defaults that did not match running daemon configuration.

Production behavior was therefore not reproducible from git alone. After deploy, the daemon would start with subtly wrong config values — review timeouts too short, rate limits too lax, etc.

The fix is a layered config approach. `config.yml` (committed) holds defaults. `config.production.yml` (gitignored, on production host only) holds production overrides. Daemon loads both and merges.

## Scope

Add overlay support to config loading. `config.yml` is base. If `config.production.yml` exists in the same directory, load it and merge over base. Unknown fields in overlay are warnings, not errors (forward compatibility).

## Files to modify

`src/config.py`:
- After loading `config.yml`, check for sibling file `config.production.yml`.
- If present, load and deep-merge over base config. Use `pydantic`'s `model_copy(update=...)` or equivalent to merge structurally.
- Log info event listing which overlay fields were applied.

`config.production.example.yml` (new file):
- Template showing common production overrides with comments. NOT loaded by daemon, just documentation.

`.gitignore`:
- Add line `config.production.yml`.

`scripts/deploy-checklist.md` (new file or extend existing):
- Document the overlay pattern.
- Reference the example file.
- Mention that `git reset` will not affect overlay file.

`tests/test_config.py`:
- Test: no overlay file → base config used.
- Test: overlay present → fields merged correctly.
- Test: overlay with field not in base → logged warning, base unchanged.
- Test: overlay path resolution (overlay must be sibling of base).

## Implementation notes

Choose YAML, not JSON. Same format as base config, easier for operator to edit by hand.

Deep merge semantics: nested dicts merge recursively. Lists in overlay replace lists in base (do not concat). This matches typical config-overlay expectations.

For the deploy checklist: include a verification step like `diff <(yq . config.yml) <(docker compose exec daemon python -c "import json; from src.config import load_config; print(json.dumps(load_config().model_dump(), default=str))")` — operator can run this to verify running daemon matches expected config.

## Success criteria

1. `config.production.example.yml` exists with comments.
2. `grep "config.production.yml" .gitignore` returns 1.
3. `grep -c "config.production.yml" src/config.py` returns at least 2.
4. New tests pass for all four scenarios.
5. `scripts/deploy-checklist.md` exists with overlay pattern documented.
6. `python -m ruff check src/` passes.
7. `python -m pytest --cov=src --cov-fail-under=100` passes.
