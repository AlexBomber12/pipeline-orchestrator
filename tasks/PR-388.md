# PR-388: Stop reading the dead recovered_tasks legacy key

Branch: pr-388-cleanup-legacy-keys
- Type: refactor
- Complexity: low
- Depends on: none
- Priority: 3
- Coder: any

## Reading order before coding

1. Read this entire spec in full, especially the "Files NOT to touch" section. It is the point of this PR.
2. Read `src/daemon/runner.py:2117-2144` - `_hydrate_status_write_failed_task_pr_ids`. It loops over two Redis keys and unions both into `self._status_write_failed_task_pr_ids`: the live status-write key from `self._status_write_failed_compat_key()` (line 2120) and the dead legacy key `"recovered_tasks:" + self.name` (line 2121).
3. Read `src/daemon/runner.py:2146-2159` - `_clear_status_write_failed_task_ids`, which deletes `"recovered_tasks:" + self.name` (line 2154) on re-upload.
4. Read `src/web/routes/repo_control.py:334` - the cleanup loop that deletes both the status-write key and `f"recovered_tasks:{repo_slug}"`.
5. Run `grep -rn "recovered_tasks" src/ --include="*.py" | grep -v test`. There are exactly three references (the two in runner.py and the one in repo_control.py). Confirm this count before and after your change.

## Problem

The Redis key `recovered_tasks:<repo>` (historically called `legacy_recovered_tasks`, the pre-PR-281 recovery fallback) is dead: nothing writes it. A repo-wide grep finds only reads and deletes, no writer. It survives only as a leftover that `_hydrate_status_write_failed_task_pr_ids` still reads and unions into the live status-write-failed set, plus two deletes that sweep it.

Reading a key that nothing writes is dead weight, and unioning its (always empty, or stale-from-a-past-version) contents into the live status-write-failed set is a latent hazard: if a stale `recovered_tasks:<repo>` value lingers in a long-lived production Redis from before PR-281, it gets merged into the active park set on every hydrate and could wrongly park a task that is no longer failed.

This PR removes the dead key from the read path. It is deliberately tiny and does exactly one thing.

## Solution

### Remove the dead key from the hydrate read loop

In `_hydrate_status_write_failed_task_pr_ids`, delete the `"recovered_tasks:" + self.name` entry from the tuple the loop iterates over (runner.py:2121). After the change the loop reads only `self._status_write_failed_compat_key()`. The surrounding loop logic (decode, union, the empty-`decoded_sets` fallback) is unchanged and works correctly with a single key.

### Keep the deletes as a stale-key sweep

Leave the two delete sites intact: `_clear_status_write_failed_task_ids` (runner.py:2154) and the repo_control.py:334 cleanup loop. They now serve only to sweep any stale `recovered_tasks:<repo>` value out of production Redis so the dead key does not linger. Removing the read while keeping the delete is the correct combination: stop trusting stale legacy data, but still clean it up.

### Do not touch anything else

This PR does not remove, rename, or alter the status-write-failed mechanism in any way. `status_write_failed` is a live, load-bearing safety net that keeps a task parked in ERROR when its durable `status: ERROR` write fails; it runs in both feature-flag modes and is consulted unconditionally in IDLE selection. It is explicitly out of scope. The only key being retired here is the dead `recovered_tasks:<repo>` legacy key.

NONE of these change. A grep for `status_write_failed` must return the same reference count after this PR as before.
- The `_clear_status_write_failed_task_ids` delete of the legacy key (runner.py:2154) and the repo_control.py:334 delete - kept as the stale-key sweep.

- The feature-flag mode logic - untouched.

## Test acceptance criteria

In `tests/test_legacy_recovered_key.py`:

- `test_hydrate_does_not_read_legacy_key`: seed a `recovered_tasks:<repo>` key with a PR id that is NOT in the status-write key; run `_hydrate_status_write_failed_task_pr_ids`; assert the seeded legacy PR id does NOT end up in `_status_write_failed_task_pr_ids` (proving the legacy key is no longer read).
- `test_hydrate_still_reads_status_write_key`: seed the live status-write key with a PR id; run hydrate; assert that PR id IS in `_status_write_failed_task_pr_ids` (proving the live mechanism is unaffected).
- `test_status_write_failed_unchanged`: a guard test asserting the status-write-failed machinery is intact - the helper methods exist and a status-write failure still parks the task in ERROR exactly as before this PR.
- `test_legacy_key_swept`: call the path that deletes `recovered_tasks:<repo>` (re-upload clear) and assert the key is removed from Redis.
- `test_single_key_hydrate_no_crash`: with no legacy key present at all, run hydrate; assert no crash and the status-write set hydrates correctly from its own key.

## Threat model

**Threat addressed**: a dead key that nothing writes is still read and unioned into the live park set, so a stale leftover in a long-lived production Redis could wrongly park a task.

**Threat introduced**: the real risk in this PR is accidentally touching the live status-write-failed mechanism while editing the same method. Mitigated by the explicit "Files NOT to touch" list, by `test_status_write_failed_unchanged`, and by the before/after grep-count check on `status_write_failed` (must be identical).

**Other layers protecting**: the deletes remain, so any stale legacy key is swept rather than left behind. The status-write-failed mechanism is fully retained, so the park behavior it provides is unchanged.

## Out of scope

- Removing the status-write-failed mechanism. That is a separate, larger effort that can only happen after the `use_single_error_exit` flag becomes the only mode (flag flipped, validated, then removed), because the default flag-off path still depends on status-write-failed. Not this PR.
- Any change to suppression records, the feature flag, or IDLE selection.
- A new startup sweep for the legacy key - the existing deletes already cover cleanup; adding a startup sweep would be scope creep.

## Success signal

On test fixture: hydrate no longer reads `recovered_tasks:<repo>`, still hydrates the status-write set from its own key, the status-write-failed machinery is provably unchanged, and the stale legacy key is swept by the existing deletes. On production: the dead key stops feeding the park set, status-write-failed behavior is identical, and no task is wrongly parked by a stale legacy value.
