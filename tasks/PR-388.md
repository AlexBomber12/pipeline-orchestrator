# PR-388: Remove legacy_recovered_tasks and dead key helpers

Branch: pr-388-cleanup-legacy-keys
- Type: refactor
- Complexity: low
- Depends on: PR-382, PR-387
- Priority: 3
- Coder: any

## Reading order before coding

1. Read this entire spec.
2. Read `src/keyspace.py` in full - note `legacy_recovered_tasks` (line 58, "Legacy PR IDs parked by pre-PR-281 recovery fallback state") and `status_write_failed_tasks` (which PR-382 should have already removed callers for).
3. Run `grep -rn "legacy_recovered_tasks\|status_write_failed_tasks\|recovered_tasks" src/ --include="*.py" | grep -v test` to confirm what still references these keys after R1.6b (PR-382) and R2.2 (PR-387).
4. Read `src/daemon/runner.py:1748-1816` - `_hydrate_status_write_failed_task_pr_ids` reads both the current and the legacy key; confirm PR-382 removed this.

## Problem

After R1.6b (PR-382) removed the status_write_failed mechanism and R2.2 (PR-387) removed the legacy parse path, two Redis key helpers and their hydration logic may be orphaned: `legacy_recovered_tasks` (pre-PR-281 recovery fallback) and `status_write_failed_tasks`. Leaving dead key helpers and any residual hydration is exactly the kind of accreted cruft this refactor exists to remove.

This is R2.3, a small cleanup that depends on PR-382 and PR-387 having removed the live callers. It is low priority and low risk - pure dead-code removal verified by grep.

## Solution

### Confirm the keys are orphaned

Before removing anything, verify via grep that no production code writes or reads `legacy_recovered_tasks` or `status_write_failed_tasks` after PR-382 and PR-387. If any reference remains, that is a sign R1.6b did not fully migrate - investigate and either complete the migration here (if trivial) or flag it; do NOT remove a key that is still read.

### Remove the helpers and any residual hydration

Once confirmed orphaned:

- Remove the `legacy_recovered_tasks` and `status_write_failed_tasks` helpers from `src/keyspace.py`.
- Remove any residual hydration/persist methods in `runner.py` that read these keys (PR-382 should have removed the primary ones; this PR sweeps any remainder).
- Add a one-time startup cleanup that deletes any stale `legacy_recovered_tasks:*` and `status_write_failed_tasks:*` keys left in production Redis from before the migration, so the keyspace is clean. Make this idempotent and best-effort (a failed cleanup must not block startup).

### Do not remove keys still in use

Other key families in keyspace.py (pipeline_state, control_*, upload_*, cli_log_*, ci_infra_retried, repo_events_*, recovery_backup_branch) are live - do not touch them. This PR removes only the two confirmed-orphaned helpers.

## Files to change

- `src/keyspace.py` - remove the two orphaned helpers (~10 LoC removal).
- `src/daemon/runner.py` - remove any residual hydration referencing them; add the idempotent stale-key cleanup at startup (~20 LoC).
- `tests/test_keyspace.py`, `tests/test_legacy_key_cleanup.py` - update keyspace test, add cleanup test.

## Files NOT to touch

- Any live key family in keyspace.py.
- The suppression store (the new owner) - unchanged.

## Test acceptance criteria

- `test_orphaned_helpers_removed`: assert `legacy_recovered_tasks` and `status_write_failed_tasks` helpers no longer exist in keyspace (import/grep-level).
- `test_no_production_references`: assert grep finds zero production references to the two key names.
- `test_stale_key_cleanup_idempotent`: seed fake stale keys, run the startup cleanup twice; assert the keys are deleted and the second run is a no-op.
- `test_cleanup_best_effort`: simulate the cleanup raising; assert startup is not blocked.
- `test_live_keys_untouched`: assert all other keyspace helpers still exist and are unchanged.

## Threat model

**Threat addressed**: dead key helpers and residual hydration left after the suppression migration - exactly the accreted cruft this refactor targets.

**Threat introduced**: removing a key that is secretly still read would break recovery. Mitigated by the grep precondition (do not remove a referenced key) and by the dependency on PR-382/PR-387 having removed the callers first.

**Other layers protecting**: the stale-key cleanup is best-effort and idempotent, so it cannot block startup; the suppression store is the sole owner now, independent of these keys.

### Caller audit

The whole PR is a caller audit: confirm zero references before removal. If a reference survives, the migration is incomplete - resolve before removing.

## Out of scope

- Removing any live key family.
- Broader keyspace refactor (the three-layer config split is separate, Sprint 16).

## Success signal

On test fixture: the two orphaned helpers are gone, no production reference remains, and the stale-key cleanup is idempotent and non-blocking. On production: leftover legacy Redis keys are swept on startup and the keyspace reflects only live mechanisms.
