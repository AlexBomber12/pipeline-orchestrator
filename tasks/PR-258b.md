## Problem

PR-247 shipped the operator-recover-from-HUNG path: the dashboard exposes a `POST /repos/{name}/recover` endpoint that sets a one-shot Redis flag `control:{name}:recover` with a 300-second TTL, the daemon's HUNG handler reads-and-clears the flag via `GETDEL` on each tick, and on observed signal it transitions the runner from HUNG to IDLE while recording the trapped task's `pr_id` in the in-memory `_recovered_task_pr_ids` set (also persisted to Redis so the marker survives a daemon restart between click and re-upload).

The end-to-end contract has three boundaries that no test currently spans together: the web endpoint sets the flag, the daemon clears it atomically, and the IDLE selector consults the recovered-set to suppress the auto-reattach to the still-open PR. Each boundary has unit-level tests; none exercise the full handshake against a live daemon. A regression in any one (TTL mistake, GETDEL reverted to non-atomic GET+DEL, recovered-set persistence path corrupted) is invisible to CI today.

The Sprint 14 incident class showed that operators rely on this button as the last line of defense when the daemon mis-classifies a stuck PR. Landing this e2e as part of the Tier-1 safety net is the smallest unit of work that makes the recover button a tested production surface.

## Scope

A single new e2e test `tests/e2e/test_hung_operator_recover.py` that:

1. Drives the daemon to HUNG via the existing FIX-then-ESCALATE path: upload `PR-A`, wait for CODING, the success shim creates the PR, daemon enters WATCH, post a failed CI status to engineer WATCH to FIX, switch shim scenario to `escalate`, wait for the daemon to enter HUNG via `fix_escalation`. This mirrors `test_fix_coder_escalate.py` until the moment the runner parks; from there this test continues into the recover path.
2. Asserts the runner is in HUNG with `current_task.pr_id == "PR-A"` and `current_pr` populated.
3. Issues `POST /repos/{slug}/recover` against the test dashboard.
4. Polls the runner state with a 60-second deadline and asserts the runner reaches IDLE with `current_task is None` and a fresh `last_updated` (timestamp greater than the pre-recover snapshot).
5. Asserts the recovered-set marker is present: either via a dedicated dashboard surface (if one exists) or via direct Redis read through `docker exec` against the test daemon container, looking up the persistence key documented in `src/daemon/handlers/hung.py:_persist_recovered_task_pr_ids`.
6. Re-uploads `PR-A` (same task file, same `pr_id`) and asserts the daemon does NOT pick it up again (the recovered-set marker suppresses re-dispatch). Then issues a stop-resume cycle so the marker is cleared via the operator-driven retry path, re-uploads, and asserts the daemon now picks up `PR-A` normally. This pins the full contract the marker is part of, not just the immediate transition.

If the testbed GitHub App lacks `Commit statuses: Write` permission, the test must skip with the same shape of message used by `test_fix_coder_escalate.py`. The same precondition exists because both tests use the same WATCH to FIX engineering trick.

## Implementation notes

The HUNG-entry path through ESCALATE is the most reliable e2e route because it does not depend on close-PR-externally timing or on a heartbeat-timeout simulation that would require either modifying the daemon's heartbeat config in test or injecting Redis state directly. The trade-off is the GitHub-App-permission gate, which is already an accepted constraint per the existing escalate test.

Setting a HUNG fallback config is unnecessary for this test: the daemon ships with the production default and reaching HUNG via ESCALATE is the production-shaped path. Avoid environment overrides that would shift the test off the production path.

The recovered-set marker key on Redis is documented inside `_persist_recovered_task_pr_ids` in the HUNG handler. Read the source to capture the exact key shape before authoring the assertion. The persistence key is keyed off `slug` and contains a JSON-encoded list; deserialize it before asserting `"PR-A" in marker`.

The re-upload assertion in step 6 is the load-bearing assertion that catches the May 4 incident class: a faulty recovered-set rebroadcast or a missed clear would let the daemon pick up the task again and re-enter the same HUNG state, re-stranding the operator. Without this assertion the test only pins half the contract.

Idempotency of the recover endpoint is also worth pinning: a second `POST /recover` while the runner is already in IDLE must return 400 with `error: "recovery_only_from_hung"` per the existing handler. Add a one-line assertion to that effect after step 4. This costs 3 LOC and pins the second-half of the safety contract.

The 60-second poll deadline in step 4 is sized for the slowest documented HUNG-tick interval in the test stack. If the daemon's HUNG poll period is configurable in the test profile, set it to 2 seconds via the test compose override so the test runs in under 30 seconds wall-clock; otherwise inherit production defaults and accept the 60-second cap.

## Success criteria

1. The test reaches HUNG with `state.current_task.pr_id == "PR-A"` and `state.state == "HUNG"`.
2. After `POST /repos/{slug}/recover`, the runner reaches IDLE with `current_task is None` within 60 seconds.
3. The recovered-set marker (Redis-persisted) contains `PR-A` after the transition.
4. After re-uploading `PR-A` without clearing the marker, the daemon does NOT dispatch it (state remains IDLE for at least 30 seconds).
5. After the operator-driven marker-clear path (stop-resume cycle, then re-upload), the daemon dispatches `PR-A` normally and reaches CODING.
6. A second `POST /recover` while the runner is in IDLE returns HTTP 400 with the documented `recovery_only_from_hung` error code.
7. The test skips cleanly with the documented permission-gap message when the testbed App lacks `Commit statuses: Write`.
8. The test passes locally and in CI without flake on three consecutive runs.
9. No production code modified.
