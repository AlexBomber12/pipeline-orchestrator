## Problem

PR-247 shipped the operator-recover-from-HUNG path: the dashboard exposes a `POST /repos/{name}/recover` endpoint that sets a one-shot Redis flag `control:{name}:recover` with a 300-second TTL, the daemon's HUNG handler reads-and-clears the flag via `GETDEL` on each tick, and on observed signal it transitions the runner from HUNG to IDLE while recording the trapped task's `pr_id` in the in-memory `_recovered_task_pr_ids` set (also persisted to Redis under key `recovered_tasks:{repo_name}` so the marker survives a daemon restart between click and re-upload).

The end-to-end contract spans four boundaries that no single test covers today: (1) the web endpoint atomically sets the flag and rejects when state is not HUNG, (2) the daemon clears the flag atomically via GETDEL and adds the trapped pr_id to the recovered-set, (3) the IDLE selector consults the recovered-set and forces task status to CANCELED so the still-open PR cannot re-derive DOING (`src/daemon/handlers/idle.py:418-427`), and (4) the upload path clears the recovered-set entry for any re-uploaded pr_id via `difference_update(uploaded_pr_ids)` and persists the trimmed set (`src/daemon/repo_ops.py:434-445`), making the upload itself the explicit retry signal.

A regression in any one boundary (TTL mistake, GETDEL reverted to non-atomic GET+DEL, recovered-set persistence path corrupted, upload-time difference_update removed) is invisible to CI today. The Sprint 14 incident class showed that operators rely on this button as the last line of defense when the daemon mis-classifies a stuck PR. Landing this e2e as part of the Tier-1 safety net is the smallest unit of work that makes the recover button a tested production surface.

## Scope

A single new e2e test `tests/e2e/test_hung_operator_recover.py` that:

1. Drives the daemon to HUNG via the existing FIX-then-ESCALATE path: upload `PR-A`, wait for CODING, the success shim creates the PR, daemon enters WATCH, post a failed CI status to engineer WATCH to FIX, switch shim scenario to `escalate`, wait for the daemon to enter HUNG via `fix_escalation`. This mirrors `test_fix_coder_escalate.py` until the moment the runner parks; from there this test continues into the recover path.
2. Asserts the runner is in HUNG with `current_task.pr_id == "PR-A"` and `current_pr` populated. Snapshots `pre_recover_last_updated` for the freshness gate.
3. Asserts the precondition that PR-A is NOT yet in `_recovered_task_pr_ids` (Redis-direct read of `recovered_tasks:{slug}` returns either missing key or a JSON list not containing PR-A). This proves the marker is added by the recover transition, not by any prior step.
4. Issues `POST /repos/{slug}/recover` against the test dashboard. Asserts HTTP 200 (signal queued).
5. Polls the runner state with a 60-second deadline and asserts the runner reaches IDLE with `current_task is None` and `last_updated > pre_recover_last_updated`.
6. Asserts the recovered-set marker NOW contains PR-A: read `recovered_tasks:{slug}` from Redis via `docker exec ... redis-cli GET recovered_tasks:{slug}`, JSON-decode the list, assert `"PR-A" in marker`. This is the marker-add assertion that pins the HUNG-handler write at `src/daemon/handlers/hung.py:307-308`.
7. Idempotency assertion: a second `POST /repos/{slug}/recover` while the runner is in IDLE returns HTTP 400 with `error: "recovery_only_from_hung"` per the existing handler at `repo_control.py:341-348`. This pins the safety contract that protects against double-clicks during the IDLE settling window.
8. Re-uploads PR-A (same task file, same `pr_id`) via the existing `upload_zip` fixture. Asserts the upload returns success.
9. Asserts the recovered-set marker NO LONGER contains PR-A within 30 seconds of the upload completing: poll the Redis key, JSON-decode, assert `"PR-A" not in marker` (or the key is missing if PR-A was the only entry, in which case the persist helper deletes the key per `runner.py:1230-1231`). This is the load-bearing assertion that pins the upload-time `difference_update` behavior in `repo_ops.py:437` plus the trimmed-set persistence in line 445.
10. Asserts the daemon DOES dispatch PR-A on the next IDLE cycle: poll runner state with a 60-second deadline, assert `current_task.pr_id == "PR-A"` and `state.state == CODING`. This pins the full contract that upload IS the retry signal — no separate operator action is needed to clear the marker.

If the testbed GitHub App lacks `Commit statuses: Write` permission, the test must skip with the same shape of message used by `test_fix_coder_escalate.py:_preflight_status_write_permission`. The same precondition exists because both tests use the same WATCH-to-FIX engineering trick.

## Implementation notes

The HUNG-entry path through ESCALATE is the most reliable e2e route because it does not depend on close-PR-externally timing or on a heartbeat-timeout simulation that would require either modifying the daemon's heartbeat config in test or injecting Redis state directly. The trade-off is the GitHub-App-permission gate, which is already an accepted constraint per the existing escalate test.

The recovered-set marker write happens inside `_apply_operator_recovery` at `hung.py:300-316`. Critically, the add-and-persist runs BEFORE `current_task = None` (line 313), so the `current_task.pr_id` reference at line 307 is still valid. The test's step 6 assertion polls Redis directly rather than the dashboard so it is independent of any UI-layer caching.

The upload-time clear path is the part that the original draft of this spec got wrong. The contract is NOT "upload is suppressed by the marker until a separate operator action clears it." The contract IS "upload IS the operator action that retries; `repo_ops.py:434-445` removes uploaded pr_ids from the marker via `difference_update(uploaded_pr_ids)` and persists the trimmed set; the next IDLE cycle then dispatches the re-uploaded task normally because its derived status is no longer forced to CANCELED." The test pins this precise sequence.

Step 9's polling deadline (30 seconds for marker clear after upload) is sized for the upload-handler's git-operations + Redis-write window. The persist call at line 445 runs synchronously inside the upload handler before HTTP 200 returns to the client, so in practice the marker is already cleared when step 8 returns. The 30-second poll budget covers the worst case where the test's docker exec to Redis lags briefly.

Step 10's polling deadline (60 seconds for CODING entry) covers one full IDLE poll period plus DAG selection plus shim coder dispatch. If the test stack uses a longer poll period in the test profile, raise the deadline accordingly; do not lower the production poll period to suit the test.

The test does NOT exercise the cross-restart marker persistence path (daemon kill between recover click and upload). That scenario is owned by a separate test in the recovery suite; this test focuses on the same-process happy path and the IDLE-side override semantics, which is what the four-boundary contract collapses to in normal operation.

The `Step 6 marker contains PR-A` and `Step 9 marker no longer contains PR-A` assertions are the load-bearing pair. Without step 6, a regression in `hung.py:307` (e.g. `add` replaced by no-op) would be invisible because the IDLE override would no longer fire, and the test could still pass on the basis of step 10 alone (daemon dispatches PR-A — but for the wrong reason, namely that the marker was never set). Without step 9, a regression in `repo_ops.py:437` (e.g. `difference_update` removed) would be invisible because step 10's CODING-entry assertion would fail with an inconclusive timeout instead of a precise marker-still-present error. Both assertions are needed for diagnostic clarity on regression.

The `Coder: claude` assignment is intentional: the test is medium-complexity with multi-step Redis assertions and timing-sensitive polls, which suits Claude's strengths over Codex's faster but smaller-window dispatch shape.

## Success criteria

1. The test reaches HUNG with `state.current_task.pr_id == "PR-A"` and `state.state == "HUNG"` via the FIX-to-ESCALATE engineering path.
2. Pre-recover assertion: Redis key `recovered_tasks:{slug}` does NOT contain `"PR-A"` before the recover click.
3. After `POST /repos/{slug}/recover`, the runner reaches IDLE with `current_task is None` and a fresh `last_updated` within 60 seconds.
4. Post-recover marker assertion: Redis key `recovered_tasks:{slug}` contains `"PR-A"` after the IDLE transition completes.
5. Idempotency assertion: a second `POST /recover` while in IDLE returns HTTP 400 with the documented `recovery_only_from_hung` error code.
6. Post-upload marker-clear assertion: within 30 seconds of re-uploading PR-A, the Redis key `recovered_tasks:{slug}` no longer contains `"PR-A"` (or the key is absent if PR-A was the only entry).
7. Post-upload dispatch assertion: within 60 seconds of the upload completing, the runner reaches CODING with `current_task.pr_id == "PR-A"`. This pins the full contract that upload IS the retry signal.
8. The test skips cleanly with the documented permission-gap message when the testbed App lacks `Commit statuses: Write`.
9. The test passes locally and in CI without flake on three consecutive runs.
10. No production code modified.
