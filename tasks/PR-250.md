# PR-250: Classify CI stuck PENDING for >Nmin as effective FAILURE

Branch: pr-250-ci-stuck-pending
- Type: bugfix
- Complexity: medium
- Depends on: none
- Priority: 2
- Coder: claude

## Problem

OBS-BM from `docs/roadmap.md`. GitHub Actions occasionally produces a check-run that registers as `queued` or `in_progress` but never transitions to a terminal state — runner died, queue worker crashed, action got stuck on a self-hosted runner with no listeners. The check-run's `status` stays at `in_progress` indefinitely, so `_map_rest_ci_status_to_enum` (in `src/github/checks.py:143`) returns `CIStatus.PENDING` forever. Daemon's WATCH state polls indefinitely and the PR sits.

WATCH timeout (PR-202 adaptive polling) eventually escalates after the review-timeout window, but for active development that wastes 20+ minutes before any signal. PR-249 caps the retrigger cycle but doesn't address the root cause that PENDING is genuinely stuck.

Fix: track the timestamp when CI first transitioned to PENDING for a given head_sha. After `ci_pending_max_min` (config-tunable, default 30 minutes), reclassify as FAILURE. WATCH then routes through normal FAILURE → handle_fix path, which can either rerun the workflow (next coder iteration) or escalate via fix_iteration_cap.

## Scope

Three deliverables:

1. Track per-PR per-head_sha PENDING start timestamp in Redis (`ci_pending_start:{repo}:{pr}:{sha}`).
2. In `_map_rest_ci_status_to_enum` or a new wrapper `classify_ci_status_with_age`, look up the stuck-PENDING age. If exceeds threshold, return FAILURE with a synthetic marker.
3. Tests covering the threshold transition, head_sha rotation reset, config-tunable threshold.

## Files to modify

`src/github/checks.py` — add a wrapper that augments `_map_rest_ci_status_to_enum` with stuck-PENDING detection:

```
def classify_ci_status_with_age(
    repo: str,
    pr_number: int,
    head_sha: str,
    redis_client: Any,
    pending_max_seconds: int,
    runs_payload: list[dict],
    statuses_payload: dict,
) -> tuple[CIStatus, str | None]:
    """Augment CI status with stuck-PENDING reclassification.

    Returns a tuple ``(status, reclassification_reason)``. When the
    raw status is PENDING for longer than ``pending_max_seconds`` on
    the same head_sha, returns ``(CIStatus.FAILURE, "stuck_pending")``;
    otherwise returns the raw status with reason ``None``. Tracks
    the first-seen-PENDING timestamp per head_sha in Redis and
    clears it on head_sha rotation.

    PR-250.
    """
    raw_status = _map_rest_ci_status_to_enum(runs_payload, statuses_payload)
    if raw_status != CIStatus.PENDING:
        # Clear any stale PENDING tracking on transition.
        _clear_pending_tracker(redis_client, repo, pr_number, head_sha)
        return raw_status, None

    first_seen = _get_or_set_pending_first_seen(
        redis_client, repo, pr_number, head_sha
    )
    age_seconds = time.time() - first_seen
    if age_seconds >= pending_max_seconds:
        return CIStatus.FAILURE, "stuck_pending"
    return raw_status, None
```

Helper functions `_clear_pending_tracker`, `_get_or_set_pending_first_seen` use Redis SET NX on key `ci_pending_start:{repo}:{pr}:{sha}` with TTL of `pending_max_seconds * 2` so abandoned trackers self-expire.

`src/daemon/handlers/watch.py` — locate the call site that resolves CIStatus and replace with the new wrapper. Pipe the reclassification reason through to event log so operator sees `[WATCH] PR #N CI reclassified PENDING -> FAILURE (stuck_pending: 31min on sha abc123)` and not just a silent FAILURE.

`src/orchestrator_config.py` — extend `DaemonConfig` with `ci_pending_max_min: int = 30`.

`config.yml` and `config.production.example.yml` — add the field with default 30.

## Implementation notes

Redis tracker uses Redis-server time, not daemon time, to avoid clock drift between daemon restarts. Use `redis.time()` to read server time on first-seen write; comparison still uses daemon-side `time.time()` for simplicity since clock drift between Redis server and daemon host is negligible for 30-minute threshold.

Threshold default 30 minutes balances: too low and routine slow-running tests trigger; too high and the bug it solves persists. Operator can tune per config — high-CI-cost repos may want 60min, fast-CI repos 15min.

After this PR ships, watching for first occurrence of `[WATCH] ... reclassified PENDING -> FAILURE` in event log validates the path is firing in production.
