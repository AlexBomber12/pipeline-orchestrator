# PR-183: Redis pub/sub upload trigger for immediate daemon wake

Branch: pr-183-redis-pubsub-upload-trigger
- Type: feature
- Complexity: medium
- Depends on: none
- Priority: 1
- Coder: any

## Problem

Currently when a user uploads tasks via the dashboard, the daemon does not pick them up until the next polling cycle. With `poll_interval_sec: 60` this means up to a minute of dead air between upload and daemon starting work on the new task. Larger `poll_interval_sec` values would make this worse and would directly conflict with PR-184 adaptive IDLE polling (which raises IDLE intervals to 300s).

The fix is event-driven wake: web layer publishes a Redis pub/sub message after a successful upload commit, daemon main loop combines its sleep timer with a Redis subscriber, whichever fires first wins. Daemon wakes within 1-2 seconds of upload regardless of nominal poll interval.

This is the prerequisite for PR-184. Without immediate wake, raising IDLE poll interval to 300s would feel broken to the user.

## Scope

Add Redis pub/sub channel for "wake-up triggers" that the daemon listens on. Web layer publishes on this channel after successful upload commit. Scope expansion to other user actions that currently wait for next tick is desirable but optional in this PR (Play button, coder swap, settings change can land in follow-up PRs if too much for one).

## Files to modify

`src/web/app.py`:
- After successful `upload_zip` git commit (look for the commit step inside the upload handler), publish a message to Redis channel.
- Channel name: `orchestrator:wake:{repo_name}` where repo_name is the slug.
- Message body: JSON with keys `event_type` (always "upload"), `repo` (slug), `timestamp` (ISO 8601).

`src/daemon/main.py`:
- In the main daemon loop where `await asyncio.sleep(tick)` is called, replace the pure sleep with `await asyncio.wait([sleep_task, redis_subscriber_task], return_when=FIRST_COMPLETED)`.
- Cancel the loser task (subscriber if sleep fired, sleep if subscriber fired).
- On subscriber wake: parse the message, set `last_run[key] = 0` for the affected repo, continue to run_cycle immediately.
- On sleep wake: continue normally.

`src/events/__init__.py` or new `src/events/wake.py`:
- Add helper functions `publish_wake(repo_name, event_type)` and `subscribe_wake(repo_names)` that hide the channel naming convention from callers.

`tests/`:
- Test: upload triggers publish.
- Test: daemon wakes on subscriber message.
- Test: daemon wakes on sleep timer normally when no message.
- Test: multiple uploads in quick succession (dedup is handled correctly by `last_run = 0` semantics — second message during cycle is harmless).
- Test: subscriber connection failure does not crash daemon (fall back to pure sleep).

## Implementation notes

Use `asyncio.wait` with `return_when=FIRST_COMPLETED`. Important: cancel and await the loser to avoid orphan tasks.

For the subscriber, use `redis.asyncio.Redis().pubsub()` and `await pubsub.get_message(timeout=tick)`. This gives a graceful fallback if the subscriber connection drops — the get_message returns None and the loop continues.

Race conditions to handle:
- Upload event arrives while daemon is mid-cycle (CODING/FIX/etc): message is buffered in Redis, daemon processes it on next IDLE iteration. Already correct because `last_run = 0` is checked on next loop.
- Multiple uploads quick succession: deduplication is implicit — `last_run = 0` is idempotent.
- Upload during rate-limited pause: respect `rate_limited_until`, do not bypass.
- Wake during stop cancellation: graceful — stop signal already propagates via existing mechanism, wake is harmless.
