## Reading order note for the implementing coder

This task EXTENDS a detection module that was already shipped in PR-289a. The module's purpose is to scan a string of captured coder output and return a list of violations when the string contains catalogued patterns. Pattern strings in back-tick markers throughout this spec are inputs the regex catalogue must DETECT — they are descriptions of what the regex must match. The implementing coder adds 4 entries to the catalogue dictionary in `src/daemon/guardrails.py` and writes regression tests with synthetic test fixture strings. The implementing coder does not run any GitHub CLI command at the org level, does not modify protected branches, and does not touch the GitHub API. All test inputs are synthetic strings constructed inside test fixtures.

## Problem

PR-289a shipped the framework with one catalogued pattern (`repo_create`) as proof of wiring. PR-289b extends the catalogue with the remaining four Tier 1 patterns so the org-level destructive set is fully covered:

1. `repo_delete` — companion to `repo_create`. Detects the GitHub CLI repo-deletion invocation.
2. `force_push_main` — detects a `git push` invocation carrying a force flag (either `--force` or `--force-with-lease`) AND a refspec resolving to the protected default branch (`main` per Phase-2 module constant).
3. `branch_delete_main` — detects a refspec deletion form (colon-prefixed empty source) targeting the protected default branch, OR a `git push --delete` (alias `-d`) targeting the protected default branch.
4. `direct_commit_main` — detects a sequence where a commit is followed by a push to the protected default branch with no `gh pr create` invocation between them. This is the trickiest pattern; implementation notes below.

After PR-289b merges, the Tier 1 catalogue covers the five org-level destructive vectors that the daemon cannot reverse. Tier 2 (PR-301..PR-304 in this batch) extends with diff-level patterns later.

## Scope

### 1. Extend `_TIER1_PATTERNS` in `src/daemon/guardrails.py`

The dictionary currently has 1 entry from PR-289a. Add 4 more entries. Each entry: a regex pattern, a human-readable rule description string for dashboard rendering, and any helper logic needed for sequence detection.

For the simple regex patterns (`repo_delete`, `force_push_main`, `branch_delete_main`):

- `repo_delete`: case-insensitive regex matching the literal token sequence `gh` + whitespace + `repo` + whitespace + `delete`, anchored on word boundaries.
- `force_push_main`: case-insensitive regex matching a `git push` invocation that carries either `--force` or `--force-with-lease` AND has a refspec where the destination resolves to the value of the module-level constant `_PROTECTED_DEFAULT_BRANCH` (defined in PR-289a as `"main"`). The regex needs two alternatives because the force flag and the refspec can appear in different orders on the command line. Reuse pattern shapes from `src/mcp/scans.py` `_ANTI_PATTERNS` if a `force_push_main` entry exists there — copy the regex literal with a comment indicating the design parallel; do NOT extract to a shared module.
- `branch_delete_main`: case-insensitive regex matching either (a) a `git push origin :<refspec>` where the refspec destination is the protected default branch, OR (b) a `git push --delete origin <refspec>` (or `-d` short form) where the refspec is the protected default branch.

For the complex sequence pattern (`direct_commit_main`):

This pattern cannot be implemented as a single regex because it requires reasoning over the relative positions of multiple lines. Implementation approach:

```
def _detect_direct_commit_main(stdout: str) -> list[GuardrailViolation]:
    """Detect git commit followed by git push to protected default branch
    without an intervening gh pr create.
    
    Splits stdout by newlines, indexes lines containing "git commit" (excluding
    "--amend" forms unless followed by a force-flagged push, which is already
    caught by force_push_main). For each commit line index, finds the first
    subsequent line matching a git push whose refspec resolves to the
    protected default branch. If found, scans intermediate lines for "gh pr
    create"; if absent, flags the commit line as a violation. Returns at most
    one violation per (commit, push) pair to avoid double-reporting.
    """
```

The function returns `list[GuardrailViolation]`. Integrate into `scan_stdout` so the main entry point calls all simple regex patterns plus this sequence detector and concatenates results.

### 2. Update sort and deduplication in `scan_stdout`

The result list ordering convention from PR-289a was alphabetical-by-key then match-start-index ascending. Maintain the same convention with the 4 new patterns. If the same line of stdout matches both `force_push_main` and `direct_commit_main` (e.g., a force-flagged direct commit-and-push sequence), report both violations — operator triage benefits from seeing both classifications.

## Implementation notes

The `direct_commit_main` detector is the trickiest pattern because it requires reasoning over relative line positions in stdout. Reference algorithm:

```
1. Split stdout into a list of (line_index, line_text) tuples.
2. Find all line_index values where line_text matches the regex for "git commit" (case-insensitive, allows arguments after).
3. Filter out commits that contain "--amend" UNLESS the subsequent push is force-flagged (those are caught by force_push_main).
4. For each remaining commit_index, walk forward through subsequent lines looking for the first match of a "git push" with refspec destination equal to _PROTECTED_DEFAULT_BRANCH.
5. If a matching push is found at push_index, scan the lines between commit_index and push_index (exclusive) for the literal substring "gh pr create".
6. If "gh pr create" is NOT found in the intermediate range, emit a GuardrailViolation with category="direct_commit_main", excerpt taken from the commit line truncated to 200 chars.
7. To avoid double-reporting when multiple commits chain into a single push, only emit one violation per (commit, push) pair: track which commits have already been associated with a flagged push and skip them on subsequent passes.
```

Edge case: an interactive rebase can produce stdout that contains `git commit` lines without an immediately following push. These commits are not violations on their own — the rule fires only when a push to the default branch follows. Walk-forward search has no upper bound on intermediate line count; if no matching push is ever found in the remainder of stdout, the commit is not flagged.

The decision to keep the `repo_create` and `repo_delete` patterns as the simplest base case reflects observation: the most common form of org-level destructive action is the GitHub CLI repository management command, which is a single line of stdout when it executes. Force-pushes and direct commits to the default branch require multi-line context, so the regex catalogue and the sequence detector run in parallel — the simple regex layer catches single-line patterns, the sequence detector catches multi-line patterns.
