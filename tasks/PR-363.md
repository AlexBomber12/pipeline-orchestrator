## Reading order before coding

1. Read this entire spec.
2. Read `src/daemon/handlers/error.py:160-197` - the 3 soft-skip branches for INFRA (line 160-172), RATE_LIMIT (line 174-185), TIMEOUT (line 186-197). Note each block does `self.state.state = PipelineState.IDLE` and `await self.publish_state()` but never clears `error_message`.
3. Read `src/daemon/handlers/error.py:239-242` and `error.py:440-444` - the two existing callsites of `_clear_error_message_on_recovery`. Note the signature and the typical `log_prefix` + `reason` arguments.
4. Read `src/models.py:218-220` - the existing `RepoState.__setattr__` hook that clears `error_message` only when `current_task` becomes None. This is why soft-skip retry paths leak: `current_task` is preserved across the retry attempt.

## Problem

`src/daemon/handlers/error.py` has 3 soft-skip branches that transition the runner back to IDLE for retry without clearing the dashboard's red error banner:

- INFRA error branch at lines 160-172: transition to IDLE, no `_clear_error_message_on_recovery` call.
- RATE_LIMIT error branch at lines 174-185: same.
- TIMEOUT error branch at lines 186-197: same.

In all three cases, the daemon correctly classifies the failure as transient, skips AI diagnosis, and resumes IDLE polling. Functionally healthy. But the banner showing the original error message (e.g. "get_open_prs failed: ... HTTP 504") persists indefinitely until either:

- `current_task` is set to None (which triggers the `RepoState.__setattr__` hook clearing error_message)
- A new genuine ERROR overwrites the message
- Operator restart followed by full IDLE -> DISPATCH cycle (which is NOT sufficient because error_message persists to Redis)

The helper `_clear_error_message_on_recovery` already exists at line 239 (rate-limit-diagnose-skip path) and 440 (successful recovery from AI diagnose path). The helper is correct - this PR just adds the missing 3 callsites.

Production observation 2026-05-06: during PR-266b WATCH cycle, GitHub API returned HTTP 504 Gateway Timeout. Daemon classified as TIMEOUT, transitioned to IDLE for retry, resumed normal WATCH polling. Banner remained visible to operator showing the original 504 error message indefinitely - misleading visibility.

## Solution

Add `await self._clear_error_message_on_recovery(...)` call inside each of the 3 soft-skip branches, before `self.state.state = PipelineState.IDLE`, mirroring the existing pattern at line 239 (rate-limit-diagnose-skip path).

### Concrete code change

In `src/daemon/handlers/error.py`, current code at INFRA branch:

```python
if _is_infra_error(context):
    self._error_skip_context = None
    self._error_skip_policy.reset(self)
    self._error_skip_active = False
    truncated = context if len(context) <= 200 else context[:197] + "..."
    self.log_event(
        f"[ERROR] Infra error detected, skipping AI diagnosis and "
        f"transitioning to IDLE for retry: {truncated}."
    )
    await _clear_cause_for_retry()
    self.state.state = PipelineState.IDLE
    await self.publish_state()
    return
```

Becomes:

```python
if _is_infra_error(context):
    self._error_skip_context = None
    self._error_skip_policy.reset(self)
    self._error_skip_active = False
    truncated = context if len(context) <= 200 else context[:197] + "..."
    self.log_event(
        f"[ERROR] Infra error detected, skipping AI diagnosis and "
        f"transitioning to IDLE for retry: {truncated}."
    )
    await _clear_cause_for_retry()
    self.state.state = PipelineState.IDLE
    await self._clear_error_message_on_recovery(
        log_prefix="[ERROR]",
        reason="infra error soft-skip to IDLE",
    )
    await self.publish_state()
    return
```

Same pattern for RATE_LIMIT branch (lines 174-185) with reason `"rate-limit soft-skip to IDLE"` and TIMEOUT branch (lines 186-197) with reason `"timeout soft-skip to IDLE"`.

### Position of the call

Place `_clear_error_message_on_recovery` AFTER setting `state.state = PipelineState.IDLE` and BEFORE `publish_state`. Reason: the helper may itself trigger a publish (depending on implementation - check the helper body), and the explicit `publish_state` at the end provides the canonical post-recovery snapshot. The order matches the existing callsite at line 239-242.

## Threat model

**Threat addressed**: stale banner misleads operator. Operator may believe daemon is stuck on the original error when it has actually recovered. Operator may take unnecessary action (restart, manual investigation) based on misleading UI.

**Other layers protecting**: none. The banner is the only UI surface showing the most recent error message.

**Why this layer needed**: matches the documented intent of `_clear_error_message_on_recovery` (clear banner on recovery transition). The 3 soft-skip branches are recovery transitions by definition.

### Caller audit

`_clear_error_message_on_recovery` is called from 2 sites today: error.py:239 (rate-limit-diagnose-skip) and error.py:440 (successful diagnose recovery). This PR adds 3 more sites. Total 5 callsites after merge. All in `handle_error` body. Consistent log_prefix "[ERROR]" across all callsites.

The helper itself: assumed safe to call multiple times in same handler invocation because the existing rate-limit-diagnose-skip path at line 228-244 already does `reset + skip + log + publish_state` then `_clear_error_message_on_recovery + publish_state` in sequence. No new concurrency concerns.

## Out of scope

- Changing `_clear_error_message_on_recovery` signature or behavior. Bug is purely missing callsites.
- Modifying the `RepoState.__setattr__` hook to also clear on state transitions. Current per-current_task clearing is correct for the disposal case; adding cross-state-transition clearing would over-trigger.
- Changing the dashboard banner template logic. The banner correctly reads `state.error_message`; fixing the source-of-truth fixes the display.

## Success signal

Post-call, state.error_message is None AND state.state == IDLE AND log event contains "infra error soft-skip to IDLE". On production: next time daemon hits transient infra/rate-limit/timeout, the red banner clears within one publish_state cycle (next dashboard 5s poll) and operator sees a clean dashboard.
