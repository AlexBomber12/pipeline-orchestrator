# PR-263: RepoState.current_queue in-memory queue snapshot

Branch: pr-263-repostate-current-queue
- Type: refactor
- Complexity: low
- Depends on: none
- Priority: 2
- Coder: codex

## Problem

`tasks/QUEUE.md` has been a derived projection from `tasks/PR-*.md` headers since PR-181 untracked it from git. After that change, four production code paths still read it from disk: idle handler, merge handler, recovery handler, and the web tasks panel route. Each read path adds a window where the on-disk projection can drift from in-memory truth (concurrent IDLE + recovery, dirty-tree races on daemon restart, manual operator edits via SFTP).

Sprint 15a #6 eliminates QUEUE.md entirely. The first preparatory step is moving the queue model into runtime state on `RepoState` so subsequent PRs can migrate read sites onto it before any disk-write paths are removed. This PR adds the field and the populator; later PRs (PR-264 web migration, PR-265 cancellation services migration, PR-266 recovery refactor) wire consumers to read from it.

## Scope

Three deliverables:

1. New field `current_queue: list[QueueTask] | None = None` on `RepoState` (the per-repo Pydantic model that already lives in Redis and tracks pipeline state).
2. Idle handler populator: at the end of `_select_next_task_or_attach`, after the DAG selection completes successfully, write `self.state.current_queue = list(self._idle_dag_tasks)` (or the legacy-merged list when applicable). The persisted snapshot is the same data already used to render QUEUE.md text.
3. Redis serialization: extend the existing `_serialize_repo_state` / `_deserialize_repo_state` helpers in `src/daemon/main.py` to round-trip the new field as a JSON list under the existing repo state key. No new Redis key, no schema version bump (Pydantic handles the additive change cleanly via the field default).

This PR is preparatory: no consumer reads `RepoState.current_queue` yet. PRs 264, 265, 266 add readers. The on-disk QUEUE.md file continues to be written by the existing code paths in the same cycle, so behavior is unchanged from the operator's perspective.

## Behavior

After this PR ships, every IDLE cycle that completes DAG selection writes a fresh snapshot to `RepoState.current_queue` and persists it to Redis as part of the existing state-write transaction. On daemon restart, `recover_state` rehydrates the snapshot along with the rest of `RepoState`. The snapshot is `None` only when the daemon has never reached IDLE for that repo (fresh clone, scaffolding interrupted).

The snapshot is a `list[QueueTask]` with `pr_id`, `title`, `branch`, `status`, `task_file`, `depends_on`, and `priority` fields populated. Status reflects the derivation result from PR-262 (which already incorporates the GH-API done-check). Order is deterministic: priority ascending then PR number ascending, matching `get_eligible_tasks` ordering.

## Implementation notes

The `current_queue: list[QueueTask] | None = None` typing is intentional. `None` sentinel distinguishes "daemon has never reached IDLE for this repo" from "queue is empty" (`[]`). PR-264's web fragment renders the `None` case as a loading indicator; the `[]` case as "All tasks complete". Without the sentinel, those two operator-visible states collapse.

The snapshot is written even when no task is dispatched (idle cycle ran but eligible was empty). This keeps the dashboard reflective of the live queue rather than stuck at the last-dispatched cycle's snapshot. The cost is one extra Redis write per cycle per repo, which is negligible against the existing per-cycle write traffic.

The serialization uses Pydantic's `model_dump(mode="json")` so the field travels over Redis as JSON-serializable scalar lists. No custom encoder, no schema migration. Deserialization via `model_validate` round-trips cleanly because `QueueTask` is itself a Pydantic model.

The `_set_queue_progress` call in idle.py already uses the same `queue_tasks` list. Placing the snapshot write right after it guarantees the two sources of truth (progress counter and detail list) cannot disagree across the two existing read paths.

## Success criteria

1. `RepoState().current_queue is None` for a freshly constructed instance.
2. After a successful IDLE cycle on a 5-task repo, `runner.state.current_queue` is a list of 5 QueueTask in priority+pr_id order.
3. Daemon restart preserves the snapshot through Redis round-trip; the rehydrated `RepoState.current_queue` equals the pre-restart value.
4. IDLE cycles that error out before DAG selection completes leave `current_queue` unchanged from the prior successful cycle.
5. No existing test fails (regression-free preparatory PR). No QUEUE.md disk write paths modified.
6. CI green on PR branch.
