# PR-267: Drop QUEUE.md write paths from idle and merge handlers

Branch: pr-267-drop-queue-md-writes
- Type: refactor
- Complexity: medium
- Depends on: PR-264, PR-265, PR-266c
- Priority: 2
- Coder: claude

## Problem

After PR-264, PR-265, and PR-266 land, every read site for `tasks/QUEUE.md` consults `RepoState.current_queue` first and falls back to disk only when the snapshot is None. The fallback path was preserved in those PRs for independent revertability. With three reader migrations now stable, the disk-write paths in `_write_generated_queue_md` (idle handler) and `_mark_queue_done` (merge handler) no longer have a reason to exist — nothing reads what they write.

This PR removes the disk writes, removes the now-dead fallback paths in PR-264 and PR-265's consumers (PR-266's recovery already does not fall back), and removes `_origin_queue_md_tracked` plus `_parse_base_queue` from `src/daemon/repo_ops.py`. After this PR ships, the daemon never writes `tasks/QUEUE.md` and never reads it during recovery or status surfaces.

## Scope

Six deliverables:

1. Remove `_write_generated_queue_md` from idle handler and its call site at the end of `_select_next_task_or_attach`.
2. Remove `_mark_queue_done` body (keep the function as no-op shim for one release cycle to absorb any straggling test references; mark deprecation warning) OR remove it entirely with merge.py call site updated. See implementation notes for the choice.
3. Remove the `parse_queue` disk fallback from `list_repo_tasks`, `_resolve_repo_task_path`, and the `/api/repo/{name}/queue` endpoint added in PR-264. Snapshot becomes the only source.
4. Remove the `parse_queue` disk fallback from `build_repo_task_nodes` (PR-265's consumer). Snapshot becomes the only source.
5. Delete `_origin_queue_md_tracked` and `_parse_base_queue` from `src/daemon/repo_ops.py` plus their test fixtures. PR-266 deprecated them; this PR removes them.
6. Remove the `_legacy_tracked_queue_md_logged` flag and the related ghost-detection helpers in idle handler that only existed to handle the legacy tracked-QUEUE.md case.

## Behavior

After this PR ships:

- `tasks/QUEUE.md` is never written by the daemon. If an operator manually creates one on disk, the daemon does not read it. The file is functionally inert from the daemon's perspective.
- `list_repo_tasks` HTMX fragment renders only from `RepoState.current_queue`. If the snapshot is None (daemon hasn't reached IDLE), the fragment shows a "Queue not yet computed; daemon syncing." 503 message.
- `/api/repo/{name}/queue` endpoint always returns `source: "snapshot"`. The `source` field is retained for forward compatibility but the `"fallback_disk"` value is no longer reachable.
- Recovery (PR-266) was already snapshot-or-headers-only; this PR does not modify recovery further.
- The dashboard cancellation surface (PR-265's consumers) renders only from snapshot.

The cleanup is symmetric: every place that used to read disk QUEUE.md now reads `RepoState.current_queue`, and the disk file is no longer maintained.

## Implementation notes

The decision between "delete `_mark_queue_done` entirely" vs "make it a no-op shim" comes down to caller count. A grep shows only `merge.py:240` calls it. Deleting it entirely is cleaner; the call site becomes an in-place `state.current_queue` update via list comprehension. Tests update accordingly.

`_generate_queue_md` (the function that renders QUEUE.md text from headers) might still be useful as a dump endpoint for operators or for export-to-disk debugging. Keep it as a pure function exported from `src/daemon/handlers/idle.py` (or move to a utilities module). The point of removal is the *write to disk*, not the *render to string*. Confirm no caller invokes it for side effects beyond the deleted `_write_generated_queue_md`.

Rolling back this PR is non-trivial because PR-264, PR-265, PR-266 are dependencies. If a regression surfaces, the fastest revert path is to add the disk-write back (restore `_write_generated_queue_md` body) without unrolling the read-side migrations — the readers are already snapshot-first with no fallback, so adding the disk write back would not re-introduce drift, just unnecessary work. Document this revert path in the PR description.
