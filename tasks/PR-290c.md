## Threat model

**Threat addressed:** Two distinct attack surfaces:
1. **Branch protection bypass**: a coder modifies `.github/branch-protection.yml` (or similar metadata used by repo settings tools like Probot/settings) to weaken branch rules, enabling future force-push or unreviewed merges.
2. **Supply-chain takeover**: a coder adds `uses: <actor>/<action>@<branch-ref>` to a workflow YAML, where the ref is mutable (a branch name like `main` or `master` or `HEAD`) instead of pinned (semver tag or 40-char commit SHA). A malicious upstream maintainer can later change the action behavior; pinned references are immutable.

**Layers that DO NOT catch this threat:** Same as PR-290a/b — pre-push hook, stdout scan, and MCP-validate operate on different signals.

**Why this layer is needed:** Branch protection metadata changes look like ordinary YAML edits and would never appear in stdout. Action references with mutable refs look syntactically valid and pass linters.

## Problem

PR-290b shipped workflow YAML patterns. PR-290c adds two more patterns that target governance and supply-chain attacks. Both share the diff-section walking pattern (matching specific file paths and content) but operate on different attack categories.

## Scope

1. **Add `branch_protection_modification` entry** to `_DIFF_PATTERNS`:

   ```python
   "branch_protection_modification": re.compile(
       # Match diff sections that modify or delete branch protection
       # metadata files. Files commonly used: .github/branch-protection.yml,
       # .github/settings.yml (probot-settings), .github/branch_protection*.
       # Modification is signaled by `+++ b/<path>` line; deletion by
       # `+++ /dev/null` paired with `--- a/<path>`. Either form flags.
       r"(?m)^\+\+\+[ \t]+(?:"
       r"b/\.github/(?:branch[-_]protection[^ \r\n]*\.ya?ml"
       r"|settings\.ya?ml)"
       r"|/dev/null"
       r")",
       re.IGNORECASE,
   ),
   ```

   This pattern flags any diff section where `+++ b/.github/branch-protection*.yml` or `+++ b/.github/settings.yml` appears (modification of these files), OR where `+++ /dev/null` appears immediately after a `--- a/.github/branch-protection*` or settings file (deletion). The match deliberately scans the `+++` line because modification AND deletion of these files are equally suspicious.

   Note: this regex flags the `+++ /dev/null` deletion marker on its own line. To avoid false-positive matches on `/dev/null` deletions of OTHER files (not branch-protection-related), we use the simplification: in PR-290c the regex flags any `+++ /dev/null` line — but PR-290b already flags workflow_destruction for `.github/workflows/`. The overlap is acceptable: a coder deleting `.github/branch-protection.yml` will get `branch_protection_modification` flag. The coder deleting `docs/foo.txt` does NOT get either flag (because `--- a/docs/foo.txt` is NOT in `.github/workflows/`).

   Actually, to remove the ambiguity, the regex should be stricter. Use a 2-line sequence pattern like `workflow_destruction`:

   ```python
   "branch_protection_modification": re.compile(
       r"(?m)^---[ \t]+a/\.github/(?:"
       r"branch[-_]protection[^ \r\n]*\.ya?ml"
       r"|settings\.ya?ml"
       r")[ \t]*\r?\n"
       r"\+\+\+[ \t]+(?:b/\.github/(?:branch[-_]protection[^ \r\n]*\.ya?ml"
       r"|settings\.ya?ml)|/dev/null)",
       re.IGNORECASE,
   ),
   ```

   This matches a `--- a/.github/branch-protection*.yml` (or `settings.yml`) header followed by either `+++ b/.github/<same-file>` (modification) or `+++ /dev/null` (deletion). False-positive risk minimized; flagging covers both attack vectors.

2. **Add `dangerous_action_external_install` entry** to `_DIFF_PATTERNS`:

   ```python
   "dangerous_action_external_install": re.compile(
       # Match `+`-prefixed lines adding `uses: <owner>/<action>@<ref>`.
       # The full validation (ref is unpinned) is done in a helper
       # function because the regex captures the ref but cannot
       # conditionally accept it.
       r"(?m)^\+[ \t]*-?[ \t]*uses:[ \t]+"
       r"(?P<repo>[\w.-]+/[\w./-]+)"
       r"@(?P<ref>[^\s\r\n]+)",
       re.IGNORECASE,
   ),
   ```

   The regex captures `<repo>@<ref>` and matches every action `uses:` line. Add a post-match filter helper:

   ```python
   _PINNED_ACTION_REF_RE = re.compile(
       # Accept: SemVer tags (v1, v1.2, v1.2.3) and 40-char commit SHAs.
       r"^(?:v\d+(?:\.\d+){0,2}|[0-9a-f]{40})$",
       re.IGNORECASE,
   )

   def _action_ref_is_pinned(ref: str) -> bool:
       """Return True if `ref` is a semver tag or 40-char commit SHA."""
       return bool(_PINNED_ACTION_REF_RE.match(ref))
   ```

   The dispatcher logic in `scan_pr_diff` (existing from PR-290a) iterates `_DIFF_PATTERNS` mechanically. To inject the pinned-ref filter, override per-category handling in `scan_pr_diff`:

   ```python
   def scan_pr_diff(diff_text: str) -> list[GuardrailViolation]:
       violations: list[GuardrailViolation] = []
       for category in sorted(_DIFF_PATTERNS):
           pattern = _DIFF_PATTERNS[category]
           for match in pattern.finditer(diff_text):
               # Per-category post-filter: dangerous_action_external_install
               # only flags when the ref is NOT a pinned form.
               if category == "dangerous_action_external_install":
                   ref = match.group("ref")
                   if _action_ref_is_pinned(ref):
                       continue
               violations.append(
                   GuardrailViolation(
                       tier=1,
                       category=category,
                       excerpt=_line_excerpt(diff_text, match.start(), match.end()),
                       rule=_DIFF_RULES[category],
                   )
               )
       return violations
   ```

   This deviates from the pure dispatcher pattern from PR-290a (which had no per-category post-filter). Operator may decide later to refactor into a structured catalogue with optional filter callbacks; for now the explicit branch is acceptable for one pattern.
