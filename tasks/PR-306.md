# PR-306: Operator override dashboard UI — guardrail-flagged PR panel with approve and reject controls

Branch: pr-306-operator-override-dashboard-ui
- Type: feature
- Complexity: medium
- Depends on: PR-305
- Priority: 1
- Coder: codex

## Problem

PR-305 ships the backend endpoint POST /repos/{name}/guardrail/{pr_id}/decision and helper `list_pending_guardrail_decisions`. Operator currently has no UI surface to invoke the endpoint — they would need to construct the POST request manually via curl or the browser dev tools. PR-306 adds the dashboard panel that surfaces flagged PRs and provides Approve/Reject buttons.

The panel shows on the per-repo detail page (`/repos/{name}`) when at least one guardrail-flagged PR is in the pending decision state for that repo. Each entry shows:
- PR identifier (e.g., `PR-296`) linked to the GitHub PR URL
- Guardrail rule that fired (e.g., "large_diff_threshold")
- Excerpt of the violation (e.g., "+1800 LOC across 35 files")
- Recorded timestamp (operator-friendly relative format: "5 minutes ago")
- Two buttons: green Approve + red Reject

The panel positions prominently near the top of the per-repo page (after repo header, before existing event log) so flagged PRs do not get lost in the event stream.

## Scope

### 1. Pending decisions data fetched server-side at template render

In the per-repo route handler at `src/web/routes/dashboard.py` (or wherever `/repos/{name}` route is registered), call `list_pending_guardrail_decisions(redis_client, repo=name)` and pass the resulting list to the template context as `guardrail_pending: list[GuardrailPending]`. Empty list when nothing pending. Do NOT fetch via JavaScript on the client — server-side render avoids flash of empty state.

### 2. New template partial `_guardrail_panel.html`

Path: `src/web/templates/components/_guardrail_panel.html`. Renders only when `guardrail_pending` is non-empty. Section heading "Pending guardrail decisions" with count badge. Each entry rendered as a row with the four data fields plus the two buttons.

Buttons use HTMX:

```html
<button
    hx-post="/repos/{{ repo_name }}/guardrail/{{ entry.pr_id }}/decision"
    hx-vals='{"decision": "approve"}'
    hx-confirm="Approve guardrail violation for {{ entry.pr_id }}? PR will proceed to MERGE."
    hx-target="closest .guardrail-row"
    hx-swap="outerHTML"
    class="approve-btn">
    Approve
</button>
<button
    hx-post="/repos/{{ repo_name }}/guardrail/{{ entry.pr_id }}/decision"
    hx-vals='{"decision": "reject"}'
    hx-confirm="Reject guardrail violation for {{ entry.pr_id }}? PR will be closed and task marked ERROR."
    hx-target="closest .guardrail-row"
    hx-swap="outerHTML"
    class="reject-btn">
    Reject
</button>
```

Both buttons use `hx-confirm` to prevent accidental clicks. On 204 success, the row is replaced with empty content (HTMX `outerHTML` swap with empty body). Subsequent dashboard refresh removes the entry from the pending list.

### 3. Render in per-repo template

Add `{% include "components/_guardrail_panel.html" %}` to `src/web/templates/repo_summary.html` (or whatever the per-repo template is named — find via grep). Position: after repo header (state badge + sprint progress), before event log. Visually distinct background to draw operator attention (yellow or amber alert color).

### 4. Empty state handling

When `guardrail_pending` is empty, the partial renders nothing (top-level `{% if guardrail_pending %}` guard). Page layout unchanged when no pending decisions.

### 5. CSS styling

Add minimal CSS (or Tailwind classes if that is the styling system) for:
- Panel container: amber/yellow background with darker border
- Approve button: green background, white text
- Reject button: red background, white text
- Row layout: PR ID + rule on left, excerpt center-truncated, buttons right-aligned

If Tailwind is in use (per existing repo_summary.html patterns), use existing utility classes; do not introduce new CSS files.

### 6. Dashboard top-level summary integration (optional)

If `src/web/templates/dashboard.html` (the multi-repo top-level page) shows a summary of repo health, add a small "N pending guardrail decisions" badge per repo card. Implement only if the existing pattern supports it (find via grep for similar badges). If not, defer to follow-up PR — main per-repo panel is sufficient for v1.

## Implementation notes

The panel is **operator-action surface**, not a status display. It should disappear immediately after action is taken (HTMX outerHTML swap) so operator gets visceral feedback. The full dashboard refresh on next page load reconciles state with backend.

The hx-confirm dialog for approve includes the consequence ("PR will proceed to MERGE") so operator does not click expecting a different outcome. Similarly for reject ("task marked ERROR").

The 200-char excerpt truncation matches the GuardrailViolation.excerpt limit from PR-289 design. If backend returns full violation text, frontend truncates display only — full text remains in cancellation cause record for audit.

The amber/yellow color choice signals "needs attention but not destructive" — matching the operator-decision UX of "you decide, we hold". Red would imply danger; green would imply safe-to-ignore. Both wrong for guardrail pending state.

Estimated diff size: ~150-180 LOC. Of that, ~80 LoC template partial, ~30 LoC route handler integration, ~20 LoC route registration, ~50-80 LoC tests.

The Coder: codex assignment is appropriate. Mostly mechanical template work. HTMX patterns established in earlier PRs (PR-283 Retry button, PR-247 Recover button before Phase 2 removed it).
