## Problem

PR-311a built the backup primitive in isolation. The daemon needs to invoke it periodically. The natural place is the IDLE handler, where existing periodic tasks (e.g., PR-300 main_commit_audit) already use a cycle-counter pattern. PR-311b adds an analogous block.

Critical: backup failures must not crash the daemon. Bundle creation is best-effort; failures are logged but daemon continues.

Add the block:

```python
self._git_bundle_backup_counter = (
    getattr(self, "_git_bundle_backup_counter", 0) + 1
)
config = self.app_config.daemon
if config.git_bundle_backup_enabled and config.git_bundle_backup_dir:
    # Convert hours to approximate cycles based on poll interval
    cycles_per_hour = max(1, 3600 // max(1, config.poll_interval_sec))
    interval_cycles = config.git_bundle_backup_interval_hours * cycles_per_hour
    if self._git_bundle_backup_counter >= interval_cycles:
        self._git_bundle_backup_counter = 0
        try:
            bundle_path = await create_repo_bundle(
                repo_path=self.repo_path,
                repo_name=self.name,
                backup_dir=config.git_bundle_backup_dir,
            )
        except Exception as exc:
            self.log_event(f"[BACKUP] bundle creation crashed: {exc}")
            bundle_path = None
        if bundle_path:
            self.log_event(
                f"[BACKUP] git bundle created: {bundle_path.name}"
            )
            try:
                removed = await prune_old_bundles(
                    backup_dir=config.git_bundle_backup_dir,
                    repo_name=self.name,
                    daily_retention=config.git_bundle_backup_daily_retention,
                    weekly_retention=config.git_bundle_backup_weekly_retention,
                )
                if removed > 0:
                    self.log_event(
                        f"[BACKUP] pruned {removed} old bundles"
                    )
            except Exception as exc:
                self.log_event(f"[BACKUP] prune failed: {exc}")
        else:
            self.log_event(
                "[BACKUP] git bundle failed; will retry next cycle"
            )
```

The counter is per-runner-instance (resets on daemon restart). After a restart, the first bundle fires after `interval_cycles` cycles, not immediately. Acceptable trade-off — operators rarely restart, and a missed window matters little for backup integrity.

If `poll_interval_sec` is unusually large (e.g., 120 seconds), `cycles_per_hour` clamps to `max(1, ...)` so the math does not divide by zero. If unusually small, the multiplication still yields a sensible cycle count.

## Risk notes (for PR description)

The cycle-counter pattern matches PR-300 main_commit_audit. Operators familiar with that pattern will find this immediately readable. A future refactor could unify the two counters into a shared scheduler primitive — out of scope here.

The counter resets on daemon restart. If operator restarts the daemon every day at the same time, backups might never fire. Mitigation: in PR-311a (already shipped), `git_bundle_backup_interval_hours` defaults to 24; operator who restarts daily should consider setting interval to 12 or lower, or scheduling restarts away from the backup window. Document in operator setup docs (Sprint 17 Documentation Sprint scope).

`create_repo_bundle` runs `git bundle create --all` which can take seconds-to-minutes on a large repo. Inside `asyncio.to_thread` (from PR-311a) so the event loop stays responsive, but the IDLE handler will not pick up the next task until backup completes. Backup happens during IDLE state where there is no active task to delay — acceptable.

If `poll_interval_sec` is misconfigured (e.g., 1 second), `cycles_per_hour = 3600` and `interval_cycles = 3600 * 24 = 86400` cycles for daily backup. Each cycle increments the counter; reaching 86400 takes 24 hours of continuous polling. The math is correct but operators with very short poll intervals should be aware of the counter magnitude.
