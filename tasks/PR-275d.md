# PR-275d: MCP cross-repo intent detection — bare cross-org owner/repo mention informational scan

Branch: pr-275d-mcp-bare-owner-repo-mention
- Type: feature
- Complexity: medium
- Depends on: PR-275c
- Priority: 3
- Coder: codex

## Problem

PR-275a/b/c cover literal command forms (`gh repo create owner/name`, `gh repo delete owner/name`, `gh repo clone other-org/foo` etc.) at spec-validation time. A residual gap remains: spec text containing bare `owner/repo` mentions WITHOUT a leading `gh` command. Examples that historically led to OBS-BT incidents:
- Task body: `Implement deployment for homelab-monitoring/dashboard service` (mentions a different repo's name in deploy context, may suggest cross-repo intent)
- Task body: `Update the schema in shared-org/data-models to match` (suggests editing another repo)

These are NOT executable commands. They are natural-language hints that the coder may misinterpret as cross-repo work even though the daemon's dispatched task is for a single repo. Detecting them at spec-validation time would catch operator-misuploaded specs before any coder dispatch occurs.

This PR is intentionally LOW PRIORITY because the trade-off is unfavorable in the regex domain: bare `owner/repo` patterns appear constantly in legitimate task prose:
- File paths (`src/utils/repo.py` matches with a stretch — actually no, slash count differs)
- Documentation links (`see github.com/python/cpython for context`)
- Dependency references (`requirements.txt: pydantic/pydantic`)
- Version pins (`upgrade to 2.5.x/lts`)

A regex-based "bare cross-org mention" detector will produce many false positives. PR-275d explicitly accepts this and emits violations as INFORMATIONAL severity rather than BLOCKING. Operator reviews informational findings during dispatch decision but daemon does not refuse to dispatch on them.

## Decision: ship or skip

This spec is drafted in case operator chooses to ship it, but the **default recommendation is SKIP** unless real production data after PR-275a/b/c plus PR-276/277 deployment shows that bare-mention cross-repo intent actually leads to incidents that other layers miss. If PR-275a/b/c plus PR-276/277 (stdout monitoring) plus PR-277 (diff scan) collectively catch all observed incidents, PR-275d adds maintenance cost without proven benefit.

If operator decides to ship: this spec is the reference. Otherwise, this spec sits in the backlog and is referenced by Sprint 15b retrospective.

## Scope

Single deliverable: extend `_ANTI_PATTERNS` with one informational pattern detecting bare `<owner>/<repo>` slug mentions where owner is not the daemon's configured owner.

Pattern: `cross_repo_bare_owner_repo_mention`
- Regex: `(?<![/\w.-])([a-zA-Z][\w.-]*)/([\w.-]+)(?![\w./-])`
  - Lookbehind ensures we don't match within a longer path like `src/foo/bar`
  - First captured group is the owner
  - Second captured group is the repo name
  - Lookahead ensures we don't continue into a longer path
- Predicate (using PR-275c's predicate infrastructure):
  - Captured owner must NOT equal `daemon_owner` (case-insensitive)
  - Captured owner must NOT be in a configurable allowlist of common-prose owners (default: `python`, `pydantic`, `microsoft`, `google`, `apache`, `mozilla`, `golang`, `rust-lang`, `numpy`, `pandas`, `flask`, `django`, `fastapi`, `pytorch` — major OSS orgs whose names appear in dependency/doc context)
  - The match must NOT be inside a markdown URL like `https://github.com/owner/repo` or `[label](https://...)` — preceded by `://` or `](` chars in the same word
  - The match must NOT be in a fenced code block or inline backticks (PR-275a helpers)
  - The match must NOT be on a line starting with `#` (markdown heading) when followed by repo-naming context (less aggressive heuristic)
- Severity: `INFORMATIONAL` rather than `BLOCKING`
- Rule message: `"Bare owner/repo mention may indicate cross-repo intent. Operator review recommended. Daemon will dispatch unless operator marks blocked."`

This requires extending `ConflictViolation` dataclass to carry a severity field. Existing violations get `severity="BLOCKING"` (current behavior) and the new pattern gets `severity="INFORMATIONAL"`.

`validate_task_spec` MCP tool returns `True` (valid) when only INFORMATIONAL violations present, but includes them in the output for operator visibility.

## Behavior

Given `daemon_owner = "AlexBomber12"`:

Triggers INFORMATIONAL violation:
- `Implement deployment for homelab-monitoring/dashboard` (looks like cross-repo)
- `Update schema in shared-org/data-models` (looks like cross-repo)
- `Sync changes from upstream-org/library to our fork` (cross-org reference)

Does NOT trigger:
- `requirements: pydantic/pydantic >=2.0` (allowlist)
- `see github.com/python/cpython for upstream behavior` (URL-context suppression + allowlist)
- `[python/cpython#1234](https://github.com/python/cpython/issues/1234)` (URL-context suppression)
- `src/foo/bar.py` (path, not slug — lookbehind prevents match because `/foo` preceded by `c`)
- `2.5.x/lts` (lookbehind allows but `2.5.x` is not a valid owner under regex `[a-zA-Z][\w.-]*` because starts with digit)
- ` ```\nsome/text\n``` ` (fenced)
- `AlexBomber12/megaraid-dashboard` (same daemon owner, suppressed by predicate)

## Implementation notes

This PR's value depends entirely on whether real incidents bypass PR-275a/b/c and PR-276/277. The defense-in-depth math:
- Layer 1 (PR-275a/b/c): catches literal commands at spec-validation time
- Layer 2 (PR-276): catches actual coder-executed commands at stdout monitoring time
- Layer 3 (PR-277): catches what survives stdout (e.g., silent commands) at post-push diff scan time
- Layer 4 (PR-275d, this PR): catches natural-language hints at spec-validation time

Layer 4 fires earliest in the pipeline (before dispatch), which is the strongest position. But its signal-to-noise ratio is the weakest because natural language is ambiguous. INFORMATIONAL severity is the compromise: catch potential issues without blocking valid work.

The allowlist mechanism is deliberately minimal — a frozenset of well-known orgs that appear constantly in dependency/doc prose. The operator-extensible env var allows fine-tuning per deployment without code changes. Operators in highly-constrained environments (single org, no third-party deps in spec text) can leave the allowlist default; operators with broader needs add their domain-specific orgs.

The severity-bifurcation in `ConflictViolation` is forward-compatible. Future patterns at varying severity (e.g., a CRITICAL severity for known credential patterns from PR-289) plug into the same field.

If skipped: this spec sits in `tasks/PR-275d.md` as a documented design ready for ship if needed. The dataclass extension to severity field is also a prerequisite for some Tier 2 work, so the prep work is not wasted even if the pattern itself is dropped.
