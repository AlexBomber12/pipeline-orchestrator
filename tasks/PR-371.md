# PR-371: Catch gh label create "already exists" error specifically

- Type: bugfix
- Complexity: low
- Depends on: none
- Priority: 3
- Coder: any

## Reading order before coding

1. Read this entire spec.
2. Read `src/daemon/fix_escalation.py:67-95` - `ensure_escalated_label`. Note the generic `except Exception` that swallows all errors including "already exists" with an opaque "skipped" log.
3. Read `src/daemon/quarantine.py` (added by PR-366) - if PR-366 is merged first, similar pattern there to be updated. If not merged yet, this PR may apply to fix_escalation only.

## Problem

`gh label create escalated` raises non-zero exit 1 when the label already exists in the repo. Current code at `src/daemon/fix_escalation.py:67-95` catches the generic exception and logs:

```
[FIX] {prefix} label create skipped: {exc}.
```

This log entry is fired EVERY escalation cycle (~1 per stuck repo) even when the label has been present in the repo for months. Operator sees recurring "skipped" entries that look like errors but are actually expected idempotent no-ops.

GitHub's actual error message is:

```
label with name "escalated" already exists; use --force to update its color and description
```

Other label-create failures (auth error, network error, GitHub down, repo deleted) are real problems that should remain visible. Squashing them all under a single "skipped" log loses signal.

## Solution

Detect "already exists" specifically and downgrade to a debug-level (non-event-log) message OR suppress entirely. Other failures continue to fire visible log_event.

### Implementation

In `ensure_escalated_label` at fix_escalation.py:67-83:

```python
try:
    gh_runner.run_gh(
        [
            "label",
            "create",
            "escalated",
            "--color",
            "B60205",
            "--description",
            "Daemon escalated, manual review required",
        ],
        repo=runner.owner_repo,
    )
except Exception as exc:
    exc_str = str(exc)
    if "already exists" in exc_str.lower():
        # Expected idempotent no-op. Suppress event log noise.
        pass
    else:
        runner.log_event(
            f"[FIX] {label_create_log_prefix} label create failed: {exc}."
        )
```

Same pattern in `apply_canceled_label` at the same file (line 98+) if it has the same shape.

If PR-366 (quarantine) is merged first, apply same pattern to `apply_quarantine_label_for_violation` at src/daemon/quarantine.py.

### Why suppress rather than info-log

The existing event log is a 100-entry circular buffer optimized for operator-actionable signals. Pure idempotent no-ops do not deserve a slot. If operator wants to verify the label apply happened, `gh label list` is the canonical source.

### Why not check existence before create

Alternative: call `gh label list` and skip the create call entirely if label present. Rejected: extra API call per escalation cycle, vs. one expected-fail call. The "ask forgiveness" pattern is cheaper.

### Why not use --force always

Alternative: `gh label create --force escalated ...` is idempotent (updates color/description if label exists). Rejected: --force changes label color/description on every call which is unwanted side effect (operator may have customized the label color).

## Threat model

**Threat addressed**: log noise from expected idempotent no-ops dilutes operator's signal density. Every escalation cycle produces a "skipped" entry that looks alarming but is benign.

**Other layers protecting**: none for this specific noise. The event log is the only operator-facing surface for this.

**Why this layer needed**: cleanliness of the event log is the most direct operator-experience improvement. This PR removes ~1-2 misleading entries per stuck repo per cycle.

## Out of scope

- Removing the label apply step error log. That error is real; keep it visible.
- Pre-create label-list check. Costlier than the current "ask forgiveness" pattern.
- --force flag adoption. Wrong semantic for idempotent-existence check.

## Success signal

On test fixture: escalation cycle on a repo where `escalated` label already exists. NO event log entry for the create step. Existing apply-label call proceeds. On production: event log no longer shows "[FIX] label create skipped: ..." entries on repeated escalations.
