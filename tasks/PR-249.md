# PR-249: WATCH circuit breaker - cap retrigger-after-HUNG cycles at N=3

Branch: pr-249-watch-circuit-breaker
- Type: bugfix
- Complexity: low
- Depends on: none
- Priority: 1
- Coder: claude

## Problem

OBS-BL from `docs/roadmap.md`. Verified 2026-05-02 production: PR-227c cycled WATCH→HUNG→WATCH 4+ times over 4 hours. Mechanism: WATCH timeout 20m fires → `_escalate_to_hung` → `handle_hung` posts `@codex review` retrigger → resets WATCH counter. If codex never produces a fresh review (silent drop, infrastructure issue, model unavailable), WATCH eventually times out again → loop.

PR-164's `BoundedRecoveryPolicy` exists for FIX iteration cap and FIX no-push cap but no equivalent guards the WATCH→HUNG→WATCH retrigger cycle. Daemon spends operator's API budget without making progress.

Fix: add a `watch_retrigger_count` field and cap. After N retriggers (default N=3) with no fresh review activity, transition to ESCALATED state (terminal until operator action) instead of resetting WATCH. Cause preserved per OBS-BE for dashboard surfacing.

## Scope

Three deliverables:

1. Add `watch_retrigger_count: int = 0` field to `PRInfo` model.
2. Increment counter in `handle_hung` immediately after a successful retrigger post; reset to 0 on detected fresh review activity (codex EYES reaction or new comment).
3. After counter hits cap (default 3, configurable via `daemon.watch_retrigger_cap` in `config.yml`), instead of resetting WATCH, transition to a terminal ESCALATED-equivalent state — for v1 keep it as HUNG with `is_escalated=True` and `_apply_escalated_label`, mirroring the existing FIX iteration cap escalation. Cancellation policy v1 (PR-255) will integrate ESCALATED proper.

Tests covering: cap reached → escalated, fresh review activity → counter resets, cap configurable.

## Files to modify

`src/models.py` — extend `PRInfo`:

```
@dataclass
class PRInfo:
    ...
    watch_retrigger_count: int = 0
```

`src/daemon/handlers/hung.py` — in `handle_hung` after the existing retrigger path. Find where `_post_codex_review_result` is called and the counter cycle is reset. Add cap check before the reset:

```
# OBS-BL: cap WATCH<->HUNG retrigger cycles to prevent infinite spend.
# Reset only when the policy permits another attempt.
cap = self.app_config.daemon.watch_retrigger_cap
current_count = current_pr.watch_retrigger_count + 1
current_pr.watch_retrigger_count = current_count

if current_count >= cap:
    self.log_event(
        f"[HUNG] PR #{current_pr.number} watch_retrigger cap reached "
        f"({current_count}/{cap}) - escalating instead of resetting WATCH."
    )
    await self._escalate_to_hung(
        current_pr,
        reason=f"watch_retrigger_cap_reached: {current_count} cycles "
               f"with no fresh review activity",
        apply_escalated_label=True,
        set_pr_escalated_flag=True,
    )
    return
```

Add reset path: in `handle_watch` when fresh review activity detected (FeedbackCheckResult.NEW path or codex EYES reaction younger than last_push), reset `current_pr.watch_retrigger_count = 0` before transitioning into FIX. Preserves the policy "make progress = reset attempts".

`src/orchestrator_config.py` (or wherever DaemonConfig dataclass lives) — extend with:

```
@dataclass
class DaemonConfig:
    ...
    watch_retrigger_cap: int = 3
```

`config.yml` and `config.production.example.yml` — add the field with default 3 and a comment explaining its purpose.

## Implementation notes

Default cap N=3 chosen as middle ground: too low (1-2) and transient codex hiccups escalate prematurely; too high (5+) and the multi-hour livelock returns. 3 retriggers over typical 60min review timeout = 3 hours minimum before escalation, which is enough to ride out genuine codex infra blips.

After this PR ships, PR-227c-class livelocks resolve to ESCALATED automatically within a bounded window. Operator gets a one-time signal in the dashboard event log instead of discovering hours of wasted budget after the fact.
