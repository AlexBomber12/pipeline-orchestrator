## Problem

Retry covers happy-path reset (frontmatter→TODO, delete cancellation, increment retry counter capped at 3, push wake). Stuck cases where Retry returns 409:
1. Retry cap=3 reached - operator needs hard reset to drop counter.
2. Orphan PR still open from prior run (e.g. coder crashed mid-fix, branch protection rejected push) - needs `gh pr close`.
3. retry_fingerprint matches current spec content (no real change), Retry refuses - operator may need to bypass.

No escape hatch today. Operator either edits spec content (forces fingerprint change) or manual `redis-cli DEL`.

## Solution

Add `POST /api/reset-task/{repo}/{task_id}` performing atomic destruction:

1. WATCH/MULTI Redis transaction:
   - DEL `cancellation:{repo}:{task_id}`
   - DEL `metrics:retry_count:{repo}:{task_id}`
   - DEL `metrics:retry_fingerprint:{repo}:{task_id}`
   - DEL `current_run_started_at:{repo}:{task_id}`
   - DEL `metrics:status_write_failed_retry:{repo}:{task_id}`
   - ZREM `cancellation_index:{repo}` `{task_id}`
2. If `close_orphan_pr=true` query param AND orphan PR detected via PR-332 diagnostic shape: `gh pr close {pr_number} --comment "Closed by operator reset"`.
3. Rewrite frontmatter status → TODO and commit+push.
4. Return 200 with cleanup summary JSON.

Returns 409 if concurrent modification (WATCH detected change). Returns 400 if task already TODO (nothing to reset). Returns 503 if Redis or git push fails partway - partial-reset state documented in error response.

### Endpoint sketch

```python
@router.post("/api/reset-task/{name}/{task_id}")
async def reset_task(
    request: Request,
    name: str,
    task_id: str,
    close_orphan_pr: bool = Query(False),
) -> JSONResponse:
    redis_client = request.app.state.redis
    deleted_keys: list[str] = []
    keys_to_delete = [
        f"cancellation:{name}:{task_id}",
        f"metrics:retry_count:{name}:{task_id}",
        f"metrics:retry_fingerprint:{name}:{task_id}",
        f"current_run_started_at:{name}:{task_id}",
        f"metrics:status_write_failed_retry:{name}:{task_id}",
    ]
    async with redis_client.pipeline(transaction=True) as pipe:
        await pipe.watch(*keys_to_delete)
        for key in keys_to_delete:
            await pipe.delete(key)
        await pipe.zrem(f"cancellation_index:{name}", task_id)
        try:
            await pipe.execute()
        except WatchError:
            return JSONResponse({"error": "concurrent_modification"}, status_code=409)
    closed_pr_number: int | None = None
    if close_orphan_pr:
        closed_pr_number = await _close_orphan_pr_if_exists(name, task_id)
    pushed = await _frontmatter_to_todo_and_push(name, task_id)
    return JSONResponse({
        "deleted_keys": keys_to_delete,
        "closed_pr_number": closed_pr_number,
        "frontmatter_pushed": pushed,
    })
```

## Threat model

**Threat addressed**: Retry cap-reached cases leave operators with no recovery path except manual redis-cli destruction. Risk of mistyped DEL command corrupting unrelated state.

**Other layers protecting**: confirmation modal (PR-335) gates the destructive action behind operator confirmation. Audit log (PR-336) records every reset for forensic review.

**Why this layer needed**: completes the recovery surface. Retry for transient issues + Reset for stuck cases = full coverage.
