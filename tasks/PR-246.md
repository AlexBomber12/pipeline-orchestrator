# PR-246: MCP functional tools (validate_task_spec + suggest_next_pr_number)

Branch: pr-246-mcp-functional-tools
- Type: feature
- Complexity: medium
- Depends on: PR-245
- Priority: 2
- Coder: claude

## Problem

The MCP server scaffold (PR-243) and read-only tools (PR-244) are in place. This PR completes the v1 tool set with the two functional tools that have logic beyond a passthrough wrap:

1. `validate_task_spec(content)` parses a candidate `tasks/PR-*.md` body and returns `{"valid": bool, "errors": list[str]}`. LLM clients generating task specs call this BEFORE attempting to upload, getting fast feedback on schema violations (missing `Branch:` field, unknown `Type:`, malformed `Depends on:`, etc.). Today validators run server-side at upload time; clients have no pre-flight check available. After this PR, `validate_task_spec` exposes the same validators (`parse_task_header` + `validate_queue` from `src/queue_parser.py`) as a tool. The bug observed 2026-05-02 (5% of LLM-generated specs were rejected at upload due to schema violations) is the direct motivator.

2. `suggest_next_pr_number(repo)` scans `/data/repos/<repo_slug>/tasks/PR-*.md`, parses out the PR numbers, and returns the next free integer. Handles subdivision suffixes (PR-219a, PR-219b, PR-227c) by taking the integer portion only. Prevents the PR numbering rule violation pattern where two parallel sessions allocate the same PR number for unrelated tasks.

## Scope

Two tools land in `src/mcp/tools/functional.py` and register via `@mcp.tool()`. Wire `src/mcp/server.py` to import the new module so registrations fire at startup.

`validate_task_spec` reuses existing `parse_task_header` and `validate_queue` machinery from `src/queue_parser.py`. The wrapper translates parser exceptions into a structured `{"valid": false, "errors": [...]}` response so MCP clients get a clean payload. No new validation logic is added; this PR only exposes the validators.

`suggest_next_pr_number` reads filenames from `/data/repos/<slug>/tasks/`, regex-matches `PR-(\\d+)([a-z])?\\.md`, takes the integer portion (ignoring the optional letter suffix), finds the maximum, returns max + 1. If the directory is empty or missing, returns 1. The function does not write to disk and does not coordinate with any other suggester; if two clients call it simultaneously they will get the same answer, which is acceptable because the daemon's continuous-numbering rule resolves collisions at upload time.

## Files to modify

`src/mcp/tools/functional.py` (new):

```
"""Functional MCP tools.

Tools with logic beyond a simple passthrough wrap. Both tools are
read-only with respect to filesystem state: ``validate_task_spec``
parses in-memory content; ``suggest_next_pr_number`` scans a
read-only mounted directory.
"""

from __future__ import annotations

import logging
import re
from pathlib import Path

from src.mcp.server import mcp
from src.queue_parser import (
    QueueValidationError,
    parse_task_header,
)

logger = logging.getLogger(__name__)

# Root path to managed repos inside the MCP container (mounted
# read-only per docker-compose.yml). Each subdirectory is one repo
# named ``<owner>__<repo>``.
_REPOS_ROOT = Path("/data/repos")

# Regex matching a task filename ``PR-<number>[<letter>].md``. The
# integer group is mandatory; the letter suffix (a/b/c for split PRs
# like PR-219a) is optional.
_PR_FILENAME = re.compile(r"^PR-(\d+)[a-z]?\.md$")


@mcp.tool()
def validate_task_spec(content: str) -> dict:
    """Validate a candidate task file body against the canonical schema.

    Wraps ``src.queue_parser.parse_task_header``. Returns a structured
    payload so MCP clients can surface errors to LLMs generating
    specs in real time, instead of waiting for upload-time rejection.

    Args:
        content: Full markdown body of a candidate ``PR-*.md`` file
            including the ``# PR-XXX: Title`` line and the header
            block (``Branch:``, ``- Type:``, ``- Complexity:``,
            ``- Depends on:``, ``- Priority:``, ``- Coder:``).

    Returns:
        ``{"valid": True}`` if the spec parses without error.
        ``{"valid": False, "errors": [<message>, ...]}`` when the
        parser raises ``QueueValidationError``. The error list
        contains one or more strings describing each violation.
    """
    try:
        parse_task_header(content)
    except QueueValidationError as exc:
        return {"valid": False, "errors": [str(exc)]}
    return {"valid": True}


@mcp.tool()
def suggest_next_pr_number(repo: str) -> int:
    """Return the next free PR number for a target repo.

    Scans ``/data/repos/<repo>/tasks/`` for files matching
    ``PR-<number>[<letter>].md`` and returns ``max + 1``. Subdivision
    suffixes (a/b/c) are collapsed to the integer; PR-219a and
    PR-219b both contribute integer 219.

    Args:
        repo: Repo slug in ``owner__repo`` form (e.g.
            ``AlexBomber12__pipeline-orchestrator``).

    Returns:
        Integer next-free PR number. Returns 1 if the tasks
        directory does not exist or contains no PR files.

    Raises:
        ValueError: if ``repo`` contains path separators or
            traversal sequences. Defensive against malformed input
            even though the docker mount is read-only.
    """
    if "/" in repo or ".." in repo or "\\" in repo:
        raise ValueError(f"Invalid repo slug: {repo!r}")

    tasks_dir = _REPOS_ROOT / repo / "tasks"
    if not tasks_dir.is_dir():
        return 1

    max_num = 0
    for entry in tasks_dir.iterdir():
        if not entry.is_file():
            continue
        match = _PR_FILENAME.match(entry.name)
        if match is None:
            continue
        max_num = max(max_num, int(match.group(1)))

    return max_num + 1
```

## Implementation notes

`validate_task_spec` returns a single error string in the `errors` list because `parse_task_header` raises `QueueValidationError` with a single message. If a future enhancement returns multiple errors (e.g., one per missing field), the list shape already accommodates it.

`suggest_next_pr_number` does NOT consult any external state (Redis, daemon-internal allocation registry, GitHub PR list). The continuous-numbering rule says PR numbers come from task files in the repo; this tool reflects that. If two operators or two LLM sessions call it simultaneously they will get the same answer, and one of their uploads will fail validation when the daemon detects the collision.

Path traversal defense: the regex `r"^PR-(\d+)[a-z]?\.md$"` already rejects filenames with `/` or `..` because those are not valid filenames at the OS level once `Path.iterdir()` returns them. The explicit check in `suggest_next_pr_number` defends against the `repo` argument containing path separators, which would let a misbehaving caller traverse outside `_REPOS_ROOT`. Even though the mount is read-only and exposes no sensitive content, the defense is cheap and aligns with general security hygiene.
