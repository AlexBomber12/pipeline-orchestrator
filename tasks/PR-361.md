## Problem

When a parent task `PR-N` is split into `PR-Na`, `PR-Nb`, `PR-Nc` during operator-driven recovery (e.g. when a single spec produces a too-large diff per OBS-DG) and the parent file `tasks/PR-N.md` is deleted from disk, any other task with `Depends on: PR-N` becomes silently blocked forever.

Concrete production observation 2026-05-15:

- PR-305 was split into PR-305a/b/c on 2026-05-14, parent file deleted.
- All three sub-tasks PR-305a/b/c merged cleanly.
- PR-306 had `Depends on: PR-305, PR-320`. Dashboard rendered "Blocked by: PR-305" indefinitely despite the full chain being complete.
- PR-308a had `Depends on: PR-307` after PR-307 -> PR-307a/b split. Same pattern.
- PR-310 had `Depends on: PR-306` and was transitively blocked.

The picker function `_filter_dag_headers_with_available_dependencies` at `src/daemon/handlers/idle.py:316-346` resolves dependencies by either:

- `dependency in merged_pr_ids` (parent ID literally appears in GitHub-merged set)
- `dependency in structured_pr_ids` (parent file still on disk)
- `(task_dir / f"{dependency}.md").exists()` (parent file on disk via path probe)

None of these match the split-parent case: parent ID never appeared in merged_pr_ids because the sub-tasks merged under different PR IDs (PR-305a/b/c), and parent file was deleted.

The operator workaround today is manual sed:

```
sed -i 's/Depends on: PR-305, PR-320/Depends on: PR-305c, PR-320/' tasks/PR-306.md
```

This is fragile, error-prone, and breaks the design contract that depends_on references stay stable across split events.

## Solution

In `_filter_dag_headers_with_available_dependencies`, add alias resolution: treat `PR-N` as satisfied when any sub-task variant `PR-N{suffix}` is found in `merged_pr_ids`. The suffix grammar matches the existing split convention used across the codebase: a single lowercase ASCII letter, optionally followed by digit-suffix (e.g. `PR-305a`, `PR-305b-1`, `PR-289b-2`, `PR-311a`).

### Concrete regex for sub-task suffix

Sub-task ID matches: `^PR-\d+(?:\.\d+)?[a-z](?:-\d+)?$`

Where:
- `^PR-` - literal prefix
- `\d+(?:\.\d+)?` - numeric parent ID (supports both `PR-305` and `PR-1.2` style)
- `[a-z]` - single lowercase letter for sub-task
- `(?:-\d+)?` - optional `-N` for nested split (e.g. `PR-289b-2`)

### Implementation

Before the existing `for header in headers:` loop, build an alias map:

```python
def _split_parent_of(pr_id: str) -> str | None:
    """Return the unsuffixed parent PR ID if pr_id is a sub-task variant.

    Examples:
        _split_parent_of("PR-305a") -> "PR-305"
        _split_parent_of("PR-289b-2") -> "PR-289"
        _split_parent_of("PR-1.2c") -> "PR-1.2"
        _split_parent_of("PR-305") -> None  # not a sub-task
    """
    match = re.match(r"^(PR-\d+(?:\.\d+)?)[a-z](?:-\d+)?$", pr_id)
    return match.group(1) if match else None

# Build {parent_id: True} for all merged sub-tasks
merged_parent_aliases: set[str] = set()
for merged_id in merged_pr_ids:
    parent = _split_parent_of(merged_id)
    if parent is not None:
        merged_parent_aliases.add(parent)
```

Then change the dependency check at line 331 from:

```python
if dependency in merged_pr_ids:
    continue
```

to:

```python
if dependency in merged_pr_ids or dependency in merged_parent_aliases:
    continue
```

The second-condition treats `Depends on: PR-305` as satisfied when any of `PR-305a`, `PR-305b`, `PR-305c` is in `merged_pr_ids`.

### What about partial split completion

If a parent is split into `PR-305a/b/c` and only `PR-305a` is merged so far, should `Depends on: PR-305` resolve? Decision: YES. Rationale:

- The split is an operator-driven recovery action; the operator implicitly accepts that the sub-tasks together replace the parent.
- If the operator wanted strict "all sub-tasks must complete" semantics, they would have written `Depends on: PR-305a, PR-305b, PR-305c` explicitly.
- Empirically (production observation 2026-05-15) the desired behavior is "first sub-task DONE = parent satisfied" because the dependent task usually only needs the shared substrate that all sub-tasks contribute to.

If this proves wrong in the future, the fix is to switch to "last sub-task DONE = parent satisfied" which is a one-line change (lookup parent ID and check the complete sub-task set is merged). Defer that decision until a real case emerges.

### Edge cases

- Parent file still on disk AND sub-tasks merged: the existing `dependency in structured_pr_ids` branch handles it - parent counts as "in queue, eligibility depends on parent state". The new alias logic does not interfere because the alias check is part of the merged-set short-circuit.
- Dependency on a sub-task directly (`Depends on: PR-305a`): unchanged, the literal match in `merged_pr_ids` resolves it.
- Sub-task IDs that look like normal PRs (none exist in this codebase): non-issue because the regex requires lowercase letter suffix.

## Threat model

**Threat addressed**: split-parent dependency orphan causes dependent tasks to be silently blocked indefinitely after operator-driven split recovery. Each occurrence requires manual sed intervention which is error-prone (typo in sub-task suffix, missed transitive blocker, breaks reproducibility).

**Other layers protecting**: none. The picker is the only gate where dependencies are evaluated.

**Why this layer needed**: split is a recovery pattern that operators use frequently (every Tier 2 GUARDRAIL trip on a too-large diff triggers a split). The picker must respect the split semantic to avoid invisible queue stalls.
