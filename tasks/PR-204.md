# PR-204: Structured per-PR outcome logging for future analytics

Branch: pr-204-structured-pr-outcome-logging
- Type: feature
- Complexity: low
- Depends on: none
- Priority: 3
- Coder: any

## Problem

Pipeline-orchestrator currently retains no structured record of what happened to each merged PR. The dashboard shows current state, the event log records human-readable activity, but no append-only outcome log exists for future analytics.

This is a foundational gap for any future capability that depends on historical data:

- Selector training (Thompson Sampling, cost-aware reward) — needs per-PR outcome data per coder × model × task type bucket.
- Cost-per-merged-PR metric (commercial product positioning) — needs aggregate cost data over time.
- Lessons learned for new repos onboarding — pattern recognition across past PRs requires structured queryable history.
- Anonymized opt-in telemetry (future product capability) — needs schema designed up front so opt-in can ship without data backfill.

The architectural decision recorded 2026-04-29: lessons learned from past PRs are valid **only for the same coder × model × version combination**. Cross-version aggregation is unsafe because each model version has different error distribution. Therefore the schema must record coder/model/version explicitly, and future analytics must default-filter to current version.

## Scope

Append-only structured log of merged PR outcomes. JSONL file format, global partitioned by year-month. No analysis layer, no telemetry, no upload — just persistence with the right schema for future use.

## Storage location and partitioning

`/data/analytics/<year>-<month>.jsonl`

Examples:
- `/data/analytics/2026-04.jsonl`
- `/data/analytics/2026-05.jsonl`

Rationale:
- Global (not per-repo): easier for cross-repo queries when product has multi-repo or multi-tenant deployments.
- Partitioned by month: easy to grep, easy to rotate (operator can archive old months), easy to upload selectively when telemetry layer is added.

## Schema

One JSON line per merged PR. All fields populated where data is available; missing fields written as `null`, never omitted. Schema:

```json
{
  "pr_id": "PR-180",
  "task_id_hash": "<sha256 of pr_id+repo_slug>",
  "repo_slug": "AlexBomber12__pipeline-orchestrator",
  "merged_at": "2026-04-29T14:25:23Z",
  "coder": "claude",
  "coder_model_string": "claude-opus-4-7",
  "coder_extension_version": "1.2.3",
  "task_type": "refactor",
  "task_complexity": "medium",
  "fix_iterations": 4,
  "ci_runs_total": 10,
  "ci_runs_failed": 8,
  "wall_clock_seconds": 14045,
  "files_changed": 12,
  "lines_added": 287,
  "lines_removed": 142,
  "review_blocker_count": 0,
  "review_nit_count": 2,
  "codex_review_iterations": 1,
  "tokens_estimate": 145000,
  "outcome": "merged"
}
```

Field semantics:

- `pr_id` — task PR id (e.g. `PR-180`).
- `task_id_hash` — sha256 hex of `f"{pr_id}::{repo_slug}"`. Provides stable anonymizable identity. Will allow future telemetry to ship `task_id_hash` instead of `pr_id`+`repo_slug` for opt-in users.
- `repo_slug` — pipeline-orchestrator slug (`<org>__<repo>`).
- `merged_at` — ISO 8601 with timezone. UTC preferred.
- `coder` — coder name as configured (`claude` or `codex`).
- `coder_model_string` — explicit model version (e.g. `claude-opus-4-7`, `gpt-5-codex`). Read from coder config or response metadata. **Critical for future analytics**: prevents unsafe cross-version aggregation.
- `coder_extension_version` — CLI tool version (e.g. `@anthropic-ai/claude-code` or `@openai/codex`). From `npm list -g` or equivalent. Allows tracking when a coder tool change correlates with outcome distribution change.
- `task_type` — from task file header. One of `architecture`, `bugfix`, `config`, `docs`, `feature`, `refactor`, `ux`.
- `task_complexity` — from task file header. One of `low`, `medium`, `high` (currently `low` and `medium` only used).
- `fix_iterations` — count of FIX state entries during this PR's lifecycle.
- `ci_runs_total` — total CI workflow runs triggered.
- `ci_runs_failed` — count of CI runs with `conclusion: failure`.
- `wall_clock_seconds` — from PR creation to merge.
- `files_changed`, `lines_added`, `lines_removed` — from final merged diff (`gh pr view --json files`).
- `review_blocker_count`, `review_nit_count` — count of Codex review comments classified as blocker vs nit. Currently no formal classification — use heuristic: comments with `[blocker]` or `[P1]` markers are blockers; rest are nits. If classification is unreliable, set both to `null` (not 0).
- `codex_review_iterations` — count of `@codex review` mentions during PR lifecycle.
- `tokens_estimate` — from `/api/oauth/usage` delta during PR lifecycle (computable from existing usage tracking; if endpoint returned 429 throughout, write `null`).
- `outcome` — `merged` for this PR. Reserved values for future: `abandoned`, `escalated`. (PR-204 only logs merge events; abandonment/escalation logging deferred.)

## Files to modify

`src/daemon/handlers/merge.py`:
- After successful PR merge, gather metadata from existing daemon state and external sources.
- Construct outcome record per schema above.
- Append as one JSON line to `/data/analytics/<year>-<month>.jsonl`. Create directory + file if missing.
- Use atomic append (open with `'a'` mode + immediate flush + fsync optional).
- File-locking: low concurrency (one merge at a time per daemon), but use `fcntl.flock` to be safe across multi-repo daemon configurations.

`src/analytics/__init__.py` (new directory):
- Module skeleton.

`src/analytics/outcome_logger.py` (new file):
- Function `log_merged_pr(pr_data: dict) -> None`.
- Encapsulates schema construction, file path resolution, locking, append.
- Computes `task_id_hash` via stdlib `hashlib`.

`src/analytics/schema.py` (new file):
- Constant `OUTCOME_SCHEMA_VERSION: int = 1` for future migration tracking.
- Constant `OUTCOME_FIELDS: list[str]` listing the 18 fields above for documentation purposes.
- Function `validate_outcome_record(record: dict) -> None` raises if required field missing or wrong type.

`tests/test_analytics_outcome_logger.py` (new file):
- Test: log a record, file is created with correct path.
- Test: subsequent log appends, does not overwrite.
- Test: month rollover creates new file, old file preserved.
- Test: missing field handling — `null` written, not omitted.
- Test: schema validation rejects malformed records.
- Test: concurrent appends from two simulated processes do not interleave bytes (flock works).
- Test: `task_id_hash` is deterministic for same `pr_id`+`repo_slug` pair.

`docs/analytics-schema.md` (new file):
- Document each field meaning, data source, version-stability semantics.
- Example queries operator can run with `jq` (e.g. `cat /data/analytics/*.jsonl | jq 'select(.coder == "claude" and .coder_model_string == "claude-opus-4-7") | .fix_iterations'`).
- Note the version-aggregation hazard explicitly: never aggregate across `coder_model_string` values without explicit operator awareness.

## SQLite consideration

JSONL chosen over SQLite for this PR for reasons:

1. **Append-only is simpler than schema migrations.** Adding a field to JSONL = no migration. Adding a column to SQLite = ALTER TABLE + backfill question.
2. **Operator inspection is trivial.** `cat *.jsonl | jq` works without any tools beyond what is already on the box.
3. **Future SQLite migration is cheap.** Read JSONL, batch INSERT into SQLite once. The schema is small, conversion is one script.
4. **Storage scale is small.** ~250 PR/year × ~500 bytes/record = ~125 KB/year. Even 10x growth (commercial product, multi-tenant) = ~1.25 MB/year per tenant. Not worth a database for this volume alone.

**However**, the day SQLite becomes worth it:

- Cross-month or cross-tenant queries where partition scanning becomes slow (>10s for typical query).
- Need for indexed columns (e.g. `coder_model_string` filter on millions of rows).
- Multi-process write concurrency that flock cannot handle gracefully.

When this happens: separate PR migrates JSONL to SQLite. Schema documented now (in `docs/analytics-schema.md`) makes that migration mechanical.

## Out of scope

- **Analysis layer / dashboards** — no UI for exploring this data. Operator uses `jq`. Dashboards come when there is a concrete decision-making need.
- **Telemetry / upload pipeline** — no data leaves the box. Opt-in telemetry deferred to future PR when product ships externally.
- **Recommendation engine** — no use of this data for selector training, lessons learned suggestions, or anything else. Pure persistence layer.
- **Logging abandoned or escalated PRs** — only merged outcomes logged in this PR. Abandonment/escalation logging requires defining the "end of PR lifecycle" event semantics, which is a separate design discussion.
- **Logging coder diffs per FIX iteration** — large data volume without clear use case currently. Defer until specific analytics question requires it.

## Architectural decision recorded

This PR encodes the decision: **lessons learned from past PRs are valid only for the same coder × model × version combination**. The schema records coder/model/version explicitly. Future analytics queries must default-filter to current version. Mixed-version aggregation is explicit opt-in with operator awareness of training-data-drift hazard.

This is documented in `docs/analytics-schema.md` and referenced in roadmap.
