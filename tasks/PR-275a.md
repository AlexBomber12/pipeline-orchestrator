# PR-275a: MCP cross-repo intent detection — literal gh repo create command match

Branch: pr-275a-mcp-literal-gh-repo-create
- Type: feature
- Complexity: low
- Depends on: PR-274
- Priority: 1
- Coder: codex

## Problem

OBS-BT documented from a 2026-05-04 production session: task files authored for one repository were uploaded into a different repository's tasks directory by mistake, and the dispatched coder detected the cross-repo intent in the task body and autonomously executed a destructive `gh repo create` operation. Operator recovery required manually deleting the misrouted task files plus closing the unauthorized PRs.

The original PR-275 attempt (PR #368) tried to detect cross-repo intent via natural-language regex patterns covering phrasings like "ships in <repo>", "targets <repo>", "lives in <repo>", plus literal `gh repo create` commands. Codex review found 10 substantive P1/P2 issues with that approach, all variations of the same problem: regex pattern matching cannot reliably distinguish between executable destructive intent ("Run `gh repo create owner/foo`") and innocent prose ("This PR targets Python 3.12", "service deploys to production", "module lives in src/..."). Each fix to one false positive opened a false negative elsewhere, resulting in a 21-iteration FIX loop that never converged. After 4 hours of operator-observed deadlock, PR #368 was closed and the work split.

PR-275a takes a deliberately narrow scope: detect ONLY the literal command form `gh repo create owner/repo-name` and `gh repo new owner/repo-name` (gh CLI alias) when the match appears outside markdown fenced code blocks (` ``` ... ``` `) and outside backtick-quoted inline code spans. Natural-language intent detection is explicitly out of scope and delegated to PR-276 (Tier 1 stdout monitoring) and PR-277 (Tier 1 diff scan), which observe what the coder actually does rather than what the task body says.

## Scope

Single deliverable: extend `src/mcp/scans.py:_ANTI_PATTERNS` with two new entries detecting literal repo-creation commands.

Pattern 1: `cross_repo_repo_create_command`
- Regex: `\bgh\s+repo\s+create\s+[\w.-]+/[\w.-]+`
- Rule message: `"AGENTS.md prohibits coder-initiated cross-repo creation. Tier 1 guardrail. OBS-BT."`
- Required slash-separated `owner/repo` argument distinguishes the command form from descriptive prose. `gh repo create` without an owner/name argument (`gh repo create` alone, `gh repo create --help`, `the gh repo create command behavior`) is NOT matched because the regex requires `\s+[\w.-]+/[\w.-]+` after `create`.

Pattern 2: `cross_repo_repo_new_command`
- Regex: `\bgh\s+repo\s+new\s+[\w.-]+/[\w.-]+`
- Rule message: same as pattern 1, since `gh repo new` is documented as alias of `gh repo create` per gh CLI docs.
- Same rationale on the slash-required argument.

Both patterns must be suppressed when the match falls inside:
- A fenced code block (between matching ` ``` ` markers anywhere in the document)
- A backtick-quoted inline code span on the same line (` `gh repo create owner/foo` ` form)
- A clause containing a negation phrase via the existing `_is_negated` helper (which already handles "do not", "must not", "never" etc.)

Do NOT add suppression for double-quoted text. The original PR-275 attempt added quote suppression and Codex review correctly flagged it as creating false negatives for real instructions like `Run "gh repo create owner/repo" now`. Quotes in spec prose are typically used to highlight rather than to disable.

## Behavior

Task body text examples that MUST trigger violation:
- `Run gh repo create AlexBomber12/homelab-monitoring as setup step`
- `gh repo create new-org/new-project --public`
- `Execute: gh repo new monorepo-org/shared-libs`

Task body text examples that MUST NOT trigger violation:
- `This PR targets Python 3.12` (no `gh repo` literal)
- `service deploys to production environment` (no `gh repo` literal)
- `module lives in src/utils/repo.py` (no `gh repo` literal)
- `the gh repo create command behavior is documented in OBS-BT` (no slash argument after `create`)
- ` ```bash\ngh repo create owner/repo\n``` ` (inside fenced code block)
- `` Use the `gh repo create owner/repo` command from a terminal `` (inside inline backticks)
- `Coders must not run gh repo create owner/repo` (negation suppression via `_is_negated`)
- `Do not gh repo new owner/repo under any circumstance` (negation suppression)

Note that quoted but not backticked phrases like `Run "gh repo create owner/repo" now` SHOULD still trigger violation. Quotes in prose typically emphasize rather than disable. Backticks are the markdown convention for "this is code, not directive."

## Files to modify

- `src/mcp/scans.py`: add the two new entries to `_ANTI_PATTERNS` list. Add a helper `_is_inside_fenced_code_block(text: str, match_start: int) -> bool` that walks the text up to `match_start` and counts unmatched ` ``` ` markers — odd count means we're inside a fenced block. Add a helper `_is_inside_inline_code(text: str, match_start: int) -> bool` that examines only the same line as the match and counts unmatched single-backtick markers before the match start. Use both helpers as suppression filters in `scan_for_conflicts` for ONLY these two new patterns; existing patterns continue working unchanged.

## Files NOT to touch

- Other `_ANTI_PATTERNS` entries (`draft_pr_flag`, `draft_pr_text`, `force_push_main`, etc.) — they have their own design and tests, modifying them is outside scope and risks regressing other guardrails.
- `src/mcp/tools/functional.py:validate_task_spec` — consumes scan output unchanged.
- Natural-language patterns (`cross_repo_ships_in`, `cross_repo_targets`, etc. that the original PR-275 attempt added) — explicitly out of scope and delegated to PR-276 stdout monitoring.

## Implementation notes

The `_is_inside_fenced_code_block` helper walks `text[:match_start]` and counts ` ``` ` occurrences. Odd count means we're inside an open fence. Edge case: a fence opened with ` ```bash ` (with language tag) still counts as one ` ``` ` occurrence, which is correct.

The `_is_inside_inline_code` helper restricts its scan to the line containing `match_start`. Within that line it finds the substring before the match and counts single backticks. Odd count means we're inside an inline span. This intentionally does NOT handle multi-backtick inline spans (` ``code`` `) because (a) those are rare in spec prose and (b) handling them adds significant complexity for marginal benefit. PR-286 in the original batch exists to extend this if real production data shows it matters.

The two new patterns share a single rule message and both serve the same Tier 1 guardrail purpose. Keeping them separate (rather than combining via regex alternation) makes the violation type field surface which exact form was matched, useful for operator review.

The suppression layer applied to ONLY these two patterns (not all of `_ANTI_PATTERNS`) preserves existing test contracts. The other patterns have their own decade-long history of tuning and adding global suppression there could regress them.

This PR explicitly does NOT attempt to detect natural-language cross-repo intent. The architectural justification: natural language ambiguity cannot be reliably disambiguated by regex patterns. Cross-repo intent detection in spec prose is an LLM-classification problem, not a regex problem. The defense-in-depth strategy is: layer 1 (this PR, plus PR-275b) catches literal destructive commands in spec body; layer 2 (PR-276) catches what the coder actually executes via stdout monitoring; layer 3 (PR-277) catches what survives stdout monitoring via post-push diff scan. Each layer simple and testable; combined coverage robust without any single layer carrying the whole burden.
