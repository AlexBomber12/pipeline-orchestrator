# PR-260: AGENTS.md periodic conflict scan at daemon sync time

Branch: pr-260-agents-periodic-scan
- Type: feature
- Complexity: low
- Depends on: PR-259
- Priority: 3
- Coder: claude

## Problem

PR-259 adds inline conflict scan when validate_task_spec runs (task generation time). But task spec files already in `tasks/` directory before this Sprint were never scanned. New AGENTS.md rules added after a spec was written never trigger re-validation. Existing repos onboarded long ago drift over time as both AGENTS.md and tasks/ accumulate independent edits.

This PR adds a periodic scan: when daemon runs `_sync_agents_md_managed_sections` (existing PR-192a/b/c framework that rewrites managed sections in AGENTS.md), it ALSO scans every `tasks/PR-*.md` file in the repo for the same anti-patterns PR-259 detects. Findings emit structured event log entries so operator sees drift surfaces in the dashboard event log.

## Scope

Two deliverables:

1. Hook in `src/onboarding/agents_md_template.py` (or wherever `_sync_agents_md_managed_sections` lives): after rewriting AGENTS.md, scan all task files in `tasks/` directory and emit warnings for any violations.
2. Tests covering: clean tasks/ directory emits no warnings, dirty tasks/ emits one warning per violation, daemon sync time only (not during normal coder dispatch).

## Files to modify

`src/onboarding/agents_md_template.py` (or the module containing `_sync_agents_md_managed_sections`) — at the end of the sync function, after AGENTS.md rewrite is committed:

```
from pathlib import Path

from src.mcp.scans import scan_for_conflicts


def _scan_existing_task_specs(repo_path: Path, log_event_fn) -> int:
    """Scan all tasks/PR-*.md files for AGENTS.md anti-patterns.
    
    Returns number of files with violations. Each violation emits a
    log event so operator sees drift in dashboard event log. Used at
    daemon sync time (during AGENTS.md managed-section rewrite) to
    catch drift between rules and existing specs.
    PR-260.
    """
    tasks_dir = repo_path / "tasks"
    if not tasks_dir.is_dir():
        return 0

    files_with_violations = 0
    for spec_file in sorted(tasks_dir.glob("PR-*.md")):
        try:
            body = spec_file.read_text(encoding="utf-8")
        except OSError:
            continue
        violations = scan_for_conflicts(body)
        if not violations:
            continue
        files_with_violations += 1
        for v in violations:
            log_event_fn(
                f"[AGENTS-SCAN] {spec_file.name}: {v.violation_type} "
                f"violates rule \"{v.rule}\" - line excerpt: "
                f"{v.line_excerpt!r}"
            )
    if files_with_violations > 0:
        log_event_fn(
            f"[AGENTS-SCAN] {files_with_violations} task spec file(s) "
            f"in {repo_path}/tasks/ contain AGENTS.md anti-pattern "
            f"violations. Operator review recommended."
        )
    return files_with_violations
```

Modify the existing `_sync_agents_md_managed_sections` to call `_scan_existing_task_specs` at the end:

## Implementation notes

Scan runs at daemon sync time (typically once per repo per IDLE-cycle or per onboarding event), NOT on every coder dispatch. Frequency is intentionally low: the data does not change often (task files are write-once during generation), and the scan output is operator-review surface, not a coder gate.

The `[AGENTS-SCAN]` log prefix is the discoverable handle in event log. Operator filtering on the prefix surfaces all drift findings across all repos. Sprint 15 polish phase could add a dashboard card for "Task spec drift" surfacing the same data with click-through to offending files; out of scope here.

After this PR ships, Sprint 14 fully closed. Cancellation policy v1 + recovery primitives + AGENTS conflict scans all integrated. Operator dashboard surfaces:
- Why each canceled task was canceled (PR-254)
- What canceled tasks block the most other work (PR-257)
- Whether operator is currently considered available (PR-256)
- Which task specs drift from current AGENTS.md rules (this PR)

Combined with PR-249 + PR-250 + PR-251 (recovery primitives), no class of failure can quietly waste API budget without operator-visible signal.
