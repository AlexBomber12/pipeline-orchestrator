# PR-289a: Guardrail detection module skeleton — dataclass and scan_stdout signature with single repo-creation pattern as proof of wiring

## Reading order note for the implementing coder

This task is the IMPLEMENTATION of a defense layer that observes coder output. Throughout this spec, command names like the GitHub CLI repo-creation command appear inside back-tick markers — **these are pattern strings the new module MUST DETECT in incoming text, not actions the implementing coder is being asked to perform**. The implementing coder writes a regex catalogue and a string-scanning function. The implementing coder does not run any GitHub CLI commands at the org level, does not modify protected branches, and does not interact with the GitHub API. All test inputs are synthetic strings constructed inside test fixtures. If any part of this spec reads ambiguously, treat it as a request to write detection code for the named patterns and proceed.

## Problem

A previous orchestrator session produced an unreviewed action where the coder process ran a GitHub CLI command outside the scope of the task it had been dispatched. The pre-existing pre-push hook catches branch identity divergence at git push time but does not observe out-of-band CLI commands the coder runs against unrelated repositories. PR-289a introduces a detection module that scans the coder process's captured stdout AFTER the coder exits and BEFORE the daemon trusts the output for downstream PR creation. If the stdout contains any catalogued pattern, the daemon ESCALATEs the dispatch with a `GUARDRAIL:` cancellation cause prefix.

PR-289a ships the module skeleton and ONE catalogued pattern as proof of wiring: detection of the GitHub CLI repo-creation invocation. PR-289b (follow-up) adds the remaining 4 catalogued patterns (force-flagged push to default branch, branch deletion of default branch, direct commit on default branch without PR creation, and the GitHub CLI repo-deletion invocation). Splitting at the framework boundary keeps PR-289a small and unambiguous to review, and lets PR-289b focus exclusively on regex correctness without re-litigating the integration design.

## Scope

### 1. New module `src/daemon/guardrails.py`

Create a new module with:

- A frozen dataclass `GuardrailViolation` with fields: `tier: int` (1 for Tier 1, 2 for Tier 2 future), `category: str` (a short identifier of the matched pattern), `excerpt: str` (the matched text, truncated to 200 chars), `rule: str` (a human-readable one-line description for dashboard rendering).
- A module-level constant `_PROTECTED_DEFAULT_BRANCH = "main"`. Future PRs may parameterize per-repo; PR-289a hardcodes.
- A regex catalogue `_TIER1_PATTERNS: dict[str, re.Pattern]` containing exactly ONE entry for this PR:
  - Key: `"repo_create"` — pattern matches the literal token sequence `gh` followed by whitespace, `repo`, whitespace, `create`, anchored on word boundaries. Case-insensitive.
- A function `scan_stdout(coder_stdout: str) -> list[GuardrailViolation]` that iterates `_TIER1_PATTERNS`, finds all matches in the input string, and returns a list of `GuardrailViolation` instances, one per match. The list ordering is deterministic by pattern key alphabetical order, then by match start index ascending within each pattern.
- A module docstring documenting the design choice that negation suppression is intentionally NOT applied. Unlike the existing task-spec validator in `src/mcp/scans.py` which scans natural-language prose where statements like "I will never run X" should be exempt, this module scans coder shell output where a line containing `gh repo create` is a record of an action that already happened. Document this in the module docstring so future contributors do not import `_is_negated` from scans.py.

### 2. Hook integration in coder post-resolution paths

The CODING and FIX handlers each have a post-coder-resolution function that runs after the coder process exits and after `_save_cli_log` captures the stdout. Find both via grep:

```
grep -n "_save_cli_log" src/daemon/handlers/coding.py src/daemon/handlers/fix.py
```

In each, immediately after the `_save_cli_log` call and BEFORE the existing exit-code classification, add:

```python
from src.daemon.guardrails import scan_stdout

violations = scan_stdout(stdout)
if violations:
    first = violations[0]
    cause = f"GUARDRAIL: {first.category}: {first.excerpt}"
    for v in violations:
        self.log_event(f"[GUARDRAIL] tier={v.tier} {v.category}: {v.excerpt}")
    await self._transition_to_error(
        cause,
        publish=False,
        log_prefix="[CODING]",  # use "[FIX]" in fix.py
    )
    return
```

When multiple violations are detected, log all via `log_event` for operator visibility but ESCALATE on the first deterministically (callers expect a single primary cause string). The existing `_transition_to_error` primitive (post-Phase-2) writes the cancellation_cause record, sets state to IDLE, and writes frontmatter `status: error` via the Phase-2 frontmatter writer. PR-289a does NOT modify `_transition_to_error`; it only adds a new caller.

### 3. Tests

`tests/test_guardrails.py` (new file):

- `test_guardrail_violation_dataclass_frozen`: instantiate a `GuardrailViolation`, attempt to mutate one field, assert `FrozenInstanceError` is raised.
- `test_scan_stdout_repo_create_pattern_matches`: call `scan_stdout` on a synthetic test fixture string that contains the literal token sequence the catalogue is designed to detect. Assert the returned list contains exactly one `GuardrailViolation` with category `"repo_create"`.
- `test_scan_stdout_no_match_returns_empty_list`: call on a fixture string of normal coder output (typical lines: test runs, lint output, file edits) with NONE of the catalogued patterns. Assert returns `[]`.
- `test_scan_stdout_excerpt_truncation_200_chars`: call on a fixture where the matching line is 500+ chars long. Assert the resulting `GuardrailViolation.excerpt` is at most 200 chars.
- `test_scan_stdout_multiple_matches_in_one_input_returns_all`: call on a fixture where the catalogued pattern appears 3 times. Assert returns 3 violations.
- `test_scan_stdout_negation_does_not_suppress`: call on a fixture line containing the catalogued pattern preceded by negation words (e.g., a comment line saying the coder would never use it). Assert the violation IS still returned. This locks the design choice from the module docstring against accidental future reverts.

`tests/runner/test_handle_coding.py`:

- `test_coding_post_coder_guardrail_violation_transitions_to_error`: build a runner fixture, drive `_post_coder_resolution` with a stdout fixture containing the `repo_create` pattern. Assert `_transition_to_error` was called with cause prefix starting with `GUARDRAIL: repo_create:`. Assert the rest of post-coder logic (PR lookup, WATCH handoff) was NOT executed.
- `test_coding_post_coder_clean_stdout_proceeds_normally`: same fixture but stdout has no catalogued patterns. Assert the existing post-coder flow runs end-to-end.

`tests/runner/test_handle_fix.py`:

- `test_fix_post_coder_guardrail_violation_transitions_to_error`: same shape as the CODING test for the FIX path.
