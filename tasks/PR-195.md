# PR-195: push_count desync fix

Branch: pr-195-push-count-desync
- Type: bugfix
- Complexity: low
- Depends on: none
- Priority: 3
- Coder: any

## Problem

This is a memory item from past sessions. Dashboard shows `Pushes: 2` but GitHub UI Commits tab shows 7. The metric is misleading — operator cannot tell how many real iterations occurred on a PR.

Root cause is two-fold:

1. `src/github_client.py:190` uses `len(commits)` from gh API response. That can be a squashed view, paginated subset, or compressed force-push history.
2. `src/daemon/handlers/fix.py:368` does local `+= 1` increment, but the next API poll overwrites the local value with whatever gh returned.

The fix is to use a single source of truth. Best option: count actual force-pushes since branch HEAD by checking the events stream (`/repos/.../pulls/{n}/events` or git reflog on remote ref).

Simpler option: count distinct head SHAs seen by daemon over the lifetime of the PR. Daemon already tracks `last_push_sha` per PR — just maintain a set of seen SHAs and report cardinality.

## Scope

Replace `push_count` semantics with "distinct head SHAs daemon has observed". Surfaces realistic count even when force-pushes overwrite remote ref.

## Files to modify

`src/models.py`:
- Add field `observed_head_shas: set[str]` to PRInfo (or wherever PR state is stored).
- Or persist to Redis as a set keyed by PR number.

`src/daemon/handlers/fix.py`:
- After detecting a push (existing logic around line 368), add the new head SHA to the observed set.
- Compute `push_count = len(observed_head_shas)` for display purposes.

`src/github_client.py`:
- In the PR list parsing (around line 190), do not overwrite push_count from API. Instead populate `observed_head_shas` with the current head SHA (so initial state has at least 1).

`src/web/templates/components/repo_summary.html` (or wherever push_count renders):
- Optionally add a tooltip explaining the metric ("distinct head SHAs seen by daemon").

`tests/`:
- Test: single push → count 1.
- Test: 5 force-pushes → count 5.
- Test: cross-restart persistence (Redis-backed) → count preserved.
- Test: API initial fetch populates set with current head.

## Implementation notes

If using Redis-backed set, key like `pr:{repo}:{pr_number}:observed_shas`. TTL: same as the PR is open, plus grace.

If using PRInfo in-memory, the set lives in daemon memory and resets on restart. Acceptable for first iteration. Cross-restart precision is a follow-up.

Document the metric meaning in event log and dashboard tooltip so operator understands what is being counted. A force-push that lands the same SHA twice should NOT bump count (that is correct behavior — same content, just a force-push retry).
