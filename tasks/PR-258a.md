## Problem

PR-252, PR-253, and PR-254 shipped the cancellation-cause substrate: a `CancellationCause` dataclass persisted to Redis under `cancellation:{repo}:{task_id}`, with a category field that takes values `CRASH`, `ESCALATE`, `TIMEOUT`, `INFRA`, `OPERATOR_RECOVERY`, and `NO_PUSH_DEADLOCK`. The dashboard reads the index and surfaces a per-repo cancellation card; the blocked-set service propagates cancellations through `depends_on` graphs so dependents are correctly tagged as transitively blocked.

The full chain (detection writes cause, cause persists, UI surfaces it, blocked-set propagation reaches dependents) is covered only by unit tests today. There is no e2e test that drives a real coder crash through the daemon, watches the daemon write the `CRASH` cause to Redis, and then asserts the cancellation card is reachable from the dashboard with the correct category and that a downstream task with `depends_on: PR-CRASHED` shows up in the blocked set.

The Sprint 14 incident class (daemon mis-cancels under specific stress patterns) and the recurring concern that the cancellation surface lies dormant during regression mean that landing this e2e closes the most directly-relevant Tier-1 gap. It also gives the next refactor against `safe_record_cancellation_cause` a load-bearing integration anchor.

## Scope

A single new e2e test `tests/e2e/test_cancellation_cause_crash.py` that:

1. Uploads two task files in one zip: `PR-A` (the crashing task) and `PR-B` (a dependent on `PR-A` so the blocked-set propagation has somewhere to reach).
2. Activates the `exit_nonzero` shim scenario, which makes the next coder invocation exit with status 1 mid-CODING.
3. Waits for the daemon to transition the runner through the cancellation path: CODING fails, runner enters the cancellation branch in `coding.py:_handle_coder_failure`, the cause is recorded with `category="CRASH"` via `safe_record_cancellation_cause`, the runner returns to IDLE.
4. Asserts via `GET /api/repo/{slug}/cancellations` (or directly via Redis through the daemon's running container if the API is not available in test) that the recorded cause for `PR-A` has `category="CRASH"`.
5. Asserts the dashboard cancellation card endpoint (the same one PR-254 added under `dashboard.py`) returns the `PR-A` entry within the recent-7-days window.
6. Asserts the blocked-set computation tags `PR-B` as transitively blocked. The most direct way is `GET /api/repo/{slug}/blocked-set` (PR-252 surface) or the equivalent dashboard fragment.

No production code changes. Only test fixtures and the test file.

## Implementation notes

The `exit_nonzero` shim returns exit code 1 with no stdout indicating ESCALATE, no branch push, no PR creation. The daemon's CODING handler observes the non-zero exit and routes to `_handle_coder_failure`. That helper records a cancellation cause with the category derived from `classify_infra_exception` for infra-class errors, or `CRASH` for an unhandled coder process exit. Verify the exact category produced for `exit_nonzero` against the production code before committing the assertion. If the production code uses a different category for "coder exited non-zero" (such as `INFRA` instead of `CRASH`), update the test assertion to match the production category and adjust the test name accordingly. The exact category is the contract this test pins.

The dependent task `PR-B` must declare `Depends on: PR-A` in its header. Use the `make_task_zip_multi` fixture to author this. The fixture should write each task file as `tests/e2e/data/PR-XXX.md` style content using the same body template as `make_task_zip`, with the only variations being the `pr_id` and the `Depends on:` line.

The blocked-set assertion is sensitive to timing: the daemon must complete the cancel-record-and-propagate step before the dashboard endpoint returns the propagated state. Use a polling loop with a 30s deadline and 1s interval, identical to the pattern in `test_sigkill_recovery.py`. Assert against the polled state rather than a single snapshot.

The Redis-direct assertion path (using `docker exec ... redis-cli HGETALL cancellation:{slug}:{pr_id}`) is acceptable as a fallback if the dashboard API surface is not stable enough for a black-box assertion. Pick one path and document the choice in the test docstring.

The test does not need to verify the full blocked-set graph; only that `PR-B.pr_id` appears in the blocked set after the propagation completes. Deeper graph cases are unit-test territory in `tests/test_blocked_set.py`.

## Success criteria

1. After the `exit_nonzero` shim crash, the daemon writes a `CancellationCause` with `category` matching the production-code value for coder-exit-nonzero (verified against `src/daemon/handlers/coding.py:_handle_coder_failure`) under Redis key `cancellation:{slug}:PR-A`.
2. The dashboard cancellation endpoint returns the `PR-A` entry within 30 seconds of the crash.
3. The blocked-set endpoint includes `PR-B.pr_id` in its response within 30 seconds of the cause being recorded.
4. The runner returns to IDLE with `current_task` cleared after the cancellation completes.
5. The test passes locally and in CI without flake on three consecutive runs.
6. No production code modified.
