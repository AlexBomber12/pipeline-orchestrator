## Problem

PR-262 wired `_branch_name_matches_task_pr_id` (in `src/task_status.py`) and the GraphQL query in `gh_pr_get_merged_branches` (in `src/github/prs.py`) into the production done-detection path. Both functions have non-trivial input domains that the existing test suite covers only indirectly through higher-level `derive_task_status` tests.

The branch matcher accepts arbitrary `pr_id` strings and arbitrary branch names, then performs case-insensitive prefix-with-separator matching across two candidate forms (raw, and the form with underscores and dots collapsed to hyphens). Edge cases that production has already produced or could produce in megaraid-dashboard and TaskU repos: empty `pr_id`, branches shorter than the candidate, IndexError when slicing past the end of the branch string, unicode in branch names (Cyrillic/CJK in Aleksei's hub-of-hubs setup), and special characters that are valid per `git check-ref-format` but unusual at the surface (`#`, `+`, `=`).

The GraphQL query in `gh_pr_get_merged_branches` is constructed by string concatenation. A subtle change in the variable naming, the query alias scheme, or the filter clause would silently shift production behavior because no existing test pins the exact wire format of the query string. The only assertion in the existing chunk-size test is `branch0=branch-00` style key presence, not the surrounding query body.

This MICRO PR closes both gaps with focused tests. No production code changes.

## Scope

Two deliverables, both test-only.

1. New unit test file `tests/test_branch_name_matches_task_pr_id.py` covering the branch matcher's edge cases. Imported directly from `src.task_status` even though the function is module-private; pinning it via direct unit tests is the explicit intent.

2. New test in `tests/github/test_pr_merged_branches.py` named `test_graphql_query_string_snapshot` that captures the exact query string passed to `gh_runner.run_gh` for a fixed input of three branches and asserts byte-for-byte equality against an expected literal. The test serves as the wire-format anchor: any future change to alias scheme, variable layout, or filter clause must update the snapshot deliberately.

No new helpers, no production-code edits, no dependencies on PR-263 or any later batch member.

## Tests

`tests/test_branch_name_matches_task_pr_id.py` (new file, 8 cases):

- `test_empty_pr_id_returns_false`: call with `pr_id=""` and `branch="pr-263-foo"`. Assert `False`. The empty candidate is filtered out by the comprehension's `if candidate` clause; the test pins that filter.
- `test_branch_shorter_than_pr_id_returns_false`: `pr_id="PR-263"` and `branch="pr-26"`. Assert `False`. The branch is shorter than the candidate so the prefix check fails before the IndexError-prone slice.
- `test_branch_equals_pr_id_returns_true`: `pr_id="PR-263"` and `branch="PR-263"`. Assert `True`. Pins the exact-equality short circuit.
- `test_branch_equals_pr_id_lowercase_returns_true`: `pr_id="PR-263"` and `branch="pr-263"`. Assert `True`. Pins the case-insensitive comparison.
- `test_branch_with_separator_after_pr_id_returns_true`: assert `True` for each of `pr-263-feat`, `pr-263_feat`, `pr-263.feat`, `pr-263/feat` against `pr_id="PR-263"`. Pins the four allowed separators.
- `test_branch_with_no_separator_returns_false`: `pr_id="PR-263"` and `branch="pr-2630-feat"`. Assert `False`. The character at position `len(candidate)` is `'0'` which is not in the separator set; the matcher must not greedily attribute the branch.
- `test_underscore_dot_normalization_in_pr_id`: `pr_id="PR_263.5"` and each of `pr-263-5`, `pr-263-5-feature`, `pr_263.5`. Assert `True` for all three. Pins the candidate normalization that maps underscore and dot to hyphen.
- `test_unicode_branch_returns_false_without_match`: `pr_id="PR-263"` and `branch="pr-263-фикс"`. Assert `True` (the Cyrillic suffix follows the hyphen separator; unicode bytes are treated as a regular suffix and the prefix-with-separator rule still holds). Then `pr_id="PR-263"` and `branch="фикс-263"`. Assert `False`.
- `test_special_chars_per_git_check_ref_format`: `pr_id="PR-263"` against branches `pr-263+rebase`, `pr-263=v2`, `pr-263#1`. The plus, equals, and hash characters are valid per `git check-ref-format` but are not in the separator set, so all three assert `False`. The branch matcher treats them as continuation, not separator.

`tests/github/test_pr_merged_branches.py` (append):

- `test_graphql_query_string_snapshot`: monkeypatch `src.github.gh_runner.run_gh` to capture the `args` argument. Call `gh_pr_get_merged_branches("AlexBomber12/megaraid-dashboard", ["pr-001-foo", "pr-002-bar", "pr-003-baz"])`. Extract the string immediately following `-f query=` from the captured args. Assert the extracted string equals an explicit expected literal containing exactly: the `query` keyword, the three input variables `$branch0 $branch1 $branch2` in order, the three field aliases `b0 b1 b2` in order, and the `first: 1, states: MERGED, headRefName: $branchN` filter clause. The expected literal is reproduced verbatim in the test body.

## Implementation notes

The branch matcher is module-private. The accepted convention in this repo for pinning module-private helpers is direct import (`from src.task_status import _branch_name_matches_task_pr_id`); see `tests/test_task_status.py` for the same pattern applied to `_branch_matches_task_pr` and other helpers. No alternative public surface needs to be created.

The unicode test case is calibrated to match production reality: `pr-263-фикс` is a branch a Russian-localized maintainer might cut. The matcher's existing logic does the right thing because Python string `startswith` and indexing operate on code points, not bytes; the test pins that contract so a future "ASCII-only" guard would surface as a deliberate change instead of regressing localized workflows silently.

The GraphQL snapshot uses a 3-branch input rather than 1 to ensure the test exercises the indexed alias loop (`b0`, `b1`, `b2`) and the variable list joiner (`, `). A 1-branch input would let a regression that drops the joiner pass undetected.

The snapshot's expected literal is a long single-line string. To keep the test readable, build the expected via an `expected = (` joined-strings concatenation in the test body so each clause is on its own physical line; the assertion compares the joined result against the captured value.

The `run_gh` monkeypatch returns `{"data": {"repository": {}}}` after capturing args, which lets the function complete normally and return an empty merged-branches set. The test then asserts on the captured args, not the return value.
