## Problem

PR-186 established the invariant that a daemon SIGKILL during CODING (before the coder pushes a branch) recovers to IDLE with the in-flight task auto-CANCELED, rather than rebooting into a CODING loop on the same crashed task. The existing e2e `tests/e2e/test_sigkill_recovery.py` exercises this contract on a single-task queue: upload one task, kill mid-CODING, restart, observe IDLE plus the crash log entry.

PR-266 (split as PR-266a, PR-266b, PR-266c) refactors the recovery code path to derive queue state from `tasks/PR-*.md` headers via the new `_parse_tasks_from_headers` helper, replacing the legacy `_parse_base_queue` probe of `tasks/QUEUE.md`. The single-task happy path is the easiest case for any recovery implementation; the harder case is recovery on a queue where one task is mid-CODING and several others are TODO. A regression in the recovery code that mis-derives the post-CANCEL queue (for example, treating the CANCELED task's `depends_on` as still-blocking, or mis-ordering the remaining TODO tasks, or failing to preserve the priority sort) would not surface in the existing single-task test.

This PR lands the multi-task variant of the SIGKILL-recovery test so PR-266a, PR-266b, and PR-266c each have a load-bearing integration anchor. With this test in place, an audit-mode divergence that the unit fixtures miss (a real-world race that rehydrates a queue subtly wrong) will fail this e2e during the audit window rather than in production.

## Scope

A single new e2e test `tests/e2e/test_sigkill_recovery_multitask.py` that:

1. Uploads four task files in one zip: `PR-A` (priority 1, no deps), `PR-B` (priority 2, no deps), `PR-C` (priority 2, depends on PR-A), `PR-D` (priority 3, no deps). The mix exercises priority ordering, depends-on edges, and a non-blocked sibling.
2. Activates the `slow` shim scenario so the next coder invocation enters CODING and sleeps 30 seconds before any local commit or push.
3. Waits for the runner to reach CODING on `PR-A` (priority 1 wins the dispatch race deterministically). Captures `pre_kill_last_updated` for the freshness gate.
4. Issues `docker kill --signal=KILL` against the daemon container while the slow shim is sleeping, asserts exit code 137 per the existing test pattern.
5. Restarts the daemon via `docker compose up -d daemon-test`, waits for the container to be Running.
6. Polls runner state with a 120-second deadline. Asserts:
   - runner state is IDLE with `current_task is None` and `last_updated` strictly greater than `pre_kill_last_updated`,
   - history contains the `[INFRA] Task PR-A crashed, marking CANCELED` event prefix,
   - the daemon does NOT re-enter CODING on `PR-A`.
7. Asserts the post-recovery queue derivation is correct via `GET /api/repo/{slug}/queue` (or the equivalent dashboard fragment): the recovered queue contains `PR-A` as CANCELED, `PR-B` as TODO, `PR-C` as TODO (its `depends_on: PR-A` does NOT block it because PR-A is CANCELED, not pending — verify this matches production behavior; if production blocks PR-C until PR-A is DONE, update the assertion accordingly), and `PR-D` as TODO. The exact CANCELED-vs-DONE depends-on-resolution policy is the contract this assertion pins.
8. Activates the `success` shim scenario, waits for the daemon to dispatch `PR-B` (the next-priority eligible TODO) within 30 seconds. Asserts `current_task.pr_id == "PR-B"`. This step is the load-bearing one for the PR-266 refactor: it confirms the post-recovery queue derivation actually feeds the IDLE selector correctly.

## Implementation notes

The slow shim sleeps 30 seconds AFTER `git_setup_branch` runs, which creates a local branch but does not push. SIGKILL during the sleep window is the canonical "before push" crash: the branch exists locally inside the killed daemon's container filesystem, no PR was created, no remote ref exists. This matches the PR-186 contract precisely. Confirm the timing window by inspecting `tests/e2e/lib/coder_shim.sh:run_slow` and adjust the wait between CODING-state observation and SIGKILL accordingly.

The post-recovery queue assertion is the most fragile piece. The dashboard's queue endpoint may be backed by `RepoState.current_queue` (post PR-263) or by parsing `tasks/QUEUE.md` (pre PR-263, current production at PR-258d ship time). Use whichever surface is current. Because PR-258d depends on nothing in the Sprint 15a #6 batch, it must work against the production code at the time of upload, which writes QUEUE.md. The test asserts on the queue endpoint output, not the underlying file, so the contract is stable across the migration.

The `depends_on` resolution policy for a CANCELED dependency is a real gotcha. Read `src/queue_parser.py` and `src/task_status.py` to determine whether `PR-C` (depending on a CANCELED `PR-A`) is itself TODO or BLOCKED post-cancel. Pin the assertion to the production behavior. If the production behavior is undocumented and the test author needs to make a call, the conservative pin is "CANCELED dependency does NOT unblock dependents" (so `PR-C` is BLOCKED and the daemon picks `PR-B` as next eligible). If the production behavior is the opposite, update the test to match. The assertion's value is in pinning the existing behavior, not in dictating a new one.

The 120-second deadline in step 6 mirrors the existing test_sigkill_recovery.py and is the budget for daemon container restart plus first IDLE tick plus state publication. Do not shorten it.

The 30-second deadline in step 8 covers one IDLE poll period plus DAG selection plus state publication. If the test stack uses a longer poll period in the test profile, raise the deadline accordingly; do not lower the production poll period to suit the test.

The shim cleanup (`exit_context`) at the end of the test must restore the scenario to `success` so subsequent tests start from a clean slate. This is already handled by the `coder_shim` context manager's `finally` block; do not add redundant cleanup.

## Success criteria

1. After `docker kill --signal=KILL` mid-CODING with the slow shim active, the daemon container exits with code 137.
2. After restart, the daemon reaches IDLE within 120 seconds with `current_task is None` and a fresh `last_updated`.
3. The history contains the `[INFRA] Task PR-A crashed, marking CANCELED` event prefix.
4. The daemon does NOT re-enter CODING on `PR-A` during the recovery window.
5. The post-recovery queue endpoint reports `PR-A` as CANCELED and the remaining tasks with their correct statuses per the production depends-on resolution policy.
6. After switching the shim scenario to `success`, the daemon dispatches the next-priority eligible TODO (`PR-B` if `PR-C` is BLOCKED on the CANCELED `PR-A`, or `PR-C` if the production policy unblocks dependents on cancel) within 30 seconds.
7. The test passes locally and in CI without flake on three consecutive runs.
8. No production code modified.
