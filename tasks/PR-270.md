## Problem

Daemon currently dispatches coders via the trigger-phrase contract: `plugin.run_planned_pr(repo_path, **kwargs)` invokes the CLI with literal prompt `"PLANNED PR"` (single line, two words). The coder is then expected to discover its task by reading AGENTS.md, finding QUEUE.md, identifying the DOING entry, and opening the corresponding `tasks/PR-*.md` file. This indirection has a recurring failure mode: the coder reads other files in `tasks/` to "understand context" and decides to combine scope across PRs, or reads ghost QUEUE.md entries, or follows AGENTS.md content that has drifted from daemon's actual dispatch state. Observed instances: 2026-04-24 PR-144/PR-145/PR-146 series, 2026-05-05 PR-263 (Codex created PR #350 on `pr-264-api-repo-queue-endpoint` branch with combined PR-263+PR-264+partial PR-265 scope; clean and mergeable but violated DAG dependency contract).

The fix is direct task injection: daemon passes the coder explicit `pr_id`, `task_file`, and the full task body inline, and the coder works strictly from those values. This PR adds the new method to the coder CLI helpers and the plugin Protocol without changing any dispatch site. Daemon switch to the new method lands in PR-271. Manual VS Code workflows continue using `run_planned_pr` indefinitely.

## Scope

Three deliverables:

1. New CLI helper `run_auto_pr_async` in `src/claude_cli.py` and `src/codex_cli.py` that formats the prompt as:
   ```
   AUTO PR
   Task: PR-270
   File: tasks/PR-270.md

   <full task body, the same content the operator uploaded>
   ```
   The method signature is `async def run_auto_pr_async(repo_path: str, pr_id: str, task_file: str, task_body: str, *, model: str | None, timeout: float, ...) -> tuple[int, str, str]`. It delegates to the existing `run_claude_async` / `run_codex_async` low-level invokers with the assembled prompt, preserving all the kwargs the existing `run_planned_pr_async` already accepts.
2. Plugin method `run_auto_pr` on `src/coders/claude.py` and `src/coders/codex.py` that delegates to the new CLI helper. Signature mirrors the CLI helper. Existing `run_planned_pr` plugin method untouched.
3. CoderPlugin Protocol in `src/coders/__init__.py` (or wherever the Protocol lives — verify location before editing) gets `run_auto_pr` added. Both implementations satisfy the new Protocol method.

The existing `run_planned_pr_async` helper, the existing `run_planned_pr` plugin method, and all dispatch sites that call `run_planned_pr` remain UNCHANGED in this PR. The new method is additive only.

## Implementation notes

The prompt format `"AUTO PR\nTask: PR-XXX\nFile: tasks/PR-XXX.md\n\n<task body>"` is chosen so that the coder's prompt parser (whatever logic eventually exists in `coding.py` post-PR-271 to extract `Task:` and `File:` headers) has unambiguous delimiters. The blank line before the task body separates headers from content. Coder is expected to use `Task:` value as `pr_id` and `File:` value as `task_file` when those are needed (e.g., for branch naming, commit message, etc.) without consulting QUEUE.md.

Reading the task body from disk should happen on the daemon side (PR-271), not in the coder CLI helper. The CLI helper is a pure function: it takes `task_body: str` as argument and embeds it in the prompt. Keep the CLI helpers free of filesystem reads — that keeps them testable as pure functions. The disk read happens in PR-271's daemon dispatch site.

The Protocol method addition is the smallest of the three deliverables. Verify the Protocol exists (search for `class CoderPlugin(Protocol)` or `CoderPlugin = Protocol` pattern) and add `run_auto_pr` with the same signature shape that the implementations use.

The kwargs handling pattern: the existing `run_planned_pr_async` accepts `**kwargs` and forwards them to `run_claude_async`. The new `run_auto_pr_async` does the same, with the addition of three new positional-or-keyword arguments `pr_id`, `task_file`, `task_body`. These are not forwarded to `run_claude_async` directly; they are consumed locally to build the prompt string.

Coverage gate: this is Sprint 9 coverage territory by inheritance — new functions in `claude_cli.py` and `codex_cli.py` need 100% coverage. Each of the three test functions per file should exercise both happy path and error propagation. If the new methods can be made unconditional (no branching), the coverage requirement is satisfied by one happy-path test per method.

The `Coder: claude` assignment is intentional: this PR is critical infrastructure that must ship cleanly without scope expansion, and Claude has demonstrated lower scope-drift tendency than Codex on past PRs based on operator's observation log. Even with PR-271/PR-272 not yet shipped, this PR must execute under the existing PLANNED PR dispatch contract; assigning to claude minimizes the risk of meta-failure where the AUTO PR rollout PR itself gets scope-expanded.
