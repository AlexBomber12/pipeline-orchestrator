# PR-273: Scaffolder template AGENTS.md alignment with four-trigger model

Branch: pr-273-scaffolder-auto-pr-template
- Type: refactor
- Complexity: low
- Depends on: PR-271
- Priority: 1
- Coder: claude

## Problem

PR-271 updated the daemon-managed AGENTS.md sections (Work Modes, Quick rules, new AUTO PR runbook) inside the source-of-truth template module that ships content via the PR-192a/b/c reconciliation framework to existing managed repos. That covers repos already onboarded — daemon's reconciliation logic propagates the new content on the next sync cycle.

What PR-271 does NOT cover is the scaffolder template content for newly onboarded repos. The scaffolder has its own initial AGENTS.md template strings that get written into a managed repo on first scaffold pass. If the scaffolder template still references the three-trigger model (PLANNED PR, MICRO PR, FIX FEEDBACK without AUTO PR), every new repo onboarded after PR-271 ships starts with stale AGENTS.md content until the daemon's next reconciliation cycle adds the daemon-managed sections. During that gap, the new repo's AGENTS.md instructs the coder via the old three-trigger model — which means a CODING dispatch in that gap window risks the same scope-expansion failure mode PR-270/271/272 are meant to prevent.

This PR aligns the scaffolder template strings with the four-trigger model so newly onboarded repos start with consistent AGENTS.md content from the very first scaffold, eliminating the reconciliation-gap risk window entirely.

## Scope

Two deliverables:

1. Scaffolder template strings for the initial AGENTS.md scaffold (search source for the exact module — likely `src/daemon/scaffolder.py` or `src/onboarding/scaffolder_templates.py` based on the project's PR-242 era naming) updated to:
   - List four triggers in Work Modes section: AUTO PR, PLANNED PR, MICRO PR, FIX FEEDBACK with the same labels and meanings as the daemon-managed content from PR-271.
   - Include a stub of the AUTO PR runbook section with section markers `<!-- pipeline-orchestrator: managed BEGIN auto_pr_runbook -->` and `<!-- pipeline-orchestrator: managed END auto_pr_runbook -->`. The stub content can be a one-line placeholder (`Daemon-managed section. Content set by pipeline-orchestrator on first sync.`) because the daemon's reconciliation framework will overwrite it with the real content from PR-271's template module on the first IDLE cycle. The stub exists only to ensure the section markers are present from the moment of scaffold so the daemon's reconciliation has a clear destination block to write into.
   - Update the Quick rules section to mention the daemon's AUTO PR mode alongside the existing manual-mode triggers.
2. `docs/onboarding.md` updated to mention the four-trigger model and to clarify that AUTO PR is the daemon's invocation mode. The onboarding doc is consumed by humans setting up new managed repos; updating it keeps the operator-facing documentation aligned with the runtime contract.

The scaffolder change is additive only on the AUTO PR side. The PLANNED PR / MICRO PR / FIX FEEDBACK sections remain in the scaffolder template because manual VS Code workflows still use them — those are not deprecated.

## Implementation notes

The scaffolder template module location is the first thing to verify. PR-242 introduced the scaffolder's CLAUDE.md handling; PR-192c brought in onboarding documentation; the actual content composition for AGENTS.md likely lives in either `src/daemon/scaffolder.py` directly (if it builds the AGENTS.md from inline string constants) or in a separate `src/onboarding/agents_md_template.py` module (if PR-192a's framework was extended). Grep for `## Work Modes` literal string to find where the template lives.

If the scaffolder builds AGENTS.md by composing daemon-managed sections via the PR-192a/b/c framework (i.e., scaffolder calls into the same template module that PR-271 edits), then this PR's deliverable becomes simpler: just add the new `auto_pr_runbook` section markers to the scaffold-time stub. The actual content is already in PR-271's module and gets injected by reconciliation on first sync. In that case, the scaffolder change is purely about adding the BEGIN/END marker pair so the daemon has somewhere to write.

If the scaffolder has independent template strings (separate copy from the PR-271 module), this PR has to update those copies too. That's a duplication that should ideally be unified in a future PR (PR-FUTURE-1 territory), but for now we accept the duplication and update both places — and add a unit test that compares the scaffolder template content to the PR-271 daemon-managed content for any drift. (Test: `test_scaffolder_template_matches_daemon_managed_content` — diff the two sources, assert they agree on Work Modes content.)

`docs/onboarding.md` is the operator-facing reference. The change there is documentation only — update the trigger phrase list and add a sentence explaining that AUTO PR is the daemon's mode. Do not document internal implementation details (Task/File header parsing, hook installation, etc.); those belong in code comments.

The scaffolder runs on every onboarding pass and on every IDLE cycle's reconciliation step (per the PR-192c framework). After this PR ships, the next IDLE cycle on each managed repo will:
1. PR-271's daemon-managed sections write the full AUTO PR runbook content into the existing AGENTS.md (existing repos already have section markers from PR-192b's apply step).
2. PR-273's scaffolder template ensures any future re-scaffold operation produces AGENTS.md with the AUTO PR markers in place from the start.
