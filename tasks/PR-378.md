## Problem

Suppression detail (excerpt, counters, approved_once) lives in Redis and is lost on Redis flush or on the second machine. The coarse fact - "this task is suppressed and the high-level reason" - must survive durably so the system degrades safely: after Redis loss, a guardrail-failed task must not auto-retry. Frontmatter is the durable store (git, the user contract), but it currently holds only `status`. It cannot distinguish "errored by guardrail, fix the spec" from "errored by crash, safe to retry".

This PR adds exactly one new frontmatter field, `blocked_reason`, carrying a canonical `SuppressionReason` value. This is the coarse durable layer of the two-layer model (refactor invariant 3). It is the minimum addition to the user-facing contract - one enum field, never the rich detail (excerpt, counters stay in Redis). This is R1.3; R1.4 makes `_transition_to_error` write it.

## Solution

### Writer adds blocked_reason atomically with status

Extend `write_frontmatter_status` (or add a sibling `write_frontmatter_status_and_reason`) so that when the daemon marks a task ERROR it can write `status` and `blocked_reason` in the SAME ruamel.yaml dump and the SAME git commit. Refactor invariant 7 and the commit-storm analysis: this must not add a second commit. The field is set in the same CommentedMap mutation as status, then dumped once.

Signature decision: prefer extending the existing function with an optional `blocked_reason: SuppressionReason | None = None` parameter so the single-commit guarantee is structural. When `blocked_reason` is None and status is not ERROR, do not write the field (avoid polluting TODO/DONE files with an empty reason). When status is set to ERROR, `blocked_reason` should be supplied; if a caller sets ERROR without a reason, default to crash and the field is written so the coarse layer is never missing a reason on an ERROR task. Decide and document this default.

### Clearing the field on recovery

When a task returns to TODO (Retry/reupload), `blocked_reason` must be removed so a recovered task does not carry a stale reason. Add removal of the field when status is written back to TODO. Confirm by reading the retry path (`src/web/routes/repo_control.py` retry endpoint writes TODO via `write_frontmatter_status`) that the TODO write goes through this function so the field is cleared there. If the retry path writes TODO through a different code path, ensure that path also clears the field.

### Parser reads the field

Extend `TaskHeader` with a `blocked_reason: str | None = None` field and parse it from frontmatter alongside `frontmatter_status`. A file without the field parses to None (legacy and TODO files are unaffected). Validate that a present `blocked_reason` is a member of the canonical taxonomy from PR-376; an unknown value is a parse rejection (consistent with how unknown status values are rejected) so a typo cannot silently produce an uncategorized suppression.

### Backward compatibility

Legacy header-format files (no frontmatter) and frontmatter files without `blocked_reason` parse exactly as before. The 301 legacy files are untouched by this PR. The field is additive.

### Document the contract

Update `docs/TASK_SCHEMA.md` to document `blocked_reason`: it is daemon-owned (operators never set it), present only on ERROR tasks, carries a canonical SuppressionReason, and is the durable coarse layer that lets the system stay fail-safe when the Redis rich layer is lost.

## Threat model

**Threat addressed**: after Redis loss the system cannot tell a guardrail failure (do not auto-retry, fix spec) from a crash (safe to retry), so it would either lose the safety stop or lose the recoverability. The durable coarse layer preserves the safe behavior.

**Threat introduced**: a new frontmatter field is part of the user contract and gets committed to the user repo. Mitigated by keeping it to ONE enum field (no rich detail), daemon-owned, documented, and removed on recovery so TODO files stay clean.

**Other layers protecting**: the Redis rich layer carries the full detail when present; this field is only the coarse fallback. The parser rejection of unknown values prevents an uncategorized suppression from a typo.

The `TaskHeader` gains a field with a default, so existing constructions are unaffected.
