## Problem

Sprint 15b/15c added Tier 1 and Tier 2 guardrails that detect dangerous coder actions (repo creation, force-push, large diffs, secrets, mass-deletion, governance changes). On hit, the task transitions to ERROR via `_transition_to_error` with subsource=guardrail and operator gets a Retry button.

But the PR with the violating diff is still mergeable through normal GitHub UI. A careless operator can hit "Merge" on the GitHub PR page bypassing the daemon entirely. The daemon's protection layer ends at "park the task"; it does not also protect the PR from merge.

Quarantine model: on guardrail hit, daemon tags the PR with a label `quarantine:{type}` (e.g. `quarantine:large_diff`, `quarantine:secrets_detected`), posts a comment with the GUARDRAIL details, and adds the PR to `state.quarantined_prs[name]` set. Daemon refuses to merge quarantined PRs even when CI is green and review is approved. Only operator action (clearing the label OR calling the `/repos/{name}/quarantine/{pr}/release` endpoint) un-quarantines.

This adds a second layer of protection: the daemon will not auto-merge a flagged PR even if reviewers approve it without realizing the GUARDRAIL context.

## Solution

### Label vocabulary

Labels mirror the GuardrailViolation category strings:

- `quarantine:large_diff` - PR exceeded large_diff_addition_threshold or large_diff_files_threshold.
- `quarantine:secrets_detected` - PR contained secrets per Group A/B/C patterns.
- `quarantine:mass_deletion` - PR exceeded mass_deletion_threshold or test_deletion_threshold.
- `quarantine:governance` - PR touched .github/CODEOWNERS, .github/dependabot.yml, .github/labels.yml, .github/settings.yml.
- `quarantine:repo_create` - Tier 1 stdout pattern matched.
- `quarantine:repo_delete` - Tier 1 stdout pattern matched.
- `quarantine:branch_delete_main` - Tier 1 stdout pattern matched.
- `quarantine:workflow` - Tier 1 diff scan matched workflow YAML modification.
- `quarantine:permissions_escalation` - Tier 1 diff scan matched.
- `quarantine:branch_protection_modification` - Tier 1 diff scan matched.
- `quarantine:dangerous_action_external_install` - Tier 1 diff scan matched.
- `quarantine:direct_commit_no_pr` - PR-300 main commit audit detected (post-merge audit category, applied retroactively).

Each label uses red color `B60205` (matches existing `escalated` label).

### Label application on guardrail hit

Inside the existing GuardrailViolation handling in `src/daemon/guardrails.py` (search for the `_transition_to_error` call sites with `subsource="guardrail"`), add a call to a new helper `apply_quarantine_label_for_violation`:

```python
def apply_quarantine_label_for_violation(
    runner: "PipelineRunner",
    pr_number: int,
    violation: GuardrailViolation,
) -> bool:
    """Apply quarantine label and write GUARDRAIL comment on the PR.

    Returns True if both label and comment posted. Soft-fails on
    either step (the load-bearing protection is the in-memory
    quarantined_prs set + handle_merge gate, not the label).
    """
    label = f"quarantine:{violation.category}"
    try:
        gh_runner.run_gh([
            "label", "create", label,
            "--color", "B60205",
            "--description", f"Daemon quarantined: {violation.rule}",
        ], repo=runner.owner_repo)
    except Exception as exc:
        runner.log_event(f"[GUARDRAIL] label create skipped: {exc}.")
    try:
        gh_runner.run_gh([
            "pr", "edit", str(pr_number),
            "--add-label", label,
        ], repo=runner.owner_repo)
    except Exception as exc:
        runner.log_event(
            f"[GUARDRAIL] label apply on PR #{pr_number} failed: {exc}."
        )
        return False
    try:
        body = (
            f"## QUARANTINE: {violation.category}\n\n"
            f"This PR has been flagged by the daemon's guardrail layer.\n\n"
            f"**Rule:** {violation.rule}\n\n"
            f"**Details:**\n```\n{violation.details}\n```\n\n"
            f"This PR will not be auto-merged by the daemon. To release "
            f"the quarantine, either remove the `{label}` label manually "
            f"or POST to `/repos/{{name}}/quarantine/{pr_number}/release`."
        )
        gh_runner.run_gh([
            "pr", "comment", str(pr_number),
            "--body", body,
        ], repo=runner.owner_repo)
    except Exception as exc:
        runner.log_event(
            f"[GUARDRAIL] comment post on PR #{pr_number} failed: {exc}."
        )
    return True
```

### Merge gate

In `src/daemon/handlers/merge.py`, at the entry of the merge action (after ready-to-merge checks pass), add:

```python
if current_pr.number in self.state.quarantined_prs:
    self.log_event(
        f"[MERGE] PR #{current_pr.number} is quarantined "
        f"({len(self.state.quarantined_prs)} quarantined in this repo); "
        f"refusing to merge."
    )
    # Stay in WATCH; do not transition to ERROR (operator may
    # release quarantine intentionally).
    self.state.state = PipelineState.WATCH
    await self.publish_state()
    return
```

### Release endpoint

New route in `src/web/routes/repo_control.py`:

```python
@router.post("/repos/{name}/quarantine/{pr_number}/release")
async def release_quarantine(name: str, pr_number: int, request: Request):
    """Operator-triggered release of a quarantined PR.

    Removes the quarantine label, removes the PR from in-memory
    quarantined_prs set, writes audit log entry, returns 200 on
    success. Idempotent: releasing a non-quarantined PR returns
    200 with status "not_quarantined".
    """
    runner = await _get_runner(name)
    if pr_number not in runner.state.quarantined_prs:
        return JSONResponse({"status": "not_quarantined", "pr": pr_number})
    # Remove all quarantine:* labels from the PR.
    try:
        labels = gh_runner.run_gh([
            "pr", "view", str(pr_number),
            "--json", "labels",
            "-q", ".labels[].name",
        ], repo=runner.owner_repo).split("\n")
        for label in labels:
            if label.strip().startswith("quarantine:"):
                gh_runner.run_gh([
                    "pr", "edit", str(pr_number),
                    "--remove-label", label.strip(),
                ], repo=runner.owner_repo)
    except Exception as exc:
        runner.log_event(f"[QUARANTINE] label removal failed: {exc}.")
    runner.state.quarantined_prs.discard(pr_number)
    await runner.publish_state()
    # Audit log via existing operator_actions infrastructure
    await write_operator_action_audit(
        action="quarantine_release",
        repo=name,
        pr=pr_number,
        operator_session_id=request.headers.get("X-Session-Id", "unknown"),
    )
    return JSONResponse({"status": "released", "pr": pr_number})
```

### Audit log

Reuse the existing operator_actions audit infrastructure (PR-336). Quarantine apply and release both write JSONL entries to `/data/audit/operator-actions/YYYY-MM-DD.jsonl`.

Apply entry:
```json

```

Release entry:
```json
{"ts": "...", "event": "quarantine_release", "repo": "...", "pr": 442, "operator_session_id": "..."}
```

### Label-removal detection on WATCH

On WATCH cycle, if PR has no `quarantine:*` label but IS in `state.quarantined_prs` set, treat as operator-released (they manually removed the label via GitHub UI). Remove from set, log the externally-released transition. Avoids stale in-memory state.

## Threat model

**Threat addressed**: a flagged PR can still be merged via GitHub UI by an operator who does not see the GUARDRAIL signal. Quarantine layer makes the protection PR-level (visible via label and blocked at daemon merge gate) rather than just task-level (parked in ERROR but PR still mergeable).

**Other layers protecting**: GuardrailViolation already parks the task in ERROR via _transition_to_error with subsource=guardrail. Operator must Retry to attempt the same PR again. Quarantine adds the GitHub-side label + comment so the PR page itself shows the warning.

**Why this layer needed**: the existing layer protects against the daemon merging on its own, but does not protect against operator-driven manual merge. Adding the label provides visibility on the GitHub PR page itself. Adding the merge gate ensures even if the daemon somehow re-enters MERGE on a quarantined PR (e.g. via Retry without operator awareness), the merge is still blocked.

## Success signal

On test fixture: GuardrailViolation fires on PR-XXX. Daemon parks task in ERROR (existing behavior) AND applies `quarantine:large_diff` label to PR. PR page on GitHub shows the label and a GUARDRAIL comment. Operator attempts `gh pr merge` manually; merge proceeds at the GitHub level but the daemon's handle_merge refuses to merge it via daemon, so the next daemon cycle does not attempt re-merge. Operator clicks Release Quarantine endpoint; label removed, in-memory set cleared, audit log entry written. Daemon resumes normal MERGE eligibility on next cycle.
