# PR-186: Recovery skip crashed-task-retry

Branch: pr-186-recovery-skip-crashed-retry
- Type: bugfix
- Complexity: low
- Depends on: none
- Priority: 1
- Coder: any

## Problem

If a task fails during CODING or PREFLIGHT (coder errors, preflight check fails, etc), recovery currently picks the same task again on next cycle. This can produce a loop where the same task fails the same way repeatedly until manual intervention.

The fix is to mark the task as crashed and skip it on next pick, falling back to the next TODO. This is similar in spirit to the existing PR-190a bounded-retry counter (which handles repeated coder failures on the same task) but applies one level higher: if the task itself caused a crash, do not retry the same task in a loop.

## Scope

In `src/daemon/recovery.py`, when recovery detects a previously-crashed task (signaled by remaining `current_task` after an unclean shutdown or a state=ERROR transition), mark the task as CANCELED in the QUEUE rather than re-picking it. The next IDLE cycle picks the next TODO task in dependency order.

The user can manually re-mark the task as TODO in the task file and re-upload to retry.

## Files to modify

`src/daemon/recovery.py`:
- In the recovery entry path, detect `state=ERROR with task in DOING state` or `crash signature with current_task set`.
- Update the task header status to CANCELED via existing task_status writer.
- Log event: `Task {pr_id} crashed, marking CANCELED. Manually re-upload to retry.`
- Clear `current_task` and transition to IDLE.

`src/task_status.py`:
- Confirm CANCELED status writer exists; if not, add it (this is part of the existing TaskStatus enum, no new states needed).

`tests/test_recovery.py`:
- Test: recovery detects crashed CODING task, marks CANCELED, transitions IDLE.
- Test: recovery detects crashed PREFLIGHT task, same behavior.
- Test: recovery detects normal IDLE shutdown, does NOT mark anything CANCELED.

## Implementation notes

Distinguish "crashed" from "stopped by user" carefully. User-initiated stop (Stop button) should not mark task CANCELED — it should leave task in DOING and resume normally on Play. Crashed = subprocess kill via SIGKILL/OOM, daemon restart with state still showing DOING but no live coder process.

Hint signal: the existing `_preserve_crashed_run_commits` path triggers on this exact condition. If that path runs and there are no preserved commits, it is a crash with no progress. If there are preserved commits, the recovery may want to keep going.

For this PR, conservative approach: any recovery from non-IDLE state where current_task is set → mark CANCELED + log + IDLE. Aggressive optimization (preserve and continue) can be a follow-up.
