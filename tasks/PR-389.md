# PR-389: Decompose _check_rate_limit into named predicates

Branch: pr-389-decompose-rate-limit
- Type: refactor
- Complexity: high
- Depends on: none
- Priority: 2

## Reading order before coding

1. Read this entire spec.
2. Read `src/daemon/rate_limit.py` in full - especially `_check_rate_limit` (lines 242-360, 228 lines, ~37 branches), `_proactive_usage_check`, `_detect_rate_limit`, `_record_rate_limit`, `_clear_rate_limit`, `_rate_limit_until_for`.
3. Read `tests/test_rate_limit.py` - the existing behavior contract this PR must preserve exactly.
4. Identify the distinct concerns inside `_check_rate_limit`: legacy pauses without coder attribution (pre-PR-066), per-coder pause checks, cross-coder clearable logic (one coder rate-limited, another active), diagnosis pauses, and the proactive-vs-reactive split.

## Problem

`_check_rate_limit` is the worst single function by complexity: 228 lines, ~37 branches, accreted from PR-066 legacy pauses, per-coder attribution, diagnosis pauses, and cross-coder clearable logic. It is near-untestable as a whole and is where the rate-limit-vs-spend-ceiling confusion lives. At two coders, the "one limited, other active" combinatorics make it almost certain some state combination is handled wrong.

This PR decomposes the monolith into named, individually-testable predicate functions WITHOUT changing any behavior. It is the prerequisite for R3.2 (merging spend-ceiling into the gate) - you cannot safely merge into a 228-line monolith. This is R3.1.

## Solution

### Behavior-preserving decomposition

Break `_check_rate_limit` into small named functions, each answering one question, composed by a thin orchestrator. Candidate decomposition (refine by reading the actual branches):

- `_legacy_pause_active(now) -> bool` - the pre-PR-066 attribution-less pause check.
- `_effective_coder_pause(coder, now) -> PauseVerdict` - is THIS coder paused, and until when.
- `_cross_coder_clearable(effective_coder, pause_coder, now) -> bool` - the "other coder paused but this one can run" logic.
- `_apply_pause_state(verdict)` - the state mutation (PAUSED, rate_limited_until, etc.) extracted so the decision functions are pure.
- A thin `_check_rate_limit` orchestrator that calls these in the same order and produces the same result.

Each extracted function is pure (decision) or narrowly side-effecting (state apply), so each gets focused tests.

### Identical behavior is the contract

This is a pure refactor. The orchestrator must produce byte-identical outcomes to the current function for every input combination. Do NOT fix any suspected bug here - if decomposition reveals a real bug, note it for a follow-up; this PR only restructures. The existing `tests/test_rate_limit.py` must pass unchanged, and new per-predicate tests are added on top.

### Map the branches before cutting

Before writing any extraction, produce a branch map: enumerate the ~37 branches and assign each to one of the new predicate functions. Include this map in the PR description so the reviewer can verify no branch was dropped or merged incorrectly. This is the safety mechanism for a high-branch decomposition.

### Keep reactive detection separate

`_detect_rate_limit` (stderr parsing for 429 / "try again in X") is already a separate function - leave it as the reactive layer. The decomposition is of the proactive gate (`_check_rate_limit` / `_proactive_usage_check`). Document the proactive-vs-reactive boundary clearly so R3.2 knows where spend-ceiling (proactive-only) plugs in.

## Files to change

- `src/daemon/rate_limit.py` - decompose `_check_rate_limit` into named predicates + thin orchestrator; extract state-apply (~150 LoC restructure, net LoC roughly flat or down).
- `tests/test_rate_limit.py` - existing tests pass unchanged; add per-predicate tests in a new section or `tests/test_rate_limit_predicates.py`.

## Files NOT to touch

- `_detect_rate_limit` - the reactive layer stays as-is.
- spend-ceiling (`_check_spend_ceiling`) - merged in R3.2, not this PR.
- Any caller of `_check_rate_limit` - the orchestrator keeps the same signature and return contract.

## Test acceptance criteria

- All existing `tests/test_rate_limit.py` tests pass unchanged (the behavior-preservation contract).
- `test_branch_map_complete`: a meta-assertion or documented mapping that every original branch is represented in a predicate (verified in review via the branch map; the test asserts the predicates collectively cover the documented input space).
- `test_legacy_pause_predicate`: focused tests for `_legacy_pause_active` across its input cases.
- `test_effective_coder_pause_predicate`: focused tests for the per-coder pause verdict.
- `test_cross_coder_clearable_predicate`: focused tests for the one-limited-other-active logic, including the combination most likely to be mishandled (both coders with different reset windows).
- `test_orchestrator_matches_original`: property-style or table test feeding many state combinations through both a captured-original-behavior oracle and the new orchestrator; assert identical results. If an oracle is impractical, assert the documented expected outcome for an enumerated set of combinations covering all predicate branches.
- `test_state_apply_isolated`: assert the decision predicates are pure (no state mutation) and only `_apply_pause_state` mutates.

## Threat model

**Threat addressed**: a 228-line / 37-branch function is near-untestable and likely harbors a wrong-state-combination bug; it also blocks safely merging spend-ceiling.

**Threat introduced**: decomposition could subtly change behavior. Mitigated by keeping existing tests passing unchanged, the explicit branch map proving coverage, the orchestrator-matches-original test, and the rule that no suspected bug is fixed here (restructure only).

**Other layers protecting**: the reactive `_detect_rate_limit` is untouched and still catches actual 429s as a backstop regardless of proactive-gate refactoring.

### Caller audit

`_check_rate_limit` keeps its signature and return contract; grep its callers and confirm none need change. The extracted predicates are internal; they have no external callers yet (R3.2 will compose spend-ceiling alongside them).

## Out of scope

- Merging spend-ceiling (R3.2).
- Fixing any bug the decomposition reveals (follow-up PR).
- Changing the reactive detection.
- UI changes (R3.3).

## Success signal

On test fixture: existing rate-limit tests pass unchanged; each predicate has focused tests; the orchestrator matches the original across enumerated combinations; the branch map shows full coverage. On production: identical rate-limit behavior, but the logic is now a set of named, testable predicates ready for spend-ceiling to plug in.
