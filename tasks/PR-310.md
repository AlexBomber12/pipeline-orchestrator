# PR-310: GUARDRAIL distinct dashboard filtering and metrics — separate guardrail-subsource ESCALATEs from generic ERRORs across UI surfaces

Branch: pr-310-guardrail-distinct-dashboard-filtering
- Type: feature
- Complexity: low
- Depends on: PR-306
- Priority: 2
- Coder: codex

## Problem

After Sprint 15b Phase 2 + PR-305/306, guardrail-flagged tasks are stored as cancellation causes with `category=ESCALATE, payload.subsource="guardrail"`, alongside other ESCALATEs (subsource coder, daemon, operator_reject). Phase 2 made all final failures terminate at `frontmatter status:ERROR + state IDLE + cancellation_cause`. From the operator's perspective today:

- The Tasks queue UI (Phase 2 PR-282) groups all error-state tasks under "ERROR" badge regardless of subsource. Operator must click each to read the cause subsource.
- The cancellation_card UI (Phase 2 PR-281) renders ESCALATE causes uniformly; PR-281 added subsource differentiation in render text but no separate filtering or grouping.
- The PR-306 guardrail panel surfaces guardrail-flagged tasks ONLY when there is a pending decision; once operator approves or rejects, the task disappears from the panel but its cancellation cause record persists in history.
- Run record metrics (Phase 2 PR-286) include `cause` field but do not separate guardrail-vs-coder-vs-daemon ESCALATE for analytics.

The original pre-Phase-2 PR-297 design proposed a distinct `PipelineState.QUARANTINE` enum value to keep guardrail-flagged tasks visually and behaviorally separate from generic HUNG. After Phase 2 removed HUNG, the equivalent distinction is by **subsource on ESCALATE causes**. PR-310 plumbs the subsource through dashboard filtering, tasks queue grouping, and run record metrics so the distinction is operator-visible without a new enum value.

This is **UX polish + analytics plumbing**, not a state machine refactor. Distinct PipelineState is intentionally NOT introduced — the Phase 2 architecture keeps PipelineState count at 8 (PREFLIGHT/IDLE/CODING/WATCH/FIX/MERGE/ERROR/PAUSED) and adding QUARANTINE would re-introduce the proliferation problem Phase 2 solved.

## Scope

### 1. Tasks queue UI sub-grouping by ERROR cause subsource

In `src/web/templates/components/tasks_panel.html` (Phase 2 PR-282), the existing ERROR badge group is split into two visual subgroups when guardrail entries exist:

- "ERROR — guardrail" subgroup: tasks with `cancellation_cause.payload.subsource == "guardrail"`. Rendered with amber/yellow accent, indicating "operator decision needed".
- "ERROR — other" subgroup: tasks with subsource in {coder, daemon, operator_reject}, OR no cancellation_cause record (legacy). Rendered with red accent, indicating "automatic failure".

Sub-grouping appears only when at least one guardrail-subsource entry exists. Otherwise existing flat ERROR list is preserved.

### 2. Cancellation history filter widget

In `src/web/templates/components/cancellation_history.html` (or wherever the cancellation history view lives — find via grep), add a filter dropdown:

```html
<select name="subsource_filter" hx-trigger="change" hx-get="/repos/{name}/cancellation_history" hx-target="#history-list">
    <option value="">All</option>
    <option value="guardrail">Guardrail only</option>
    <option value="coder">Coder ESCALATE only</option>
    <option value="daemon">Daemon-detected only</option>
    <option value="operator_reject">Operator rejections only</option>
</select>
```

Backend route accepts `subsource_filter` query param and filters cancellation cause results accordingly.

### 3. Run record metrics: distinct cause sub-categories

Phase 2 PR-286 added `cause` field on RunRecord with values `CRASH/ESCALATE/TIMEOUT/INFRA/NO_PUSH_DEADLOCK`. PR-310 extends the cause column for ESCALATE entries to record subsource alongside.

New optional field on RunRecord: `cause_subsource: Literal["coder", "daemon", "guardrail", "operator_reject"] | None = None`. Populated only when `cause == "ESCALATE"`. Other causes leave subsource None.

Update save_run_record callsites (Phase 2 PR-286) to pass subsource through. Backfill script for legacy ESCALATE records (PR-310-companion) sets subsource=None for unknown legacy entries — analytics queries that need subsource filtering exclude these via `WHERE subsource IS NOT NULL`.

### 4. Analytics queries enabled by this PR

After PR-310 ships, the following queries become trivial:

- "Failure rate by guardrail rule": filter cause=ESCALATE + subsource=guardrail, group by `cancellation_cause.payload.rule`. Surfaces which guardrail (large_diff, secrets, mass_deletion, etc) fires most often.
- "Operator override rate": count operator_reject vs operator_approve outcomes. Approve = cause cleared by PR-305 endpoint (run record gets outcome=merged); Reject = subsource=operator_reject in run record. Ratio reflects guardrail false-positive rate.
- "Coder ESCALATE rate by complexity": filter cause=ESCALATE + subsource=coder, group by `complexity` field. High coder-ESCALATE rate on high-complexity tasks signals task decomposition need.
- "Daemon-detected ESCALATE by category": filter cause=ESCALATE + subsource=daemon, group by `cancellation_cause.payload.reason_text` keyword. Surfaces which daemon-side detection fires most (review timeout, NO_PUSH_DEADLOCK fallback, FIX cap).

Implementation of these queries is NOT in scope of PR-310. PR-310 is the data + UX substrate; specific analytics dashboards are separate Sprint 16+ work.

## Implementation notes

The decision to plumb subsource through metrics rather than introducing a distinct PipelineState reflects the Phase 2 architectural choice: keep state machine narrow, push semantic differentiation into payload data. This composes better with future cause categories (e.g., if Sprint 16 adds a "performance_regression" subsource) — no enum change needed, just a new payload value.

The Tasks queue sub-grouping is the most operator-visible part of PR-310. After deploy, operator's Tasks queue now answers "what needs my attention?" at a glance: guardrail-subgroup entries need decisions; other-subgroup entries need triage or are awaiting Retry/re-upload.

Operator reject action (PR-305 reject flow) writes subsource=operator_reject. This should NOT appear in the guardrail subgroup (operator already decided), and should NOT appear as actionable in PR-306 panel (panel filters by subsource=guardrail only). The cancellation history filter does include operator_reject as a separate option for audit retrospection.
