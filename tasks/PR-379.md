## Problem

Most `_transition_to_error` callsites set repo state to ERROR and record a Redis cancellation cause, but do not write the task's frontmatter status. So the task stays at its prior frontmatter status (often DOING), the dashboard renders it in the "doing" group, and the Retry button (which only appears for tasks in the "error" group) never shows. The operator is stuck: daemon is in ERROR, but there is no task-level Retry, and the coarse durable layer is missing so a Redis flush loses the reason entirely. Only watch.py and merge.py currently write status first.

This PR makes the coarse durable write (frontmatter status:error + blocked_reason) a guaranteed part of every ERROR transition. It fixes the audit's bug #4 and begins collapsing the `status_write_failed` mechanism (52 references) into "the coarse write is mandatory; if it fails, retry it" rather than a separate parked-state machine. This is R1.4. Refactor invariant 3: coarse durable layer written first.

## Solution

### Move the coarse write inside _transition_to_error

`_transition_to_error` already accepts a `cancellation_cause` carrying the canonical subsource. Use it to derive the `SuppressionReason` (via PR-376 mapping when the cause came from an ErrorCategory path, or directly when the cause already carries a canonical subsource). Then, as part of the transition and BEFORE the best-effort Redis cause write, perform the coarse durable write: frontmatter status ERROR + blocked_reason, via the PR-378 writer through `_commit_task_status_change` (extended to pass blocked_reason).

Order (refactor invariant 3): coarse durable write first (it is the safety-critical fact), then the rich Redis cause write best-effort. If the coarse write fails, that is the only genuinely failed write - handle it as a retryable infra error, not as a separate parked-state mechanism.

### Add a parameter to control the coarse write

The two callsites (watch.py, merge.py) that already wrote status before calling `_transition_to_error` must not double-write. Add a parameter `commit_task_status: bool = True` to `_transition_to_error`. Default True (the common case writes the coarse layer). The two pre-writing callsites pass `commit_task_status=False` and instead pass the reason so the transition still derives blocked_reason for the cause. Audit those two callsites to ensure they pass the same reason they wrote, so coarse and rich agree.

### Collapse status_write_failed into a retry of the coarse write

Today `_mark_status_write_failed_task` registers an in-memory marker and a Redis set when the frontmatter write fails, then a parallel machinery keeps the task parked. With the coarse write now mandatory and primary, simplify: if the coarse write fails, log it as an infra error and retry on the next cycle (the transition still set state to ERROR in memory, so the daemon does not proceed past it). Do NOT delete the `status_write_failed` mechanism in this PR if other code still reads it - that full removal is R1.6. In this PR, ensure the coarse write is attempted on every transition and that a failure is visible and retried, reducing reliance on the parked-marker path. Read all readers of `status_write_failed_tasks` before deciding how much to simplify here versus defer to R1.6.

### Reason derivation must be exhaustive

Every `_transition_to_error` callsite must end up with a non-None canonical reason for the coarse write. For callsites that pass an explicit `cancellation_cause`, take the reason from it. For callsites that pass none (the default crash cause), use crash. For the guardrail callsite (coding.py), the cause already carries subsource guardrail - that becomes blocked_reason guardrail, which is the fix that lets R1.5 give guardrail a proper operator-park exit. Verify by reading each callsite that the derived reason matches the failure it represents.

- `test_guardrail_transition_writes_guardrail_reason`: drive the guardrail path; assert frontmatter blocked_reason is guardrail (the fix that unblocks R1.5).

- `test_coarse_before_rich`: assert the frontmatter (coarse) write is attempted before the Redis cause (rich) write; if the rich write fails, the coarse write still happened.
- `test_coarse_write_failure_retried`: simulate the coarse write failing; assert it is logged as infra and the daemon stays in ERROR (does not proceed), so the next cycle retries.
- `test_every_callsite_reason_nonnull`: parametrized over the cause types the callsites pass; assert each yields a non-None canonical reason for the coarse write.
- `test_reason_matches_cause`: for a sample of callsites (guardrail, infra, review_timeout, crash), assert the blocked_reason written matches the cause subsource.

## Threat model

**Threat addressed**: ERROR transitions that do not write the task status leave the task in DOING, hide the Retry button, and lose the reason on Redis flush (audit bug #4). The operator is stuck with no recourse short of docker restart.

**Threat introduced**: the coarse write is the heavy git path (fetch+reset+commit+push to main). Doing it on every transition adds git ops. Mitigated by the existing low frequency (transitions are 1-2 per task lifetime, per the commit-storm analysis), by the `commit_task_status=False` opt-out for callsites that already wrote, and by collapsing rather than adding mechanisms. The 7-git-op path itself (J) is a known future collapse when SQLite owns status.

**Other layers protecting**: the in-memory ERROR state set by the transition keeps the daemon parked even if the coarse write fails, so a failed write degrades to "retry next cycle" rather than "proceed as if not errored".

### Caller audit

This PR exists because of a caller-contract audit. Run `grep -rn "_transition_to_error" src/daemon/`. For each callsite verify: does it pass a cause whose subsource maps to the correct reason? Does it pre-write status (only watch.py, merge.py do)? Document the audit in the PR description as a table of callsite -> reason. The two pre-writing callsites are the only ones that change; the rest are verified-unchanged.

## Out of scope

- Removing the 8 mechanisms (R1.6).
- Rewriting the main-loop ERROR exit (R1.5).
- Variant 2 frontmatter/GitHub reconciliation (R1.7).
- Collapsing the 7-git-op status write into fewer ops (deferred to SQLite era).

## Success signal

On test fixture: every ERROR transition writes status:error + correct blocked_reason in one coarse write, the Retry button appears, and a coarse-write failure parks-and-retries rather than spawning a separate marker machine. On production: a guardrail or crash failure shows the task in the error group with a Retry button immediately, and a `docker compose restart` is no longer needed to surface the button.
