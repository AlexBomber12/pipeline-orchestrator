# PR-395: Bind review requests and approvals to the exact PR HEAD

Branch: pr-395-review-head-provenance
- Type: bugfix
- Complexity: high
- Depends on: PR-394
- Priority: 1
- Coder: any

Audit references: A09.

## Problem and intended result

src/github/reviews.py accepts an anchor +1 without proving which HEAD was reviewed and has a body-reaction fallback that approves when freshness metadata is unavailable. Commit author/committer dates are not authoritative push times. A new HEAD must never inherit approval just because a reaction exists or metadata lookup failed.

Build review evidence around the trusted identity policy from the prerequisite and a concrete review request/HEAD association. Preserve the user's +1 review contract and the exact @codex review trigger.

Verified production connector example: PR #530 has a body +1 by actor 199175422 and a comment by the same actor at https://github.com/AlexBomber12/pipeline-orchestrator/pull/530#issuecomment-5645119473. Its codex-pull-request-review-summary marker identifies a completed Code Review for abbreviated commit 6379c4e, triggered by PR opened. The actual full PR head is 6379c4e5146230929bf7cfbc160eadfc67723bc5. Support this observed shape; requiring every approval to arrive on an explicit comment anchor would break the working connector.

## Required behavior

1. Represent request identity with repo, PR number, full HEAD SHA, invocation kind, exact anchor comment ID when one exists, trustworthy creation/observation metadata and trusted reviewer identity. A PR-open invocation may instead use a trusted review record or the connector completion-summary identity/version. Persist enough provenance to recover an active request after restart without treating the current HEAD as the historical HEAD of an old anchor. Use the existing state/Redis conventions; do not create a second review scheduler.
2. When posting a request, observe HEAD before and after obtaining the created comment ID. Accept the association only if the observations agree. A timeout/ambiguous POST result must be reconciled before another trigger is sent. Preserve existing bounded deduplication, including the case where the coder already posted the required trigger. Unknown historical anchors must be reconciled using trustworthy version evidence or replaced by a fresh request; do not infer identity solely from commit timestamps.
3. Accept an anchor +1 only from a trusted actor on an anchor proven to belong to the current HEAD. A body +1 may be accepted only with independent review provenance tying that trusted review and the approval to the same current HEAD. If the API does not supply enough evidence for that body reaction, remain pending and request a fresh anchored review rather than authorizing from dates alone. Do not replace the +1 contract with a textual APPROVED review by itself.
   Treat the observed trusted connector summary as one explicitly parsed provenance adapter: require its recognized marker, completed relevant review, trusted author, current summary version and resolvable commit identity. Resolve an abbreviated commit unambiguously to the full SHA in the same repository and verify it against the current PR HEAD. A prefix match by itself is insufficient. Reject malformed, ambiguous, conflicting or untrusted summaries. Keep +1 mandatory alongside completed provenance; handle PR-open review without fabricating an anchor. A newer completed summary must not revive a body +1 left over from an earlier review: require affirmative linkage of that reaction to the current review invocation, using trustworthy event metadata, or request a fresh review. Add a recorded-shape fixture for PR #530 with external calls mocked.
4. Remove all approval-on-missing-metadata fallbacks. Eyes remains an in-progress signal; actionable current-request feedback remains changes requested. If positive and negative signals cannot be ordered reliably, wait for a current unambiguous verdict instead of choosing approval.
5. Any HEAD change, including pre-merge sync or an external push, invalidates request-bound approval and relevant scan/review cache state. Preserve bounded request/repost rules without reusing the previous HEAD's exhaustion state. A complete valid same-HEAD request survives polling and restart.
6. Update the review section of docs/operations.md and managed review instructions where needed. State how coder-posted and daemon-posted anchors are reconciled. No broad AGENTS rewrite is part of the task.

## Acceptance criteria

- A +1 on an old anchor is not approval for a new HEAD, including when the new commit has an older commit timestamp.
- Missing commit/review metadata cannot authorize merge.
- A trusted, current, proven anchor +1 passes; untrusted or mismatched request/PR/repo evidence fails to pass.
- Posting ambiguity, duplicate poll, same-second timestamps, external pushes and restart cannot duplicate approval or reuse stale provenance.
- Body-only approval with insufficient HEAD linkage waits and has a bounded path to obtaining a valid current anchor.
- The observed PR-open/body-+1/completed-summary shape passes when its resolved full SHA equals the current HEAD and the reaction belongs to that review; an old body +1 combined with a newer completed summary does not pass.
- Existing timeout/repost tests remain meaningful for the same PR after HEAD changes.
