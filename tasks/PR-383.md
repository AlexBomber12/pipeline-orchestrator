## Problem

`derive_task_status` lets frontmatter win unconditionally. If frontmatter says `done` but the PR is not actually merged (e.g. an optimistic status write, or a status write that succeeded while the merge later reverted), the task is treated DONE while its PR stays open forever - a "zombie task". For the operator's central metric (merged PRs), a zombie task corrupts the count: marked done, work not actually merged.

Operator decision (2026-05-22): Variant 2. GitHub is the source of truth for DONE/DOING (real merge state); frontmatter is the source of truth for ERROR/suppression. This removes zombie tasks at the cost of needing GitHub reachable to confirm DONE - which is safe (an unreachable GitHub leaves the task pending, not falsely done).

This is R1.7. Refactor invariant 1: one owner per fact - merge state is owned by GitHub, suppression by frontmatter.

## Solution

### Reorder the resolution priority

Rewrite `derive_task_status` so the priority is:

1. ERROR / suppression: if frontmatter status is ERROR (and, after R1, if there is an active operator-clearable suppression), the task is ERROR. Frontmatter wins here - this is the suppression layer it owns.
2. DONE: a task is DONE only if GitHub confirms the merge - the branch is in merged_branches, or the PR id is in merged_pr_ids, or a matching merged PR is found. Frontmatter `done` alone is NOT sufficient; it must be corroborated by GitHub. If frontmatter says done but GitHub shows the PR still open, the task is DOING (or TODO if no PR), NOT DONE.
3. DOING: a matching open PR exists, or the task is the current_task.
4. TODO: default.

The key inversion: frontmatter `done` no longer short-circuits. GitHub merge state is consulted for DONE/DOING. Frontmatter still short-circuits for ERROR.

### Handle GitHub-unreachable safely

When the GitHub merge state is unavailable (`MergedState.api_available` is False), do not fabricate DONE from frontmatter. Treat an unconfirmable `done` as DOING/pending so the daemon re-checks when GitHub returns. This is the safe degradation: a task waits rather than being falsely marked done. Read `_resolve_merged_state` to see how api_available is set and ensure the unreachable path does not regress to trusting frontmatter for DONE.

### Preserve the merged-split-parent and alias logic

`derive_task_status` and surrounding code handle split-parent aliases (PR-N satisfied by PR-Na/Nb/Nc) and branch-name matching. Preserve all of that; this PR changes only the frontmatter-vs-GitHub priority for the DONE/DOING decision, not the matching logic.

### Coordinate with the coarse-write contract

PR-379 writes frontmatter done on merge (merge.py). Under Variant 2 that write is still useful as a durable hint and for offline display, but it is no longer authoritative for the DONE decision - GitHub is. Confirm that the merge handler still writes done (for durability and for the analytics/UI), and that derive_task_status corroborates it against GitHub rather than trusting it blindly.

## Threat model

**Threat addressed**: zombie tasks - frontmatter says done while the PR is open - corrupt the merged-PR metric and strand open PRs. Variant 2 makes GitHub authoritative for merge state.

**Threat introduced**: a task whose merge GitHub cannot confirm (API down) is treated pending rather than done, briefly. This is the intended safe trade: pending-and-recheck beats falsely-done. Mitigated by `test_github_unreachable_safe` and by the daemon's normal re-poll once GitHub returns.

**Other layers protecting**: the merge handler still writes frontmatter done (durable hint, offline display); the analytics record is written at merge time independent of this derivation; ERROR/suppression remains frontmatter-owned so this change cannot affect the park logic.
