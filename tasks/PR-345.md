# PR-345: Cancellation TTL refresh on read for 90-day forensic window

## Problem

Cancellation records expire after 30 days. Operators investigating a flaky test pattern across 60-90 days have records evicted before they finish the investigation. Index ZADD already has 30-day TTL on `cancellation_index:<repo>` keys per OBS-CW fix; full record TTL matches.

Worse: dashboard rendering touches a record for display, but reads don't refresh TTL. The record evicts at fixed time-since-write regardless of operator interest.

## Solution

Add TTL refresh on read in `read_cancellation`. When operator (or daemon) reads a record via display path, EXPIRE the key to push TTL to 90 days from now. Records actively under investigation persist.

Records never read by anyone naturally evict at original 30 days. Active forensic targets get extended automatically. No new index, no garbage collection scheme.

### Storage change

```python
async def read_cancellation(
    redis_client,
    repo: str,
    task_id: str,
    refresh_ttl: bool = True,
) -> CancellationCause | None:
    key = f"cancellation:{repo}:{task_id}"
    raw = await redis_client.get(key)
    if raw is None:
        return None
    cause = CancellationCause.model_validate_json(raw)
    if refresh_ttl:
        await redis_client.expire(key, 90 * 86400)
        await redis_client.zadd(
            f"cancellation_index:{repo}",
            {task_id: cause.canceled_at.timestamp()},
        )
        await redis_client.expire(f"cancellation_index:{repo}", 90 * 86400)
    return cause
```

Default `refresh_ttl=True`. Daemon callers in tight loops can pass `refresh_ttl=False` to avoid trivial network round-trips.

## Threat model

**Threat addressed**: forensic data eviction. 30-day window too narrow for slow-burn investigations.

**Other layers protecting**: PR-343 disk log preserves event stream forever (operator-managed). PR-345 is the Redis-side complement for cancellation records specifically.

**Why this layer needed**: cancellation records contain richer structured data than event log lines (full subsource payload, retry context). Operators need them queryable from Redis for fast diagnostic UI; disk log alone forces grep-heavy workflows.

### Caller audit

`read_cancellation` callers (per `grep -n "read_cancellation\|get_cancellation_cause" src/`): diagnostic endpoint, dashboard rendering, audit_findings, escalation logic. Daemon-side automated callers may want `refresh_ttl=False` to avoid extending TTL on every render cycle:

- Dashboard 5-second poll renders every PAUSED card → if refresh_ttl=True naively, every visible record perpetually pinned. Acceptable IF operator intent matches "record is visible in dashboard = operator interested". Document this as the policy.
- If unwanted: pass `refresh_ttl=False` from dashboard 5s loop and `refresh_ttl=True` only from diagnostic_panel explicit-click flow.

Recommend: dashboard 5s loop uses `refresh_ttl=False` (cheap polling shouldn't extend lifetime). Explicit diagnostic_panel click → `refresh_ttl=True` (operator showing interest).

## Out of scope

- Index pruning of stale entries - index has its own 30-day TTL per OBS-CW; ZREM on expiry not in scope.
- Cross-repo cancellation search - separate spec.
- Cancellation export to PDF/CSV - out of scope; dashboard view is read-only forensic surface.

## Success signal

Operator visits diagnostic panel for a 35-day-old cancellation record. Record TTL refreshes to 90 days. Future visits within 90 days continue extending. Records nobody touches for 30 days evict naturally.
