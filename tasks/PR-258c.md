## Problem

PR-248 wired the WATCH-to-FIX transition on `ReviewStatus.CHANGES_REQUESTED` with a feedback-freshness gate (`_has_new_codex_feedback_since_last_push`) so the daemon does not loop into FIX on a stale review left from a previous push. The transition path lives in `src/daemon/handlers/watch.py:278` and depends on three signals working together: the GitHub API report of the review state, the head commit timestamp, and the Codex review reaction cache.

Unit tests cover each signal in isolation. The integration is exercised only by `tests/test_runner.py` style mocks that stub the GitHub layer wholesale; no e2e drives a real review on a real testbed PR through the daemon's WATCH cycle.

The Sprint 13.5 tool-registration bug demonstrated that the gap between unit tests and live daemon behavior can hide regressions for weeks. Codex review trigger logic is sensitive to GitHub API rate-limit behavior, ETag cache staleness, and the head SHA tracking inside `prs.py`; an e2e that drives an actual `CHANGES_REQUESTED` review and asserts the WATCH-to-FIX transition is the smallest unit of coverage that surfaces an integration regression in any of those layers.

## Scope

A single new e2e test `tests/e2e/test_watch_changes_requested.py` that:

1. Uploads `PR-A`, waits for CODING with the success shim, the shim creates the PR and pushes the branch.
2. Waits for the runner to reach WATCH with `current_pr` populated.
3. Posts a `CHANGES_REQUESTED` review on the testbed PR via `gh api` REST: `POST /repos/{owner}/{repo}/pulls/{number}/reviews` with `event=REQUEST_CHANGES` and a body string. The review is posted under whatever identity the test runs as; this is sufficient because the daemon's freshness check anchors on the head commit timestamp, not the reviewer identity.
4. Polls the runner state with a 90-second deadline (the WATCH poll period plus the freshness-check round-trip plus the FIX entry transition) and asserts the runner reaches FIX with `current_pr.number` equal to the same testbed PR.
5. Switches the shim scenario to `escalate` so the FIX cycle exits cleanly to HUNG/IDLE without a second push, keeping the test self-contained.
6. Cleans up by closing the testbed PR and deleting its branch via `reset_testbed_full` (already handled by the session-level fixture, but the test must not rely on per-test cleanup for the GitHub-side state).

## Tests

This PR is itself a test. The success criteria below double as the assertion list.

`tests/e2e/test_watch_changes_requested.py` (single test function):

- `test_changes_requested_review_drives_watch_to_fix`: the sequence described in Scope.

The test marks itself with `@pytest.mark.e2e` (or the existing equivalent marker; check `tests/e2e/conftest.py` for the project convention). It depends on `reset_testbed` so each invocation starts from the canonical clean slate.

The test must NOT skip on any GitHub-App-permission gap; posting a review only requires `Pull requests: Write` which is already part of the testbed App's standard scope per `docs/ci-setup.md`. If `gh api` returns a 403 anyway, the test fails loud rather than skips, because the missing permission would also break a slice of production.

## Implementation notes

The WATCH-to-FIX transition runs through `_has_new_codex_feedback_since_last_push` which compares review submission time against the head commit timestamp. The test's review post happens after the head commit was pushed, so the freshness gate returns NEW and the transition fires. There is no need to mock or skip the freshness check.

The daemon's WATCH poll period in the test stack is the relevant timing constant. It is read from `config.yml` or the test override and is typically 5 to 10 seconds. The 90-second test deadline accommodates 2 polls plus the freshness round-trip plus the FIX entry transition with a comfortable margin.

The shim transition from `success` (used during CODING) to `escalate` (used during the entry to FIX) must happen AFTER the daemon enters FIX, not during it. Use `coder_shim("success")` as the outer context manager and switch to `escalate` only after the FIX state assertion passes. The simplest pattern is to manually write the scenario file via `SHIM_SCENARIO_PATH.write_text("escalate\n")` between the FIX assertion and any further wait.

The Codex review reaction cache (in `src/github/reactions.py` and `src/github/cache.py`) is keyed by repo and PR number; this test ships a fresh PR per run, so cache pollution from prior runs is not a concern. Do not add cache-clearing logic that the production daemon would not also run.

The test does not need to verify the FIX cycle's coder-prompt content. PR-258c's contract is solely "WATCH transitions to FIX on CHANGES_REQUESTED with fresh feedback"; the FIX cycle internals are owned by separate test files.

If the testbed PR is closed by a previous test run and re-opened by `_reset_testbed_session`, the head commit timestamp is preserved. The freshness gate compares review-submitted-at against head-commit-committer-date, both of which are stable across PR re-open. No additional setup is needed.

## Success criteria

1. After `gh api` posts a `CHANGES_REQUESTED` review on the testbed PR, the runner reaches FIX with `current_pr.number` equal to the testbed PR number within 90 seconds.
2. The transition log entry contains the `[WATCH] PR #{n}` prefix with `CHANGES_REQUESTED` mentioned in the event body, matching the production log format in `watch.py:278-294`.
3. The shim switch to `escalate` lets the FIX cycle complete without a second push or merge, leaving the testbed in a clean state for the next test.
4. The test does not skip on permission gaps for `Pull requests: Write` (skipping there would mask a production regression).
5. The test passes locally and in CI without flake on three consecutive runs.
6. No production code modified.
