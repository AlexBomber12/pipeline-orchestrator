# PR-266c: Drop recovery audit flags and legacy QUEUE.md probe path

Branch: pr-266c-recovery-cleanup
- Type: refactor
- Complexity: low
- Depends on: PR-266b
- Priority: 2
- Coder: codex

## Problem

PR-266b shipped the audit-mode infrastructure for recovery. After 24-48 hours of `AUDIT_LEGACY_APPLIES` mode in production with zero divergence events, the operator flipped to `HEADERS_ONLY` for one or two daemon restart cycles, again with zero anomalies. The new path is now the production truth; the legacy path is dead code and the env-var dance is operational overhead.

This PR removes the flags, the legacy `_parse_base_queue` and `_origin_queue_md_tracked` helpers, and the audit-diff machinery. After it ships, `recover_state` has one path: read PR-*.md headers, derive statuses via `_resolve_merged_state`, hydrate `state.current_queue`. Simpler, faster, and one less surface for future regressions to hide behind.

This PR is the prerequisite for PR-267 dropping the QUEUE.md write paths in idle and merge handlers. After PR-266c, no production code path reads `tasks/QUEUE.md` from disk; PR-267 then removes the writes.

## Scope

Five deliverables:

1. Remove the two env vars and `_resolve_recovery_mode` from `src/daemon/recovery.py`. Delete the audit-mode branch logic.
2. Delete `_recovery_audit_diff` and the `[AUDIT] recover_state divergence:` log path.
3. Delete `_parse_base_queue` from `src/daemon/repo_ops.py`.
4. Delete `_origin_queue_md_tracked` from `src/daemon/repo_ops.py`. Note: this method is also referenced by `_write_generated_queue_md` and `_mark_queue_done`. PR-267 removes those two write paths; this PR leaves them temporarily reading a hardcoded `False` (treat all repos as post-PR-181) instead of probing. PR-267 removes the calls altogether.
5. Delete `_drop_ghost_queue_entries` from `src/daemon/recovery.py`. Ghost detection is no longer needed when recovery parses PR-*.md files directly (a missing file is implicitly absent from the headers list, not a ghost row that needs filtering).

## Behavior

After this PR ships:

- `recover_state` has a single linear path: load recovered task pr_id set, parse PR-*.md headers via `_parse_tasks_from_headers`, derive statuses, apply state mutations, hydrate `state.current_queue`, return. No env-var branches, no audit comparator, no ghost filter.
- The `_origin_queue_md_tracked` probe is gone. Any caller that was checking the tristate (`True`/`False`/`None`) collapses to "post-PR-181 always" semantics. The two remaining callers are `_write_generated_queue_md` and `_mark_queue_done`; both are gated by a hardcoded `False` return so they fall through to the write path. PR-267 removes the write paths and these callers entirely.
- `_parse_base_queue` is gone. No caller remains.
- The `docs/operations.md` env-vars section is updated to remove `PIPELINE_RECOVERY_AUDIT` and `PIPELINE_RECOVERY_FROM_HEADERS`.

## Implementation notes

This PR is small in line count but high in deletion velocity. Roughly 100-150 lines come out of `recovery.py` and `repo_ops.py`. Reviewers should focus on whether any non-obvious caller relied on the deleted paths. A grep for `_parse_base_queue`, `_origin_queue_md_tracked`, `_drop_ghost_queue_entries`, `_recovery_audit_diff`, `PIPELINE_RECOVERY_AUDIT`, `PIPELINE_RECOVERY_FROM_HEADERS` should return zero hits in `src/` and only fixture/test references in `tests/` after this PR.

The transitional stub for `_origin_queue_md_tracked` returning `False` is a defensive coupling: PR-267 has not yet shipped, and `_write_generated_queue_md` plus `_mark_queue_done` still call this method. Returning a constant False makes their `if self._origin_queue_md_tracked() is not False: return` guards always fall through to the disk-write path, which matches the post-PR-181 normal behavior. Once PR-267 removes the writes, the stub gets deleted along with its last callers.

After this PR is deployed and observed clean, the daemon's recovery codepath has dropped from ~150 lines (with the four-mode branch) to ~60 lines, and the QUEUE.md disk-read surface has shrunk from three production paths (recovery + idle + merge) to two (idle + merge, both writes). PR-267 closes the loop.

If a regression surfaces in production after this PR, the revert path is: re-add `_parse_base_queue`, `_origin_queue_md_tracked`, the audit-diff machinery, and the env-var branch. Because PR-266b's audit window was the primary safety net, regression discovery this late is unlikely; the audit data is in operator log archives if needed.
