## Reading order note for the implementing coder

This task adds a NEW DOCUMENTATION SECTION to the AGENTS.md file that lists rules future coder dispatches must follow. The section content describes prohibited actions in plain English so a coder reading AGENTS.md top-to-bottom understands the rules before starting work. Throughout this spec, command names appear inside back-tick markers — these are the literal strings the documentation section must contain in its rendered form so that future coders see them. The implementing coder edits an AGENTS.md file (a documentation file), edits a Python tuple constant, and writes 4 short tests. The implementing coder does not run any GitHub CLI commands at the org level, does not modify protected branches, and does not interact with the GitHub API. All test inputs are synthetic strings constructed inside test fixtures.

## Problem

PR-289a/PR-289b ship enforcement code that scans coder stdout for forbidden actions and ESCALATEs the dispatch when matches are found. PR-290 ships post-push diff scanning. Both layers detect violations at runtime, but a coder reading AGENTS.md top-to-bottom finds no explicit prohibition list — the rules can only be inferred indirectly from existing sections (`work_modes`, `daemon_mode`, `auto_pr_runbook`, `review_fix_runbook`).

PR-291 adds an explicit `forbidden_actions` managed section to AGENTS.md that lists the Tier 1 prohibitions in plain language. Coders following the AGENTS.md top-to-bottom convention encounter the rule before any work mode execution. The managed section reconciliation framework (PR-192a/b/c) propagates the section to all managed repos via operator-driven `/onboarding/apply`. After PR-291 merges and operator runs apply on each managed repo, the prohibition list lives in megaraid-dashboard and sms-gateway-v2 AGENTS.md as well.

The section is **declarative documentation, not enforcement**. Enforcement is in PR-289a/PR-289b (Tier 1 stdout scan + diff scan). PR-291 closes the documentation gap so a coder asked to "do X" where X is forbidden has explicit guidance to refuse rather than relying on indirect inference from runbooks.

The earlier original PR-275 spec-validation regex layer was architecturally deprecated 2026-05-07 per OBS-CR. Defense in depth shifted entirely to runtime layers (PR-289a/b stdout, PR-290 diff). PR-291 documents the rules that the runtime layers enforce.

The section content (literal text to insert into AGENTS.md):

```
<!-- pipeline-orchestrator: managed BEGIN forbidden_actions -->
## Forbidden actions

The following actions are NEVER permitted under any work mode (AUTO PR, PLANNED PR, MICRO PR, FIX FEEDBACK). The pipeline-orchestrator daemon detects them at two runtime layers (coder stdout scan, PR diff scan) and ESCALATEs the dispatch with a `GUARDRAIL: <category>: <excerpt>` cancellation cause. If you find yourself about to take any of these actions, STOP and add an `ESCALATE: <reason>` line to your stdout instead.

- **Repository creation or deletion via the GitHub CLI**: the daemon authorizes you to operate within the repository where the task lives. Creating or deleting repositories at GitHub-org level is out of scope for any task.
- **Force-push to the default branch**: rewriting the protected branch history is out of scope. Use a feature branch and a normal PR.
- **Default branch deletion**: deleting the default branch (via colon-refspec form or `--delete` flag) is out of scope.
- **Direct commit to the default branch without PR creation**: bypassing PR review and CI gates is out of scope. All changes go through `gh pr create` to a feature branch.
- **Acting on intent referenced indirectly in the task spec**: if the task body mentions another repository or another organization as context, do NOT switch your working directory to it or run commands against it. Operate only within the repository where the task file lives.
<!-- pipeline-orchestrator: managed END forbidden_actions -->
```

The literal text above goes verbatim into AGENTS.md. Markdown bullet formatting and the BEGIN/END markers are required for the managed section reconciliation framework to recognize and propagate the section.
