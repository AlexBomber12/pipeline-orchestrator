## Problem

PR-277 Tier 1 introduced `.github/` modification detection for workflow YAMLs (`workflow_destruction`, `permissions_escalation`) and branch protection (`branch_protection_modification`). Other `.github/` files have governance impact comparable to those covered, but Tier 1 does not flag changes to them:

1. **`.github/CODEOWNERS`** — controls who must review which paths. Modifying CODEOWNERS to drop the operator from the reviewer list, or to assign the coder's bot account as code owner, lets the coder self-approve future PRs.
2. **`.github/dependabot.yml`** — controls automated dependency PRs. Disabling dependabot or narrowing its scope removes a defense layer against vulnerable dependencies.
3. **`.github/labels.yml`** (or equivalent if the repo uses label-sync) — controls semantic labels used by automation. Modifying could break label-driven workflows.
4. **`.github/settings.yml`** (when probot/settings is used) — controls repo-wide settings including merge button options, branch protection, secrets exposure. Modification has same impact as direct API change.
5. **`.github/auto-merge.yml`** or `merge-config.yml` — controls automerge behavior. Modification could enable bypass of human review.

These five files plus any future governance addition (e.g., `.github/PULL_REQUEST_TEMPLATE.md`) matter less but still warrant flagging since they're operator-curated. PR-291 extends `scan_pr_diff` with a governance-file pattern matcher.

This is **defense-in-depth advisory** — a PR modifying CODEOWNERS may be legitimate (operator added a new team member), but operator should review the diff before merge regardless. Without operator-override UI (PR-292 in future batch), a flagged PR stays HUNG until manually merged.

## Scope

Extend `src/daemon/guardrails.py` `scan_pr_diff` with governance-file detection.

### 1. New constant `GOVERNANCE_FILE_PATTERNS`

```python
GOVERNANCE_FILE_PATTERNS = {
    "codeowners": re.compile(
        r"^(?:\.github|docs|src)/CODEOWNERS$"
    ),  # GitHub looks in 3 locations
    "dependabot_config": re.compile(
        r"^\.github/dependabot\.ya?ml$"
    ),
    "labels_sync": re.compile(
        r"^\.github/(?:labels|labeler)\.ya?ml$"
    ),
    "repo_settings": re.compile(
        r"^\.github/settings\.ya?ml$"
    ),
    "auto_merge_config": re.compile(
        r"^\.github/(?:auto-merge|automerge|merge-config)\.ya?ml$"
    ),
    "issue_pr_template": re.compile(
        r"^\.github/(?:ISSUE_TEMPLATE|PULL_REQUEST_TEMPLATE)/?"
    ),
    "funding": re.compile(
        r"^\.github/FUNDING\.ya?ml$"
    ),
}
```

The PR-277 `branch_protection_modification` pattern remains in place; PR-291 adds these new categories without overlapping that one.

### 2. Helper `_scan_governance_files(diff_text)`

Iterates over `diff --git a/X b/Y` headers in the diff. For each modified or added file, checks against `GOVERNANCE_FILE_PATTERNS`. Returns list of `(file_path, governance_category)` tuples.

The function does NOT distinguish add/modify/delete operations at this layer — any change to a governance file is flagged. This is intentional: even adding a new CODEOWNERS file (when none existed) changes who can approve PRs and warrants operator review.

### 3. Extend `scan_pr_diff`

After existing Tier 1 + Tier 2 (PR-288, PR-289, PR-290) checks:

```python
governance_findings = _scan_governance_files(diff_text)
for file_path, governance_category in governance_findings:
    excerpt = (
        f"Governance file modified: {file_path} "
        f"(category: {governance_category}). Operator review required."
    )
    violations.append(GuardrailViolation(
        tier=2,
        category="governance_file_modified",
        excerpt=excerpt[:200],
        rule=(
            "Changes to governance files (CODEOWNERS, dependabot, "
            "label sync, repo settings, auto-merge config) require "
            "operator approval. PR cannot proceed without override."
        ),
    ))
```

The structured `category` is the constant `"governance_file_modified"` for all governance findings; the specific governance subtype (`codeowners`, `dependabot_config`, etc.) appears in the excerpt. This mirrors the secret-scan design from PR-289 where multiple subtypes share one outer category.

### 4. No new config fields

Unlike PR-288 (numeric thresholds) and PR-290 (count thresholds), PR-291's check is **categorical**: any modification to a matching path triggers. No threshold to tune. The PR-289 `secret_scan_enabled` flag pattern could be mirrored here if operators need a per-repo opt-out:

```python
governance_scan_enabled: bool = Field(default=True)
```

Add this flag for symmetry with `secret_scan_enabled`. Default-on; operator can disable per-repo if a particular repo legitimately reorganizes governance files frequently (rare).

## Implementation notes

The pattern catalogue is conservative — only files with widely-recognized governance impact across GitHub's tooling and common bot ecosystems (probot/settings, dependabot, labeler-action). Repo-specific governance conventions (e.g., a custom `.maintainers` file the operator keeps in repo root) are not covered; if a repo has its own governance pattern, the operator can extend the catalogue in a follow-up PR.

Modifying `.github/PULL_REQUEST_TEMPLATE.md` is the lowest-risk governance change (it changes only the default body of new PRs, doesn't bypass any review gate). Operators may consider this noisy; if false-positive feedback emerges, drop the `issue_pr_template` pattern in a follow-up.

The `governance_scan_enabled` config flag mirrors PR-289's `secret_scan_enabled` for consistency. Both default-on with per-repo override path via `repo_config` already established.

Estimated diff size: ~100-150 LOC. Of that, ~50-70 LOC is the catalogue + helper + scan extension, ~3 LOC is config, ~50-80 LOC is tests.

Coder: codex assignment is appropriate. Mechanical regex catalogue extension, scope-strict, full Tier 1 + Tier 2 (PR-288, 289, 290) layers active.
