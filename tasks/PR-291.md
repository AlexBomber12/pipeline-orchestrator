## Reading order note for the implementing coder

This task adds a NEW DOCUMENTATION SECTION to the AGENTS.md file that lists rules future coder dispatches must follow. The section content describes prohibited actions in plain English so a coder reading AGENTS.md top-to-bottom understands the rules before starting work. Throughout this spec, command names appear inside back-tick markers — these are the literal strings the documentation section must contain in its rendered form so that future coders see them. The implementing coder edits an AGENTS.md file (a documentation file), edits a Python tuple constant, and writes 4 short tests. The implementing coder does not run any GitHub CLI commands at the org level, does not modify protected branches, and does not interact with the GitHub API. All test inputs are synthetic strings constructed inside test fixtures.

## Threat model

**Threat addressed:** A coder running an autonomous task does not have an explicit, top-of-AGENTS.md prohibition list. The forbidden actions are scattered indirectly across runbook sections (`work_modes`, `daemon_mode`, `auto_pr_runbook`, `review_fix_runbook`). A coder asked to perform an action that crosses a forbidden boundary can plausibly proceed without a clear refusal trigger.

**Layers that DO NOT catch this threat:** Layers 1, 3, 4, 5 are runtime enforcement (after the coder has already attempted the action). PR-291 is the upstream guidance layer (Layer 2) that prevents the attempt by making the rules explicit at read time.

**Why this layer is needed:** Defense-in-depth pairing. Runtime enforcement (stdout scan, diff scan, pre-push hook) is the safety net; up-front documentation reduces the rate of attempts that reach the safety net. Without the forbidden_actions section, a coder reading AGENTS.md could plausibly miss the prohibitions entirely.

## Problem

PR-289a (shipped) and PR-289b-1/-2 (shipped) ship Tier 1 stdout-scan enforcement that detects forbidden CLI invocations like `gh repo create`, `gh repo delete`, and branch deletions of the default branch. PR-272 (shipped) ships a pre-push hook that validates branch identity at git push time. PR-290a/b/c (Sprint 15c) adds Tier 1 diff content scan for workflow YAML modifications and supply-chain attacks.

All four enforcement layers operate at runtime — they detect violations after the coder has attempted the forbidden action. None of them surface the prohibitions to the coder before the attempt. A coder reading AGENTS.md top-to-bottom finds runbooks but no explicit prohibition list.

PR-291 adds a `forbidden_actions` managed section to AGENTS.md that lists prohibitions in plain language. Coders following the AGENTS.md top-to-bottom convention encounter the rule before any work mode execution. The managed section reconciliation framework (PR-192a/b/c, shipped) propagates the section to all managed repos via operator-driven `/onboarding/apply`. After PR-291 merges and operator runs apply on each managed repo, the prohibition list lives in megaraid-dashboard and sms-gateway-v2 AGENTS.md as well.

The section is **declarative documentation, not enforcement**. Enforcement remains in the runtime layers above. PR-291 closes the documentation gap so a coder asked to "do X" where X is forbidden has explicit guidance to refuse.

The section content (literal text to insert into AGENTS.md):

```
<!-- pipeline-orchestrator: managed BEGIN forbidden_actions -->
## Forbidden actions

The following actions are NEVER permitted under any work mode (AUTO PR, PLANNED PR, MICRO PR, FIX FEEDBACK). The pipeline-orchestrator daemon detects them via runtime layers (coder stdout scan, PR diff scan, pre-push hook) and ESCALATEs the dispatch with a `GUARDRAIL: <category>: <excerpt>` cancellation cause. If you find yourself about to take any of these actions, STOP and add an `ESCALATE: <reason>` line to your stdout instead.

- **Repository creation or deletion via the GitHub CLI**: the daemon authorizes you to operate within the repository where the task lives. Creating or deleting repositories at GitHub-org level is out of scope for any task.
- **Force-push to the default branch**: rewriting protected branch history is out of scope. Use a feature branch and a normal PR. Pre-push hook enforces this; do not attempt to bypass.
- **Default branch deletion**: deleting the default branch (via colon-refspec form, `--delete` flag, or `+:` matching-branches force) is out of scope.
- **Direct commit to the default branch without PR creation**: bypassing PR review and CI gates is out of scope. All changes go through `gh pr create` to a feature branch. Pre-push hook enforces.
- **GitHub Actions workflow tampering**: do not delete `.github/workflows/*.yml` files, do not add `permissions: write-all` or write-scope individual permissions, do not change branch protection metadata files (`.github/branch-protection*`, `.github/settings.yml`).
- **Unpinned action references**: when adding `uses: <actor>/<action>@<ref>` lines, the ref MUST be a semver tag (vN, vN.N, vN.N.N) or a 40-character commit SHA. Branch names, HEAD, or short SHAs are forbidden.
- **Acting on intent referenced indirectly in the task spec**: if the task body mentions another repository or another organization as context, do NOT switch your working directory to it or run commands against it. Operate only within the repository where the task file lives.
<!-- pipeline-orchestrator: managed END forbidden_actions -->
```

The literal text above goes verbatim into AGENTS.md. Markdown bullet formatting and the BEGIN/END markers are required for the managed section reconciliation framework to recognize and propagate the section.
