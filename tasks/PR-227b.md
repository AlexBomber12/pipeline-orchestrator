# PR-227b: Migrate rate-limit policy from claude-specific to plugin-owned

Branch: pr-227b-rate-limit-policy-plugin
- Type: refactor
- Complexity: medium
- Depends on: PR-227a
- Priority: 1
- Coder: claude

## Problem

This is part 2 of 3 in the PR-227 split. PR-227a migrated breach lifecycle. PR-227b migrates rate-limit policy thresholds.

Today, session/weekly pause percentages are claude-specific constants checked inline in handlers. Codex does not use the same thresholds (its rate-limit semantics differ). Hardcoded checks like `if usage_session_percent >= 95:` assume Anthropic-specific behavior; for Codex they should be no-op (`>= 100` effectively never triggers).

After this PR, plugins declare their session and weekly pause thresholds; handlers query the plugin instead of using hardcoded constants.

## Scope

Add `default_session_pause_percent` and `default_weekly_pause_percent` properties to `CoderPlugin` Protocol. Implement in `ClaudePlugin` (95 / 80) and `CodexPlugin` (100 / 100). Replace all hardcoded threshold checks in handlers with plugin property reads.

Example before:

```
    pause()
```

## Implementation notes

The 95/80 thresholds for Claude come from existing code; preserve them exactly. If a handler had a different inline value (e.g. 90 instead of 95), that is an existing inconsistency — flag it in PR description but keep the existing per-handler value via passing a non-default plugin property override (or accept the inconsistency for now and fix in a follow-up).

For Codex, the value of 100 means "never trigger pause". This is intentional — Codex rate-limit handling goes through a different code path (Codex pauses via `codex_resets_at` field, not threshold percentages).

After PR-227b, the threshold values are still claude-specific (95/80) but the source is now plugin-owned. A third coder integrated tomorrow declares its own thresholds without editing handlers.
