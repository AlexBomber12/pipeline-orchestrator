# PR-275c: MCP cross-repo intent detection — cross-org clone and fork command match

Branch: pr-275c-mcp-cross-org-clone-fork
- Type: feature
- Complexity: medium
- Depends on: PR-275a, PR-275b
- Priority: 2
- Coder: codex

## Problem

PR-275a/b cover creation, deletion, and archive of repos at literal-command level. A separate destructive surface exists at lower severity: cross-organization clone and fork operations. `gh repo clone owner/name` is read-only but exfiltrates code if the source is private and the daemon's authenticated identity has access. `gh repo fork owner/name` creates a new repo in the daemon's identity space, which is creation but at fork-source-org level rather than free-form-name level.

Both operations are appropriate when the daemon is dispatched to work on its own organization's repo (allow current daemon owner). Both are out-of-scope when the target organization is not the daemon's configured owner.

PR-275c adds detection contingent on the OWNER segment of the matched literal command differing from the daemon's currently-configured owner. This requires injecting the owner value into the scan invocation, which differs architecturally from PR-275a/b's pure-text detection.

## Scope

Three deliverables:

1. Modify `scan_for_conflicts` signature to accept an optional `daemon_owner: str | None = None` parameter. When provided, contextual checks like cross-org detection can compare against it. When None (default), contextual checks are skipped and the function behaves identically to PR-275a/b's contract.

2. Two new `_ANTI_PATTERNS` entries with **per-pattern context predicates** rather than pure regex match. Refactor `_ANTI_PATTERNS` element type from `tuple[str, re.Pattern, str]` to a small dataclass `AntiPattern` with fields `name`, `pattern`, `rule`, and an optional `predicate: Callable[[Match, dict], bool] | None`. The predicate, when provided, receives the match and a context dict (containing `daemon_owner` among other things) and returns True to confirm violation, False to suppress. Existing patterns get `predicate=None` and behave unchanged.

3. Wire `validate_task_spec` MCP tool to pass `daemon_owner` extracted from the daemon's loaded config when the tool is invoked. If the tool is invoked outside a daemon context (standalone CLI test), `daemon_owner` is None and cross-org checks are skipped.

Pattern 1: `cross_repo_clone_other_org`
- Regex: `\bgh\s+repo\s+clone\s+([\w.-]+)/[\w.-]+`
- Predicate: returns True iff captured group 1 (the owner) is not None AND not equal (case-insensitive) to `daemon_owner`. If `daemon_owner` is None, predicate returns False (skip).
- Rule message: `"Cross-org clone detected. Tier 1 guardrail. Operator review required for read-only access to non-daemon-owned repos. OBS-BT."`

Pattern 2: `cross_repo_fork_other_org`
- Regex: `\bgh\s+repo\s+fork\s+([\w.-]+)/[\w.-]+`
- Predicate: same logic as pattern 1.
- Rule message: `"Cross-org fork detected. Tier 1 guardrail. Forks create new repos in daemon's identity space from external sources. OBS-BT."`

Suppression layer (fenced code blocks, inline backticks, negation) reuses PR-275a helpers, applied to both new patterns.

## Behavior

Given `daemon_owner = "AlexBomber12"`:

Task body text MUST trigger violation:
- `Run gh repo clone other-org/private-repo` (other org)
- `gh repo fork upstream-org/library` (other org)
- `Execute gh repo clone competitor/secret-project --depth=1` (other org)

Task body text MUST NOT trigger violation:
- `Run gh repo clone AlexBomber12/megaraid-dashboard` (same owner — daemon's own repo, OK)
- `gh repo fork alexbomber12/legacy-fork` (same owner case-insensitive)
- `the gh repo clone command needs an argument` (no slash arg)
- ` ```bash\ngh repo clone other-org/foo\n``` ` (fenced)
- `Do not run gh repo clone other-org/foo` (negation)

When `daemon_owner is None` (e.g. standalone CLI invocation of validate_task_spec without daemon context):
- All cross-org checks suppressed
- Task body containing `gh repo clone competitor/foo` produces NO violation
- Existing patterns continue working unchanged

## Files to modify

- `src/mcp/scans.py`:
  - Introduce dataclass `AntiPattern` with fields described above. Migrate existing `_ANTI_PATTERNS` entries to the new shape with `predicate=None`.
  - Add the two new entries with predicate functions.
  - Modify `scan_for_conflicts` signature to accept `daemon_owner: str | None = None`.
  - Build context dict with `daemon_owner` and pass to predicate when present.
- `src/mcp/tools/functional.py:validate_task_spec`:
  - Accept and forward `daemon_owner` from daemon config when running in daemon context. The MCP tool already has access to the daemon's repo config via existing infrastructure; threading the owner through is a minor signature update.
- `src/daemon/handlers/idle.py` (or wherever `scan_for_conflicts` is invoked from daemon code): pass `self.owner_repo.split("/")[0]` (the owner part of the `owner/repo` slug) as `daemon_owner` argument.

## Files NOT to touch

- PR-275a's existing patterns (`cross_repo_repo_create_command`, etc.) — they remain pure-regex with `predicate=None`. The dataclass migration is mechanical and does not alter their behavior.
- `_is_inside_fenced_code_block`, `_is_inside_inline_code`, `_is_negated` helpers from PR-275a.
- Other handlers that don't invoke `scan_for_conflicts`.

## Implementation notes

The dataclass refactor of `_ANTI_PATTERNS` is the structural cost of this PR. It is contained within `src/mcp/scans.py` and does not propagate to call sites because they iterate the list and consume tuple unpacking that becomes attribute access. Exact migration: change `for vtype, pattern, rule in _ANTI_PATTERNS:` to `for entry in _ANTI_PATTERNS: vtype, pattern, rule = entry.name, entry.pattern, entry.rule`. Predicate consultation happens after the regex match and before recording the violation.

The `daemon_owner` threading from daemon config to scan invocation is the API surface cost. Threading it through `validate_task_spec` MCP tool plus the direct daemon invocation are the two call sites. Both have access to the daemon's owner via existing infrastructure (the daemon already owns `self.owner_repo` for every other GitHub interaction). The MCP tool, when invoked from claude.ai or a CLI client without daemon context, simply omits `daemon_owner` and the cross-org checks no-op.

The suppression-when-None default is intentional: it means standalone use of `validate_task_spec` (e.g., by an operator running the MCP tool from claude.ai during spec drafting) does NOT flag cross-org references because the operator's context — drafting a spec for a yet-to-be-determined daemon — cannot resolve the cross-org question. Only daemon-runtime invocation has the context. This avoids over-flagging during spec authoring while still catching the real issue at dispatch time.

Why this PR ships with priority 2 rather than 1 (matching PR-275a/b): clone and fork are read or copy operations at the GitHub level. Even when cross-org, the blast radius is bounded compared to create/delete/archive. PR-276 stdout monitoring and PR-277 diff scan also catch these, so PR-275c is one of three layers rather than the only one. Skipping or deferring PR-275c does not leave the system unguarded — it leaves only the spec-text early-warning layer thinner.

If real production data after PR-276/277 ship shows cross-org clone or fork getting through both stdout and diff layers and causing incidents, PR-275c's value is empirically validated. If they don't get through, PR-275c is belt-and-suspenders coverage with low cost (small spec change, mechanical refactor of `_ANTI_PATTERNS`).
