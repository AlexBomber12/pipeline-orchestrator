# PR-297: error_message lifecycle helper — single _clear_error_on_recovery primitive replacing scattered None-assignments

## Problem

`self.state.error_message = None` is assigned at 18 distinct sites across handlers (verified via grep on cb02e07): coding.py 5 sites, fix.py 6 sites, idle.py 3 sites, error.py 3 sites, merge.py 1 site. Each site represents a recovery transition where the daemon resumes from an error state. The assignments are inconsistent in three ways:

1. **Some sites also log the recovery, others do not.** When the operator sees `error_message` blink off the dashboard with no event log entry, they cannot reconstruct what cleared the error.
2. **Rate-limit-vs-other classification is duplicated in idle.py.** Lines 766-787 and 813-834 each contain the same `lowered = error_message.lower(); is_rate_limit_msg = "rate limit" in lowered or 429-regex; if rate_limit: clear else: re-transition` pattern. Drift between the two copies is a latent bug.
3. **Recovery transitions (HUNG → IDLE, ERROR → IDLE, PAUSED → resume) do not centralize error_message hygiene.** A future handler added to a recovery path may forget the assignment, leaving the stale red banner on the dashboard.

OBS-CH from prior session work tracking: stale red `error_message` banner on dashboard after the daemon has actually recovered. Sprint 12 calibration session 2026-05-05 noted it as Sprint 15c polish item.

## Scope

Two coupled deliverables:

### 1. Add `_clear_error_message_on_recovery` helper to runner.py

New method on the runner mixin (alongside `_transition_to_error` at runner.py:1027+):

```python
async def _clear_error_message_on_recovery(
    self,
    *,
    log_prefix: str,
    reason: str,
    publish: bool = False,
) -> None:
    """Atomic clear of state.error_message at recovery transitions.
    
    Logs the clearing event so operators can reconstruct dashboard
    state changes from the event log. Mirrors _transition_to_error's
    discipline: every error_message lifecycle write goes through a
    primitive with logging.
    
    Args:
      log_prefix: prefix matching the calling handler ("[CODING]",
        "[FIX]", "[IDLE]", "[ERROR]", "[MERGE]").
      reason: human-readable cause of the recovery
        (e.g., "coder ran successfully", "rate-limit window
        elapsed", "manual operator resume").
      publish: when True, calls self._publish_state_for_repo()
        so SSE pushes the cleared state immediately. Default False
        so the caller's existing publish flow is not duplicated.
    """
    if self.state.error_message is None:
        return  # nothing to clear; no-op without log spam
    previous = self.state.error_message
    self.state.error_message = None
    self.log_event(
        f"{log_prefix} cleared error_message ({reason}): "
        f"{previous[:120]}"
    )
    if publish:
        await self._publish_state_for_repo()
```

Truncate the previous message to 120 chars in the log line so very long error contexts (e.g., stack traces) do not bloat the event log entry. The full previous message is gone after the assignment, which is fine — the operator already saw it on the dashboard before recovery; the log line records that recovery happened, not the exact prior content.

### 2. Replace scattered `self.state.error_message = None` sites with helper calls

For each of the 18 sites identified by grep, replace `self.state.error_message = None` with `await self._clear_error_message_on_recovery(log_prefix=..., reason=...)`. The exact log_prefix and reason for each site:

- `src/daemon/handlers/coding.py:344, 354, 376, 563, 584` → log_prefix="[CODING]", reason chosen per-site (e.g., "PR observed on GitHub", "coder pushed successfully", "PLANNED PR resolved").
- `src/daemon/handlers/fix.py:244, 405, 456, 488, 631, 643` → log_prefix="[FIX]", reason per-site.

The helper invocation is `await`-prefixed (it is async to allow the optional publish call). Sites that were inside synchronous helpers may need refactoring; verify each site is in an async context. If any site is in a sync function, that site is left as-is for this PR with an XXX/TODO comment, and a follow-up PR refactors it.

### 3. Consolidate the duplicated rate-limit branch logic in idle.py

Extract the duplicated 22-line block at lines 766-787 and 813-834 into a single helper method on the idle handler:

```python
async def _resolve_rate_limit_error_state(
    self,
    *,
    log_prefix: str,
    label: str,
) -> bool:
    """Process state.error_message during rate-limit recovery.
    
    Returns True if caller should return immediately (state was
    transitioned back to ERROR because the message was non-rate-limit
    context). Returns False if caller should continue normal recovery
    (message was rate-limit-related and got cleared).
    """
    if self.state.error_message is None:
        return False
    lowered = self.state.error_message.lower()
    is_rate_limit_msg = (
        "rate limit" in lowered or re.search(r"\b429\b", lowered)
    )
    if is_rate_limit_msg:
        await self._clear_error_message_on_recovery(
            log_prefix=log_prefix,
            reason=f"{label}, cleared legacy rate-limit error",
        )
        return False
    await self._transition_to_error(
        self.state.error_message,
        save_run_record_as=None,
        publish=False,
        log_prefix=f"{log_prefix} {label} -> ERROR (preserved context):",
    )
    return True
```

Both call sites at lines 766-787 and 813-834 become:

```python
if await self._resolve_rate_limit_error_state(
    log_prefix="[RATE-LIMIT]", label=label_for_this_site
):
    return
```

This collapses 44 lines of duplicated logic into 1 helper method + 2 short call sites.

## Implementation notes

The helper-introduction is mechanical refactor with no behavior change at call sites that previously just assigned None. The behavior change is the new log line at every recovery — operators get visibility they didn't have before. This is the desired outcome (OBS-CH original observation: stale red banner with no event log trail).

Risk consideration: 18 sites means 18 new log lines per recovery cycle. In normal operation the daemon recovers from error rarely (per OBS-CH the issue is the BANNER persisting, not the rate of recovery). Each recovery emits 1-2 log lines max. Event log throughput impact is negligible. The dedup mechanism (already shipped in event_log) collapses repeated identical entries into a single dedupe-counter entry, so even in pathological retry loops the log does not bloat unbounded.

The two-branch consolidation in idle.py reduces 44 lines to 1 helper + 2 calls. After consolidation, the rate-limit-vs-other classification lives in one place — future drift of the regex (e.g., adding "throttled" or "quota" patterns) requires touching only the helper.

Estimated diff: ~150-200 LOC across 6 files. Of that, ~50 LOC is the new helper + idle.py rate-limit consolidation, ~80 LOC is mechanical replacement at 16 remaining sites, ~70 LOC is tests.
