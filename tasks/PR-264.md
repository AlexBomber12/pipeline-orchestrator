# PR-264: /api/repo/{name}/queue endpoint backed by RepoState.current_queue

## Problem

`src/web/routes/repo_control.py:list_repo_tasks` (around line 473-510) reads `tasks/QUEUE.md` from disk via `_app.parse_queue` to render the HTMX tasks panel. PR-263 made `RepoState.current_queue` the in-memory truth; this route still reads the projection on disk. Migrating the route off the file is the prerequisite for PR-267 dropping the disk-write paths.

`_resolve_repo_task_path` (around line 513-555 in the same file) also calls `_app.parse_queue` to honor non-default `Tasks file:` mappings. That call needs the same migration treatment so a single file viewer request does not re-introduce disk parsing.

## Scope

Three deliverables:

1. New endpoint `GET /api/repo/{name}/queue` returning JSON of the repo's `RepoState.current_queue`. Source of truth: Redis-backed runtime state.
2. Migrate `list_repo_tasks` HTMX fragment to read from `RepoState.current_queue` via the new endpoint's helper, falling back to the existing `parse_queue` path only when the snapshot is None (daemon has not yet reached IDLE).
3. Migrate `_resolve_repo_task_path` to consult `RepoState.current_queue` for `task_file` mappings, with the same None fallback to `parse_queue`.

## Behavior

`GET /api/repo/{name}/queue` returns:

```
{
  "repo": "<owner__repo>",
  "snapshot_at": "<ISO-8601 of last IDLE cycle that wrote the snapshot>",
  "queue": [
    {"pr_id": "PR-005", "title": "...", "branch": "pr-005-foo",
     "status": "DOING", "task_file": "tasks/PR-005.md",
     "depends_on": [], "priority": 2},
    ...
  ],
  "source": "snapshot" | "fallback_disk"
}
```

The `source` field tells consumers whether the response came from the in-memory snapshot or the disk-read fallback. Dashboard JS uses this for an inline degraded-mode indicator (shipped behind a separate UI PR; not in scope here, but the field is exposed now for forward compatibility).

`list_repo_tasks` consumer:
1. Read `RepoState.current_queue` from Redis.
2. If non-None, render the panel from the snapshot.
3. If None, fall through to the existing `parse_queue` path for backward compatibility through Sprint 15a #6 (will be removed in PR-267).
4. If both fail (Redis unavailable AND parse_queue raises), return the existing 503 fragment.

`_resolve_repo_task_path` consumer:
1. Read `RepoState.current_queue` from Redis.
2. If non-None, find the `pr_id` entry and use its `task_file` value.
3. If None, fall through to the existing `parse_queue` path.
4. If neither finds a mapping, fall through to default `tasks/{pr_id}.md`.

The fallback path is preserved in PR-264 so this PR is independently revertable. PR-267 deletes the fallback after PR-265 and PR-266 land.

## Implementation notes

The `source` field is exposed in the JSON response so the dashboard JS can show the operator when the page is rendered from a stale-but-recent snapshot vs a freshly-parsed disk file. A subsequent UX PR (Sprint 15b polish bucket) will use it; exposing the field now is forward compatibility.

The `_load_current_queue_snapshot` helper deliberately does not raise when Redis is unreachable — it returns `(None, "fallback_disk")` so the route's existing exception-handling chain stays simple. Operators see disk-source rendering during a Redis outage rather than a 5xx page.

The `tasks_panel.html` template renders a list of QueueTask via a Jinja for-loop accessing `t.pr_id`, `t.title`, `t.status`, `t.branch`. The snapshot QueueTask shape is identical to what `parse_queue` returns (same Pydantic model in both paths), so no template change is required. CI catches any drift on this assumption via the existing snapshot-rendering tests.

The new endpoint URL `/api/repo/{name}/queue` follows the existing `/api/...` convention used elsewhere in `repo_control.py`. Distinct from the HTMX fragment endpoint `/repos/{name}/tasks` which returns HTML; the JSON endpoint is the programmatic surface.

This PR's fallback path is the last on-disk reader for the daemon's `_write_generated_queue_md` output (apart from PR-265's cancellation services which migrate in parallel and PR-266's recovery which migrates separately). After PR-267 ships, all three readers go to RepoState exclusively.

## Success criteria

1. `GET /api/repo/{name}/queue` returns JSON with `source: "snapshot"` when Redis has a populated `current_queue`.
2. Endpoint returns `source: "fallback_disk"` when Redis snapshot is None but disk file exists.
3. Endpoint returns 503 when both sources fail; 404 for unknown repo name.
4. `list_repo_tasks` HTMX fragment renders identical HTML when sourced from snapshot vs disk on the same fixture data.
5. `_resolve_repo_task_path` honors snapshot's `task_file` mapping.
6. Existing test suite (`tests/test_web_app.py tests/web/`) green.
7. CI green on PR branch.
