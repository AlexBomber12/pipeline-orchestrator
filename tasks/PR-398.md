# PR-398: Supervise complete coder process groups through stop and timeout

## Problem and intended result

The daemon and Claude/Codex wrappers terminate the direct subprocess object. Descendants can survive timeout/cancellation and continue tests or Git work after the runner assumes the attempt ended. Auxiliary coder paths such as diagnosis and merge-conflict resolution also require supervision.

Establish one lifecycle helper for processes launched by the orchestrator on the supported Linux/Docker deployment. All normal descendants in the launch group must be gone before Stop/timeout is considered complete and before another attempt or destructive Git cleanup starts.

## Required behavior

1. Use a shared supervisor with an owned process group/session for Linux launches, a lifecycle identity and an idempotent termination operation. Preserve stdout/stderr capture, timeout return conventions and on_process_start compatibility as explicit adapters. No shell=True is needed.
2. Termination sends TERM to the owned group, waits for the configured bounded grace period, then sends KILL if necessary and reaps the direct child. Cancellation during cleanup must not abandon the group. Do not signal the daemon's own group or a process group that is not owned by this launch.
3. A leader exiting first is not proof that its descendants exited. Cover group liveness through leader exit, repeated termination, process disappearance races and descendants inheriting output descriptors. Define a bounded cleanup-failed result; do not publish successful completion or start subsequent work while cleanup is unconfirmed.
4. Normal exit, timeout, operator Stop, external PR resolution and daemon shutdown all use the same lifecycle contract. Wire CODING, FIX, diagnosis, auxiliary conflict-resolution and other orchestrator-launched coder helpers. Audit all direct launch and kill sites; document any intentionally separate non-coder subprocesses.
5. Preserve existing pause/resume semantics and rate-limit detection. This PR supplies process lifecycle guarantees; it does not change which UI controls are allowed or make global Stop durable. Those command issues are the next sprint.
6. Explicitly document the guarantee boundary: a POSIX process group handles ordinary descendants, not a malicious child that creates a new session or escapes into another container. Stronger containment is planned with sandbox/cgroup policy. Do not claim complete hostile-process isolation from process groups alone.

## Acceptance criteria

- Isolated helper processes exercise child/grandchild survival, a leader exiting first and TERM-ignoring children; timeout/cancel/Stop cleans the owned group.
- Repeated Stop and process disappearance races are harmless and never signal unrelated processes.
- Failure to confirm cleanup blocks subsequent launch/destructive work and produces a diagnostic result.
- Output capture and bounded grace behavior remain correct for both CLI wrappers and auxiliary paths.
- Tests clean up their own fixture processes even when an assertion fails; they use no real coder accounts or production processes.

## Files and boundaries

Expected changes: a small shared supervision module, existing CLI wrappers and daemon adapters, related tests and docs/operations.md. Keep Linux as the deployment target; unsupported platforms need an explicit guarded behavior. Do not change Docker privileges, mount the Docker socket, change sandbox policy or introduce an entire worker platform.

Success means the daemon owns and confirms cleanup of its normal coder launch group instead of treating direct-child termination as the end of the attempt.
