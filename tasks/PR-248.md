# PR-248: WATCH elif chain - CHANGES_REQUESTED takes precedence over PENDING

Branch: pr-248-watch-elif-precedence
- Type: bugfix
- Complexity: low
- Depends on: none
- Priority: 1
- Coder: claude

## Problem

OBS-BK from `docs/roadmap.md`. In `src/daemon/handlers/watch.py` around lines 182-189 the elif chain is:

```
elif ci == CIStatus.FAILURE:
    await self.handle_fix()
    return
elif ci == CIStatus.PENDING:
    pass
elif review == ReviewStatus.CHANGES_REQUESTED:
    ...
```

When CI is PENDING AND review is CHANGES_REQUESTED simultaneously (common during CI re-run after FIX push), the PENDING branch hits first with `pass`, the CHANGES_REQUESTED branch never evaluates, and a fresh codex review trigger is missed. The PR sits in WATCH waiting for CI green and then waiting again for a stale-review timeout when feedback was actually present and actionable.

Fix: reorder so review state is checked before CI PENDING. CHANGES_REQUESTED is actionable regardless of CI state; PENDING means "wait" only when no review feedback to act on.

## Scope

Single file edit: reorder the elif chain so `review == ReviewStatus.CHANGES_REQUESTED` is evaluated before `ci == CIStatus.PENDING`. Behavior for FAILURE stays first (highest priority signal). Tests covering the new precedence.

## Files to modify

`src/daemon/handlers/watch.py` — locate the elif chain (around line 182). Reorder:

```
elif ci == CIStatus.FAILURE:
    await self.handle_fix()
    return
elif review == ReviewStatus.CHANGES_REQUESTED:
    result = self._has_new_codex_feedback_since_last_push()
    if result == FeedbackCheckResult.NEW:
        await self.handle_fix()
        return
    if result == FeedbackCheckResult.UNKNOWN:
        self.log_event(
            f"[WATCH] PR #{found.number} CHANGES_REQUESTED but "
            f"feedback check failed; staying in WATCH, will retry "
            f"next cycle."
        )
        return
    self.log_event(
        f"[WATCH] PR #{found.number} CHANGES_REQUESTED but no new "
        f"Codex feedback since last push; waiting for fresh review."
    )
    self._maybe_retrigger_stale_review(found.number)
elif ci == CIStatus.PENDING:
    pass
```

CHANGES_REQUESTED block now precedes PENDING. The rest of `handle_watch` (EYES bot-error retrigger, last_activity, timeout escalation) is unchanged.

## Implementation notes

The bug has been latent because under typical timing the CI PENDING window is shorter than the review-stale-timeout window, so the missed CHANGES_REQUESTED eventually surfaces via the timeout. Symptom is "fix iterations take twice as long as expected" rather than a hard hang. After this PR ships, FIX cycles should converge faster on PRs that have both pending CI and outstanding feedback.

No risk of regressing the pure-PENDING case: when review is NOT CHANGES_REQUESTED, the CHANGES_REQUESTED elif falls through immediately to the PENDING `pass`.
