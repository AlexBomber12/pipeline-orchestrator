## Problem

Operator (solo, evening sessions) does not poll the dashboard continuously. A Tier 2 secret-in-diff finding (PR-302) needs immediate operator attention because exposed credentials must be revoked promptly — minutes-hours, not next morning. A Tier 1 governance file modification (PR-304) similarly warrants immediate notification.

Today the only signal channel is the dashboard event log + cancellation cause records. Operator must be at a browser to see them. PR-307 adds a notification webhook: when a Tier 1 or Tier 2 GUARDRAIL escalation fires, daemon POSTs a JSON payload to an operator-configured URL. Operator sets up the URL pointing at Slack/Discord incoming webhook (or any HTTP endpoint they control); the message lands in their phone notifications within seconds.

This is **defense-in-depth on the operator side** — guardrail detection (PR-289b..291) catches the violation; override UI (PR-305..293) lets operator decide; notification webhook makes sure operator hears about it ASAP.

## Scope

Three deliverables:

### 1. Config: notification webhook URL

Add to `src/config.py` `DaemonConfig`:

```python
guardrail_notification_webhook_url: str | None = Field(default=None)
guardrail_notification_min_tier: int = Field(default=1, ge=1, le=2)
guardrail_notification_timeout_seconds: float = Field(default=5.0, ge=1.0, le=30.0)
```

Default `None` disables the feature (no webhook). When set, daemon POSTs to URL on every GUARDRAIL escalation at or above `min_tier`. Default `min_tier=1` includes everything; operator can raise to 2 to receive only Tier 2 advisories (filtering out the categorical Tier 1 prohibitions which are typically already-blocked attack surfaces operator does not need notified about).

### 2. Notification payload + delivery

New module `src/daemon/notifications.py`:

```python
import json
import asyncio
from typing import Any

import httpx

async def send_guardrail_notification(
    *,
    webhook_url: str | None,
    repo_name: str,
    pr_id: str,
    pr_number: int | None,
    owner_repo: str,
    tier: int,
    category: str,
    excerpt: str,
    rule: str,
    timeout_seconds: float = 5.0,
    dashboard_base_url: str | None = None,
) -> None:
    """Best-effort POST of guardrail escalation to operator webhook.
    
    Failures are logged via the caller's log_event, not raised — daemon
    must not crash on notification delivery problems.
    """
    if webhook_url is None:
        return
    
    # Build dashboard link if base URL configured
    dashboard_link = None
    if dashboard_base_url:
        dashboard_link = f"{dashboard_base_url.rstrip('/')}/repo/{repo_name}"
    
    # Build GitHub PR link if PR number known
    github_link = None
    if pr_number is not None:
        github_link = f"https://github.com/{owner_repo}/pull/{pr_number}"
    
    # Generic structured payload
    payload: dict[str, Any] = {
        "event": "guardrail_escalation",
        "repo_name": repo_name,
        "pr_id": pr_id,
        "tier": tier,
        "category": category,
        "excerpt": excerpt[:500],  # cap excerpt for notification readability
        "rule": rule,
        "github_pr_url": github_link,
        "dashboard_url": dashboard_link,
    }
    
    # Slack-compatible alternative payload via "text" field for incoming-webhook
    # endpoints that expect the Slack format. Many providers (Slack, Discord
    # via slack-compat, Teams) accept either form; sending both is harmless.
    text_summary = (
        f"GUARDRAIL Tier {tier}: {category} on {repo_name} {pr_id}. "
        f"{excerpt[:200]}"
    )
    if dashboard_link:
        text_summary += f"\nDashboard: {dashboard_link}"
    if github_link:
        text_summary += f"\nGitHub: {github_link}"
    payload["text"] = text_summary
    
    try:
        async with httpx.AsyncClient(timeout=timeout_seconds) as client:
            await client.post(webhook_url, json=payload)
    except Exception:
        # Caller logs; raising would crash the daemon's escalation path
        raise
```

The function is best-effort. The caller wraps it in try/except + log_event. Asyncio timeout prevents a slow webhook from blocking the daemon's escalation path.

### 3. Integration in runner.py `_transition_to_error`

Extending the side-effect block from PR-305 (which adds pr_id to pending set when cause prefix matches `GUARDRAIL:`):

```python
# In runner.py:_transition_to_error, alongside the PR-305 pending-set update:
if message.startswith("GUARDRAIL:") and self.state.current_task is not None:
    pr_id = self.state.current_task.pr_id
    # PR-305: pending set update
    try:
        await self.redis.sadd(
            control_guardrail_pending(self.name), pr_id
        )
    except Exception as exc:
        self.log_event(
            f"[GUARDRAIL] pending set add failed: {exc}"
        )
    # PR-307: webhook notification
    parsed = _parse_guardrail_cause_for_notification(message)
    if (
        parsed
        and self.app_config.daemon.guardrail_notification_webhook_url
        and parsed["tier"] >= self.app_config.daemon.guardrail_notification_min_tier
    ):
        try:
            await asyncio.wait_for(
                send_guardrail_notification(
                    webhook_url=self.app_config.daemon.guardrail_notification_webhook_url,
                    repo_name=self.name,
                    pr_id=pr_id,
                    pr_number=(
                        self.state.current_pr.number
                        if self.state.current_pr
                        else None
                    ),
                    owner_repo=self.owner_repo,
                    tier=parsed["tier"],
                    category=parsed["category"],
                    excerpt=parsed["excerpt"],
                    rule=parsed["rule"],
                    timeout_seconds=self.app_config.daemon.guardrail_notification_timeout_seconds,
                    dashboard_base_url=self.app_config.daemon.dashboard_base_url,
                ),
                timeout=self.app_config.daemon.guardrail_notification_timeout_seconds + 2.0,
            )
        except asyncio.TimeoutError:
            self.log_event(
                "[GUARDRAIL] notification webhook timed out"
            )
        except Exception as exc:
            self.log_event(
                f"[GUARDRAIL] notification webhook failed: {exc}"
            )
```

Helper `_parse_guardrail_cause_for_notification` mirrors PR-306's `_parse_guardrail_cause` but lives in the daemon side to avoid web→daemon import dependency. It parses the GUARDRAIL cause string and infers the tier from the category (Tier 1 categories are hardcoded; everything else defaults to Tier 2).

The outer `asyncio.wait_for` adds a 2-second buffer above the inner httpx timeout so that a misbehaving webhook server cannot stall the daemon's escalation path past `timeout_seconds + 2`. Total worst-case escalation latency increase: ~7 seconds (5s default + 2s buffer).

## Implementation notes

The dual-format payload (structured fields + Slack-style `text`) gives operators flexibility. Slack incoming webhooks consume `text`; custom n8n/zapier-style endpoints can parse the structured fields. Discord webhooks accept Slack-compatible format via `?wait=true` query param. This pattern works for ~80% of common notification destinations without per-provider adapters.

The Tier inference relies on a hardcoded category-to-tier map in `_parse_guardrail_cause_for_notification`. As new Tier 2 categories ship in future PRs (e.g., Sprint 15d Defense in Depth), update the map. A more maintainable approach would be to embed the tier in the cancellation cause string itself — e.g., `GUARDRAIL: tier=2 large_diff_threshold: ...`. PR-307 v1 stays with the inferred-tier approach to avoid changing the cause format that PR-305 dashboard parser already consumes; revisit in a future cause-format refactor if maintenance burden grows.

The `wait_for` outer timeout is critical for daemon stability. Without it, a webhook server that opens TCP but never responds would block the asyncio event loop until the OS-level TCP timeout (~2 minutes), stalling all daemon activity for that repo. The 7-second worst case (`timeout_seconds + 2.0`) is acceptable.
