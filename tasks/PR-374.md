# PR-374: Cache load_config with mtime invalidation

Branch: pr-374-config-cache
- Type: refactor
- Complexity: medium
- Depends on: none
- Priority: 2
- Coder: any

## Reading order before coding

1. Read this entire spec.
2. Read `src/config.py:275-340` - the `load_config` function. Note it reads `config.yml` plus a sibling overlay from disk, deep-merges, applies env overrides, then runs full Pydantic validation of all 96 daemon fields on every call.
3. Run `grep -rn "load_config(" src/ --include="*.py" | grep -v test | grep -v "def load_config"` to enumerate every caller. There are 44 callsites, 34 of them in `src/web/routes/`, with 4 in `src/web/routes/dashboard.py` alone.
4. Read `src/web/routes/dashboard.py` callsites to confirm they run on hot SSE/poll paths.

## Problem

`load_config` performs disk reads, a deep merge, env-override application, and full Pydantic validation of 96 fields on every single invocation. It is uncached and called 44 times across the codebase, 34 in web routes that fire on every dashboard render, SSE reconnect, and `/api/states` poll. This is wasted CPU and I/O on a path that runs constantly. Config changes are rare (only via Settings UI writes); reads are frequent. This is the classic cache candidate.

This is the R0.1 warmup PR of the systemic refactor plan (see roadmap "Refactor execution plan R0-R5"). It is intentionally low-coupling: it proves the refactor pipeline works on a contained change before the suppression-node work begins.

## Solution

### Cache keyed on file mtime

Add a module-level cache in `src/config.py` that stores the last parsed `AppConfig` along with the modification times of the base config file and the overlay file. On each `load_config` call:

1. Resolve the config path and overlay path the same way the current code does.
2. Stat both files to get their current mtimes (treat a missing overlay as mtime 0).
3. If a cached entry exists for this exact resolved path AND both mtimes match the cached mtimes, return the cached `AppConfig` unchanged.
4. Otherwise parse from disk as today, store the result plus both mtimes in the cache keyed by resolved path, and return it.

The cache key must be the resolved path string so that callers pinning an explicit path (tests, settings writers) get their own cache entry and never collide with the default-path entry.

### Invalidation must be correct, not just fast

The mtime check is the invalidation mechanism. When the Settings UI writes a new config, the file mtime changes, so the next read misses the cache and reparses. When env overrides could change between calls within one process, note that env is read at parse time. If env overrides are part of the cache identity, include a hash of the relevant env-override variables in the cache key. Inspect `_apply_daemon_env_overrides` to determine which env vars participate; if they are read once at process start and never change at runtime, document that assumption in a code comment and skip env in the key. Do not guess - read the function and decide based on what it actually reads.

### Thread/async safety

The web layer is async and the daemon calls `load_config` from multiple coroutines. Guard the cache dict mutation with a simple lock so a concurrent miss does not corrupt the cache. The lock is held only for the dict read/write, never across the disk parse, to avoid serializing parses behind the lock. Mirror the microsecond-hold pattern documented in `src/usage.py` around its `_lock`.

### Explicit invalidation hook

Provide a module-level `invalidate_config_cache()` function that clears the cache. The settings writer path (`src/web/services/config_writer.py`) should call it after writing a new config so the change is visible immediately on the same process without waiting for the next mtime stat. This is belt-and-suspenders: mtime invalidation already covers it, but an explicit clear after a known write removes any mtime-resolution race on fast successive writes.

## Files to change

- `src/config.py` - add the mtime-keyed cache, the lock, and `invalidate_config_cache`. Wrap `load_config`'s parse path; do not change its signature or return type (~60 LoC).
- `src/web/services/config_writer.py` - call `invalidate_config_cache()` after a successful config write (~3 LoC).
- `tests/config/test_config_cache.py` - new test file.

## Files NOT to touch

- The `AppConfig` model definition and field set - unchanged.
- Any caller of `load_config` other than the config writer - the cache is transparent; callers see identical behavior.
- `src/usage.py` - referenced only as the lock-pattern model, not modified.

## Test acceptance criteria

In `tests/config/test_config_cache.py`:

- `test_cache_hit_returns_identical_config`: call `load_config` twice on the same unchanged file; assert the second call returns a config equal to the first and that the file was read from disk only once (patch the disk-read helper and assert call count is 1).
- `test_cache_miss_on_mtime_change`: load once, modify the file and bump its mtime, load again; assert the disk-read helper is called a second time and the new content is reflected.
- `test_overlay_mtime_change_invalidates`: with a sibling overlay present, change only the overlay mtime; assert reparse occurs.
- `test_distinct_paths_cached_separately`: load two different explicit paths; assert each is cached independently and neither evicts the other.
- `test_explicit_invalidate_clears_cache`: load once, call `invalidate_config_cache()`, load again; assert reparse occurs even though mtime did not change.
- `test_missing_overlay_treated_as_absent`: load with no overlay present; assert no crash and a subsequent load with an overlay added triggers reparse.
- `test_config_writer_invalidates`: patch `invalidate_config_cache`, call the config writer path, assert it was invoked once after the write.
- `test_concurrent_miss_single_parse`: simulate two concurrent misses (threads or asyncio tasks) on the same path; assert the cache ends in a consistent state and the returned configs are equal.

## Threat model

**Threat addressed**: repeated full-config parse and validation on every web request degrades dashboard responsiveness and wastes CPU. Relates to the prior "45-second UI load" observation and the Sprint 13 OBS-AY note about sync `load_config` in `/api/states`.

**Threat introduced by the cache**: a stale config served after a write. Mitigated two ways: mtime invalidation (file write changes mtime) and the explicit `invalidate_config_cache()` call from the writer path. Both must be present so neither a slow mtime resolution nor a forgotten explicit clear can serve stale config.

**Other layers protecting**: the daemon reloads config on its own cadence via `reload_repo_config_if_dirty` and the `config_dirty` control flag; those paths are independent of this cache and continue to function.

### Caller audit

All 44 callers receive an `AppConfig` with identical shape and values to the uncached path on a cache hit, and a freshly parsed one on a miss. The signature is unchanged, so no caller needs modification except the config writer which gains the explicit invalidation call. Run `grep -rn "load_config(" src/` after the change and confirm no caller passes arguments the cache key does not account for.

## Out of scope

- Caching per-repo config resolution (`reload_repo_config_if_dirty`) - that path has its own dirty-flag mechanism; not touched here.
- Async parallelization of per-repo Redis reads in `/api/states` - that is the separate Fix B of OBS-AY, not this PR.
- Removing any `load_config` callsite - the cache makes the existing call count cheap; deduplicating callers is a separate concern.

## Success signal

On test fixture: a second `load_config` on an unchanged file performs zero disk reads. On production: dashboard renders and `/api/states` polls no longer reparse config on every request; config edits via Settings UI remain visible immediately because the writer invalidates the cache.
