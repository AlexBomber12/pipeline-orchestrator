## Problem

Guardrail webhook URL is edited via SSH + config.yml + restart today. Setting up Slack/Discord notification or rotating webhook secret requires same friction as PR-344a documented.

## Solution

Extend Settings page with "Notifications" section exposing 4 fields:

- `guardrail_notification_webhook_url` (text, URL validation)
- `guardrail_notification_min_tier` (enum dropdown: P1/P2/P3)
- `guardrail_notification_timeout_sec` (int, 1-30 range)
- `dashboard_base_url` (text, used in webhook payload to construct dashboard links)

## Threat model

**Threat addressed**: webhook rotation friction. SSH+restart deters operator from rotating secrets routinely. Result: stale URLs leak in incident response.

**Other layers protecting**: URL validation prevents obvious typos. min_tier dropdown prevents arbitrary string injection.

**Why this layer needed**: webhook URL is the most rotation-sensitive config field (Slack/Discord tokens have explicit rotation policies). Bringing it into UI matches the rotation cadence.

### Caller audit

Same endpoint pattern as PR-344a. Field allow-list expansion is additive. ruamel.yaml round-trip preserves comments. Verify webhook URL is not logged in plaintext when invalid (security concern - log message should redact URL or use placeholder).

`webhook_url` field may contain secrets (Slack channel tokens). Verify dashboard middleware enforces same access control as existing config endpoints. If endpoint reachable without auth, this is a regression - surface as concern.
