## Problem

PR-186 ships backup-branch push when daemon crashes mid-commit during CODING. Pattern: if main feature branch push fails with "remote rejected" (branch protection or non-fast-forward), backup is not attempted. Operator loses work.

Branch protection on PR-side feature branches is uncommon, but force-push protection on shared branches can cause this. Some repos have org-wide protection patterns.

## Solution

In the recovery push pipeline, on "remote rejected" failure, attempt fallback push to `crash-backup/{task_id}/{timestamp}` branch. This branch follows naming pattern that branch protection generally allows (no slash conflicts, no protected glob match unless org-wide `crash-backup/**` rule, which is operator's choice).

On fallback success, write metadata to Redis: `recovery:backup_branch:{repo}:{task_id}` = branch name. Surface in dashboard cancellation card as "Crash backup available on branch X" with copy-to-clipboard button.

### Recovery push pseudocode

```python
async def push_recovery_branch(
    repo_path: Path,
    task_id: str,
    target_branch: str,
    redis_client,
    repo_slug: str,
) -> RecoveryPushResult:
    # Try target branch first (existing PR-186 path)
    primary_result = await _git_push(repo_path, target_branch, force=False)
    if primary_result.success:
        return RecoveryPushResult(success=True, branch=target_branch)

    # On "remote rejected" or "non-fast-forward", try crash-backup branch
    if "remote rejected" in primary_result.stderr or "non-fast-forward" in primary_result.stderr:
        timestamp = datetime.now(timezone.utc).strftime("%Y%m%d-%H%M%S")
        backup_branch = f"crash-backup/{task_id}/{timestamp}"
        fallback_result = await _git_push(repo_path, backup_branch, force=False)
        if fallback_result.success:
            await redis_client.set(
                f"recovery:backup_branch:{repo_slug}:{task_id}",
                backup_branch,
                ex=30 * 86400,
            )
            return RecoveryPushResult(
                success=True,
                branch=backup_branch,
                fallback_used=True,
            )

    return RecoveryPushResult(
        success=False,
        branch=None,
        error=primary_result.stderr,
    )
```

## Threat model

**Threat addressed**: PR-186 silently drops work when primary push rejected. Operator unaware data was recoverable via different branch path.

**Other layers protecting**: existing crash detection writes to Redis state. Operator sees task in ERROR. But branch with work is missing → operator forced to re-run from scratch.

**Why this layer needed**: graceful degradation. crash-backup branch is naming pattern that branch protection rules generally don't match (unless explicitly opted in).

### Caller audit

`push_recovery_branch` callers per grep: only the crash recovery handler. Signature changes are additive (return type extended with fallback_used field). Existing callers either ignore the new field or surface it in logs.

`recovery:backup_branch:` Redis key: new namespace. Verify no collision with existing keys. TTL 30 days matches cancellation record original window.

git push error parsing: stderr message format is git CLI version dependent. Test against git 2.40+ (production version). Regression risk: future git release changes message - periodic verification needed. Document in module-level comment.

## Out of scope

- Auto-rebase on non-fast-forward - out of scope; backup is safer than rebase.
- Cleanup of old crash-backup branches - manual operator task; can be cron job later.
- Recovery of work FROM backup branch (cherry-pick / merge wizard) - out of scope; operator does manual `git fetch && git checkout crash-backup/...` today.
