# PR-202: WATCH adaptive polling — slow-start, fast-tail

Branch: pr-202-watch-adaptive-polling-slow-start
- Type: feature
- Complexity: low
- Depends on: PR-180
- Priority: 2
- Coder: any

## Problem

Empirical observation 2026-04-29 from production daemon: GitHub API quota burn is **dominated by WATCH state**, not IDLE. While in WATCH, daemon polls GitHub roughly every `poll_interval_sec` (60s) for CI status, review state, and bot comments.

But Codex Review and CI have well-known minimum response times:
- **Codex Review:** typically 2-7 minutes from `@codex review` post to first response.
- **CI:** typically 5-15 minutes from push to conclusion (depends on test suite size).

Polling every 30-60s for the first 5 minutes wastes 5-10 GraphQL hits on a **scheduled wait**. Reviewer has not yet processed the request, CI is mid-flight. The polls return identical pending state every cycle.

Standard exponential backoff (fast-start → slow-tail on inactivity) is the wrong pattern here. The right pattern is **inverted**: slow-start → fast-tail. We anticipate that the first few minutes will produce nothing, so we slow polling there. After the expected response window opens, we increase polling frequency because the result could arrive any second.

## Scope

State-aware adaptive polling specifically for the WATCH state. Track time since WATCH entry (or last event). Use slow polling during the "no response expected" window, fast polling after.

This builds on PR-184 (IDLE adaptive polling) but for a different state with inverted logic. The two adaptive policies coexist: each phase has its own polling profile per the Phase-resource separation observation in roadmap architecture decisions section.

PR-202 depends on PR-180 (REST replacement) so the polling that benefits from this adjustment is already on REST core quota — the daemon is using the right API surface before we tune polling rate.

## Files to modify

`src/daemon/handlers/watch.py`:
- Add tracking attribute `_watch_entered_at: datetime | None` and `_watch_last_event_at: datetime | None` per active PR.
- On WATCH state entry, set `_watch_entered_at = now()`.
- On any detected event (push, review, comment, CI conclusion change), update `_watch_last_event_at = now()`.
- Add method `effective_watch_poll_interval()`:
  - Compute `seconds_since_anchor = now - max(_watch_entered_at, _watch_last_event_at)`.
  - If `seconds_since_anchor < watch_slow_window_sec` (default 300): return `watch_slow_poll_interval_sec` (default 300).
  - Else: return `watch_fast_poll_interval_sec` (default 45).

`src/daemon/runner.py` or `main.py`:
- Wire `effective_watch_poll_interval()` into the polling cadence calculation when state is WATCH. Use it in the same place the existing `poll_interval_sec` is consulted (or stack with rate-limit slowdown multiplier — take max of the two).

`src/config.py` and `config.yml`:
- Add new fields:
  - `daemon.watch_slow_window_sec: int = 300`
  - `daemon.watch_slow_poll_interval_sec: int = 300`
  - `daemon.watch_fast_poll_interval_sec: int = 45`

`src/web/templates/components/repo_summary.html` (optional):
- If GitHub API budget bar from PR-185 is rendered, surface "current poll interval" near it for visibility.

`tests/test_watch_handler.py`:
- Test: WATCH entry → first poll interval is slow (300s).
- Test: WATCH at 4 min → still slow.
- Test: WATCH at 5 min 1 sec → fast (45s).
- Test: event arrives at 6 min → resets to slow window from event timestamp.
- Test: stacking with rate-limit slowdown — uses max of the two.
- Test: `_watch_entered_at` cleared on transition out of WATCH (avoids stale value persisting into next WATCH session).

## Implementation notes

The "event detected" set must be the same set that already triggers state transitions. Do not invent new event detection here; reuse existing comment/review/push detection in watch.py.

Edge case: very fast CI (under 5 min) may complete and post conclusion while daemon is in slow-poll window. Daemon misses it for up to 5 min (one slow poll cycle). This is acceptable trade-off — saves 5-10 wasted polls on the typical case at cost of 5 min latency in the atypical fast-CI case.

If user manually intervenes (e.g. force-pushes via terminal), `_watch_last_event_at` does not update because daemon has not seen the push yet. Daemon will detect on the next slow-poll cycle. This is correct — manual intervention is rare and 5 min detection latency is acceptable.

For stacking with rate-limit slowdown: take the **max** of the two intervals. If rate-limit says "slow to 600s" and watch-adaptive says "slow to 300s" — use 600s. If watch-adaptive says "fast to 45s" and rate-limit says "slow to 600s" — use 600s. Rate-limit always wins because it is a hard ceiling.

## Phase-resource separation context

This PR exists because of the observation captured in roadmap "Phase-resource separation" architecture section: WATCH dominates GitHub burn, IDLE and other phases dominate other resources. Adaptive polling cannot use one global multiplier; each phase needs its own profile.

PR-184 implements IDLE adaptive polling (worker pattern: fast → slow on consecutive inactive cycles). PR-202 implements WATCH adaptive polling (response-anticipation pattern: slow → fast after expected wait window). Both are valid because they target different phases with appropriate logic for each.
