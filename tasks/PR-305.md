# PR-305: Operator override backend — guardrail decision endpoint integrating with Phase 2 cancellation cause + Retry button infrastructure

Branch: pr-305-operator-override-backend
- Type: feature
- Complexity: medium
- Depends on: PR-304
- Priority: 1
- Coder: codex

## Problem

Tier 2 guardrails (PR-301 large-diff, PR-302 secrets, PR-303 mass-deletion, PR-304 governance) detect violations during WATCH-time post-push diff scanning and call `safe_record_cancellation_cause` with category=ESCALATE plus payload `{"subsource": "guardrail", "rule": "large_diff_threshold", "excerpt": "+1800 LOC across 35 files"}`. After Sprint 15b Phase 2, the task transitions to `frontmatter status:ERROR + state.state IDLE`; the open PR remains on GitHub with the `escalated` label applied. Daemon picker skips the task on subsequent IDLE cycles because `derive_task_status` returns `TaskStatus.ERROR`.

Operator currently has two triage paths from Sprint 15b Phase 2:
- **Re-upload changed file** (PR-284): operator edits task spec content, validator detects content hash change, transitions to queued. Wrong fit here — operator does not want to change the spec, they want to approve THIS specific PR.
- **Per-task Retry button** (PR-283): one-click reset of frontmatter status to TODO + clear cancellation_cause. Wrong fit here — Retry resumes the task from CODING which would re-run the coder; operator does not want a new coder run, they want to keep the existing PR's commits and let it merge.

Neither matches the guardrail-override intent: "I have reviewed PR #N, the violation is acceptable for this specific PR, proceed to MERGE without re-running anything." A third triage path is required.

PR-305 adds a **per-PR guardrail decision endpoint** that:
- For `approve`: clears the cancellation_cause record, removes the GitHub `escalated` label, writes frontmatter `status: TODO`, transitions the daemon to WATCH if the open PR exists. Daemon's existing WATCH cycle then polls CI/review and proceeds to MERGE when ready. The coder's commits are preserved — no re-dispatch.
- For `reject`: same as the existing per-task Retry-with-cap-3 reject semantic (PR-283). Transitions to ERROR for re-triage, decrements no counter (this is operator-initiated reject, not retry-counter exhaustion).

Symmetric to PR-283 Retry but with different downstream effect.

## Scope

### 1. New cancellation cause subsource value `"guardrail"` documented

The PR-281 cancellation cause unification documented `payload.subsource = "coder" | "daemon"`. PR-305 adds a third value: `"guardrail"`. Update `src/cancellation/storage.py` ESCALATE category docstring to enumerate all three subsource values. No schema change — `payload` is a dict and accepts any string.

### 2. Guardrail-flagged PR enumeration helper

Backend needs to enumerate currently-open guardrail-flagged PRs across repos for the dashboard panel (PR-306). Implement as a Redis SCAN over `cancellation:*` keys filtered for `payload.subsource == "guardrail"`, returning a list of `(repo, pr_id, rule, excerpt)` tuples. Add helper `list_pending_guardrail_decisions(redis_client, repo: str | None = None) -> list[GuardrailPending]` in `src/cancellation/storage.py`. When `repo=None`, returns across all repos.

```python
@dataclass(frozen=True)
class GuardrailPending:
    repo: str
    pr_id: str
    rule: str
    excerpt: str
    recorded_at: int  # epoch seconds
```

The function reads `cancellation_index:{repo}` ZSET (existing index from PR-281) and filters entries by reading the cancellation_cause payload. Bounded scan: limit 100 entries per repo at one time.

### 3. POST /repos/{name}/guardrail/{pr_id}/decision endpoint

New endpoint in `src/web/routes/repo_control.py` mirroring the structure of `/tasks/{pr_id}/retry` (from PR-283). Payload accepts `decision` field with value `approve` or `reject`. Validates pr_id matches `^PR-\d{1,4}[a-z]?$` to prevent path injection.

Approve flow:
- Read cancellation cause for `(repo, pr_id)`. If absent or `payload.subsource != "guardrail"`, return 404 with hint "PR has no pending guardrail decision".
- Determine if there is an open PR on GitHub for this task. Read `RepoState` from Redis to check if `current_pr.pr_id == pr_id` (active PR) OR scan recent open PRs via `gh pr list` if not active. If no open PR exists, return 409 with hint "Open PR not found; reject and re-upload spec instead".
- Call `gh api ... -X DELETE /repos/{owner}/{repo}/issues/{pr_number}/labels/escalated` to remove the label. Best-effort; log on failure but proceed.
- Call `write_frontmatter_status(task_path, "TODO")` (from PR-279 writer) and `_commit_task_status_change(current_task, "TODO", f"guardrail decision approve for PR-{pr_id}")` with `[skip ci]` trailer.
- Delete cancellation cause: `redis.delete(cause_key(repo, pr_id))` and `ZREM cancellation_index:{repo} {entry}`.
- If the task is currently the active task in RepoState (state.current_task.pr_id == pr_id), transition state to WATCH so daemon picks up the open PR for merge polling. If not active, just leave at IDLE — next IDLE cycle picks the now-TODO task and natural CODING/WATCH/MERGE flow takes over (open PR is detected by existing PR-by-branch matching at coding.py).
- Wake daemon via `wake_daemon_for_repo`. Return 204.

Reject flow:
- Read cancellation cause; if absent or wrong subsource, return 404.
- Re-record cancellation cause with category=ESCALATE, payload.subsource="operator_reject", payload.reason_text=`f"Operator rejected guardrail-flagged PR #{pr_number} via dashboard"`, payload.original_rule=rule.
- Frontmatter stays at `status: ERROR`. Open PR is closed via `gh pr close {pr_number} --comment "Guardrail violation rejected by operator"` (best-effort). Branch deletion handled by GitHub auto-delete-branch setting if enabled, otherwise left for operator.
- Return 204.

### 4. Atomic state machine guards

Use Redis `WATCH` on the cancellation cause key during decision read-modify-delete. If the cause changes between read and delete, retry once; if it changes again, return 409 "Concurrent state change; retry". This prevents two operators clicking approve and reject simultaneously from leaving inconsistent state.

### 5. GET /repos/{name}/guardrail/pending endpoint

Read-only endpoint returning JSON list of pending guardrail decisions for this repo. Calls `list_pending_guardrail_decisions(redis_client, repo=name)` and returns sorted by `recorded_at` ascending (oldest first).

```json
{
    "pending": [
        {"pr_id": "PR-296", "rule": "large_diff_threshold", "excerpt": "+1800 LOC across 35 files", "recorded_at": 1746789012},
        {"pr_id": "PR-301", "rule": "secret_in_diff", "excerpt": "AKIA[REDACTED]EXAMPLE", "recorded_at": 1746789105}
    ]
}
```

Used by PR-306 dashboard panel for enumeration without scanning all task files.

## Implementation notes

The approve flow is **not symmetric** with the per-task Retry button (PR-283) despite both transitioning ERROR→TODO. Critical difference: Retry button is for the case where operator wants the daemon to re-attempt with a fresh CODING dispatch (new coder run, new commits). Guardrail approve is for the case where operator wants to KEEP the existing PR's commits and let the existing flow proceed to MERGE. The state-transition target differs: Retry → daemon picks task at next IDLE → CODING dispatch; Approve → state.state = WATCH directly so daemon resumes polling the existing PR.

If approve is requested on a task whose open PR no longer exists (closed externally, branch deleted), the 409 hint asks operator to use Retry instead. This avoids creating an orphan TODO task with no PR.

Reject flow records `subsource="operator_reject"` as a NEW cancellation cause. This serves two purposes: audit trail (we know the operator explicitly rejected, distinct from coder-driven failure), and dashboard rendering (operator_reject renders differently from guardrail in PR-306 — green/orange "rejected by you" vs red/yellow "needs your attention").

Concurrency design: the WATCH/MULTI transaction guards against the race where operator clicks approve in tab 1, reject in tab 2, both within the same second. Last-write-wins without WATCH; with WATCH, the second click gets 409 and operator sees a clear retry message.

The pending set Redis index from the original PR-292 design is dropped in favor of scanning `cancellation_index:{repo}` ZSET filtered by payload.subsource. This avoids a separate index that could drift; the cancellation_index is already maintained by Phase 2 PR-281 storage helpers.

Estimated diff size: ~250-300 LOC across 4 files. Of that, ~120 LoC web routes, ~50 LoC storage helper, ~80-130 LoC tests.
