# PR-275b: MCP cross-repo intent detection — literal gh repo delete and archive command match

Branch: pr-275b-mcp-literal-gh-repo-delete
- Type: feature
- Complexity: low
- Depends on: PR-275a
- Priority: 1
- Coder: codex

## Problem

PR-275a established the literal-command detection approach for `gh repo create` and `gh repo new`. The same destructive-action surface includes repo deletion (`gh repo delete owner/name`) and archiving (`gh repo archive owner/name`). Both are GitHub-org-level destructive operations: deletion is irreversible after a short grace window, archiving disables the repo for writes and is a heavyweight operator decision. Neither belongs to a coder's authorized action set under any current daemon-dispatched task.

PR-275b adds two more patterns mirroring PR-275a's approach: literal-command match with required `owner/name` argument, suppressed inside fenced code blocks, inline backticks, and negation phrases.

## Scope

Single deliverable: extend `src/mcp/scans.py:_ANTI_PATTERNS` with two new entries detecting literal repo-deletion and repo-archive commands.

Pattern 1: `cross_repo_repo_delete_command`
- Regex: `\bgh\s+repo\s+delete\s+[\w.-]+/[\w.-]+`
- Rule message: `"AGENTS.md prohibits coder-initiated repo deletion. Tier 1 guardrail. OBS-BT."`

Pattern 2: `cross_repo_repo_archive_command`
- Regex: `\bgh\s+repo\s+archive\s+[\w.-]+/[\w.-]+`
- Rule message: `"AGENTS.md prohibits coder-initiated repo archive. Tier 1 guardrail. OBS-BT."`

Both patterns reuse the suppression helpers `_is_inside_fenced_code_block` and `_is_inside_inline_code` introduced in PR-275a. Both reuse the existing `_is_negated` helper. No new helpers required.

## Behavior

Task body text examples that MUST trigger violation:
- `Run gh repo delete AlexBomber12/old-repo to clean up`
- `gh repo archive owner/legacy-project --confirm`
- `Execute: gh repo delete monorepo-org/sandbox`

Task body text examples that MUST NOT trigger violation:
- `the gh repo delete command requires confirmation flag` (no slash argument after `delete`)
- ` ```bash\ngh repo delete owner/foo\n``` ` (fenced code block)
- `` use `gh repo archive owner/foo` to deprecate `` (inline backticks)
- `Coders must not run gh repo delete owner/repo` (negation)
- `Do not gh repo archive owner/anything ever` (negation)

## Implementation notes

The split between PR-275a (create/new) and PR-275b (delete/archive) is by destructive direction: 275a covers creation surface, 275b covers deletion/archive surface. Independent revertability per PR per the MICRO eligibility constraints.

After PR-275b ships, the four primary cross-repo destructive commands are covered at spec-validation layer:
- `gh repo create owner/name` (PR-275a)
- `gh repo new owner/name` (PR-275a alias)
- `gh repo delete owner/name` (PR-275b)
- `gh repo archive owner/name` (PR-275b)

This is intentionally narrow. Other destructive operations the gh CLI supports (`gh repo edit owner/name --visibility=public` to change repo visibility, `gh repo rename owner/name new-name`) are not covered here. They are less catastrophic than create/delete/archive and the spec-text occurrence of those patterns is rare. If real production incidents surface them as gaps, PR-275-extended specs can add coverage on demand. Premature coverage adds maintenance burden without proven incident class.
