# PR-284: Re-upload validator refuses identical content via SHA-256 hash, hints to Retry button

Branch: pr-284-reupload-changed-only-enforcement
- Type: feature
- Complexity: low
- Depends on: PR-283
- Priority: 1
- Coder: codex

## Problem

PR-283 ships the Retry button for "spec unchanged, retry" intent. Re-upload via UI is for "spec changed, try again with new content" intent. Currently re-upload triggers CANCELED→TODO transition (`src/daemon/repo_ops.py:393-398`) regardless of content change — operator can re-upload identical file and clear the cancellation_cause without explicitly choosing the Retry path.

Sprint 15b Phase 1 decision: enforce mutually exclusive operator intents. Re-upload only for content-changed; identical re-upload is rejected with hint to use Retry button.

## Scope

1. **Compute and persist task_spec_hash on dispatch.** In the dispatch path (likely `src/daemon/handlers/coding.py` where coder is invoked with task_file), compute `hashlib.sha256(task_file.read_bytes()).hexdigest()` and persist to Redis `task_spec_hash:{repo}:{task_id}` (TTL 30 days, matches cancellation_cause TTL). This hash represents "the spec content the daemon last attempted".

2. **Validator hash check on upload.** In `src/web/routes/upload.py` (or wherever upload endpoint lives — find via `grep -rn "/upload" src/web/`), on each uploaded `tasks/PR-*.md` file:
   - Compute SHA-256 of uploaded content.
   - Read `task_spec_hash:{repo}:{task_id}` from Redis (if exists).
   - If existing hash matches uploaded hash AND task is currently in error state: refuse upload of this file with HTTP 409 Conflict, response body `"File unchanged. Use Retry button to re-attempt without changes."`. Multi-file batch upload reports the rejection per file in the aggregated error report (existing pattern at upload.py).
   - If hashes differ: proceed with normal upload flow. Update Redis `task_spec_hash:{repo}:{task_id}` to the new hash. Reset retry counter `metrics:retry_count:{repo}:{task_id}` to 0 (counter reset on content change per PR-283 design).

3. **Hash management on Retry button.** When Retry endpoint (PR-283) writes `status: queued` and clears cause, it does NOT update `task_spec_hash` (content hasn't changed). When Retry counter reaches cap, hash also stays — this preserves the "if you re-upload same content, it's still rejected" semantic.

4. **Hash cleanup on merge.** When daemon writes `status: merged` after successful merge (PR-279), delete `task_spec_hash:{repo}:{task_id}` from Redis (no longer needed; task is done). Also delete retry counter for cleanliness.

## Files to modify

- `src/daemon/handlers/coding.py` (dispatch path): compute and persist task_spec_hash on each dispatch.
- `src/web/routes/upload.py` (or batch validator): hash check on uploaded files, refuse identical with 409.
- `src/daemon/handlers/merge.py`: cleanup task_spec_hash and retry counter on merge success.
- `src/cancellation/storage.py` (or new helpers module): add `task_spec_hash_key` and helper functions for read/write/delete.

## Files NOT to touch

- `src/web/routes/repo_control.py` retry endpoint (from PR-283): do NOT modify hash logic there. Hash unchanged on Retry by design.
- Any task spec file. Branch name MUST match exactly (`pr-284-reupload-changed-only-enforcement`).

## Tests

`tests/web/test_upload.py`:
- `test_reupload_identical_content_returns_409`: setup task in error state with task_spec_hash in Redis, upload file with identical content, assert 409 + hint message.
- `test_reupload_changed_content_proceeds`: same setup but uploaded content differs by 1 char, assert upload accepted, hash updated, retry counter reset to 0.
- `test_upload_new_task_no_existing_hash_proceeds`: never-uploaded task, assert no 409 (no hash to compare).
- `test_batch_upload_partial_rejection`: 3 files, one identical to existing, two new; assert per-file report shows 1 rejected and 2 accepted.

`tests/runner/test_handle_coding.py`:
- `test_dispatch_persists_task_spec_hash`: trigger CODING dispatch, assert Redis has `task_spec_hash:{repo}:{task_id}` matching SHA-256 of file content.

`tests/runner/test_handle_merge.py`:
- `test_merge_cleans_up_hash_and_retry_counter`: simulate successful merge, assert Redis hash and retry counter keys deleted.

## Success criteria

- Identical re-upload rejected with hint to Retry button.
- Changed re-upload proceeds, resets retry counter.
- Hash cleaned up on merge.
- pytest exits 0.
- Manual smoke: re-upload unchanged file, observe 409 message; modify one char, re-upload, observe accept; click Retry button N+1 times, observe cap then change file, observe counter resets.
