## Reading order note for the implementing coder

This task is the **POST decision endpoint** of the operator override backend — the third and final piece of the split. The storage helper landed in PR-305a; the GET pending endpoint landed in PR-305b; this PR adds the mutation endpoint with `approve` and `reject` branches.

If implementation exceeds 200 LoC (excluding test file), escalate via stdout. The approve/reject branches share validation logic; aggressive code duplication is a smell, factor common helpers.

## Problem

Tier 2 guardrails (large-diff, secrets, mass-deletion, governance) escalate flagged PRs to `frontmatter status:ERROR` with `cancellation_cause.payload.subsource="guardrail"`. Operator currently has two triage paths from Sprint 15b Phase 2:

- **Re-upload changed file** (PR-284): for cases where operator wants to change the spec.
- **Per-task Retry button** (PR-283): for cases where operator wants a fresh coder run.

Neither matches the **guardrail-override** intent: "I have reviewed PR #N, the violation is acceptable for this specific PR, proceed to MERGE without re-running anything." A third triage path is required: approve the existing PR's commits without re-dispatching the coder, OR explicitly reject and close.

## Scope

### 1. New POST endpoint

Add to `src/web/routes/repo_control.py`, near the existing retry endpoint (which lives at line 1001, `@router.post("/repos/{name}/tasks/{pr_id}/retry", ...)`). Use that endpoint's structure as the model.

```python
@router.post(
    "/repos/{name}/guardrail/{pr_id}/decision",
    response_class=HTMLResponse,
)
async def post_repo_guardrail_decision(
    request: Request,
    name: str,
    pr_id: str,
    decision: str = Form(...),
) -> Response:
    """Operator-driven approve/reject of a guardrail-flagged PR.

    Approve: clears the cancellation_cause, removes the GitHub
    ``escalated`` label, writes frontmatter ``status: TODO``,
    transitions daemon to WATCH if the open PR exists. Coder's commits
    are preserved — no re-dispatch.

    Reject: records a new cancellation_cause with
    ``subsource="operator_reject"``, leaves frontmatter at
    ``status: ERROR``, closes the open PR.
    """
```

### 2. Request validation

Reject early on invalid input. Use the existing `_TASK_PR_ID_PATTERN` regex at line 44:

```python
if not _TASK_PR_ID_PATTERN.match(pr_id):
    return HTMLResponse("Invalid task identifier", status_code=400)
if decision not in ("approve", "reject"):
    return HTMLResponse(
        f"Invalid decision: {decision!r}; expected 'approve' or 'reject'",
        status_code=400,
    )
```

### 3. Approve branch

1. Look up repo config via `_find_repo_config_by_name(request, name)`. Return 404 if absent.
2. Resolve `repo_slug` from config.
3. Read cancellation cause: `cause = await get_cancellation_cause(redis_client, repo_slug, pr_id)`.
4. If `cause is None` OR `cause.payload.get("subsource") != "guardrail"`, return 404 with hint `"PR has no pending guardrail decision"`.
5. Read RepoState to determine the GitHub PR number:
   - If `state.current_task.pr_id == pr_id` and `state.current_pr is not None`, use `state.current_pr.number`.
   - Otherwise, the open PR may exist but not be the active task — return 409 with hint `"Open PR not active in daemon state; reject and re-upload spec instead"`. Approve flow REQUIRES the daemon-tracked active PR for the WATCH transition to make sense. Operators can still close+reject inactive cases.
6. Remove the `escalated` label on the GitHub PR via subprocess: `gh api -X DELETE repos/{owner}/{repo}/issues/{pr_number}/labels/escalated`. Best-effort; log on failure but proceed. Use the same subprocess wrapper pattern as `_run_retry_git` (line 477 area) — capture stderr, do not raise on non-zero return for this best-effort step.
7. Write frontmatter status:
   - Compute `task_path = repo_root / "tasks" / f"{pr_id}.md"` (match the path computation in the retry endpoint).
   - Call `write_frontmatter_status(task_path, "TODO")` (existing PR-279 writer).
   - Commit the frontmatter change to main with `[skip ci]` trailer via existing `_run_retry_git` helper pattern (commit message: `f"chore(tasks): guardrail decision approve for {pr_id} [skip ci]"`).
8. Delete the cancellation cause atomically (see section 5 below).
9. Transition daemon state:
   - If `state.current_task.pr_id == pr_id`, set `state.state = PipelineState.WATCH` and persist back to Redis using the same write pattern as the retry endpoint.
   - Wake the daemon via existing `wake_daemon_for_repo(redis_client, repo_slug)` helper (used elsewhere in the file — locate via grep).
10. Return `HTMLResponse("", status_code=204)`.

### 4. Reject branch

1. Same lookups as approve (repo config, repo_slug, cancellation cause).
2. If cause absent or wrong subsource, return 404.
3. Determine PR number from `state.current_pr.number` if active task matches, OR via `gh pr list --head {branch} --json number,state` fallback for inactive cases (model on existing `gh` invocations in the file).
4. Re-record cancellation cause with the new subsource:
   ```python
   await record_cancellation_cause(
       redis_client,
       repo_slug,
       pr_id,
       category="ESCALATE",
       payload={
           "subsource": "operator_reject",
           "reason_text": f"Operator rejected guardrail-flagged PR #{pr_number} via dashboard",
           "original_rule": cause.payload.get("rule", ""),
           "original_excerpt": cause.payload.get("excerpt", ""),
       },
   )
   ```
5. Close the GitHub PR via subprocess: `gh pr close {pr_number} --comment "Guardrail violation rejected by operator"`. Best-effort.
6. Leave frontmatter at `status: ERROR` (do NOT call `write_frontmatter_status`).
7. Return `HTMLResponse("", status_code=204)`.

### 5. Atomic state machine guard (WATCH/MULTI)

The approve flow has 3 mutations (label removal, frontmatter commit, cancellation_cause delete). Two operators clicking approve and reject simultaneously could interleave these mutations. Use Redis WATCH on the `cause_key(repo_slug, pr_id)` key during the read-modify-delete sequence:

```python
async with redis_client.pipeline(transaction=True) as pipe:
    await pipe.watch(cause_key(repo_slug, pr_id))
    cause_bytes = await pipe.get(cause_key(repo_slug, pr_id))
    if cause_bytes is None:
        await pipe.unwatch()
        return HTMLResponse("PR has no pending guardrail decision", status_code=404)
    cause = CancellationCause.from_redis(cause_bytes)
    if cause.payload.get("subsource") != "guardrail":
        await pipe.unwatch()
        return HTMLResponse("PR has no pending guardrail decision", status_code=404)

    # ... perform label removal, frontmatter write, commit ...

    pipe.multi()
    pipe.delete(cause_key(repo_slug, pr_id))
    pipe.zrem(index_key(repo_slug), pr_id)
    try:
        await pipe.execute()
    except aioredis.WatchError:
        return HTMLResponse(
            "Concurrent state change detected; please retry the decision",
            status_code=409,
        )
```

Retry once on WatchError if practical; if the second attempt also conflicts, return 409. Use the WATCH/MULTI pattern only for approve flow — reject is idempotent enough that the simpler `await record_cancellation_cause(...)` sequence suffices (last-write-wins is acceptable for reject because both operators clicking reject produce the same end state).

## Risk notes (for PR description, not code)

- The approve branch has the most surface area: label removal + frontmatter + git commit + cause deletion + state transition + daemon wake. Each is best-effort except the cause deletion (which is the atomic guard). If any intermediate step fails, the operator sees an error but partial state may persist — for example, label removed but frontmatter unchanged. The atomic guard protects against concurrent mutations but not against partial-failure cleanup. Mitigation: log every step at INFO level so operator can diagnose stuck states. The cancellation cause delete is the LAST mutation: if it succeeds, the operator's "approve" is durable; if it fails (WatchError), the operator gets 409 and nothing was deleted.
- Reject branch is simpler: idempotent re-record + best-effort PR close. Operator clicking reject twice produces the same end state.
- The 409-on-inactive-task constraint is a deliberate UX choice (matches spec). Operators with an open PR but no daemon-tracked active task should use the reject path to close cleanly, then re-upload the task spec via the existing PR-284 flow.
