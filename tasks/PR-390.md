# PR-390: Merge spend-ceiling into the unified usage gate

- Depends on: PR-389

## Reading order before coding

1. Read this entire spec and PR-389 (the decomposed rate-limit predicates).
2. Read `src/daemon/rate_limit.py` - both `_check_rate_limit` (now decomposed) and `_check_spend_ceiling` (lines 33-68), `_enter_spend_ceiling_paused` (70-88), `_maybe_send_ceiling_warning` (90-153).
3. Read `src/config.py:170-179` - the fields `spend_ceiling_session_percent`, `spend_ceiling_weekly_percent`, `spend_ceiling_warning_percent`, and `rate_limit_session_pause_percent`, `rate_limit_weekly_pause_percent`.
4. Read where each gate is called: `grep -rn "_check_rate_limit\|_check_spend_ceiling" src/daemon/ | grep -v test` (coding.py:181, fix.py:240 call spend-ceiling; the rate-limit gate is called elsewhere).

## Problem

Rate-limit and spend-ceiling are two threshold checks on the same usage metric (session_percent / weekly_percent) leading to the same action (PAUSED until reset, via `_record_rate_limit`). The differences are narrow: rate-limit has a reactive 429-detect layer; spend-ceiling has a warning webhook. They are presented as two unrelated systems with two Settings sections, and the operator finds the distinction unclear (confirmed in audit #9).

This PR merges them into one "usage gate" with named sub-predicates (building on PR-389's decomposition). Spend-ceiling becomes one more proactive threshold predicate alongside the rate-limit pause threshold. Config fields are consolidated with backward-compatible aliases. This is R3.2.

## Solution

### One gate, multiple threshold predicates

Compose a single `usage_gate(coder)` that runs the proactive predicates in order:

- The rate-limit pause threshold (from PR-389's decomposition).
- The spend-ceiling threshold (session and weekly), currently in `_check_spend_ceiling`, refactored into a predicate of the same shape.

Both read the same usage snapshot. Both, on breach, enter the same PAUSED state via the same `_record_rate_limit` / pause-apply path. The gate returns "dispatch may proceed" or pauses. The reactive `_detect_rate_limit` (stderr 429 parsing) remains a separate post-CLI layer, unchanged.

### Preserve the two genuine differences

- The warning webhook (`_maybe_send_ceiling_warning`) is a spend-ceiling feature; keep it as a property of the spend-threshold predicate (fire warning at warning_percent before the pause threshold). Generalize it so it could apply to the rate-limit threshold too if desired, but do not change rate-limit's current no-warning behavior unless explicitly intended - keep behavior identical, just unified in structure.
- The reactive 429 layer is rate-limit-only and stays separate.

### Consolidate config with backward-compat aliases

The fields overlap conceptually. Consolidate the UI-facing model into one coherent set, e.g. a pause threshold and a warning threshold per window, while KEEPING the existing field names readable from config for backward compatibility:

- Keep `rate_limit_session_pause_percent`, `rate_limit_weekly_pause_percent`, `spend_ceiling_session_percent`, `spend_ceiling_weekly_percent`, `spend_ceiling_warning_percent` parseable so existing config.yml and the production overlay do not break.
- Internally, map them onto the unified gate's threshold inputs. Document which legacy field feeds which gate input.
- Do NOT delete config fields in this PR (deleting would break the production overlay). Mark the redundant ones as deprecated-aliases in comments; a future PR can remove them after the overlay is updated.

### Behavior identical, structure unified

Like PR-389, this is behavior-preserving where the two systems already agreed, and a clarification where they overlapped. The pause outcomes for any given usage snapshot must be identical to today (rate-limit threshold breach pauses, spend-ceiling breach pauses). The only intended change is structural unification and the consolidated internal threshold model.

## Files to change

- `src/daemon/rate_limit.py` - introduce `usage_gate` composing rate-limit and spend-ceiling predicates; refactor `_check_spend_ceiling` into a predicate; keep the warning webhook as a spend-threshold property (~120 LoC restructure).
- `src/config.py` - map legacy fields onto unified gate inputs, mark redundant aliases deprecated (keep parseable) (~20 LoC).
- `src/daemon/handlers/coding.py`, `src/daemon/handlers/fix.py` - call the unified `usage_gate` instead of separate `_check_spend_ceiling` (~10 LoC).
- `tests/test_usage_gate.py` - new test file.

## Files NOT to touch

- `_detect_rate_limit` reactive layer - unchanged.
- The production config overlay - must keep working via backward-compat parsing.
- The UI Settings sections - merged in R3.3, not here (this PR is backend unification).

## Test acceptance criteria

In `tests/test_usage_gate.py`:

- `test_rate_limit_threshold_pauses`: usage above rate-limit pause threshold; assert the gate pauses identically to the old `_check_rate_limit`.
- `test_spend_ceiling_threshold_pauses`: usage above spend-ceiling; assert the gate pauses identically to the old `_check_spend_ceiling`.
- `test_both_thresholds_same_pause_state`: assert both breaches enter the same PAUSED state via the same path (the unification point).
- `test_warning_webhook_preserved`: at warning_percent, assert the spend-ceiling warning webhook fires once (dedup preserved), exactly as before.
- `test_reactive_429_still_separate`: assert `_detect_rate_limit` is still called post-CLI and unchanged.
- `test_legacy_config_fields_parse`: assert a config.yml with the old field names still parses and feeds the gate correctly (backward compat).
- `test_behavior_identical_to_pre_merge`: table test of usage snapshots through the unified gate vs the documented old behavior; assert identical pause outcomes.
- `test_no_config_field_deleted`: assert all legacy config fields are still present and parseable (deprecation, not removal).

## Threat model

**Threat addressed**: two near-duplicate threshold systems on one metric, confusing the operator and duplicating Settings and logic.

**Threat introduced**: merging could change a pause outcome or break the production overlay's config fields. Mitigated by the behavior-identical contract with table tests, by keeping all legacy config fields parseable (no deletion), and by building on PR-389's already-tested decomposition.

**Other layers protecting**: the reactive 429 layer is untouched and still catches real provider limits; the warning webhook dedup is preserved.

### Caller audit

The spend-ceiling callers (coding.py, fix.py) switch to the unified gate; confirm the gate's return contract matches what they expect (proceed/pause). The rate-limit gate callers keep their interface via PR-389's orchestrator. Grep both old gate names after the change and confirm only the unified gate remains as the call target.

## Out of scope

- Deleting redundant config fields (future, after overlay update).
- The UI merge of the two Settings sections (R3.3).
- Adding a dollar-cost dimension - that is the product-metric work (M), separate.

## Success signal

On test fixture: rate-limit and spend-ceiling both pause via one unified gate with identical outcomes to today; the warning webhook and reactive layer are preserved; legacy config fields still parse. On production: one usage gate governs pausing; behavior is unchanged; the conceptual duplication is gone at the backend, ready for the UI merge.
