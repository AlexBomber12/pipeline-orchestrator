## Problem

When operator uploads a task batch while the daemon is in CODING/FIX/WATCH/MERGE state, the upload route extracts files to a working tree but does NOT commit them. Files wait until daemon reaches IDLE before the upload route's pending commit fires.

During this wait window:

- Operator sees "Uploaded N files" success toast and assumes the upload landed.
- The files are NOT yet visible in tasks/ from the dashboard view.
- If operator rebuilds the daemon container or daemon crashes during the wait, the uncommitted working-tree files may be lost or cause confusion on next boot.

Production observation 2026-05-10: operator uploaded v4 zip during active CODING state. Upload waited 5+ minutes for IDLE. Operator restarted daemon to clear unrelated issue, lost the pending upload.

## Solution

Show a small "Upload pending: N files queued for next IDLE" badge on the affected repo's card whenever the upload route has files waiting in the working tree.

### Detection

The upload route already tracks pending state via an in-memory Redis key or a tempdir convention (verify exact mechanism in `repo_ops.py`). Add a query helper:

```python
async def get_upload_pending_count(repo_slug: str, redis: Redis) -> int:
    """Return the count of files waiting in the pending-upload buffer.

    0 means no pending upload. Non-zero means N files are extracted
    to the working tree but not yet committed.
    """
    val = await redis.get(f"upload_pending_count:{repo_slug}")
    if val is None:
        return 0
    return int(val.decode() if isinstance(val, bytes) else val)
```

Wire the upload route to SET this key when files extracted but not yet committed, and DELETE when the deferred commit completes.

### Badge rendering

In `src/web/templates/components/repo_cards.html`, near the existing status badges (around line 100-115), add:

```jinja2
{% if repo.upload_pending_count and repo.upload_pending_count > 0 %}
<span class="ml-2 inline-flex items-center gap-1 rounded border border-warn/40 bg-warn/10 px-2 py-0.5 text-[11px] text-warn"
      title="{{ repo.upload_pending_count }} files extracted to working tree, awaiting IDLE state to commit">
    <svg class="h-3 w-3" ...><!-- clock or hourglass icon --></svg>
    Upload pending ({{ repo.upload_pending_count }})
</span>
{% endif %}
```

### Dashboard payload

In `src/web/routes/dashboard.py`, the repo card composition reads various per-repo state. Add a call to `get_upload_pending_count(name, redis_client)` and include in payload as `upload_pending_count`.

### Optional cancel button

NOT in this PR scope. If operator wants to cancel a pending upload (delete working-tree files without committing), that requires a separate cancel endpoint. Defer.

## Threat model

**Threat addressed**: invisible "in-flight" upload state. Operator may take destructive action (restart, force-pull) under the false belief that upload is complete, losing the pending files.

**Other layers protecting**: upload success toast fires when files extract OK (regardless of commit status). Toast wording is misleading because it does not distinguish "extracted but not committed" from "committed".

**Why this layer needed**: dashboard is the source of truth for daemon state. Adding an explicit pending indicator is the right place to surface the in-flight upload.

### Caller audit

`get_upload_pending_count` is new. Called only from dashboard repo card composition.

Redis key `upload_pending_count:{repo}` is new. Set by upload route, deleted by deferred-commit completion (success or failure path). No external consumers.

Template change is additive: badge appears only when count > 0.

## Out of scope

- Cancel button for pending upload. Defer to follow-up PR if frequency justifies.
- Listing the specific pending file names. Out of scope; count is sufficient signal.
- Estimated time-until-commit. Out of scope; operator can read daemon state to estimate (CODING/FIX has known timeouts).

## Success signal

On test fixture: upload during CODING state shows "Upload pending (3)" badge on repo card. Once daemon transitions to IDLE and deferred commit fires, badge disappears within one dashboard 5s poll. On production: operator sees the badge, knows not to restart, can wait for IDLE confirmation before any other action.
