# PR-512: Do not count inherited FIX work again on merge-only recovery runs

Branch: pr-512-ui-fix-count-recovery
- Type: bugfix
- Complexity: low
- Depends on: PR-468
- Priority: 1
- Coder: any

Audit baseline: current main `284b5d072e8dff2c453e53a0d6fd3be44d264202` (2026-10-31).

## Outcome

The existing task-attempt UI projection counts real FIX dispatches once. A
merge-only recovery record with no coder invocations contributes zero FIX work,
even when its retained fix_iterations/fix_recovery_baseline are positive. History,
attempts, duration, provider allowance and escalation accounting stay unchanged.

## Confirmed cause and scope

src/metrics.py:_run_fix_dispatches already counts captured FIX snapshots and
preserves unknown legacy FIX counters. Its empty-record fallback only treats
run_phase=fix specially, then returns fix_iterations for all other phases.
The observed shape is two CODING records (zero FIX), one FIX record with one FIX
snapshot and counter 1, and an operator MERGE recovery record with counter 1,
baseline 1 and invocations=[]. task_attempt_totals currently reports two instead
of one. Use an anonymized fixture of this shape, not production data/credentials.

Fix the projection using the established run_phase=merge zero-coder contract.
Captured invocations still take precedence: a record containing actual FIX
snapshots must count them even if its final phase is merge. A structurally proved
zero is known zero for telemetry completeness. Unknown legacy records remain
unknown; absence of snapshots alone does not prove that a historical coding/FIX
record executed nothing. Do not rewrite stored records or add invocation records.

## Acceptance criteria

- The four-record fixture yields attempt_count=4 and fix_iterations=1, with the
  merge-only zero included as known telemetry. Repeated input copies/checkpoints
  do not duplicate run or invocation counts.
- Separate FIX runs with cumulative counters 1 then 2 and one captured dispatch
  each count two. Separate Retry chains may reuse iteration numbers; preserve
  their distinct run identity. Duplicate snapshots within one run stay deduped.
- A merge record with captured FIX evidence counts that evidence. A positive
  legacy coding counter keeps its documented compatibility; legacy FIX without
  dispatch evidence keeps unknown/partial semantics.
- JSON round-trip and UI rendering retain the same task/run/attempt identities,
  terminal outcomes and stored payloads. The UI shows the correct confirmed
  count and existing unknown/partial indicators, not a fabricated complete total.
- Provider retry credits, fix_recovery_baseline, merge reconstruction and the
  creation/finalization lifecycle are untouched.
