# PR-207: Parallelize per-repo run_cycle to unblock cross-repo polling

Branch: pr-207-parallel-run-cycle
- Type: refactor
- Complexity: medium
- Depends on: none
- Priority: 2
- Coder: any

## Problem

Discovered during the multi-repo isolation audit (`docs/multi-repo-audit-2026-04-29.md`, concern 2). The daemon main loop in `src/daemon/main.py` iterates over runners sequentially with `await runner.run_cycle()`. While runner A is in CODING and awaits the coder subprocess (which can run for 30+ minutes during a PLANNED PR), the loop cannot advance to runner B. As a result:

- Repo B's WATCH polling stalls — newly merged PRs are not detected promptly.
- Repo B's MERGE state cannot progress.
- Repo B's IDLE state cannot pick up the next task from QUEUE.md.
- Redis pub/sub wake events for repo B are buffered until the loop comes back around.

Today the production deployment has only one managed repo, so this never bites. Adding a second repo (e.g. for the megaraid-dashboard onboarding test) would expose it immediately. The slug, Redis keys, tasks/ paths, and event log are all properly isolated; serial scheduling is the remaining blocker.

## Scope

Schedule each runner's `run_cycle` as an independent asyncio task so a long-running CODING/FIX subprocess on one repo does not delay polling on another. Keep the existing per-runner due-time/poll-interval logic intact; only the dispatch is parallelized.

Out of scope: limiting the number of *concurrent coder subprocesses*. That is an orthogonal rate-limit concern (the coder semaphore, if needed, can be added later). This PR only ensures that one repo's CODING does not starve other repos of polling.

## Files to modify

`src/daemon/main.py`:
- Replace the sequential `for key, runner in list(runners.items()): ... await runner.run_cycle()` loop with a per-runner background task scheduler.
- Maintain a `dict[str, asyncio.Task]` of in-flight cycles. On each main-loop tick, for each runner whose previous task has finished and whose `last_run + interval` is due, spawn a new `asyncio.create_task(runner.run_cycle())`.
- Skip scheduling a new cycle while the previous one is still running (per-runner).
- On config reload / runner removal, await/cancel the in-flight task for the removed runner before discarding it.
- Preserve the existing `try/except` isolation so one runner's exception does not poison another's task.

`src/daemon/runner.py`:
- No behavior changes expected. If `run_cycle` has any implicit assumption about being called from the main loop (e.g. ordering with `publish_state`), surface and document it.

`tests/test_daemon_main.py`:
- Test: two runners, runner A's `run_cycle` blocks for N seconds, runner B is still polled within one tick (i.e., B's cycle starts before A's completes).
- Test: a single runner with a still-running cycle is not scheduled twice on consecutive main-loop ticks.
- Test: when a runner is removed during config reload, its in-flight task is cancelled or awaited and not leaked.
- Test: an exception raised inside one runner's cycle does not cancel the other runner's cycle.

## Implementation notes

`asyncio.create_task` plus a per-runner task handle is the simplest pattern; `asyncio.gather` would force the loop to wait for the slowest runner each tick, defeating the point.

Watch out for the `last_run[key]` bookkeeping — it must update when the cycle is *scheduled*, not when it completes, otherwise a long cycle would re-schedule itself the moment it returns.

Test the cancellation path carefully. The CODING handler already handles `asyncio.CancelledError` (see `src/daemon/handlers/coding.py:138`). The new code must not break that contract.

## Success criteria

1. With two runners configured, blocking runner A's `run_cycle` for 5 seconds in a unit test does not delay runner B's `run_cycle` start by more than the configured poll interval plus a small jitter budget.
2. `python -m ruff check src/` passes.
3. `python -m pytest --cov=src --cov-fail-under=100` passes.
