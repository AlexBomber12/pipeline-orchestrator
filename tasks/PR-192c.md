# PR-192c: Onboarding doc and dry-run reconciliation mode

- Coder: any

## Problem

PR-192a built the section-marker framework. PR-192b applied it to AGENTS.md. This PR is the operator-facing piece: a dry-run mode that shows what reconciliation would do without writing anything, plus user documentation for the onboarding workflow.

Without dry-run, the operator has to trust the daemon to modify AGENTS.md correctly the first time. Given that AGENTS.md often contains hand-crafted important content (security policies, hardware targets), trust must be earned with visibility.

## Scope

CLI command or web endpoint that takes a repo path, applies onboarding reconciliation to its AGENTS.md, returns a unified diff showing what would change. Operator reviews the diff and chooses to apply or abort.

Plus user-facing documentation: how to onboard an existing repo, what daemon sections are added, how to opt out of specific sections.

## Files to modify

`src/onboarding/reconciliation.py` (new file):
- Function `reconcile_agents_md(file_path, dry_run=True)` returns either:
  - dry_run=True: tuple (proposed_content, unified_diff_text)
  - dry_run=False: writes file, returns (final_content, applied_diff_text)
- Uses PR-192a framework + PR-192b template.

`src/web/app.py` or new endpoint module:
- Endpoint `POST /onboarding/preview` accepting repo URL or local path, returns diff.
- Endpoint `POST /onboarding/apply` (after preview confirmation).
- Both endpoints return JSON with diff text and applied/proposed status.

`docs/onboarding-existing-projects.md` (new file):
- Step-by-step guide.
- Explanation of which sections are daemon-managed.
- How to preserve user-owned sections.
- How to opt out (delete the marker block; daemon will not re-add until next reconciliation cycle).
- Example walkthrough using a fictional `my-app` repo.

`tests/test_onboarding_reconciliation.py`:
- Test: dry-run on a repo without AGENTS.md proposes adding daemon sections.
- Test: dry-run on a repo with existing AGENTS.md but no markers proposes appending daemon sections, preserves user content.
- Test: dry-run on a repo with existing markers proposes updating in place.
- Test: apply (non-dry-run) actually writes the file.
- Test: idempotence — apply twice produces same result.

## Implementation notes

Dry-run is the primary mode. Apply mode is just dry-run + write. Implement them via shared internal helper.

The diff output should be unified diff (`difflib.unified_diff` in Python stdlib).

For the web endpoints, sandbox path traversal carefully — no `..` or absolute paths outside known repo roots.
