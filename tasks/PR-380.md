## Reading order before coding

1. Read this entire spec.
2. Read PR-376/377/378/379 - taxonomy, port, frontmatter blocked_reason, coarse write.
3. Read `src/daemon/runner.py:2609-2651` - the main-loop ERROR branch. It has three sub-branches (rate_limited_until -> PAUSED; skip_ai_error_diagnose -> wait for `_review_timeout_park_cleared` -> IDLE; error_handler_use_ai -> handle_error) and an implicit fourth path: if `error_handler_use_ai` is False, NOTHING happens and the daemon stays in ERROR silently forever (audit finding E).
4. Read `src/daemon/runner.py:1623-1644` - `_review_timeout_park_cleared`, the existing operator-park-cleared check (returns True when the cancellation cause is gone).
5. Read `src/daemon/handlers/error.py:136-468` - `handle_error`, the AI-diagnosis path. Note its early-return IDLE paths (infra, rate-limit, timeout) and its stays-ERROR paths (diagnose ceiling, ESCALATE verdict, coder unavailable). guardrail currently falls into AI diagnosis and gets stuck.
6. Read `src/web/routes/repo_control.py` retry endpoint - it clears the cancellation cause and diagnose_exhausted, writes TODO, and publishes a wake. This is the operator action that should release the park.

## Problem

The main-loop ERROR branch handles only three cases explicitly and has a silent fourth (error_handler_use_ai False -> eternal ERROR, no log). The `skip_ai_error_diagnose` flag plus `_review_timeout_park_cleared` is a special-case operator-park that works ONLY for review_timeout. guardrail and other non-self-healing failures have no operator-park: they route into AI diagnosis, hit the diagnose ceiling, and stay ERROR with no clean exit. Reupload does not help because `process_pending_uploads` runs only in the IDLE cycle, and a stuck-in-ERROR daemon never reaches IDLE.

This PR generalizes the review_timeout park into ONE operator-clearable park for all non-self-healing ERRORs, driven by the suppression store. It fixes the guardrail-stuck bug and the silent-eternal-ERROR hole (E) by design (refactor invariant 4: every ERROR has a visible exit). This is R1.5, the riskiest PR in R1 - it ships behind a feature flag with canary.

## Solution

### Classify ERROR exits into two kinds

Read each `_transition_to_error` reason and classify it as either:

- Self-healing (auto-exit to IDLE for retry): infra_failure, rate_limit, review_timeout's transient retry, timeout. These are the cases `handle_error` already early-returns to IDLE for. They keep that behavior.
- Operator-clearable park (stay ERROR with a visible reason until the operator clears it): guardrail, diagnose_exhausted, coder_escalate (ESCALATE verdict), no_push_deadlock, fix_iteration_cap, operator_stopped. These require human action (fix the spec, change the approach). They must NOT loop through AI diagnosis indefinitely.

The classification is a property of the canonical SuppressionReason (PR-376). Add an `is_operator_clearable` (or `auto_recoverable`) attribute to the registry metadata for each reason, or a helper that derives it. Decide each reason's class by reading where it is produced; document the table.

### One generalized park-cleared check

Generalize `_review_timeout_park_cleared` into `_suppression_cleared(task_id)` that asks the suppression store `is_suppressed`. When the operator presses Retry or reuploads (both clear the suppression / cancellation cause), `is_suppressed` returns None and the park is released to IDLE. This replaces the review_timeout-specific flag with a store query that works for every operator-clearable reason.

### Rewrite the main-loop ERROR branch

Replace the three-branches-plus-silent-hole with one coherent flow:

1. If rate-limited, go PAUSED (unchanged - rate-limit is its own resume machinery).
2. Otherwise, read the task's suppression reason (from the suppression store, with frontmatter blocked_reason as the durable fallback when the store has no record - this is where the two-layer model pays off after a Redis flush).
3. If the reason is operator-clearable: check `_suppression_cleared`. Cleared -> IDLE (operator acted). Not cleared -> stay ERROR with the visible reason; log once per reason (not every cycle - dedup) so there is never a silent park. Do NOT route into AI diagnosis.
4. If the reason is self-healing: run the existing self-healing path (handle_error with AI diagnosis if `error_handler_use_ai`, or the early-return IDLE paths). 
5. Remove the silent fourth path: if `error_handler_use_ai` is False and the reason is self-healing, exit to IDLE for a plain retry rather than doing nothing. There is no code path that leaves ERROR with no log and no exit.

### guardrail gets a real exit

Because R1.4 now writes blocked_reason guardrail, and guardrail is operator-clearable, a guardrail ERROR now: stays ERROR with a visible "guardrail - edit the spec before retrying" state, does NOT burn AI-diagnosis cycles, and exits to IDLE when the operator clears it via Retry or reupload. The reupload path works because clearing the suppression releases the park independent of whether the daemon was in IDLE.

### Feature flag and canary

This changes the hottest control path. Gate the new ERROR-branch logic behind a config flag (default False), mirroring the PR-329 unified-inhibitor pattern. Ship with the flag False, deploy, then flip True on the pipeline-orchestrator repo itself as the canary (NOT megaraid - PR-330b lesson). The old three-branch logic remains behind the flag until the canary proves the new path over 24-48h.

## Test acceptance criteria

In `tests/test_single_error_exit.py`:

- `test_guardrail_stays_parked_until_cleared`: drive a guardrail ERROR; assert the daemon stays ERROR with a visible reason and does NOT call AI diagnosis; then clear the suppression (simulate Retry); assert next cycle goes IDLE.
- `test_guardrail_does_not_loop_diagnosis`: assert over multiple cycles that a guardrail ERROR never invokes the diagnose coder.
- `test_silent_hole_removed`: set `error_handler_use_ai=False` and drive a self-healing ERROR; assert the daemon exits to IDLE for retry (not silent eternal ERROR) and logs the exit.
- `test_no_error_cycle_without_log`: drive every reason class through the ERROR branch; assert each cycle either transitions state or logs the park reason (deduped) - never a silent no-op cycle.
- `test_self_healing_unchanged`: drive infra and rate-limit ERRORs; assert they still early-return to IDLE / PAUSED as before.
- `test_reupload_releases_park_from_error`: with the daemon in a guardrail park, clear the suppression (simulating reupload's cause delete); assert the park releases to IDLE even though the daemon was in ERROR (not IDLE) when the clear happened.
- `test_frontmatter_fallback_after_redis_loss`: simulate the suppression store returning None (Redis flush) but frontmatter blocked_reason=guardrail present; assert the daemon treats it as an operator-clearable park (stays ERROR safely), not as a clear.
- `test_flag_off_uses_legacy_branch`: with the feature flag False, assert the original three-branch behavior is preserved exactly.
- `test_park_log_deduped`: assert the park reason is logged once, not every poll cycle.

## Threat model

**Threat addressed**: guardrail and other operator-required failures get stuck in ERROR forever (route into AI diagnosis, hit ceiling, no exit), and `error_handler_use_ai=False` produces silent eternal ERROR. Reupload cannot help while stuck in ERROR. This is the operator's reported pain.

**Threat introduced**: this rewrites the hottest control path; a mistake could mis-route a self-healing error into a permanent park or vice versa. Mitigated by the feature flag (default False), the canary on the orchestrator repo, the explicit two-class classification with tests for each, and `test_flag_off_uses_legacy_branch` proving the old path is intact for rollback.

**Other layers protecting**: the repo-level Reset-to-IDLE button (R1.8) is the manual escape hatch independent of this logic. The frontmatter durable fallback keeps the safe (stay-parked) behavior after Redis loss.
