# PR-266b: recover_state swap behind feature flag with audit-mode comparison

Branch: pr-266b-recovery-flag-audit
- Type: feature
- Complexity: medium
- Depends on: PR-263, PR-266a
- Priority: 2
- Coder: claude

## Problem

PR-266a landed `_parse_tasks_from_headers` and the eight golden recovery fixtures without changing any production behavior. This PR introduces the production switch, gated behind a feature flag, with an audit mode that runs both recovery paths in parallel and logs structured diffs so the operator can verify equivalence on real production traffic before retiring the legacy QUEUE.md path.

The audit mode is the safety net that distinguishes this work from the original monolithic PR-266. With audit logs over a 24-48 hour window across two active production repos, any divergence between the new and old paths surfaces in the event log as a `[AUDIT]` entry the operator can review without daemon disruption. Once divergences are zero, the operator flips the flag and PR-266c retires the legacy path.

## Scope

Five deliverables:

1. Two new environment variables read at daemon startup:
   - `PIPELINE_RECOVERY_FROM_HEADERS=0` (default; 0 means use legacy `_parse_base_queue` path).
   - `PIPELINE_RECOVERY_AUDIT=0` (default; 1 enables side-by-side execution and diff logging regardless of the flag above).
2. Refactor `recover_state` to consult both env flags and choose execution mode:
   - audit=0, headers=0: legacy path only (current behavior).
   - audit=1, headers=0: legacy path applies state; new path runs in dry-run, results compared, diffs logged. Default for the audit window.
   - audit=0, headers=1: new path applies state; legacy retired (no execution). Production target after audit clean.
   - audit=1, headers=1: new path applies state, legacy runs in dry-run, diffs logged for one extra cycle of paranoia.
3. New `_recovery_audit_diff` structured logger that compares the two recovery results and emits a `[AUDIT] recover_state divergence:` event when they differ. The diff covers pipeline state, current_task pr_id, current_pr number, pending_queue_sync_branch, and the current_queue list contents (length + per-entry pr_id/status set comparison).
4. Hydrate `state.current_queue` at the end of recover_state when the new path is the active one, so post-restart state matches the snapshot model.
5. Integration tests exercising recover_state against the eight golden fixtures from PR-266a, parameterized over flag combinations.

## Behavior

Mode selection at daemon startup:

```
modes = {
  (audit=0, headers=0): "LEGACY_ONLY",
  (audit=1, headers=0): "AUDIT_LEGACY_APPLIES",
  (audit=0, headers=1): "HEADERS_ONLY",
  (audit=1, headers=1): "AUDIT_HEADERS_APPLIES",
}
```

In `LEGACY_ONLY` mode the recovery handler runs unchanged from pre-PR-266 behavior. The `_parse_tasks_from_headers` helper added in PR-266a is not invoked.

In `AUDIT_LEGACY_APPLIES` mode (the deploy default for this PR) the handler:
1. Runs the legacy `_parse_base_queue` path and uses its result for state mutations (pipeline_state transitions, current_task assignment, etc.).
2. Runs `_parse_tasks_from_headers` against the same input snapshot (open_prs, merged_pr_ids, crashed/recovered sets) but discards its mutations.
3. Calls `_recovery_audit_diff` with both result projections.
4. If diffs found: emit `[AUDIT] recover_state divergence: <structured-diff-summary>` event. Operator reviews logs.

In `HEADERS_ONLY` mode the legacy path is skipped entirely. The new path applies state. `state.current_queue` is hydrated from the headers-derived task list. This is the post-audit production target.

In `AUDIT_HEADERS_APPLIES` mode the new path applies; legacy runs as the dry-run reference. One paranoia cycle before PR-266c removes the legacy path entirely.

The audit-diff logger output schema:

```
{
  "audit": "recover_state",
  "mode": "AUDIT_LEGACY_APPLIES",
  "diff": {
    "pipeline_state": {"legacy": "IDLE", "new": "WATCH"},
    "current_task_pr_id": {"legacy": null, "new": "PR-005"},
    "current_pr_number": {"legacy": null, "new": 142},
    "current_queue_length": {"legacy": 8, "new": 8},
    "current_queue_status_drift": [
      {"pr_id": "PR-005", "legacy_status": "TODO", "new_status": "DONE"}
    ]
  }
}
```

When all fields match, no audit event is emitted (zero log noise on parity).

## Implementation notes

The audit-diff comparator is deliberately structured (dict output, JSON-loggable) rather than free-form prose. Operators viewing `[AUDIT]` events in the dashboard or grep'ing `docker compose logs daemon` should be able to filter on specific divergence types (e.g. `current_queue_status_drift` only). Free-form messages would be unparseable and would balloon log volume.

Mode `AUDIT_LEGACY_APPLIES` is the recommended deploy state for this PR. Operator runs daemon with audit=1 headers=0 for a planned 24-48h window across production repos. During the window, every recovery (daemon restart + cycle-trigger inside long-running daemon) emits zero `[AUDIT]` events on parity, or structured diffs on divergence. After 24-48h of zero events, operator flips audit=0 headers=1 (HEADERS_ONLY). After one or two more daemon restarts confirm clean operation, PR-266c ships and removes the legacy path entirely.

The dry-run side of audit mode does NOT mutate `RepoState`. It runs the discarded helper, captures its return value, and feeds it to `_recovery_audit_diff`. This is critical for safety: a buggy new path must not write to Redis state during the audit window.

The two-flag design (audit and headers as separate booleans) gives operators four distinct operational modes during the rollout, which lets us recover from a bad new-path bug by flipping headers=0 without losing the audit comparison data. Single-flag designs (e.g. enum mode value) require redeploy on flip; two booleans flip via `docker compose restart` only.

The `state.current_queue` hydration in HEADERS_ONLY mode is the moment when PR-263's snapshot model becomes load-bearing for recovery. After this PR ships and the flag flips, post-restart state matches the in-memory snapshot model. Before the flag flip, `state.current_queue` may still be None on first cycle after daemon restart in legacy mode; PR-263's IDLE-cycle populator backfills on the first IDLE tick.

If the audit window surfaces divergences that are NOT bugs but are correct improvements (e.g. the new path correctly identifies a merged task that legacy missed via convention), the operator confirms the improvement is intentional and proceeds. Each `[AUDIT]` event includes enough context for operator-side reasoning without rerunning the recovery.

The env var defaults are intentionally conservative: 0 and 0. Existing deployments inherit `LEGACY_ONLY` automatically and notice no behavior change. The audit window starts when the operator explicitly sets audit=1 in `docker-compose.yml` or via `docker compose run -e PIPELINE_RECOVERY_AUDIT=1 daemon`.

## Success criteria

1. With no env vars set, recover_state behavior is byte-identical to pre-PR-266 (regression-free legacy path).
2. With audit=1 headers=0, both recovery paths execute, legacy applies state, diffs are logged on divergence, no event on parity.
3. With audit=0 headers=1, only new path executes, state mutations match the eight golden fixtures' expected projections.
4. `state.current_queue` is populated at the end of recovery in any mode where the new path is active.
5. Megaraid golden scenario resolves to IDLE when headers=1 (stale DOING ignored via API merged-set).
6. `[AUDIT] recover_state divergence:` events are JSON-structured and grep-friendly.
7. Existing recovery tests green in default mode.
8. CI green on PR branch.
