# PR-313: Fix OBS-AR — `gh api --include` returns exit 1 on HTTP 304 making ETag conditional cache fall through to error path

Branch: pr-313-obs-ar-etag-304-handling
- Type: bugfix
- Complexity: low
- Depends on: none
- Priority: 1
- Coder: codex

## Problem

OBS-AR observed in production 2026-05-04+, persisted through Sprint 15a/15b, and visibly polluted the event log during PR-285 dispatch on 2026-05-08. The event log shows:

```
[FIX] GitHub API poll failed: gh api repos/AlexBomber12/pipeline-orchestrator/pulls/382 --include -H If-None-Match: W/"a513a751abd87d23fd69feb0a63c0c9c7b512a5f09872467aa1c27b7a36a53c5" failed (exit 1): gh: HTTP 304, preserving deadline.
```

Multiple `[FIX] GitHub API poll failed` entries per minute, all carrying `HTTP 304` (Not Modified, the SUCCESS conditional-request response). HTTP 304 is the desired outcome of an If-None-Match conditional read — it confirms the cached payload is current and consumes zero rate-limit budget. It should be silent, not log-spam.

Root cause: `gh` CLI treats **any non-2xx status as an error** and exits with code 1 when given `--include`, including 304 responses. `subprocess.run(...)` returns `returncode=1`, `run_gh` (src/github/gh_runner.py:43-47) raises `RuntimeError("gh ... failed (exit 1): gh: HTTP 304, ...")`. Control returns to `cache._etag_get` (src/github/cache.py:124), the `RuntimeError` propagates up to `gh_prs.get_branch_last_push_time` (src/github/prs.py:537-539) which catches `(RuntimeError, ...)` and re-raises as `GitHubPollError`, which `fix_supervision.py:72-75` catches and logs.

The 304-handling branch at `cache.py:133-141` is unreachable because `run_gh` raises before `_split_include_response` runs. The pre-existing logic that should:
- Read cached payload when status==304 + cached present
- Retry without If-None-Match when status==304 + cached absent

...is dead code as long as `gh api --include` exits non-zero on 304.

Effect today: every IDLE/WATCH/FIX cycle that polls `repos/{owner}/{repo}/pulls/{pr_number}` with a primed ETag cache produces a `[FIX] GitHub API poll failed` event log line. Real operational signals (push events, CI status changes, review activity) get pushed beyond the 100-entry event log cap. Operator visibility on actual daemon behavior degrades.

Fix: detect HTTP 304 from the `RuntimeError` stderr message in `cache._etag_get` BEFORE letting the exception propagate. Map to the existing 304 success path (return cached payload, or retry without If-None-Match when cache is empty).

## Scope

### 1. Modify `cache._etag_get` to handle 304-from-RuntimeError

In `src/github/cache.py:105-155`, wrap the `gh_runner.run_gh` call in a try/except that distinguishes "HTTP 304 success" from "real gh failure":

```python
def _etag_get(path: str) -> object:
    """Fetch a single-resource REST endpoint with ETag conditional caching.
    
    ... (existing docstring preserved) ...
    """
    args: list[str] = ["api", path, "--include"]
    cached = _etag_cache.get(path)
    if cached is not None:
        args.extend(["-H", f"If-None-Match: {cached[0]}"])

    try:
        raw = gh_runner.run_gh(args)
    except RuntimeError as exc:
        # gh CLI exits non-zero on any non-2xx status when --include is set,
        # including HTTP 304 (Not Modified). 304 is the SUCCESS case for
        # conditional reads — surface it to the existing 304 branch below
        # rather than re-raising. Detection: stderr substring match on the
        # canonical "HTTP 304" token gh emits.
        if _is_http_304_error(exc):
            if cached is not None:
                _etag_cache.move_to_end(path)
                return cached[1]
            # 304 with empty cache: edge case (cache eviction or restart).
            # Retry without If-None-Match to force fresh 200 + body.
            return _etag_get_no_cache(path)
        raise

    # When stubbed (tests mock ``run_gh`` to return a pre-parsed object or a
    # bare ``--jq`` scalar), bypass ``--include`` parsing and surface the
    # value directly so existing call-site tests keep their semantics.
    if not isinstance(raw, str) or not raw.lstrip().startswith("HTTP/"):
        return raw

    status, headers, body = _split_include_response(raw)
    # The status==304 branch below is now dead in practice (gh exits non-zero
    # on 304 with --include) but kept as defense in depth in case gh CLI
    # behavior changes in a future version.
    if status == 304:
        if cached is None:
            return _etag_get_no_cache(path)
        _etag_cache.move_to_end(path)
        return cached[1]
    if status is None or not (200 <= status < 300):
        return None
    body = body.strip()
    if not body:
        return None
    try:
        payload = json.loads(body)
    except json.JSONDecodeError:
        return None

    etag = headers.get("etag")
    if etag:
        _etag_cache_put(path, etag, payload)
    return payload
```

### 2. Add `_is_http_304_error` helper

```python
_HTTP_304_PATTERN = re.compile(r"\bHTTP\s+304\b")

def _is_http_304_error(exc: RuntimeError) -> bool:
    """Detect whether a RuntimeError from run_gh represents HTTP 304 success.
    
    gh CLI exits with code 1 on any non-2xx response when ``--include`` is
    passed, with stderr containing the status line. 304 Not Modified is the
    desired outcome of a conditional read (zero rate-limit cost), but the
    non-zero exit makes it indistinguishable from a real failure without
    inspecting the message.
    
    Returns True iff the exception message contains the canonical "HTTP 304"
    token gh emits. Anchored on word boundaries so substrings like "1304" or
    "HTTP 3040" do not falsely match.
    """
    return bool(_HTTP_304_PATTERN.search(str(exc)))
```

Place near top of `src/github/cache.py` next to existing module-level helpers.

### 5. Defense in depth: improve event log filtering for any residual 304 messages

Even after the fix, in case of edge cases (e.g., a future gh CLI version emitting a different message format), add a guard in `src/daemon/fix_supervision.py:73-75` to suppress 304-tagged messages:

```python
except gh_prs.GitHubPollError as exc:
    msg = str(exc)
    if "HTTP 304" not in msg:
        runner.log_event(
            f"[FIX] GitHub API poll failed: {exc}, preserving deadline."
        )
    latest_push_at = None
```

This is a safety net; the primary fix is in cache.py. With the cache.py change, this guard is dormant (poll never sees 304 errors).
