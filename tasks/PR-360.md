## Problem

When a task enters ERROR state and the AI diagnose path runs, `handle_error` at `src/daemon/handlers/error.py:249-252` does:

```python
self._error_diagnose_policy.increment(self)
if await self._error_diagnose_policy.maybe_escalate(self):
    return
```

After `_error_diagnose_count` reaches `max_attempts=4`, `maybe_escalate` returns True AND runs `_on_error_diagnose_threshold` callback which logs `[ERROR] diagnose_error: max attempts (3) reached, staying ERROR.` at `runner.py:508`. The counter is NOT reset.

On every subsequent poll cycle while task stays in ERROR, `handle_error` is dispatched again, counter increments to 5, 6, 7..., `maybe_escalate` still returns True, `on_threshold` runs AGAIN, the same log line is emitted AGAIN. Production observation 2026-05-14: 331 identical log entries over 7 hours on a single parked PR. Operator-visible event log is polluted, real signals get rotated out.

Functional behavior is fine - daemon does correctly stop trying to diagnose. The issue is pure noise pollution that masks real events.

## Solution

After the first threshold log, set a Redis sentinel `diagnose_exhausted:{repo_slug}:{task_id}` with 7-day TTL. Gate `handle_error` entry on absence of sentinel. Clear sentinel on Retry button (existing endpoint at `src/web/routes/repo_control.py:1028`).

### Redis key shape

```
diagnose_exhausted:{repo_slug}:{task_id}
  value: ISO-8601 timestamp of when threshold was first hit
  TTL: 7 days (matches cancellation cause retention)
```

Why 7 days: matches the existing forensic retention window for cancellation_cause entries (PR-252 substrate). After 7 days, sentinel naturally expires; if task somehow re-enters ERROR via a code path that doesn't go through the Retry endpoint, the diagnose attempt will happen once more and then re-set sentinel. That is acceptable degradation.

### Changes

In `src/daemon/runner.py` constructor, around the existing `_error_diagnose_policy` block at line 483-490, no change to the policy itself.

Add a new method on the runner (or in a suitable mixin):

```python
async def _is_diagnose_exhausted(self, task_id: str) -> bool:
    if not task_id:
        return False
    key = f"diagnose_exhausted:{self.name}:{task_id}"
    val = await self.redis.get(key)
    return val is not None

async def _mark_diagnose_exhausted(self, task_id: str) -> None:
    if not task_id:
        return
    key = f"diagnose_exhausted:{self.name}:{task_id}"
    await self.redis.set(
        key,
        datetime.now(timezone.utc).isoformat(),
        ex=7 * 24 * 3600,
    )

async def _clear_diagnose_exhausted(self, task_id: str) -> None:
    if not task_id:
        return
    key = f"diagnose_exhausted:{self.name}:{task_id}"
    await self.redis.delete(key)
```

In `src/daemon/handlers/error.py:handle_error`, near the top of the function (after the existing infra/rate-limit/timeout short-circuit branches, before line 249 increment), add:

```python
current_task = self.state.current_task
task_id = getattr(current_task, "pr_id", "") if current_task else ""
if task_id and await self._is_diagnose_exhausted(task_id):
    return
```

After the existing threshold check at line 250-252, if the threshold callback fired, mark the sentinel:

```python
self._error_diagnose_policy.increment(self)
if await self._error_diagnose_policy.maybe_escalate(self):
    if task_id:
        await self._mark_diagnose_exhausted(task_id)
    return
```

In `src/web/routes/repo_control.py` Retry endpoint (around line 1028 where ERROR task gets cleared), add a call to clear the sentinel:

```python
await runner._clear_diagnose_exhausted(task_id)
```

Place it adjacent to the existing `DELETE cancellation:{repo}:{task_id}` step so retry semantics are consistent.

Also clear the sentinel on natural ERROR exit from `_clear_error_message_on_recovery` (the helper used when soft-skip retry succeeds) - search for callsites in `src/daemon/handlers/error.py` and inject one call there too. This handles the path where the operator never clicks Retry but the daemon recovers naturally (rare but possible).

## Threat model

**Threat addressed**: log noise pollution from repeated `[ERROR] diagnose_error: max attempts (3) reached` entries on parked ERROR tasks. Real operational signals get pushed out of the 100-entry event log history cap within minutes.

**Other layers protecting**: none. This is the only place where the log spam originates.

**Why this layer needed**: cleanliness of operator-visible event log is a load-bearing diagnostic surface. When it fills with the same line every minute, operators miss real events.

### Caller audit

`_error_diagnose_policy.maybe_escalate` is called only from `handle_error` at error.py:250. No other callsite needs the sentinel gate.

`_error_diagnose_count` resets happen in 3 places: `error.py:243` (rate-limit soft-skip path), `error.py:445` (successful recovery from diagnose path), `runner.py:361` (constructor init). Sentinel is independent of counter resets - sentinel persists through counter reset because the SAME task is still parked. Only Retry button (explicit operator intent) or 7-day TTL clears it.

`_clear_diagnose_exhausted` callsites: Retry endpoint + `_clear_error_message_on_recovery` (defensive natural-recovery path). If a future fix adds a third recovery path, that fix must also call the sentinel-clearer; document this as a contract in the helper method docstring.

## Out of scope

- Changing `max_attempts` default (currently 4, mapped semantically to "3 retries after first attempt"). The bug is the post-threshold loop, not the threshold value.
- Removing `_on_error_diagnose_threshold` callback. Keep the first-occurrence log because that IS a useful signal ("daemon gave up on this one"). Only suppress repeats.
- Migrating to a different counter substrate (e.g. moving counter into Redis). The counter is per-runner-process; if daemon restarts, sentinel persists in Redis while counter resets to 0 - that is the correct behavior because a daemon restart should not retry on already-exhausted tasks.

## Success signal

On test fixture: task fixture in ERROR, AI diagnose path eligible. Daemon runs handle_error 10 times in a row. First 3 calls produce normal "diagnose attempt N/4" event entries. 4th call produces the threshold log entry "max attempts (3) reached" AND sets the Redis sentinel. Calls 5-10 produce NO new log entries; handle_error returns early at the sentinel gate. Sentinel key visible via `redis-cli KEYS "diagnose_exhausted:*"` on production after deploy when first stuck ERROR task hits the threshold.
