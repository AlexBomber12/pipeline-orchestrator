# PR-280: Recovery reads frontmatter status ERROR on startup, derive_task_status simplifies, parser drops legacy tokens

Branch: pr-280-recovery-reads-frontmatter-status
- Type: refactor
- Complexity: medium
- Depends on: PR-279
- Priority: 1
- Coder: codex

## Problem

PR-279 added the write side: daemon writes `status: ERROR` (uppercase) to task file frontmatter on final failure and `status: DONE` on merge. This PR adds the read side so persistence is meaningful, simplifies `derive_task_status` mapping, and removes the legacy 6 lowercase tokens from `_FRONTMATTER_STATUS_VALUES`.

Two scenarios where read matters:

1. **Redis-flush recovery.** After Redis is wiped, daemon recovery scans `tasks/PR-*.md` to rebuild state. Without frontmatter read, daemon would see status absent (default TODO), pick up the previously failed task, dispatch coder again, hit the same failure. Reading `status: ERROR` from frontmatter prevents the loop.

2. **derive_task_status simplification.** Currently `src/task_status.py:78-85` maps 6 legacy lowercase values to 4 TaskStatus enum values. Phase 2 finalizes 3 canonical values (TODO/DONE/ERROR uppercase, parser-normalized to lowercase internally). Mapping reduces to 3 entries.

After this PR, `_FRONTMATTER_STATUS_VALUES` set contains only `{"todo", "done", "error"}` (lowercase tokens, since parser normalizes input case). Pre-Phase-2 MICRO had added these alongside the 6 legacy tokens. PR-280 removes the legacy tokens because no task file uses them in production (verified by grep) and post-Phase-2 daemon never emits them.

## Scope

1. **Update derive_task_status mapping** at `src/task_status.py:78-85`:
   - `frontmatter_status == "done"` → `TaskStatus.DONE`
   - `frontmatter_status == "error"` → `TaskStatus.ERROR`
   - `frontmatter_status == "todo"` → `TaskStatus.TODO`
   - No frontmatter present → fall through to existing git/PR-state derivation
   - Any other value → fall through (treated as missing frontmatter)
   - Legacy 6 values are no longer recognized after PR-280; parser will reject them outright per scope item 4 below.

2. **Recovery reads frontmatter** at startup. In `src/daemon/recovery.py` `recover_state` method, before existing `_parse_tasks_from_headers` logic, additionally check each task header's `frontmatter_status` field. If `frontmatter_status == "error"`, mark the task in `_crashed_task_pr_ids` set so the next IDLE picker excludes it from dispatch (existing protection at recovery.py:371-380 already handles `_crashed_task_pr_ids` for "do not redispatch" semantics). This preserves "ERROR means do not retry" contract across Redis flush.

3. **Rename TaskStatus.CANCELED to TaskStatus.ERROR**. Full enum value change at `src/models.py:24`. Old `CANCELED = "CANCELED"` becomes `ERROR = "ERROR"`. All callsite references update from `TaskStatus.CANCELED` to `TaskStatus.ERROR`. JSON serialization changes from `"CANCELED"` to `"ERROR"` — Redis migration of any existing run_records or cancellation entries with `"CANCELED"` value handled by the migration script in PR-278 (extend that script to also rewrite `"CANCELED"` → `"ERROR"` in any RepoState JSON, OR a new tiny migration if PR-278 has already shipped — operator decides at deploy time).

4. **Remove legacy tokens from `_FRONTMATTER_STATUS_VALUES`** at `src/queue_parser.py:35`. Final set: `{"todo", "done", "error"}`. Three lowercase tokens. Parser case-insensitive normalization preserved (operator can write `status: TODO` or `status: todo` in file, both accepted). Legacy 6 tokens (queued/in_progress/in_review/merged/blocked/canceled) deleted from set. Pre-Phase-2 MICRO had them transiently for one-cycle compat; this PR completes the cleanup.

5. **Update parser error message** at line ~345 to reflect new 3-value set in the rejection text.
