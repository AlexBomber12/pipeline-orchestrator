# PR-292: Operator override backend — guardrail decision state machine and API for approve or reject

Branch: pr-292-operator-override-backend
- Type: feature
- Complexity: medium
- Depends on: PR-291
- Priority: 1
- Coder: codex

## Problem

Tier 2 guardrails (PR-288 large-diff, PR-289 secrets, PR-290 mass-deletion, PR-291 governance) all ESCALATE flagged PRs to HUNG state with `cancellation_cause` records like `GUARDRAIL: large_diff_threshold: +1800 LOC across 35 files`. Without an override mechanism, every flagged PR stays HUNG until operator either:

1. Manually merges externally via GitHub UI (bypasses daemon awareness).
2. Closes the PR and reopens (loses CI history).
3. Clicks the existing operator-recovery button (treats the PR as canceled, wasting the work).

None of these are right when the operator has reviewed the diff and decided the violation is **acceptable for this specific PR**. Example: legitimate dependency upgrade triggers `large_diff_threshold` because the lockfile exemption did not catch the package manager. Operator wants to say "this one's fine, proceed to merge" without canceling the work.

The `_check_operator_recovery_signal` infrastructure (PR-247, hung.py:251) already implements the atomic Redis GETDEL pattern for one-shot signals from web to daemon. PR-292 generalizes this from a single-decision (recover-or-stay-HUNG) to a three-way decision (approve / reject / pending) per (repo, pr_id) keyed on guardrail-specific state.

## Scope

Three deliverables:

### 1. New Redis keys for guardrail decisions

Two new keys in `src/keyspace.py` (or wherever existing `control_*` helpers live):

```python
def control_guardrail_decision(repo: str, pr_id: str) -> str:
    """Per-(repo, pr_id) guardrail decision key. Value: 'approve' or 'reject'."""
    return f"control:{repo}:guardrail_decision:{pr_id}"

def control_guardrail_pending(repo: str) -> str:
    """Set of pr_ids currently in pending-decision state for this repo."""
    return f"control:{repo}:guardrail_pending"
```

The `control_guardrail_pending` is a Redis SET; the daemon adds pr_id to it on ESCALATE-with-GUARDRAIL-cause and the dashboard reads it to enumerate flagged PRs without scanning all task files. Removed when decision is recorded.

### 2. Daemon: handle_hung extension for guardrail decisions

In `src/daemon/handlers/hung.py:handle_hung` near the existing operator-recovery check at line 320, add a guardrail-decision check:

```python
async def _check_guardrail_decision(self) -> str | None:
    """Atomically read-and-clear per-PR guardrail decision.
    
    Returns 'approve', 'reject', or None when no decision recorded.
    """
    if self.state.current_pr is None or self.state.current_task is None:
        return None
    pr_id = self.state.current_task.pr_id
    key = control_guardrail_decision(self.name, pr_id)
    try:
        raw = await self.redis.getdel(key)
    except Exception:
        return None
    if raw is None:
        return None
    decision = raw.decode("utf-8") if isinstance(raw, bytes) else str(raw)
    return decision if decision in ("approve", "reject") else None

async def _perform_guardrail_approve(self) -> None:
    """Apply operator approval: clear cancellation cause, exit HUNG to WATCH.
    
    The PR resumes the normal flow: WATCH polls for merge readiness,
    proceeds to MERGE when CI green and review approved. The guardrail
    violation is preserved in the audit log (event_log) but no longer
    blocks progress.
    """
    pr_id = self.state.current_task.pr_id
    self.log_event(
        f"[GUARDRAIL] Operator approved override for PR #"
        f"{self.state.current_pr.number} ({pr_id}); resuming -> WATCH."
    )
    # Remove from pending set
    await self._remove_from_guardrail_pending(pr_id)
    # Clear the cancellation cause so dashboard does not keep showing it
    await safe_delete_cancellation_cause(
        self.redis, self.name, pr_id
    )
    # Resume to WATCH; the existing watch flow handles merge readiness
    self.state.error_message = None
    self.state.state = PipelineState.WATCH
    await self.publish_state()

async def _perform_guardrail_reject(self) -> None:
    """Apply operator rejection: same as operator-recovery flow.
    
    Treats the PR as canceled. The coder's work is not merged; operator
    gets a clean slate and can re-upload a corrected task spec.
    """
    pr_id = self.state.current_task.pr_id
    self.log_event(
        f"[GUARDRAIL] Operator rejected override for PR #"
        f"{self.state.current_pr.number} ({pr_id}); canceling -> IDLE."
    )
    await self._remove_from_guardrail_pending(pr_id)
    # Reuse existing operator-recovery path (already cancels current_task)
    await self._perform_operator_recovery()

async def _remove_from_guardrail_pending(self, pr_id: str) -> None:
    """Best-effort removal from pending set; failures are non-fatal."""
    try:
        await self.redis.srem(
            control_guardrail_pending(self.name), pr_id
        )
    except Exception as exc:
        self.log_event(
            f"[GUARDRAIL] pending set cleanup failed: {exc}"
        )
```

Insert at handle_hung entry, before existing `_check_operator_recovery_signal`:

```python
async def handle_hung(self) -> None:
    decision = await self._check_guardrail_decision()
    if decision == "approve":
        await self._perform_guardrail_approve()
        return
    if decision == "reject":
        await self._perform_guardrail_reject()
        return
    if await self._check_operator_recovery_signal():
        await self._perform_operator_recovery()
        return
```

### 3. Daemon: ESCALATE side adds pr_id to pending set

When daemon ESCALATEs with a GUARDRAIL cause (called from coding.py post-coder, fix.py post-coder, watch.py post-PR-diff-scan via `_transition_to_error` with cause prefix `GUARDRAIL:`), the pr_id should be added to the pending set so dashboard knows to surface it.

The cleanest hook is in `_transition_to_error` at runner.py — when the cause string starts with `"GUARDRAIL:"`, add to set. This avoids adding the call to every guardrail call site:

```python
# In runner.py:_transition_to_error, after existing telemetry code:
if message.startswith("GUARDRAIL:") and self.state.current_task is not None:
    pr_id = self.state.current_task.pr_id
    try:
        await self.redis.sadd(
            control_guardrail_pending(self.name), pr_id
        )
    except Exception as exc:
        # Non-fatal; the dashboard can still discover via cancellation
        # cause records, just less efficiently
        self.log_event(
            f"[GUARDRAIL] pending set add failed: {exc}"
        )
```

### 4. Web API: POST /repos/{name}/guardrail/{pr_id}/decision

New endpoint in `src/web/routes/repo_control.py` mirroring the existing `/recover` endpoint pattern at line 373+. Payload accepts `decision` field with value `approve` or `reject`. Atomic Redis WATCH/MULTI transaction on `pipeline:{name}` to verify HUNG state before writing the decision key.

```python
@router.post("/repos/{name}/guardrail/{pr_id}/decision")
async def repo_guardrail_decision(
    request: Request,
    name: str,
    pr_id: str,
    decision: str = Form(...),
) -> Response:
    """Record operator decision on a guardrail-flagged PR."""
    if decision not in ("approve", "reject"):
        return HTMLResponse(
            "Invalid decision; must be 'approve' or 'reject'",
            status_code=400,
        )
    # Verify pr_id matches the canonical PR-NNN[a-z]? form to prevent
    # path injection into Redis keys
    if not re.match(r"^PR-\d{1,4}[a-z]?$", pr_id):
        return HTMLResponse("Invalid pr_id format", status_code=400)
    try:
        redis_client, state_key, repo_url = await _apply_repo_control_update(
            request, name
        )
    except _RepoStateMutationError as exc:
        return HTMLResponse(exc.message, status_code=exc.status_code)
    
    decision_key = control_guardrail_decision(name, pr_id)
    
    async def _transaction(pipe: Any) -> None:
        raw = await pipe.get(state_key)
        if raw is None:
            raise _RepoStateMutationError("Repository state unavailable", 404)
        state = RepoState.model_validate_json(raw)
        if state.state != PipelineState.HUNG:
            raise _DecisionNotHung(state.state.value)
        # Verify the current_task matches the pr_id under decision
        if (
            state.current_task is None
            or state.current_task.pr_id != pr_id
        ):
            raise _DecisionPrMismatch(
                state.current_task.pr_id if state.current_task else "no task"
            )
        pipe.multi()
        pipe.set(decision_key, decision, ex=300)
    
    try:
        await redis_client.transaction(_transaction, state_key)
    except _DecisionNotHung as exc:
        return HTMLResponse(
            f"Decision only allowed from HUNG state (current: {exc.state})",
            status_code=400,
        )
    except _DecisionPrMismatch as exc:
        return HTMLResponse(
            f"PR mismatch: current_task is {exc.current_pr_id}",
            status_code=400,
        )
    except WatchError:
        return HTMLResponse(
            "Concurrent state change; retry",
            status_code=409,
        )
    
    # Wake daemon so handle_hung consumes the decision quickly
    await wake_daemon_for_repo(redis_client, name)
    
    return HTMLResponse("", status_code=204)
```

### 5. Web API: GET /repos/{name}/guardrail/pending

New endpoint that returns the list of pr_ids currently in pending-decision state. Used by the dashboard panel (PR-293) to enumerate flagged PRs without re-scanning state.

```python
@router.get("/repos/{name}/guardrail/pending")
async def repo_guardrail_pending(
    request: Request, name: str,
) -> Response:
    """Return JSON list of pr_ids in pending guardrail decision."""
    redis_client = _get_redis_client(request)
    try:
        pending_ids = await redis_client.smembers(
            control_guardrail_pending(name)
        )
    except Exception:
        return JSONResponse({"pending": []}, status_code=200)
    decoded = [
        pid.decode("utf-8") if isinstance(pid, bytes) else pid
        for pid in pending_ids
    ]
    return JSONResponse({"pending": sorted(decoded)})
```

## Implementation notes

The atomic GETDEL pattern from `_check_operator_recovery_signal` is the design template — single Redis round-trip read-and-clear ensures the daemon never observes a decision whose clearing failed. Same shape extends to per-PR decision keys.

The pending set is **eventually consistent**. If the daemon adds to it but a Redis hiccup causes the entry to disappear, the dashboard might miss the flagged PR but the cancellation cause record still exists; operator can find the PR through the cancellation history view (existing surface). So pending set is a **performance optimization** for dashboard enumeration, not the source of truth. Defensive: if dashboard SET membership lookup fails, fall back to scanning cancellation causes.

The 300s TTL on decision keys handles the rare case where operator clicks approve/reject but daemon crashes before consuming. A 300s window gives the daemon time to restart and process. After expiry, the decision is lost; operator must re-click. Acceptable interim — alternative (no TTL) could leave stale decision keys influencing future HUNG cycles unrelated to the original click.

The `_DecisionPrMismatch` guard ensures the operator's click on the dashboard panel (PR-293) corresponds to the actual PR currently in HUNG. Without this guard, a dashboard rendered with stale state could submit a decision for a PR that already moved on.
