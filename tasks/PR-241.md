# PR-241: Add lightweight /api/alerts endpoint, swap checkAlerts off /api/states

Branch: pr-241-alerts-endpoint
- Type: feature
- Complexity: medium
- Depends on: PR-240
- Priority: 2
- Coder: claude

## Problem

PR-238 stops frontend setInterval leaks; PR-240 makes `/api/states` itself faster (async config load + parallel Redis reads). At 3 repos with PR-240 fixes, response times drop to sub-second. But `/api/states` still returns the FULL repo state JSON for every alert-check call, which is wasteful: `checkAlerts` only needs to know "is there at least one alert across all repos" (a single boolean). Returning ~5KB of state JSON per repo to compute one bool is ~10x overhead at the 5-repo mark, ~20x at 10 repos.

This PR adds a dedicated `/api/alerts` endpoint that returns a minimal payload `{has_alerts: bool, count: int}` and switches the frontend `checkAlerts` to consume it. Result: alert-check polling becomes a fixed-cost request regardless of repo count, and `/api/states` is reserved for the full-state use cases (initial dashboard render, manual refresh) where the heavier payload is justified.

This is OBS-AY Fix B.2. With B.1 + B.2 shipped, the dashboard scales cleanly to 10+ repos without any single endpoint becoming a bottleneck.

## Scope

Three deliverables:

1. New `/api/alerts` GET endpoint in `src/web/routes/dashboard.py` that returns `{"has_alerts": bool, "count": int}` JSON. Logic: scan repo states (reuse the same Redis-backed lookup as `/api/states`), count those in alert states (HUNG, ERROR, ESCALATED if defined, or whatever the existing alert criterion is). Return summary only.

2. Frontend swap in `src/web/templates/base.html`: `checkAlerts` calls `/api/alerts` instead of `/api/states`. Existing alert-display logic in `checkAlerts` only reads a boolean, so the new payload is sufficient.

3. Tests covering both endpoints stay independent: `/api/states` unchanged, `/api/alerts` covered by new tests.

## Files to modify

`src/web/routes/dashboard.py` — add a new route. Find an existing dashboard route (e.g. `@router.get("/api/states")`) for placement reference. Add nearby:

```
@router.get("/api/alerts")
async def api_alerts(request: Request) -> dict:
    """Return alert summary across all repos.

    Lightweight alternative to /api/states for the frontend's
    checkAlerts polling loop. Returns a minimal payload sized
    independently of the repo count so the dashboard scales cleanly
    to 10+ repos without per-poll cost growing super-linearly.
    PR-241.
    """
    redis_client = getattr(request.app.state, "redis", None)
    states, _redis_warning = await _app.get_all_repo_states(redis_client)

    alert_states = {"HUNG", "ERROR", "ESCALATED"}
    alerts = [s for s in states if str(s.state).upper() in alert_states]

    return {
        "has_alerts": len(alerts) > 0,
        "count": len(alerts),
    }
```

The exact set of "alert states" depends on what the existing frontend `checkAlerts` considers an alert. If the frontend currently treats only `HUNG` as alert-worthy, narrow this set accordingly. Verify by reading `checkAlerts` body in base.html and matching the criteria.

If the alert criterion is more nuanced (e.g., HUNG with `is_escalated=True`, or stale WATCH past timeout threshold), replicate that exact logic in `api_alerts` so the two endpoints agree on what an alert means. Mismatch would create UX confusion (alert badge shows but dashboard does not, or vice versa).

```
async function checkAlerts() {
    try {
        const response = await fetch('/api/alerts');
        const data = await response.json();
        // data is now { has_alerts: bool, count: int }
        const indicator = document.getElementById('alert-indicator');
        if (indicator) {

                indicator.classList.remove('hidden');

        }
```

```
"""Tests for /api/alerts lightweight endpoint - PR-241."""

from __future__ import annotations

import pytest
from fastapi.testclient import TestClient


@pytest.fixture
def client_with_states(monkeypatch):
    """Fixture providing a TestClient with patched repo states."""
    from src.web import app

    fake_states = []

    async def fake_get_states(_redis):
        return fake_states, None

    monkeypatch.setattr(app, "get_all_repo_states", fake_get_states)
    return TestClient(app.app), fake_states


def test_alerts_endpoint_returns_zero_when_no_alerts(client_with_states):
    client, states = client_with_states
    states[:] = [_make_state("IDLE"), _make_state("WATCH")]

    resp = client.get("/api/alerts")
    assert resp.status_code == 200
    payload = resp.json()
    assert payload == {"has_alerts": False, "count": 0}


def test_alerts_endpoint_counts_hung_states(client_with_states):
    client, states = client_with_states
    states[:] = [
        _make_state("IDLE"),
        _make_state("HUNG"),
        _make_state("ERROR"),
        _make_state("WATCH"),
    ]

    resp = client.get("/api/alerts")
    assert resp.json() == {"has_alerts": True, "count": 2}


def test_alerts_endpoint_payload_size_independent_of_repo_count(
    client_with_states,
):
    """PR-241 design intent: payload size does not grow with repo count."""
    import json

    client, states = client_with_states
    for n_repos in (1, 10, 50):
        states[:] = [_make_state("IDLE")] * n_repos
        resp = client.get("/api/alerts")
        assert len(json.dumps(resp.json())) < 100  # Tiny constant payload.


def _make_state(state_str):
    """Build a minimal RepoState mock for endpoint tests."""
    from unittest.mock import MagicMock

    s = MagicMock()
    s.state = state_str
    return s
```

## Implementation notes

The endpoint reuses `get_all_repo_states` rather than reimplementing repo enumeration. Cost: one Redis ping + one config load + N parallel Redis reads per call (per PR-240 optimizations). With sub-second response time at 5+ repos, this is acceptable for a 10-second poll interval.

If even this cost is too high at very large repo counts (50+), a future optimization is a 5-second TTL cache on the `/api/alerts` response. Out of scope for v1; defer until measurements show it matters.

After this PR ships, full UX flow validation:
1. Open dashboard, confirm `/api/alerts` is what `checkAlerts` polls (Network tab).
2. Trigger an alert state (e.g., manually set a repo to HUNG via dashboard control or simulated state).
3. Within 10 seconds, alert indicator appears.
4. Resolve the alert (clear HUNG); within 10 seconds, indicator disappears.
5. Multi-repo navigation no longer freezes the dashboard.
