## Problem

Dashboard shows sandbox badge as binary on/off based on config flag. If `coder_filesystem_isolation: true` but `bwrap` binary missing, badge shows "enabled" while runtime falls back to no-sandbox (or fails to start, depending on current behavior). UI lies to operator.

## Solution

Replace 2-state badge with 3-state:

- `disabled` - config says off, no runtime check needed.
- `active` - config says on AND bwrap binary present AND last sandbox smoke test passed.
- `unavailable` - config says on BUT bwrap missing OR smoke test failed.

Runtime smoke test runs at daemon startup and every config reload: `bwrap --version` + minimal `bwrap --bind / / --dev-bind /dev /dev /bin/true`. Result cached in Redis `sandbox_state` key.

### Sandbox runtime check module

```python
"""Runtime detection of bubblewrap sandbox availability.

Three-state outcome:
- disabled: config flag is off
- active: config on AND bwrap binary present AND smoke test passed
- unavailable: config on but binary missing or smoke test failed
"""

from __future__ import annotations

import asyncio
import shutil
from enum import Enum
from typing import Optional


class SandboxState(str, Enum):
    DISABLED = "disabled"
    ACTIVE = "active"
    UNAVAILABLE = "unavailable"


async def detect_sandbox_state(coder_filesystem_isolation: bool) -> SandboxState:
    if not coder_filesystem_isolation:
        return SandboxState.DISABLED
    if shutil.which("bwrap") is None:
        return SandboxState.UNAVAILABLE
    try:
        proc = await asyncio.create_subprocess_exec(
            "bwrap",
            "--bind", "/", "/",
            "--dev-bind", "/dev", "/dev",
            "/bin/true",
            stdout=asyncio.subprocess.PIPE,
            stderr=asyncio.subprocess.PIPE,
        )
        await asyncio.wait_for(proc.wait(), timeout=5.0)
        if proc.returncode != 0:
            return SandboxState.UNAVAILABLE
    except (asyncio.TimeoutError, OSError):
        return SandboxState.UNAVAILABLE
    return SandboxState.ACTIVE
```

### Daemon startup hook

In `src/daemon/main.py` init:

```python
sandbox_state = await detect_sandbox_state(cfg.daemon.coder_filesystem_isolation)
await redis_client.set("daemon:sandbox_state", sandbox_state.value)
if sandbox_state == SandboxState.UNAVAILABLE and cfg.daemon.coder_filesystem_isolation:
    logger.warning(
        "Sandbox enabled in config but bubblewrap unavailable. "
        "Coders will run WITHOUT sandbox. Install bwrap or set "
        "coder_filesystem_isolation=false to suppress this warning."
    )
```

Re-run on inotify config reload (PR-342).

## Test acceptance criteria

- `test_detect_disabled_when_config_off`: config flag False, assert DISABLED regardless of bwrap presence.
- `test_detect_unavailable_when_bwrap_missing`: monkey-patch shutil.which to return None, assert UNAVAILABLE.
- `test_detect_active_when_bwrap_present_and_smoke_passes`: shutil.which returns path, subprocess mock returncode=0, assert ACTIVE.
- `test_detect_unavailable_when_smoke_test_fails`: subprocess mock returncode=1, assert UNAVAILABLE.
- `test_detect_unavailable_when_smoke_test_times_out`: subprocess mock hangs, assert UNAVAILABLE within 6 seconds.
- `test_redis_state_written_on_startup`: end-to-end daemon init, assert "daemon:sandbox_state" key set.
- `test_redis_state_refreshed_on_config_reload`: change config flag, trigger reload, assert state updated.
- `test_dashboard_renders_unavailable_badge_when_state_is_unavailable`: assert correct CSS classes.
- `test_dashboard_renders_active_badge_when_state_is_active`: assert correct CSS classes.
- `test_warning_logged_when_enabled_but_unavailable`: capture logs, assert WARNING line includes installation guidance.

## Threat model

**Threat addressed**: UI mismatch with runtime. Operator believes sandbox active when binary missing.

**Other layers protecting**: log warning at startup. Settings page (PR-344c) renders same badge inline with sandbox toggle.

**Why this layer needed**: trust. Sandbox is a defense-in-depth claim; if UI says "active" while reality is "no sandbox", operator decisions are based on false premise.

### Caller audit

`detect_sandbox_state` is called from daemon main on startup + config watcher on reload. Redis key `daemon:sandbox_state` consumed by dashboard template context. No other consumers expected; verify via grep that nothing else writes the key (collision risk).

bwrap smoke test: subprocess execution at startup adds ~100-200ms boot time. Acceptable. Production daemon restarts are infrequent.

Race condition: if config reload changes flag mid-CODING-cycle, current coder's sandbox state is what it was at dispatch time. Detection refresh doesn't retroactively affect running coders. Document.

## Out of scope

- Per-coder sandbox config (claude in sandbox, codex without) - out of scope; daemon-wide flag.
- Sandbox escape detection / monitoring - out of scope.
- Fallback policy when UNAVAILABLE (refuse to dispatch vs dispatch without sandbox) - out of scope; current behavior preserved.

## Success signal

On production AI-Server with bwrap installed and config flag True: dashboard shows "sandbox: active" (green). Uninstall bwrap, reload daemon (or trigger config reload): badge transitions to "sandbox: unavailable" (red). Warning logged in daemon stdout.
