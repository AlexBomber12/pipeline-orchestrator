## Problem

The current upload route processes each task file independently:

1. For each file in the uploaded zip:
   - Validate frontmatter via queue_parser.
   - If valid: extract to tasks/, stage, commit.
   - If invalid: log error, skip.

When a batch contains both valid and invalid files, the valid ones reach disk and the invalid ones do not. This breaks dependency chains: if PR-001 is valid and PR-002 depends on PR-001 but PR-002 is invalid due to a `Complexity: small` typo, PR-001 lands and the daemon dispatches it immediately. PR-002 (the missing dep) gets fixed and re-uploaded later, but by then PR-001 may have already merged and the operator has lost the chance to ship them as a coordinated batch.

Worse: when invalid files declare missing dependencies (e.g. PR-002 depends on PR-003 which was also rejected), the rejected files become invisible to the dashboard while the orphaned dependents loiter in queue with confusing "Blocked by" badges.

Production observation 2026-05-01: operator uploaded 7 specs, one (PR-001) had `Complexity: small` not in canonical set, two more had cascading frontmatter errors. PR-001 was rejected, the other 6 valid files landed and triggered an unintended dispatch chain.

## Solution

Switch the upload route to atomic semantics: ALL files in the batch validate successfully OR NONE commit to disk. Validation errors are reported in aggregate, the operator fixes them all, and re-uploads.

### Two-phase commit pattern

Phase 1 (validate all):
1. Extract zip to temporary directory `/tmp/upload-{uuid}/`.
2. For each file, run full validation (frontmatter parse, dependency graph closure check, anti-pattern scan).
3. Collect all validation errors into a list.
4. If error list is non-empty: respond with structured error report, clean up temp dir, do NOT touch tasks/.

Phase 2 (commit all):
1. If validation passed: for each file, apply `preserve_terminal_status_on_collision` (PR-337 helper) and write to tasks/.
2. Stage all files in one git operation.
3. Commit with message including operator-supplied subject or default "Daemon upload: N tasks".
4. Push.
5. Clean up temp dir.
6. Respond with success summary listing all files.

### Validation aggregation

The response on validation failure should be operator-friendly. Group errors by category:

```json
{
  "status": "validation_failed",
  "files_in_batch": 7,
  "files_with_errors": 3,
  "errors": [
    {
      "file": "PR-001.md",
      "errors": [
        "Complexity 'small' is not in canonical set {low, medium, high}. Did you mean 'low'?"
      ]
    },
    {
      "file": "PR-002.md",
      "errors": [
        "Depends on PR-003 which is not in this upload and not in tasks/."
      ]
    },
    {
      "file": "PR-003.md",
      "errors": [
        "Type 'infrastructure' is not a valid type. Valid types: bugfix, feature, refactor, config, docs, architecture, ux."
      ]
    }
  ],
  "commit": null
}
```

The dashboard upload form already shows error messages via `upload_error.html` template; extend it to render the list of per-file errors.

### Dependency closure check

A new validation rule (part of Phase 1): every `depends_on` entry must reference either:
- A PR already in the existing tasks/ directory.
- A PR already merged on GitHub (via existing `merged_pr_ids` set from picker).
- Another PR being uploaded in this same batch.

If a depends_on entry references nothing in any of these three sources, the upload is invalid.

This closure check prevents the "orphaned dependent" pattern where operator uploads PR-N depending on a PR-N-1 they thought was already in queue but had been removed.

### Symlink-safe temp extraction

Use `zipfile.ZipFile.extractall` with explicit `members=` filter to reject any file containing `..` or absolute paths. Reject zips with non-`.md` files (current behavior, preserved).

### Existing tasks/ files

Files already on disk that are NOT in the upload zip are untouched. Atomic validation does NOT mean "delete everything not in the upload". The atomicity is per-upload-batch only.

### Commit message

Default commit message: `tasks: upload batch ({N} files)`. If operator supplies a subject via form field, use that. Body lists files committed in alphabetical order.

## Threat model

**Threat addressed**: partial upload leaves the queue in an inconsistent state - some valid files dispatched, dependents blocked invisibly, operator unaware until daemon picks an orphan task and HUNGs.

**Other layers protecting**: per-file validation already rejects malformed frontmatter. This PR adds atomicity so that ANY rejection short-circuits the whole batch.

**Why this layer needed**: spec authoring is iterative; operator often uploads a batch, fixes errors, re-uploads. Atomic semantics make the iteration loop coherent: each upload either fully lands or fully rejects, no half-states.

### Caller audit

The upload route is called only from the dashboard form. No programmatic upload callers in src/. CI/CD does not upload via this path; CI/CD commits directly to tasks/ via git operations.

`preserve_terminal_status_on_collision` (PR-337) is called per-file inside the commit phase. Pre-existing semantics unchanged; only the surrounding control flow changes.

`repo_ops.py` staging helper needs minor refactor to accept a list of pre-validated files; existing single-file call sites elsewhere in the codebase (if any) preserved.

## Out of scope

- Allowing operator to override the atomicity ("partial upload OK"). The atomicity is the point; an override defeats the safety property.
- Diff-based dependency closure ("operator wants to delete PR-999 in this upload"). Out of scope; deletions of existing tasks happen through different operator actions, not upload.
- Streaming upload feedback (progress bar). Current upload is fast enough that batch processing in a single request is acceptable.
- ZIP-in-ZIP or nested archive support. Reject as malformed.

## Success signal

On test fixture: upload zip with 1 invalid spec out of 5; response is validation_failed with 1 error entry, tasks/ unchanged. Re-upload same zip with the 1 spec fixed; response is success, all 5 files commit in one git operation. On production: next time operator uploads a batch with a frontmatter typo, the rejection is visible immediately, no orphans land, fix-and-re-upload loop is clean.
