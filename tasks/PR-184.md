# PR-184: Adaptive IDLE polling

Branch: pr-184-adaptive-idle-polling
- Type: feature
- Complexity: low
- Depends on: PR-183
- Priority: 2
- Coder: any

## Problem

Continuing the GraphQL diet from OBS-AC. Currently `poll_interval_sec` is fixed at 60 across all states. During long IDLE periods (no work to do, no PRs to monitor) this still costs ~60-180 GraphQL points per cycle through `_get_codex_review_signals` and friends. Multiplied by 60 cycles per hour that is meaningful burn for zero useful work.

The fix is state-aware adaptive polling: when daemon has been IDLE without PRs for several consecutive cycles, slow polling to a longer interval. Resume normal polling immediately on either (a) Redis pub/sub wake event from PR-183, or (b) a state transition out of IDLE.

This depends on PR-183 because without immediate-wake on upload, slowing IDLE polling to 300s would make new uploads feel broken (300s wait between upload and pickup).

## Scope

Track consecutive IDLE cycles in the daemon runner. After 3 consecutive IDLE cycles without an open PR and without any pending upload, switch to a slower poll interval. Reset to normal on state change or wake event.

This is purely a polling rate adjustment. Daemon behavior in IDLE state is unchanged otherwise.

## Files to modify

`src/daemon/runner.py`:
- Add instance attribute `_idle_streak: int = 0`.
- In the IDLE handler entry path, increment `_idle_streak` if state was already IDLE, reset to 0 on transition into IDLE from another state.
- Add a property or method `effective_idle_poll_interval` that returns the configured `poll_interval_sec` for streak < 3, and a longer interval (configurable, default 300s) for streak >= 3.
- Wire this into the existing rate-limit slowdown multiplier path (around `_enter_github_api_slowdown`) so behavior stacks correctly.

`src/daemon/main.py`:
- Use `effective_idle_poll_interval` instead of static `poll_interval_sec` when computing the next sleep duration for an IDLE repo.
- On Redis wake event from PR-183, reset `_idle_streak` to 0 for that repo (so next cycle uses fast polling).

`src/config.py` and `config.yml`:
- Add new field `daemon.idle_extended_poll_interval_sec: int = 300`.
- Add new field `daemon.idle_extended_after_cycles: int = 3`.

`tests/test_runner.py`:
- Test: 1st, 2nd IDLE cycle uses base interval.
- Test: 3rd+ consecutive IDLE cycle uses extended interval.
- Test: state transition out of IDLE resets streak.
- Test: Redis wake event resets streak.
- Test: rate-limit slowdown stacks with adaptive polling correctly (the larger of the two).

## Implementation notes

Choosing between base and extended is per-repo, not global. Two repos can be in different polling cadences simultaneously (one IDLE long-term, one actively WATCHing).

Do not let `_idle_streak` grow unbounded — cap at some sane value like 100 to avoid integer concerns over long uptimes.
